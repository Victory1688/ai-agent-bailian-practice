一、代码的目的与定位

一句话：用一个 task_id 做命名空间，让三个并行任务的对话历史各存各的、互不污染——解决多任务并发时的"串台"问题。

char09-05 的并行执行有一个隐含前提：三个子 Agent 不需要记忆（各自只干一件事，干完就扔）。但如果每个任务都需要自己的对话上下文（比如多轮对话、中间结果保留），直接并行就会出现一个经典问题：任务 A 的对话历史被任务 B 读到了。本篇用一个 ContextScope 类解决这个问题：

# 没有隔离的世界（危险）
contexts = []
thread1.append({"role": "user", "content": "中国经济..."})  # 宏观经济对话
thread2.append({"role": "user", "content": "人工智能..."})  # AI 对话
# 两个线程共用一个列表 → 上下文混在一起，LLM 会串台！

# 有隔离的世界（安全）
contexts = {
  "task_001": [...],   # 宏观经济上下文
  "task_002": [...],   # AI 上下文
  "task_003": [...],   # NLP 上下文
}
架构一句话：隔离 = 一个大字典，task_id 是 key，每个 key 对应独立的对话历史列表——这就是"命名空间隔离"的最简实现。

三、核心设计思想：隔离的三层含义

3.1 命名空间隔离：task_id = 物理分界线

class ContextScope:
    def __init__(self):
        self.contexts: Dict[str, list] = {}   # 一个大字典，key 是 task_id

    def create(self, task_id: str):
        self.contexts[task_id] = []            # 为每个任务创建独立列表

    def append(self, task_id: str, message: dict):
        if task_id in self.contexts:
            self.contexts[task_id].append(message)  # 只往自己的列表追加

    def get(self, task_id: str) -> list:
        return self.contexts.get(task_id, [])      # 只取自己的列表

隔离的关键：所有读写操作都带 task_id 参数。AgentTask 线程只操作自己 task_id 对应的列表，永远不碰其他 task_id 的数据。这就是"物理隔离"——数据结构层面就不可能串。

3.2 生命周期管理：create → append → destroy

# create：任务开始前创建
self.scope.create(self.task_id)

# append：运行中随时追加（多轮对话就是多次 append）
self.scope.append(self.task_id, {"role": "user", "content": ...})
self.scope.append(self.task_id, {"role": "assistant", "content": ...})

# destroy：任务结束后清理（原代码没调用，但方法已预留）
self.scope.destroy(self.task_id)

ContextScope 预留了 destroy() 方法但原代码没调用——生产环境里任务跑完必须清理，否则 self.contexts 会无限膨胀（内存泄漏）。本篇作为教学示例故意省略，但这个"创建-使用-销毁"的生命周期模式值得记住。

3.3 线程安全：GIL 下为什么不需要额外锁

ContextScope 的 create/append/get 操作都是对 Dict[str, list] 的单 key 操作（如 self.contexts[task_id].append(msg)）。在 CPython 中，单 key 字典操作 + 单 list append 都是原子的（GIL 保护），所以不需要额外加 Lock——这与 char09-05 的 ParallelExecutor 不同（那里是 results[name] = result，涉及字典大小更新，GIL 下不一定原子）。

小坑提醒：虽然本篇不需要加锁，但如果 create/append 改为复合操作（如"检查 key 是否存在 → 不存在则创建 → 追加消息"），就需要加锁了。规则：复合操作必须加锁，单 key 操作靠 GIL。

五、隔离 vs 不隔离：对比实验

场景上下文数据结构结果
本篇（隔离）Dict[str, list] 按 task_id 分桶三个任务各聊各的，互不干扰
不隔离（想象）list 一个大列表混装所有消息task_001 调 LLM 时，历史里有 task_002 的"2023年 AI 发展"，LLM 可能串台
生产级隔离Redis Hash / 数据库行存储跨进程、跨机器的任务隔离

生产系统中的隔离方案与本篇是同一家族：Redis Hash（field=task_id, value=序列化的消息列表）、数据库（每个 task_id 存一行对话历史）、MCP 协议（每个 session 独立上下文）——核心思想都是 "一个标识符 → 一份独立数据"。

七、动手练习

  1. 加多轮对话：每个 AgentTask 跑 3 轮（用户问 → LLM 答 → 用户追问 → LLM 答 → ...），观察每个 task_id 的消息数量是否正确增长（2 → 4 → 6）。
  2. 模拟串台：故意让两个 task_id 写同一个上下文（比如 task_001 和 task_002 共用同一个 task_id），观察 LLM 输出是否开始互相引用。
  3. 加 destroy + 内存检查：任务完成后调 scope.destroy(task_id)，跑完三个任务后打印 len(scope.contexts) 验证是否已清理。
  4. 换 Redis Hash 实现：把 ContextScope 的 self.contexts 换成 Redis Hash（field=task_id, value=json.dumps(列表)），实现跨进程隔离——这就是生产级的做法。

八、总结

本篇的核心资产是一个 40 行的 ContextScope 类——它把"多任务上下文隔离"这个问题，用一个 Dict[str, list] 结构就解决了。隔离的关键只有一条：所有读写都带 task_id 参数，让每个任务的数据结构上就不可能串。

实测验证了隔离的有效性：三个任务主题完全不同（宏观经济 / AI 发展 / NLP 简介），输出完全没有互相引用。上下文隔离检查的小代码段（打印每个 task_id 的消息数量与角色序列）也值得记住——写完隔离代码后，务必加一行验证它真的隔离了。

最后记住与 char09-05 的组合：并行执行 + 上下文隔离 = 多任务并发的完整解决方案——5 篇解决"怎么同时跑"，6 篇解决"跑起来不串台"，两者缺一不可。
