【例9-1】3个Agent联动的财经系统 —— 主从架构多智能体入门

char09 开篇 | 改写验证于 dashscope qwen-plus | 生成日期：2026-10-12

一、代码的目的与定位

一句话：从"一个 Agent 包打天下"跨入"多个 Agent 分工协作"——本篇是 char09（多智能体系统）的开篇，演示最主流的"主控-子任务"主从架构。

char01-08 全部在打磨单个 Agent 的能力（状态感知、参数解析、异常处理、记忆、上下文压缩）。当任务复杂到一定程度，单 Agent 的提示词会臃肿不堪、工具列表会超出模型的取舍能力——于是把系统拆成多个各司其职的 Agent，成为自然选择。本篇用一个财经预测系统展示最简分工：

角色类职责输入来源
主控 AgentControlAgent任务拆解、按依赖顺序调度、最终整合用户 query
资讯 AgentNewsAgent抓取财经新闻并生成摘要（模拟）用户 query
分析 AgentForecastAgent基于资讯做 GDP 预测（模拟）资讯 Agent 的输出
架构一句话：主控不干活，只编排；子 Agent 各管一段；上游输出是下游输入——这是一条串行流水线。

三、核心设计思想：主从架构的三条分工原则

3.1 职责单一：每个 Agent 只回答一个问题

NewsAgent 只答"现在有什么消息"，ForecastAgent 只答"消息意味着什么"。对比单 Agent 版本（需要在一条提示词里同时约束检索与建模），职责拆分后每段提示词更短、更聚焦、更容易调试。

3.2 依赖显式化：数据流向即调用顺序

本例中预测依赖资讯（forecast_tool.call(summary)），所以调用顺序必须是先新闻后分析——数据依赖决定调度顺序。这条原则在 char05 的 LangGraph 顺序图中 formalize 过（节点按边连接执行），本篇是它的手写版。

3.3 整合收口：LLM 只在"需要智能"的地方出场

三个环节里只有最后一步调 LLM：前两步是确定性调度（谁先谁后写死在代码里），只有"把任务目标 + 资讯 + 预测揉成一份报告"需要语言生成能力。这不是偷懒——能确定的不交给模型，正是 char02"决策/执行分离"不变式在多 Agent 场景的延续。

四、代码结构逐段解析

4.1 子 Agent：从 Tool 继承到纯类

class NewsAgent:
    def __init__(self):
        self.name = "news_agent"          # 原写法：super().__init__(name=..., description=...)
        self.description = "抓取并提取财经新闻"

    def call(self, query: str) -> str:
        return f"[资讯摘要] 当前宏观新闻显示：制造业回暖，CPI保持温和，出口增长稳定。"

去掉虚构的 Tool 继承后，子 Agent 就是一个"有名字、有描述、有 call() 方法"的普通对象。name/description 两个属性看似没用上，实际是为后续升级预留的接口：当主控从"硬编码调度"升级为"function calling 自主选择工具"时（char04 的做法），这两个字段就是注册给模型的工具元数据。

4.2 主控 Agent：run() 三步调度链（核心，原样保留）

def run(self, user_query: str) -> str:
    # Step 1：资讯
    summary = self.news_tool.call(user_query)
    # Step 2：预测（吃 Step 1 的输出——串行依赖）
    forecast = self.forecast_tool.call(summary)
    # Step 3：拼 final_prompt，LLM 整合
    final_prompt = f"""请基于以下任务链条返回统一回应：
任务目标：{user_query}
资讯摘要：{summary}
预测输出：{forecast}
请以财经顾问语气生成最终报告："""

三步的分工一目了然。注意 final_prompt 的构造方式：把中间结果全部标注来源后塞进提示词——这就是 char07 上下文工程"标注前缀"思想（[资讯摘要] / [预测结果]）的手工雏形，让模型能区分哪段是目标、哪段是证据。

4.3 LLM 调用：虚构 agent.chat 换 dashscope

response = dashscope.Generation.call(
    model="qwen-plus",
    messages=[{"role": "user", "content": final_prompt}],
    temperature=0.3, max_tokens=512, result_format='message'
)
return response.output.choices[0].message.content

与 char08 系列完全同款的调用范式——本篇唯一真实的模型调用点。

→ 调用新闻Agent进行资讯提取...

调用qwen-plus生成中……

--- Qwen3.0最终响应 ---
【财经顾问季度宏观展望报告｜2024年中国GDP走势研判】
基于对最新宏观经济数据与政策动向的系统性评估，我们审慎预测：2024年我国GDP将实现约5.3%的同比增长……
✅ 制造业持续回暖：1—4月制造业PMI均值达50.7，连续6个月位于荣枯线上方……
✅ CPI保持温和可控（1—4月平均同比+0.3%）……
✅ 出口韧性超预期：在"新三样"出口额同比增长29.2%的带动下……

实测发现：假数据被 LLM "幻觉放大"成专业报告

最重要的观察：子 Agent 只喂了两个硬编码事实（"制造业回暖/温和 CPI/出口稳定" + "GDP 预计 5.3%"），但 qwen-plus 在整合时自行编造了大量看似精确的支撑细节——PMI 均值 50.7、CPI +0.3%、新三样出口 29.2%、贸易顺差扩大 18.6%……这些数字全部是模型幻觉，报告读起来却极其可信。

这正是多 Agent 系统的经典风险链条：上游 Agent 给出低质量数据 → 下游 LLM 为了"把报告写圆"而补造证据 → 最终输出比假数据本身危险得多（假数据一眼可见，幻觉报告具有迷惑性）。生产系统中，每个子 Agent 的输出都要过数据校验（如 char08-02 的参数解析思路），LLM 整合 prompt 中应显式约束"只允许引用给定材料，不得补充数据"。

六、教学要点与不变式

#不变式本篇体现
1决策/执行分离（char02）主控只编排（决策），子 Agent 只执行，LLM 只在整合环节出场
2数据依赖决定调度顺序（char05）forecast 依赖 summary → 必须串行；无依赖时可并行（char05-10）
3标注前缀让注意力更精准（char07）final_prompt 中 [资讯摘要]/[预测输出] 标注信息来源
4统一调用范式（全系列）dashscope.Generation.call + result_format='message'，与 char08 同款

七、跨章节对照：三种"多角色协作"形态

本篇处于光谱的"最手工"一端：调度逻辑全写在 run() 里。它的价值是让新人先看清多 Agent 协作的裸骨架——后续章节再看到"路由 Agent""监督者模式""LangGraph 多节点"时，会发现它们只是把这段手写 if 换成了不同形式的自动调度。

八、动手练习

  1. 加一个下游角色：新增 RiskAgent（输入 forecast 输出，输出风险提示），挂到调度链 Step 2.5，观察 final_prompt 需要怎么改。
  2. 把假数据换成真 LLM：让 NewsAgent 内部也调 dashscope 生成摘要（而不是硬编码），对比运行耗时与报告质量的变化。
  3. 堵幻觉口子：在 final_prompt 中加入"严格只允许引用资讯摘要与预测输出中给出的信息，禁止补充任何具体数字"，重跑并对比幻觉细节是否减少。
  4. 升级为自主调度：参考 char04-07，把两个子 Agent 注册为 function calling 工具，让模型自己决定调用顺序——对比手写版与自主版的差异。

九、总结

本篇用 60 行代码演示了多智能体系统的最小骨架：主控编排 + 子 Agent 执行 + 上游输出即下游输入 + LLM 收口整合。改写只动了框架层（虚构 qwen_agent → dashscope），三类角色的职责划分与三步调度链原样保留。实测暴露了"假数据被幻觉放大"的经典风险——记住这条教训，它比架构本身更值钱。char09 后续篇章将在此基础上展开更多协作形态。
