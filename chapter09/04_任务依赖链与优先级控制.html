一、代码的目的与定位

一句话：用一个 TaskExecutor 类，实现"依赖约束 + 优先级"的 DAG（有向无环图）调度——先按依赖解锁，同层再按优先级择优执行。

char09-01/02 的调度是写死顺序（run() 里 if...else），03 的调度是无依赖选一个（TaskDispatcher 只在"谁都可以干"的 Agent 里选）。本篇解决两个更复杂的问题：

  1. 依赖约束：有些任务必须等上游完成才能开始（如 model 分析必须等 fetch_news 抓取）
  2. 同层优先级：多个任务同时解锁时，先干重要的（如 report 优先级 2 > graph 优先级 1）

4 个任务的依赖结构（画成 DAG 一眼就懂）：

fetch_news(优先级3) → model(优先级4) → report(优先级2)
                                    → graph(优先级1)

model 是分叉点——它完成后，report 和 graph 同时解锁，这时候优先级才发挥作用（report 先执行）。

三、核心设计思想：DAG 调度的三个关键算法

3.1 Task：最小调度单元

class Task:
    def __init__(self, id, func, depends=None, priority=1):
        self.id = id
        self.func = func               # 任务函数（无参数，返回值存 result）
        self.depends = depends or []   # 前置依赖 ID 列表
        self.priority = priority       # 优先级（越大越高）
        self.executed = False          # 是否已执行
        self.result = None             # 执行结果

Task 是一个纯数据对象——不包含任何调度逻辑。调度逻辑全在 TaskExecutor 里。这种"数据与执行分离"的模式让 Task 可以被序列化、持久化、跨进程传递——生产系统里任务队列（如 Celery、Airflow）都是这种设计。

3.2 优先级堆：heapq + 负号 = 大根堆

heapq.heappush(pq, (-task.priority, task.id))    # 入堆
_, tid = heapq.heappop(pq)                       # 出堆 = 堆顶

Python 标准库 heapq 实现的是最小堆（堆顶总是最小值）。要实现"优先级大的先出"，经典技巧就是存负数——priority 4 变成 -4，priority 3 变成 -3，-4 < -3，所以堆顶先弹出 priority 4 的任务。

小坑提醒：如果两个任务优先级相同，heapq 会比较 tuple 的第二个元素（task.id 字符串），按字典序排列——这意味着同优先级任务的执行顺序是确定性的（字典序），而不是随机的。如果需要同优先级内随机，可以给 tuple 加第三个随机元素 (-priority, random.random(), task.id)。

3.3 级联解锁：依赖约束优先于优先级

while pq:
    _, tid = heapq.heappop(pq)
    task = self.tasks[tid]

    if task.executed:     # 已执行过，跳过
        continue
    if not self._can_execute(task):  # 依赖还没满足，跳过
        continue

    # 执行任务...
    task.executed = True

    # 解锁下游：检查所有未执行任务，哪些现在可以了
    for t in self.tasks.values():
        if not t.executed and self._can_execute(t):
            heapq.heappush(pq, (-t.priority, t.id))

这里有个精妙之处：任务可能被多次入堆。比如 graph 任务在注册时就可以入堆（无依赖？不，它依赖 model），所以初始不入堆。model 执行完后 graph 解锁，入堆。但如果此时 graph 已经在堆里了（比如之前被其他路径解锁过），heapq 允许重复元素——执行时的 if executed 检查 + if _can_execute 检查就是防重。

依赖约束优先的实证：model 的优先级是 4（比 fetch_news 的 3 高），但它必须等 fetch_news 完成才能解锁，所以执行顺序 fetch_news → model——优先级再高，依赖没满足也得等着。

四、实测运行结果（真机验证）

=== 启动带依赖与优先级调度的Agent任务系统 ===
→ 执行任务：fetch_news（优先级：3）    ← 唯一根任务，先执行
→ 执行任务：model（优先级：4）         ← 依赖 fetch_news，解锁后执行
→ 执行任务：report（优先级：2）         ← 与 graph 同层，优先级高先执行
→ 执行任务：graph（优先级：1）          ← 同层优先级低，后执行

实测验证了 DAG 调度的两阶段逻辑

阶段 2：同层择优堆顶优先级最大的先出report(2) > graph(1)，所以 report 先执行

五、算法骨架：与生产级调度器的对照

维度本篇 TaskExecutor生产级（Airflow / Celery / LangGraph）
DAG 建模depends 列表手写声明式拓扑（@dag decorator / 边连接）
调度触发执行完手动扫全表解锁下游事件驱动（执行完 emit 事件 → 下游监听到自动入队）

本篇的调度算法骨架是拓扑排序 + 优先级队列——这是几乎所有 DAG 调度器的核心算法。生产级实现只是在并发、容错、持久化上加强，但"依赖约束优先、同层按优先级"这个核心逻辑不变。

七、动手练习

  1. 加一个新根任务：新增 task_fetch_market（优先级 5），不依赖任何任务——观察它是否与 fetch_news 同时入堆、谁先执行（优先级大的先出）。
  2. 制造循环依赖：让 graph 依赖 report，report 依赖 graph——运行看看会发生什么（应该永远解不了锁，executor 空转）。
  3. 加并发执行：同层任务解锁后，用 threading 同时执行（如 report 和 graph 一起跑），对比串行耗时。
  4. 加失败重试：让某个任务有概率失败，executor 捕获异常后重试 2 次，还是失败则标记为 FAILED 并跳过下游。

八、总结

本篇的核心资产是一个 60 行的 TaskExecutor 类——它把"怎么按依赖和优先级调度任务"这个问题，拆成了三个清晰的算法步骤：

  1. 根任务入堆：所有 depends 为空的任务先入优先级堆
  2. 堆顶执行：堆顶 = 当前优先级最高且依赖满足的任务
  3. 级联解锁：执行完后扫全表，把现在能执行的下游任务入堆

实测执行顺序 fetch_news → model → report → graph 完美验证了"依赖约束优先、同层再看优先级"的调度铁律。这个算法骨架与 Airflow、Celery、LangGraph 等生产级调度器同源——理解了它，再看任何 DAG 调度框架都不会觉得是黑盒。
