【例9-2】多智能体间的状态共享机制 —— 用中心状态池解耦 Agent

char09 第二篇 | 改写验证于 dashscope qwen-plus | 生成日期：2026-10-12

一、代码的目的与定位

一句话：用一个全局状态字典（SharedState）做"公共信箱"——每个 Agent 只管往里面写或从里面读，彼此不直接调用，实现解耦。

char09-01 的主从架构里，ForecastAgent.call(summary) 的参数来自 NewsAgent 的返回值——下游显式依赖上游。如果以后想换一个新闻来源，就得改 run() 里的参数传递代码。本篇引入 中心状态管理器 解决这个问题：

对比维度char09-01（直接传递）char09-02（状态共享）
数据流向上游返回值 → 下游参数上游写状态池 key → 下游读同一 key
下游感知上游知道上游是谁（调了谁的 call）不知道，只知道读哪个 key
换上游时要改 run() 里的调用链只改"写 econ_trend 的 Agent"，下游不动
可观测性散落在各 Agent 的 return 里统一 dump() 导出全部中间结果
架构一句话：状态池 = 公共的 Dict[str, Any]，所有 Agent 通过 update()/get() 读写同一个池子——这就是"黑板架构（Blackboard Architecture）"的教学简化版。

三、核心设计思想：解耦的三层含义

3.1 角色解耦：写入方不知道谁在读

AnalysisAgent 只做 self.shared.update("econ_trend", result)——它不知道这个 key 被谁读，也不关心。ReportAgent 只做 self.shared.get("econ_trend")——它也不关心谁写的。这种"只管自己的事"的模式让每个 Agent 可以独立开发和替换。

3.2 调用解耦：数据不靠函数参数传递

char09-01 的 forecast_tool.call(summary) 需要显式把上游返回值当参数传下去。本篇的 report_tool.call("") 传的是空串——数据完全靠状态池传递。这个细节值得注意：

# char09-01：参数传递（显式依赖）
forecast = self.forecast_tool.call(summary)   # summary 是上游返回值

# char09-02：状态池传递（隐式解耦）
report = self.report_tool.call("")            # 参数空串，数据在状态池 econ_trend 里

3.3 观测解耦：全部中间结果可 dump

运行结束后 shared.dump() 能拿到完整快照：{"user_input": "...", "econ_trend": "...", "final_report": "..."}。这在排查"哪个环节出了问题"时极其方便——不需要翻各 Agent 的 return 值，直接看状态池里缺了哪个 key。

四、代码结构逐段解析

4.1 SharedState：全局状态池（本篇灵魂）

class SharedState:
    def __init__(self):
        self.state: Dict[str, Any] = {}

    def update(self, key: str, value: Any):
        print(f"→ [状态更新] {key} = {value}")   # 更新即打印——调试友好
        self.state[key] = value

    def get(self, key: str, default=None):
        return self.state.get(key, default)        # 不存在时给默认值

    def dump(self) -> Dict[str, Any]:
        return self.state.copy()                   # 复制一份——防止外部修改内部

三个方法覆盖了一个全局 Dict 的全部核心操作——它不是什么神奇的框架，就是一个带日志的普通 Dict 封装。但就是这个"薄封装"，把 Agent 间的数据交互标准化成了"写 key 读 key"，比散落在各处的函数返回值统一得多。

4.2 两子 Agent：写入方和读取方

# 写入方：只管写 econ_trend
class AnalysisAgent:
    def call(self, query: str) -> str:
        result = "制造业增长、CPI温和回落、出口回升"   # 模拟数据
        self.shared.update("econ_trend", result)      # 写状态池
        return f"[分析完成] 趋势：{result}"

# 读取方：只管读 econ_trend、写 final_report
class ReportAgent:
    def call(self, _: str) -> str:                     # 参数 _ 表示不使用
        trend = self.shared.get("econ_trend", "无数据")  # 读状态池
        report = f"2024年经济展望：预计{trend}..."
        self.shared.update("final_report", report)      # 写状态池
        return report

两个类各约 10 行，职责清晰。注意 ReportAgent.call(self, _: str) 里的 _——Python 约定用下划线表示"这个参数我不用"。数据不从参数来，从状态池来。

4.3 ControllerAgent.execute()：三步调度 + 状态池贯穿

def execute(self, user_query: str) -> str:
    self.shared.update("user_input", user_query)          # Step 0：主控也写状态池

    analysis = self.analysis_tool.call(user_query)        # Step 1：写 econ_trend
    report = self.report_tool.call("")                    # Step 2：读 econ_trend，写 final_report

    prompt = f"""请基于以下信息生成一段完整用户报告：
用户问题：{self.shared.get('user_input')}           # 主控读状态池
分析内容：{self.shared.get('econ_trend')}           # 主控读状态池
最终报告：{self.shared.get('final_report')}"""       # 主控读状态池

有意思的是主控 Agent 既是写入方（update user_input）也是读取方（get 三个 key 拼 prompt）——它自己也用这个公共信箱。这说明状态池不是"子 Agent 专用"，而是整个多 Agent 系统的共享内存。

实测发现 1：状态池日志 = 系统执行轨迹

四行 [状态更新] 日志就是整个系统的执行轨迹——user_input → econ_trend → final_report，key 名即数据流方向。比 char09-01 靠 print() 手动打印 return 值更标准化。

实测发现 2：LLM 幻觉放大假数据（与 01 篇同风险）

同一个教训，换了载体：状态池里只有三句硬编码事实（制造业增长 / CPI 温和 / 出口回升），但 qwen-plus 照样编造了 PMI 51.2、CPI 0.4%、"新三样"出口 12.3% 等精确数字——状态共享架构没有解决"假数据被幻觉放大"的问题，它只是解决了"Agent 间怎么传数据"的问题。幻觉的治理要在数据源头加校验（char08-02）+ 在 LLM 整合 prompt 里显式约束（char09-01 练习 3）。

七、黑板架构 vs 直接传递：三种多 Agent 数据交互模式

模式代表数据流解耦度适用场景
直接参数传递char09-01上游 return → 下游 param低链路固定、Agent 少
黑板架构本篇 char09-02write key → read key高Agent 多、链路可变、需要中间结果观测
消息总线char09 后续篇章 / 生产 MQ订阅主题 → 发布消息最高分布式、异步、多消费者

本篇是黑板架构（Blackboard Architecture）的极简教学版——真实系统中"黑板"可能是 Redis（进程间共享）、数据库（持久化共享）、甚至 Redis Streams（带订阅的消息黑板）。但核心模式不变：写入方不关心谁在读，读取方不关心谁在写。

八、动手练习

  1. 加新写入方：新增 MarketAgent 往状态池写 market_index，让 ReportAgent 也读这个 key——观察改动量（应该只改 ReportAgent 的 call 和 SharedState，不动 Controller）。
  2. 替换写入方：把 AnalysisAgent 的硬编码换成真 LLM 摘要（调 dashscope），下游 ReportAgent 完全不需要改——验证解耦效果。
  3. 状态持久化：把 SharedState 的 self.state 改成 JSON 文件读写（char06 持久化思路），让中间结果跨进程可见——这是走向真实黑板架构的第一步。
  4. 堵幻觉口子：在 final_prompt 里加"严格只允许引用状态池中的三句话，禁止补充任何具体数字或百分比"——重跑对比。

九、总结

本篇的核心资产是一个 30 行的 SharedState 类——它不是什么框架魔法，就是一个带日志的普通 Dict 封装。但它带来的架构收益是真实的：Agent 间解耦、数据流可观测、替换写入方零成本。char09-01 和 02 形成了一个清晰的对比：当 Agent 数量少时直接传递简单高效，当 Agent 数量增多或链路需要变化时，黑板架构就成了必然选择。

同样必须记住：状态共享解决的是"Agent 间怎么传数据"的问题，不是"数据质量"的问题——假数据被幻觉放大的风险在两种架构里都存在，需要在数据源头加校验、在 LLM 整合时加约束。架构能帮你传递数据，但不能帮你保证数据可信。
