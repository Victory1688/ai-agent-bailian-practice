三、核心设计思想：临界区与互斥锁

3.1 临界区：锁内的代码块

def write_log(self, agent_name: str, message: str):
    with self.lock:                # 临界区开始
        entry = f"[{agent_name}]：{message}"
        print(f"→ 写入日志：{entry}")
        self.logs.append(entry)
        time.sleep(0.5)            # 模拟慢速写入（在锁内！）
    # 临界区结束：with 块退出时自动释放锁

with self.lock: 的语义：同一时刻只有一个线程能进入这个块。其他线程会在 with 行阻塞等待，直到当前线程退出块释放锁。这就是"互斥"（Mutex = Mutual Exclusion）。

为什么打印 + append + sleep 都要放进锁内？如果只有 self.logs.append(entry) 在锁内而打印在外面，多个线程的打印会交错输出（日志可读性破坏）。教材把整段"组装-打印-写入-延迟"都放进临界区，是为了让新人直观看到"临界区内的操作是原子的、不可分割的"。但注意：sleep 放锁内是教学演示，生产环境严禁在临界区内做耗时操作——它会强迫所有线程排队等 0.5 秒。

3.2 锁的粒度：粗粒度简单，细粒度高效

粒度本篇做法生产级做法
一把大锁整个 write_log 一把锁，写和读都串行读写锁（RWLock）：读可并行、写独占
锁持有时间含 sleep(0.5)，一次写入 0.5 秒只包住真正的内存写操作（微秒级）
适用场景教学演示互斥语义高并发日志系统（如异步写入队列）

生产级日志系统根本不会在临界区里做耗时操作——常见做法是先在锁内把消息塞进队列（微秒级），锁外由专门的写入线程慢慢消费队列。这就是"生产者-消费者"模式，把"互斥"和"慢操作"解耦。

3.3 并发调度的不确定性：完成顺序随机，写入顺序由锁决定

本篇两次实测的写入顺序不同（第一次 Agent_2→3→1，第二次 Agent_2→1→3）——因为三个 LLM 调用是并发的，谁先返回谁先抢锁，返回顺序受网络延迟影响是随机的。但无论顺序怎么变，锁保证每条日志完整、不交错——这正是"调度顺序不确定 + 执行结果确定"的并发设计精髓。

五、竞态条件：如果没有锁会怎样

# 想象没有锁的 write_log（危险版本）
def write_log(self, agent_name, message):
    entry = f"[{agent_name}]：{message}"
    print(f"→ 写入日志：{entry}")    # 三个线程的打印交错输出
    self.logs.append(entry)          # list.append 在 GIL 下原子，勉强安全
    time.sleep(0.5)                  # 但如果这里是"读-改-写"复合操作就完了
场景风险典型症状
打印交错日志可读性破坏Agent_1 的内容打到一半插进 Agent_2 的
复合读改写更新丢失counter += 1 三个线程各跑一次结果只加了 1
check-then-act条件被绕过两个线程同时判断"日志未满"然后都写入，超限

本篇的 self.logs.append(entry) 本身在 CPython 的 GIL 下是原子操作（单条字节码），即使没锁也大概率不丢数据——但 打印交错 + sleep 期间的逻辑混乱 依然会发生。教材用锁是正确的习惯：不依赖 GIL 的实现细节，用显式锁表达"这是共享资源"的设计意图（换 PyPy / 换 Java / 换多进程时这套代码依然正确）。

六、跨章节对照：并发工具箱

工具代表篇语义适用场景
threading.Lockchar09-05 / 07互斥：同一时刻一个线程进入保护共享读写
命名空间隔离char09-06分桶：各用各的数据，根本不共享多任务各自独立上下文
Thread.joinchar09-05/06/07屏障：等所有线程结束再往下并行任务收口汇总
queue.Queue生产级（本篇未用）线程安全队列，天然免锁生产者-消费者解耦
读写锁 RWLock生产级（本篇未用）读并行、写独占读多写少的共享配置

设计优先级：能隔离就不共享（06），能免锁工具（Queue）就不手写锁，必须共享时才用 Lock（05/07）——锁是最后手段，不是第一选择。

七、动手练习

  1. 去掉锁看交错：把 with self.lock: 去掉（直接缩进），把 sleep 改成 0.1s，多跑几次观察打印是否交错、日志是否依然完整——体会"GIL 下 append 安全但打印必然交错"。
  2. 加读锁验证：在 join 完成前让主线程调用 read_logs()，观察读到的日志条数是否少于 3——体会"读写没有同步时的脏读"。
  3. 换 Queue 实现：把 SharedLog 改成 queue.Queue + 一个专门的写入线程（生产者-消费者模式），对比两版代码的锁使用差异。
  4. 统计锁等待：在 write_log 进入 with 前后记录时间戳，打印每个线程等锁花了多久——量化"临界区慢操作"的代价。

八、总结

本篇的核心资产是一个 15 行的 SharedLog 类——它用一把 threading.Lock 演示了并发编程最基础的"临界区互斥"：

  1. 临界区：with lock 块内的操作是原子的，任意时刻只有一个线程在执行
  2. 串行化代价：锁内 sleep(0.5) 让三次写入至少耗时 1.5s——锁保护正确性，但牺牲并发性
  3. 调度不确定 + 结果确定：LLM 返回顺序随机（两次实测顺序都不同），但锁保证日志永远完整无交错

并发三部曲至此完整：05 解决"怎么同时跑"（Thread + join），06 解决"跑起来不串台"（命名空间隔离），07 解决"共享资源不被写坏"（Lock 临界区）。三者组合就是多 Agent 并发系统的最小完备工具集。
