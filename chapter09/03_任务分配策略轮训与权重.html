一、代码的目的与定位

一句话：用一个 TaskDispatcher 类封装两种经典调度策略——轮询（均匀）和加权（按权重概率），对比它们在同一组 Agent 上的分配行为。

char09-01 和 02 的调度都是写死的：主控 Agent 里 news.call() → forecast.call() 顺序不可变。但现实中往往有多个同类 Agent 副本可以干同一件事（比如 3 个财经预测 Agent 并行排队），这时候就需要一个调度器来决定"这次任务给谁"。本篇引入两种最经典的调度策略：

策略核心思想代码实现适用场景
轮询 Round-Robin均匀依次分配，循环往复agents[counter % len(agents)]所有 Agent 能力相当、任务同质
加权 Weighted按权重概率分配，强者多干活_build_weighted_pool() 重池 + random.choiceAgent 能力有差异、想让强者多接任务
架构一句话：调度器 = 策略 + Agent 池。策略决定"选谁"，Agent 池是"候选集"。切换策略不改主控代码，只改 dispatcher.strategy。

三、核心设计思想：调度器的三个设计要点

3.1 轮询：一行代码的均匀分配

def dispatch(self):
    if self.strategy == "round_robin":
        agent = self.agents[self.counter % len(self.agents)]   # 关键：counter % 3 → 0,1,2,0,1,2...
        self.counter += 1
        return agent

counter % len(agents) 是轮询的灵魂——计数器每次 +1，对 Agent 数量取模后永远落在合法下标范围内，形成 0→1→2→0→1→2→... 的循环序列。不需要任何额外数据结构，一行搞定。

3.2 加权：重池构造 = 把概率问题转成等概率选择

def _build_weighted_pool(self):
    """权重 1:1:3 → pool = [agent1, agent2, agent3, agent3, agent3]"""
    pool = []
    for agent in self.agents:
        weight = self.weights.get(agent.name, 1)
        pool.extend([agent] * weight)   # 复制 weight 份
    return pool

def dispatch(self):
    elif self.strategy == "weighted":
        return random.choice(self.pool)   # 在重池里等概率选

这是一个非常聪明的转换：把"按权重概率选"这个带概率的问题，转成"在重池里等概率选"这个简单问题。权重 1:1:3 意味着 pool 有 5 个元素，agent3 占 3 份，所以它被 random.choice 选中的概率天然就是 3/5 = 60%。

注意权重与 quality 的关系：本篇的权重（weight_map 1:1:3）和 quality（0.85/0.90/0.95）是独立配置——权重决定"分到多少活"，quality 决定"干得多好"。教学示例故意让高 quality 的 Agent 分到更多权重，但生产环境中这两个维度可能独立调优（比如高 quality 但高成本的 Agent 只分配到关键任务）。

3.3 策略可替换：dispatcher 是注入的

class ControlSystem:
    def __init__(self, dispatcher: TaskDispatcher):
        self.dispatcher = dispatcher   # 注入，不是自己 new

# 主流程里：换策略 = 换 dispatcher 实例
round_dispatcher = TaskDispatcher(..., strategy="round_robin")
weighted_dispatcher = TaskDispatcher(..., strategy="weighted", weights=...)

主控系统不持有调度逻辑——它只持有一个 dispatcher 引用。换策略 = 换一个 dispatcher 实例，主控代码零改动。这就是依赖注入（DI）的简化版——策略与消费者解耦。

四、实测运行结果（真机验证）

轮询策略 3 次：完美均匀

--- 轮询第 1 次 → 分配给Agent：econ_agent_1
--- 轮询第 2 次 → 分配给Agent：econ_agent_2
--- 轮询第 3 次 → 分配给Agent：econ_agent_3

3 次恰好覆盖全部 3 个 Agent，counter % 3 输出 0, 1, 2——轮询行为确定可预测。

加权策略 3 次：小样本不严格按比例

--- 加权第 1 次 → 分配给Agent：econ_agent_3
--- 加权第 2 次 → 分配给Agent：econ_agent_1
--- 加权第 3 次 → 分配给Agent：econ_agent_1
教学点：权重是概率，不是配额。权重 1:1:3 意味着每个 Agent 被选中的概率是 20%/20%/60%，但 3 次样本里 agent_1 分到 2 次（67%）、agent_3 只分到 1 次（33%）——这是正常的随机波动。跑 100 次后比例才会逼近 20%/20%/60%。如果任务量很小但必须严格按比例分配，应该用"加权轮询（Weighted Round-Robin）"而非"加权随机"。

五、两种调度策略的优劣势对照

维度轮询 Round-Robin加权 Weighted
分配行为确定性（counter 递增，结果可预测）概率性（random.choice，小样本有波动）
代码复杂度极低（一行取模）中（重池构造 + random）
负载均衡完美均匀长期趋近权重比例，短期有波动
适合场景Agent 能力同质、任务量可预测Agent 能力异质、强者该多干活
生产升级加权轮询（WWRR）平滑过渡最小连接数 / 平滑加权轮询

七、动手练习

  1. 跑大样本看权重收敛：把加权策略的循环次数从 3 改成 100，统计每个 Agent 被分到的次数——应该逼近 20/20/60。
  2. 实现第三种策略：加权轮询：让高权重 Agent 多轮几次但保持确定性（如权重 1:1:3 → 分配序列 3,1,3,2,3,1,3,2,3...），对比加权随机的差异。
  3. 把权重绑定到 quality：让 weights 自动从 Agent 的 quality 属性推导（如 quality×10 取整），实现"能力越强权重越高"。
  4. 加超时降级：如果某个 Agent 的 call() 超过 2 秒还没返回，调度器自动切给下一个——这就是 char08-03 异常处理思想在调度层的延伸。

八、总结

本篇的核心资产是一个 40 行的 TaskDispatcher 类——它把"怎么选 Agent"这个决策从主控代码里抽离出来，封装成一个可注入、可替换的策略对象。轮询用一行取模实现均匀分配，加权用重池构造把概率问题转成等概率选择——两个设计都值得记住。

最重要的认知：权重是概率不是配额，小样本里的波动是正常现象。如果任务量很小但必须严格按比例，应该用加权轮询而非加权随机——这是教学示例故意没做但生产必须考虑的边界条件。
