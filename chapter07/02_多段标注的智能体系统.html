02_多段标注的智能体系统 - 代码解析

对应文件：char07/02_多段标注的智能体系统.py | 教材出处：第7章 MCP协议 例7-2 | 环境实测：qwen-plus + 模拟 DeepSeek 工具 | 生成日期：2026-10-12

一、这份代码整体在做什么（一段话讲给新人）

本篇是 char07 第二篇——**MCP 上下文段的三类标注实战**。与 01 篇的五字段结构完全同构，但 01 篇只演示了 input/response/observation 三种 type，本篇把 type 扩展到 **system / memory / input / tool** 四种——三类标注组装成结构化上下文，让 LLM 同时看到"该怎么说话"、"用户喜欢什么"、"事实是什么"。这比 LangChain 单一 system prompt + 对话历史的扁平结构更灵活：偏好可以随时更新、工具结果可以随时追加、多任务可以隔离。

四类标注类型速查表（比 01 篇多了 system/memory）

type 字段值含义role 字段值在本例中的内容作用
system系统提示段system"政府咨询顾问，专业简明有依据"定义 Agent 身份和风格
memory记忆偏好段memory"用户偏好简明扼要，避免冗长"注入用户长期偏好
input用户输入段user"预测2024财政收入趋势"当前用户提问
tool工具结果段tool"增长5%，来源消费税/企业所得税"整合外部数据辅助推理

整体执行流程图

  build_segment() × 4 → 四类标注组装
    [SYSTEM] system: "政府咨询顾问..."    ← 该怎么说话
    [MEMORY] memory: "用户偏好简明..."    ← 用户喜欢什么
    [INPUT] user: "预测2024财政收入..."   ← 用户问什么
    [TOOL] tool: "增长5%，消费税/所得税"  ← 事实是什么（带 meta.tool="deepseek-v1"）
        │
        ▼
  "\n".join([f"[{TYPE}] {role}: {content}" for s in segments])
    → 拼成带标注的上下文摘要
        │
        ▼
  dashscope.Generation.call(qwen-plus, final_prompt)
    → LLM 同时看到"该怎么说话"+"用户喜欢什么"+"事实是什么"
    → 生成回答（专业、简明、有依据——三类标注全部生效）

逐段代码讲解

4.1 三类标注的组装逻辑（本篇核心教学资产，原样保留）

segments = []

# 标注 1：system —— 定义 Agent 身份
segments.append(build_segment("system", "政府咨询顾问...", "system", task_id="t001"))

# 标注 2：memory —— 注入用户偏好
segments.append(build_segment("memory", "用户偏好简明扼要...", "memory", task_id="t001"))

# 标注 3：input —— 当前用户提问
segments.append(build_segment("user", "预测2024财政收入...", "input", task_id="t001"))

# 标注 4：tool —— 外部工具返回的事实数据
segments.append(build_segment("tool", tool_response, "tool", task_id="t001",
                               meta={"tool": "deepseek-v1"}))

关键设计：三类标注都是"上下文段"，统一存储、统一传递、统一消费——不像 LangChain 里 system prompt 是单独字段、对话历史是另一个字段、工具结果又是另一个字段。这种"全部都是段"的设计是 MCP 协议的核心思想之一。

4.2 context_summary：带标注的上下文组装（原样保留）

context_summary = "\n".join(
    [f"[{s['type'].upper()}] {s['role']}: {s['content']}" for s in segments]
)
# 产出：
# [SYSTEM] system: 你是一位熟悉中国经济政策的政府咨询顾问...
# [MEMORY] memory: 用户偏好获取简明扼要的政策摘要...
# [INPUT] user: 请预测2024年中国的财政收入趋势...
# [TOOL] tool: [DeepSeek Tool] 增长5%左右，主要来源为消费税和企业所得税

每行前加 [TYPE] 标注——让 LLM 一眼看出"这是什么类型的信息"。LLM 虽然能从 role 猜出，但显式标注让注意力分配更精准（看到 [SYSTEM] 就知道这是角色设定，看到 [TOOL] 就知道这是事实数据）。

隐藏教学点：三类标注 vs LangChain 单一 system prompt

两种上下文组织方式的本质差异
LangChain 扁平结构：                 MCP 多段标注结构：
  messages = [                          segments = [
    {"role": "system", "content": "..."},    {role, content, type, task_id, meta},
    {"role": "user", "content": "..."},      ...（四类标注统一存储）
  ]                                   ]
  system 是独立字段                    system 只是一种 type
  memory 没有独立位置                  memory 有专门的 type
  tool 结果混在 messages 里            tool 有专门的 type
  无法区分"用户偏好"和"用户输入"        memory vs input 明确区分

关键认识：LangChain 的 messages 是"两字段扁平列表"，能表达的只有"谁在说话"——但无法表达"这句话是什么性质"（是角色设定？是用户偏好？是事实数据？）。MCP 的 type 字段补上了这块空白。

真实运行输出

已在本机实际运行验证（qwen-plus 真实调用 + DeepSeek 模拟工具）
--- qwen-plus 回答 ---
2024年全国一般公共预算收入预计增长约5%，与年初预算目标基本一致。
主要增长来源为：
- 消费税：汽车、成品油等重点商品消费回暖...
- 企业所得税：制造业利润修复、留抵退税政策效应逐步消化。
（依据：财政部2024年预算报告及一季度执行情况分析）

三类标注全部生效的实证：回答专业、简明（memory 偏好生效）、有依据（system 角色设定生效 + tool 数据生效）。如果去掉 memory 段，LLM 可能写得更冗长；如果去掉 tool 段，LLM 可能凭训练记忆编数据。

与 01 篇的对照：type 字段的扩展

  01 篇的 type 值：input / response / observation（三种）
  02 篇的 type 值：system / memory / input / tool（四种）
  ────────────────────────────────────────────
  完整 type 枚举（生产可能用到的）：
    system    —— Agent 角色设定
    memory    —— 用户偏好/历史
    input     —— 用户当前输入
    response  —— LLM 生成回答
    tool      —— 外部工具返回的事实数据
    observation —— 辅助模型/监控系统输出（01 篇）
  → type 字段是"可扩展"的，新增类型不破坏现有结构

生产视角

  • type 字段的扩展性：本篇 4 种 type 是生产起点，还可以加 feedback（用户对回答的评价）、plan（Agent 的任务规划）等——新增类型不破坏现有结构，这是 MCP 设计的精髓
  • 多 Agent 场景：不同 Agent 可以消费同一个 segments 列表，按 type 过滤各自需要的信息——系统 Agent 看 system，记忆 Agent 看 memory，执行 Agent 看 tool
  • tool 段的 meta 扩展：生产里可以存 tool_call_id（对应具体的 tool_calls）、latency（工具执行耗时）、status_code（工具返回状态）——这些是可追溯、可调试的关键信息
  • DeepSeek 假标题：同 01 篇 call_deepseek_v1，保持模拟函数不影响本篇 MCP 教学重心

动手练习

  1. 验证三类标注的有效性：分别去掉 system 段、memory 段、tool 段各跑一次——观察三次回答的差异（专业度/简洁度/数据准确性各受什么影响）。
  2. 新增 feedback 类型：加一个 type="feedback" 的段，内容是"用户认为消费税分析不够详细"——观察下一轮对话 LLM 是否能感知这个反馈。
  3. meta 字段扩展：在 tool 段的 meta 里加 latency（工具耗时毫秒数）和 status_code（200）——体验"可追溯"的生产需求。
  4. 接真 DeepSeek：把 call_deepseek_tool 改成真调用——openai 兼容模式（base_url="https://api.deepseek.com"），体验工具段里存真实数据。
