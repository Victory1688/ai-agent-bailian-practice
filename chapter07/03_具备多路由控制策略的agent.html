对应文件：char07/03_具备多路由控制策略的agent.py | 教材出处：第7章 MCP协议 例7-3 | 环境实测：qwen-plus 真实调用 + 模拟 DeepSeek/Tool 模块 | 生成日期：2026-10-12

一、这份代码整体在做什么（一段话讲给新人）

本篇是 char07 第三篇——基于上下文标注的路由机制。前两篇解决了"上下文怎么表示"（01 篇五字段结构）、"上下文怎么组装"（02 篇四类标注），本篇解决"请求进来后该交给谁处理"：用 determine_route() 关键词路由函数把复杂请求拆分成原子子任务，逐个判断路由目标（Qwen / DeepSeek / 工具 / 默认模型），分发执行后合并响应统一输出。这是"多模块智能体系统"的最小调度内核——真实的多 Agent 系统里，路由器就是流量分发的大脑。

二、路由规则速查表（determine_route 的四级判断）

判断顺序命中关键词路由目标执行者设计意图
1（最高优先级）"政策" 或 "法律"qwenqwen-plus 真实调用政策/法律类问题交给主力大模型
2"数据" 或 "预测"deepseek模拟函数（返回假数据）数据/预测类问题交给专用模型
3"调用" 且 "工具"（同时含）toolDataSummaryTool 本地工具明确要求调工具时走本地工具
4（兜底）以上都不命中defaultqwen-plus 真实调用默认模型处理长尾请求
两个容易忽视的设计细节
  • 顺序即优先级：if/elif 链决定了"政策"比"数据"优先——一句话同时含两类关键词时，永远路由到先判断的分支。路由表不是集合，是有序规则。
  • "且"与"或"的差别：tool 路由要求"调用"和"工具"同时出现（and），其他路由是任一命中（or）——工具误触发的代价高，所以条件最严。

四、逐段代码讲解

4.1 determine_route()：四级关键词路由（本篇核心教学资产，原样保留）

def determine_route(user_input: str) -> str:
    if "政策" in user_input or "法律" in user_input:
        return "qwen"
    elif "数据" in user_input or "预测" in user_input:
        return "deepseek"
    elif "调用" in user_input and "工具" in user_input:
        return "tool"
    else:
        return "default"

整份代码最有生命力的部分就是这 8 行：输入一句话，输出一个模块名。路由函数把"决策"从业务代码里抽离出来——主循环只认 route == "qwen" 这样的契约，不关心路由怎么算出来的。将来想把关键词匹配换成 LLM 意图分类或向量相似度，只改这一个函数，主循环零改动。

4.2 任务拆分：硬编码的子任务列表（教学简化，注意局限）

sub_tasks = [
    "分析2023年的财政数据",           # 教材注释：route → tool（实测：deepseek，见第五节）
    "预测2024年中国GDP的增长情况",    # route → deepseek
    "说明近期的主要财政政策"          # route → qwen
]

教材把"复杂请求 → 原子子任务"的拆分直接硬编码了。注意 user_input 变量定义后从未被使用——真实系统里这一步应由 LLM 完成意图拆解（比如让 qwen-plus 输出 JSON 数组的子任务列表），这是本篇与生产之间最大的简化鸿沟。

4.3 分发循环：统一契约下的三种执行者

for task in sub_tasks:
    route = determine_route(task)
    if route == "qwen":
        response = dashscope.Generation.call(model="qwen-plus",
            messages=[build_context_message("user", prompt)], ...)
        result = response.output.choices[0].message.content
    elif route == "deepseek":
        result = call_deepseek_module(task)      # 模拟函数
    elif route == "tool":
        result = tool.call(task)                 # 本地工具
    responses.append(result)

关键观察：四个分支的产出物契约完全一致——都返回一个字符串塞进 responses。远程大模型、模拟函数、本地工具在调度循环眼里没有区别，这就是"面向接口编程"：调度层只依赖"给输入、还字符串"这个最小契约。

4.4 build_context_message：虚构 Message → dict

# 原写法：return Message(role=role, content=content)   ← qwen_agent.context.Message 虚构类
return {"role": role, "content": content}              ← dashscope 接受的标准 dict

与 01/02 篇一致，dashscope 的 messages 参数吃的就是 {"role", "content"} 字典列表——虚构的 Message 包装类毫无必要，函数保留是为了让主流程代码结构不变。

五、实测发现：教材注释与实际路由行为不符（本篇最重要的坑）

教材注释标错路由，实测还原真相

教材给 sub_tasks[0] 标注 # route → tool，但实测运行结果：

子任务教材注释实际路由（实测）原因
分析2023年的财政数据route → tooldeepseek含"数据"（命中第2级），不含"调用"+"工具"（第3级永不命中）
预测2024年中国GDP的增长情况route → deepseekdeepseek含"预测"，一致
说明近期的主要财政政策route → qwenqwen含"政策"，一致

根因：教材想当然认为"分析财政数据"会走 tool 分支，但拆分后的子任务文本已经丢掉了原请求里的"调用工具"字样——"调用" in "分析2023年的财政数据" 为 False。tool 路由分支在这份代码里永远不会被触发，是死代码。这印证了系列方法论：教材注释与输出永远以实测为准。

附带的第二个观察：max_tokens=512 的截断

子任务3 的 qwen-plus 政策详述（赤字率3%、专项债3.9万亿、减税降费等）写到第 5 点"扩大政府采购对中小微"戛然而止——被 512 token 上限截断。教学示例够用，但说明回答长度预期要与 max_tokens 匹配。

六、char07 章内演进：01 → 02 → 03 的递进关系

篇目解决什么问题核心资产一句话概括
01 上下文段结构化表示上下文怎么表示build_context_segment 五字段（role/content/type/task_id/meta）上下文是一等公民的数据结构
02 多段标注的智能体系统上下文怎么组装四类标注（system/memory/input/tool）+ [TYPE] 前缀拼接多源信息统一成带标注的段

三篇合起来是一个完整的"多模块智能体系统"骨架：结构化上下文（01/02）+ 路由调度（03）。教材借 MCP 之名讲的是"如果把上下文和请求都当作可编程的数据，智能体系统就能像网络设备一样做转发决策"。

七、架构视角：三种"决策机制"的对照

机制决策依据成本确定性代表
关键词路由（本篇）硬编码关键词匹配零（纯字符串判断）100% 确定可复现determine_route()、char05-02 条件边
Agent function callingLLM 自主选择工具一次 LLM 调用有随机性（temperature）char02 agent_chat、char04 initialize_agent
显式图条件边路由函数 + 映射表零100% 确定可复现char05-02 add_conditional_edges
本篇路由与 LangGraph 条件边是"同一家族"

本篇的 route = determine_route(task); if route == "qwen": ... 与 char05-02 的 add_conditional_edges("judge", route_fn, {"positive": ..., "negative": ...}) 思想完全一致：用确定性函数做流量决策。区别只是 char05 把决策交给图的引擎执行，本篇手写 for 循环执行。当路由目标多了、需要并行/重试时，就值得迁到 LangGraph——那时本篇的 determine_route 函数可以原封不动地当条件边路由函数用。

八、教学版 vs 生产版差距

教学简化生产要求
子任务列表硬编码LLM 做意图拆解（输出 JSON 子任务数组），或规则引擎解析
关键词精确匹配意图分类模型 / 向量相似度 / 小样本微调分类器，处理同义表达（"走势"匹配不到"预测"）
call_deepseek_module 返回假数据真实 DeepSeek API（dashscope 兼容模式或 openai SDK），带超时与重试
串行 for 循环逐个执行三个子任务互不依赖，应并行分发（asyncio / 线程池），延迟降为最慢分支
responses 简单列表合并结果冲突检测 + 汇总 LLM 二次加工（如"综合三个回答生成最终报告"）
无失败处理某分支失败时的降级路由（qwen 挂了降级到 default）

九、动手练习（巩固本篇技能）

  1. 复现注释陷阱：把 sub_tasks 换回教材注释的预期，加一行 print(f"实际路由: {determine_route(task)}")，验证"分析2023年的财政数据"确实命中 deepseek 而非 tool。
  2. 激活死代码：把子任务1 改成"请调用工具分析2023年的财政数据"（补上"调用"和"工具"），观察 tool 分支首次被触发。
  3. 升级路由函数：给 determine_route 增加一条规则——含"翻译"路由到 "translate"，并在主循环加对应分支（体会"加一个路由目标只需要改两处"）。
  4. 进阶挑战：用 concurrent.futures.ThreadPoolExecutor 把串行 for 循环改成并行分发，用计时对比加速比（参考 char03-04 的多线程改造）。
