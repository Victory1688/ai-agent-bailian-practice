一、这份代码整体在做什么（一段话讲给新人）

本篇是 char07 第四篇——路由的第二种形态：模型入口选择。03 篇解决了"把请求拆给谁处理"（Agent / 工具 / 模型），本篇解决了"同类请求也可以走不同模型入口"——用 route_decision() 对每条 query 做四级判断，路由到 qwen（政策类）/ deepseek（预测类）/ hybrid（组合分析类）/ default（兜底）四个入口。新增的 hybrid 入口是关键升级：它不再是一对一分发，而是一对多 fan-out + 结果融合，这就是"模型集成"思想的最小雏形——与 char05-10 的广播+并行汇聚是同一家族。

any() vs in：03→04 的写法升级
# 03 篇写法（硬编码关键词对，难扩展）
if "政策" in user_input or "法律" in user_input:
    return "qwen"

# 04 篇写法（关键词数组，加一行即可扩展）
if any(k in query for k in ["政策", "法规", "概述", "总结"]):
    return "qwen"

any() 生成器表达式的好处：新增关键词只需往数组里加一项，不用改 if 条件本身。路由规则本质是"关键词→目标"的映射表，数组比散落的 or 表达式更接近数据驱动的设计。

四、逐段代码讲解

4.1 route_decision()：any() 生成器表达式（本篇核心教学资产，原样保留）

def route_decision(query: str) -> str:
    if any(k in query for k in ["政策", "法规", "概述", "总结"]):
        return "qwen"
    elif any(k in query for k in ["预测", "趋势", "估计", "数据"]):
        return "deepseek"
    elif any(k in query for k in ["综合分析", "多维度", "对比"]):
        return "hybrid"
    else:
        return "default"

相比 03 篇的 determine_route()，本篇有三个值得学习的改进：关键词数组化（加一行扩关键词）、新增 hybrid 分支（一对多融合）、default 走真实模型（兜底也是真的）。但也引入了新问题——顺序优先级更隐蔽了（见第五节）。

4.2 HybridAnalysisTool：一对多融合的雏形（新增分支，原样保留）

class HybridAnalysisTool:
    def call(self, inputs: Dict[str, str]) -> str:   # 注意：签名是 Dict，不是 str
        qwen_result = call_qwen3(inputs["policy"])
        deepseek_result = call_deepseek(inputs["forecast"])
        return f"[组合分析] 综合政策视角：{qwen_result}\n数据预测视角：{deepseek_result}"

这是 char07 四篇里第一个多模型协作的例子。call 方法的输入签名从 03 篇的 call(query: str) 升级为 call(inputs: Dict[str, str])——因为融合需要两个独立维度的输入（政策视角 + 预测视角），一个字符串装不下。内部执行顺序是串行（先 qwen 后 deepseek），但 两个分支互不依赖，可以改并行（见第八节进阶挑战）。

4.3 default 分支：唯一需要改写的地方

# 原写法：result = agent.chat(messages=[Message(role="user", content=query)]).content
# 改写：dashscope.Generation.call（qwen-plus）
response = dashscope.Generation.call(
    model="qwen-plus",
    messages=[{"role": "user", "content": query}],
    temperature=0.3, max_tokens=512,
    result_format='message'
)
result = response.output.choices[0].message.content

与 01-03 篇一致的改写模式——替换虚构 qwen_agent 框架为 dashscope 真实调用。注意 default 分支在本次三条 query 里也没触发，但它是"兜底"而非"死代码"——任何不命中前三个关键词组的 query 都会走这里。

五、实测发现：hybrid 路由也是死代码（与 03 篇 tool 同一家族）

第三条请求被 qwen 截胡，hybrid 分支永远不触发

教材的第三条请求意图命中 hybrid 分支：

"请对近期财政补贴政策与经济增长趋势进行多维度综合分析"
                                                         ↑hybrid 关键词组

但实测运行结果：

--- 处理第3条请求 ---
→ Qwen3.0入口已触发。          ← 实际走了 qwen 分支！
结果输出：[Qwen3.0] 回答：针对'...政策...多维度综合分析'，已完成语言生成与政策解读。

根因：route_decision() 是 if/elif 顺序判断，"政策"关键词在第一级就命中了，hybrid 分支的第三级永远没机会执行。三条 query 里只有"预测GDP趋势"这种纯预测类能顺利走 deepseek；只要 query 同时含"政策"和"综合分析"，永远被 qwen 截胡。

char07 路由死代码谱系
篇死代码分支根因修复方式
03 多路由控制策略tool 分支子任务拆分后丢失了"调用"+"工具"关键词子任务补上完整意图
04 模型分支路由hybrid 分支if/elif 顺序优先级——"综合分析"排在"政策"之后hybrid 提升到最高优先级
04 模型分支路由default 分支（本次）三条 query 都命中前三级加一条无关键词的长尾 query

共性结论：if/elif 路由函数的分支顺序就是隐式优先级——"组合类"分支需要最高优先级，因为它的关键词组常常同时包含其他分支的关键词。这不是路由本身的 bug，是教材写路由时没有意识到"一个 query 可能同时命中多组关键词"。

六、03 → 04 架构演进：一对一分发 → 一对多融合

03 篇 determine_route()：                04 篇 route_decision()：
  query → 1 个目标（一对一）               query → 可能 1 个目标（qwen/deepseek/default）
  ├─ qwen                                 或 → 2 个目标 + 融合（hybrid）
  ├─ deepseek                                ├─ fan-out: call_qwen3() + call_deepseek()
  ├─ tool                                    └─ fan-in: 拼接两个结果
  └─ default
  
  路由 ≈ 交换机                          路由 ≈ 带汇聚的扇出拓扑
  1:N=1:1                               1:N=1:1 或 1:2

这个一对多融合就是 char05-10 广播+并行图 的简化版——05-10 是"多条并行分支 → 屏障汇聚"，本篇是"两个模拟模型 → 字符串拼接"。当 hybrid 里的 call_qwen3 和 call_deepseek 都换成 dashscope 真实调用、再改并行时，就和 char05 的并行图一模一样了。

进阶挑战：HybridAnalysisTool 并行化改造
# 生产版写法：用 concurrent.futures.ThreadPoolExecutor 并行调两个模型
from concurrent.futures import ThreadPoolExecutor, as_completed

def call_real_qwen(prompt):
    return dashscope.Generation.call(model="qwen-plus", messages=[...])...content

def call_real_deepseek(prompt):
    return openai.OpenAI(base_url="https://api.deepseek.com").chat.completions.create(...)

class HybridAnalysisTool:
    def call(self, inputs):
        with ThreadPoolExecutor(max_workers=2) as executor:
            futures = {
                executor.submit(call_real_qwen, inputs["policy"]): "qwen",
                executor.submit(call_real_deepseek, inputs["forecast"]): "deepseek"
            }
            results = {}
            for future in as_completed(futures):
                results[futures[future]] = future.result()
        return f"[组合分析] 政策视角：{results['qwen']}\n预测视角：{results['deepseek']}"

这个并行化改造正好对应 char05-10 的"并行扇出 → 屏障汇聚"——把 call_qwen3 和 call_deepseek 换成 ThreadPoolExecutor 提交，as_completed 就是"屏障"，全部返回后才进下一行。

九、动手练习（巩固本篇技能）

  1. 复现实测陷阱：加一行 print(f"决策: {decision}")，验证第三条请求实际命中 qwen 而非 hybrid。
  2. 激活 hybrid 分支：新增一条纯 hybrid 请求（不含"政策"/"法规"/"概述"/"总结"），比如"请对比近三年主要政策的综合效应"——这条应该能顺利命中 hybrid。
  3. 修复路由优先级：把 hybrid 的 any() 判断移到 qwen 之前，让"综合分析/多维度/对比"优先级最高（因为组合类请求通常同时含单类关键词）。再跑一次三条 query，观察 hybrid 是否被正确触发。
  4. 激活 default 分支：新增一条不含任何关键词的长尾 query（比如"帮我写一首诗"），观察 default 分支走 qwen-plus 真实调用。
  5. 进阶：并行化 hybrid：参考第八节的 ThreadPoolExecutor 写法，把 HybridAnalysisTool 里的两个串行调用改成并行，打印计时对比（串行 ≈ 两模型耗时之和，并行 ≈ 最慢模型耗时）。
