对应文件：char07/01_上下文段结构化表示.py | 教材出处：第7章 MCP协议 例7-1 | 环境实测：qwen-plus + 模拟 DeepSeek | 生成日期：2026-10-12

一、这份代码整体在做什么（一段话讲给新人）

char07 是MCP 协议（Model Context Protocol）开篇——MCP 解决的核心矛盾是"上下文怎么表示才既能追溯又能恢复"。本篇用一个五字段上下文段结构（role/content/type/task_id/meta）把对话历史从"乱序消息列表"变成"可追溯、可过滤、可恢复"的结构化记录。多模型协同（qwen-plus + 模拟 DeepSeek）展示了同一个上下文可以被多个模型消费。

标题里的 "DeepSeek" 是假的（同 char06-09 的假标题谱系）

call_deepseek_v1() 是模拟函数，直接返回假数据。真接 DeepSeek 可以按 OpenAI 兼容模式改写：openai.OpenAI(base_url="https://api.deepseek.com")。改写时保持原状，因为本篇核心是 MCP 上下文结构，不是多模型调用。

上下文段五字段结构速查表

字段含义可选值在本例中的作用
role消息角色user / model / tool / system区分谁说的
content上下文内容任意字符串对话/工具返回的文本
type段落类型input / response / observationinput=用户输入，response=模型回答，observation=工具/辅助模型输出
task_id所属任务标识任意字符串跨任务隔离（t001 是当前任务）
meta附加元信息字典（默认空）时间戳、状态码、来源、mock 标记等

逐段代码讲解

4.1 build_context_segment：本篇的灵魂函数（原样保留）

def build_context_segment(role, content, segment_type, task_id, meta=None):
    return {
        "role": role,         # user / model / tool / system
        "content": content,   # 对话文本
        "type": segment_type, # input / response / observation
        "task_id": task_id,   # 任务隔离
        "meta": meta or {}    # 时间戳/来源/状态码等
    }

这是 MCP 的核心概念之一——上下文不再是"role + content"两字段的扁平消息列表，而是五字段的结构化段。多出来的 type/task_id/meta 让上下文能：①按类型过滤（只看 input/response）；②按任务隔离（t001 的对话和 t002 不混）；③附加元信息（哪个模型回答的、是否 mock）。

4.2 StructuredContextQueryTool：上下文查询工具（改写：去掉虚构 Tool 继承）

class StructuredContextQueryTool:              # 原：class StructuredContextQueryTool(Tool):
    def call(self, query: str) -> str:
        relevant = [seg for seg in self.segments
                    if seg["type"] in ["input", "response"]]   # 过滤：排除 observation
        context_summary = "\n".join([
            f"{seg['role']}: {seg['content']}"
            for seg in relevant[-4:]                            # 取最近 4 段
        ])
        return f"【对话上下文】\n{context_summary}\n【用户问题】\n{query}"

核心逻辑原样保留——两个关键动作：①按 type 过滤（排除 observation，因为辅助模型的模拟回答不应该进主模型的上下文）；②取最近 4 段（控制上下文窗口，避免过长）。

隐藏教学点：MCP 上下文 vs LangChain messages 的本质差异

两种上下文表示的对比
LangChain messages（char02/03 用的）：     MCP 上下文段（本篇）：
  [                                          [
    {"role": "user", "content": "..."},         {"role": "user", "content": "...",
    {"role": "assistant", "content": "..."},     "type": "input", "task_id": "t001",
  ]                                              "meta": {}}
                                              ]
  两字段：role + content                      五字段：role + content + type + task_id + meta
  扁平列表，无过滤能力                        可过滤、可隔离、可追溯
  多任务混在一起                              按 task_id 隔离
  谁回答的不知道                              meta 里记来源、时间戳

关键认识：LangChain messages 是"够用但不够用"——简单场景 OK，但多任务、多模型、可追溯、可恢复这些生产需求就不够了。MCP 的五字段结构是"够了"的那个临界点。

生产视角

  • MCP 协议的完整定义：本篇只教了"上下文段"的表示层，完整 MCP 还有工具协议（Tool）、资源协议（Resource）——三个原语构成 Agent 间通信的标准
  • task_id 的生产价值：多用户、多会话场景下，靠 task_id 隔离上下文是刚需（否则 A 的对话出现在 B 的上下文里）
  • type 字段的过滤价值：input（用户输入）→ response（模型回答）→ observation（工具/辅助模型输出）的区分，让"只看对话历史"和"看完整决策链路"两种视图成为可能
  • meta 字段的扩展性：时间戳、token 用量、工具执行耗时、模型版本——这些生产需要追溯的信息都塞这里

动手练习

  1. 验证 type 过滤：把 StructuredContextQueryTool 里的过滤条件改成 ["input", "response", "observation"]——让 observation 也进主模型上下文，观察 qwen-plus 的回答是否受模拟 DeepSeek 输出的干扰。
  2. 多任务隔离实验：加一个 task_id="t002" 的第二任务，构建独立的 context_segments——验证两个任务的上下文是否真的隔离。
  3. meta 扩展：在 build_context_segment 里加 timestamp 字段（time.time()）——让每条上下文段自带创建时间戳。
  4. 接真 DeepSeek：把 call_deepseek_v1 改成真调用——openai.OpenAI(base_url="https://api.deepseek.com", api_key=os.environ.get('DEEPSEEK_API_KEY')).chat.completions.create(...)，体验双模型真协同。
