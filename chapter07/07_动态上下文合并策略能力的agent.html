一、这份代码整体在做什么（一段话讲给新人）

本篇是 char07 第七篇——上下文的"编辑器"：不是所有段都值得塞给 LLM。06 篇解决"同样的 prompt 别重复算"（缓存），本篇解决"不同的信息怎么挑选组合"（合并策略）。上下文池里堆了 7 段信息（系统提示 + 2 轮历史对话 + 工具输出 + 当前提问），dynamic_merge_context() 按三级筛选挑出 6 段、按优先级排序拼成最终 prompt——系统提示全保留（身份不能丢）、工具段留最新 1 条（事实要新鲜）、交互历史留最近 4 条（太久远的对话价值衰减）。这是"Token 预算管理"的最小实现。

二、三级筛选策略速查表

筛选级筛选对象保留规则本例结果设计理由
第一级type == "system"全保留1 段身份设定丢了，整个回答风格就崩了
第二级type == "tool"按 timestamp 倒序，只留最新 1 条1 段（2024预测5.3%）工具数据会过时，旧工具输出不如新的准
第三级type in ["input", "response"]按 timestamp 倒序，留最近 4 条（约 2 轮对话）4 段（2023问/答 + 2022答 + 当前提问）近期对话与当前意图相关性最高
筛选后的排序顺序（注意：不是时间序，是策略序）
[SYSTEM-system] 你是一位国家政策与宏观经济专家...        ← 第1级：身份
[TOOL-tool] [DeepSeek-V1] 2024年预计5.3%。               ← 第2级：最新事实
[USER-input] 请基于历史数据与趋势，判断2024年GDP是否...   ← 第3级：最近交互（倒序取的4条）
[ASSISTANT-response] 2023年GDP增长约为5.2%。                 按时间新→旧排列：
[USER-input] 2023年预计呢？                                  当前提问 → 2023问答 → 2022问答
[ASSISTANT-response] 2022年中国GDP增长为3.0%。

注意历史段的顺序是新→旧（倒序截断后直接 extend）——当前提问紧跟在工具事实后面，最久远的 2022 对话垫底。这个顺序对 LLM 注意力分配友好：越重要的信息越靠前。

三、整体执行流程图

context_pool（7 段，时间序）
  ├─ system 段（专家身份）
  ├─ user 段 "2022年GDP增长率是多少？"
  ├─ assistant 段 "2022年增长3.0%"
  ├─ user 段 "2023年预计呢？"
  ├─ assistant 段 "2023年约5.2%"
  ├─ tool 段（DeepSeek 模拟：2024预计5.3%）
  └─ user 段 "2024年GDP能否超过5.5%？"      ← 当前提问
        │
        ▼
dynamic_merge_context(context_pool, task_type="forecast")
  三级筛选：system 全留 + tool 留最新1 + 历史留最近4
        │
        ▼
final_prompt（6 段，带 [ROLE-TYPE] 前缀，策略序排列）
        │
        ▼
dashscope.Generation.call(qwen-plus)
  → 输出："超过5.5%的可能性不足20%"（基于 5.3% 预测 + 历史增速推演）

四、逐段代码讲解

4.1 build_segment：四字段结构（原样保留）

def build_segment(role, content, segment_type, timestamp=None) -> Dict:
    return {
        "role": role,
        "content": content,
        "type": segment_type,
        "timestamp": timestamp or time.time()   # 默认当前时间——合并策略按它排序
    }

与 01 篇五字段（role/content/type/task_id/meta）相比，本篇砍掉 task_id/meta、新增 timestamp——因为合并策略的核心排序依据就是时间。字段设计跟着用途走：要按时间筛选，就带 timestamp；要跨任务隔离，就带 task_id。

4.2 dynamic_merge_context：三级筛选（本篇核心教学资产，原样保留）

# 第一级：系统提示全保留
system_segments = [s for s in segments if s["type"] == "system"]
selected.extend(system_segments)

# 第二级：工具段留最新1条（key=lambda x: -x["timestamp"] 倒序）
tool_segments = sorted([s for s in segments if s["type"] == "tool"],
                       key=lambda x: -x["timestamp"])
if tool_segments:
    selected.append(tool_segments[0])

# 第三级：交互历史留最近4条
history = sorted([s for s in segments if s["type"] in ["input", "response"]],
                 key=lambda x: -x["timestamp"])
selected.extend(history[:4])

三个值得学的写法细节：列表推导式做分类（按 type 一刀切三组）；sorted + lambda 负号做倒序（-x["timestamp"] 等价于 reverse=True）；切片 [:4] 做窗口截断（"最近 N 条"就是倒序后的前 N 个）。

4.3 [ROLE-TYPE] 前缀拼接：与 02 篇 [TYPE] 前缀同源

prefix = f"[{seg['role'].upper()}-{seg['type']}]"    # 如 [SYSTEM-system]、[TOOL-tool]
merged += f"{prefix} {seg['content']}\n"

02 篇用的是 [{type.upper()}]（如 [SYSTEM]），本篇升级为 [{ROLE}-{TYPE}] 双信息标注——LLM 不仅知道"这是什么性质的信息"（system/tool），还知道"谁在说话"（USER/ASSISTANT）。信息密度更高的标注，换来更精准的注意力分配。

4.4 task_type 参数：定义了但没用上

dynamic_merge_context(segments, task_type="forecast") 的 task_type 在函数体内从未被引用——教材预留了"按任务类型切换合并策略"的扩展点（比如 forecast 类型偏重工具段、chat 类型偏重历史），但没实现。这是和 03 篇 user_input 未使用同款的"教材占位参数"。

五、实测验证：合并策略真的生效了吗

实测：7 段进 → 6 段出，被裁掉的是谁

本例 context_pool 共 7 段：1 system + 2 tool 调用前历史（4 段交互）+ 1 tool + 1 当前提问。合并后输出 6 段——交互历史 5 段只保留了 4 段（2022 年的提问"2022年GDP增长率是多少？"被裁掉，它的回答留下了）。看合并结果的时间轴：

保留：当前提问 → 2023问答 → 2022回答        （4条：input/response 各按需）
裁掉：2022年提问 "2022年GDP增长率是多少？"   （倒序第5条，超出 [:4] 窗口）

这个实测细节揭示了窗口截断的"锯齿效应"：截断按条数不按对话轮——问和答可能被拆开（问被裁、答保留）。生产实现通常按"轮"截断（一轮 = input+response 成对保留），避免出现"只有答案没有问题"的孤儿段。

LLM 输出验证：合并 prompt 的信息足够回答问题

qwen-plus 基于合并后的 prompt 给出了高质量回答："2024年GDP实现5.3%±0.1%概率超75%；突破5.5%需同时满足三个强假设...超过5.5%的可能性不足20%"——它正确引用了工具段的 5.3% 预测、历史段的 2022（3.0%）/2023（5.2%）数据做推演。三级筛选没有丢失回答所需的关键信息，这正是合并策略成功的判据。

七、架构视角：上下文压缩的三种流派

流派核心思路优点缺点代表
规则窗口截断（本篇）按 type/时间硬规则筛选零成本、确定性强、可解释不理解语义，可能裁掉关键信息本篇、char02 BufferMemory
语义相关性检索embedding 相似度挑 Top-K语义精准，长历史也不丢要点需要向量库 + 嵌入调用成本char06 全章（RAG 本质就是上下文筛选）
LLM 摘要压缩让小模型把旧历史压缩成摘要保留语义且大幅省 Token摘要本身有失真 + 额外 LLM 成本char04 SummaryMemory 思想

三种流派可以叠加：生产系统常见组合是"规则粗筛（本篇）→ 语义精选（RAG）→ 摘要兜底（超长历史）"三层漏斗。

八、教学版 vs 生产版差距

教学简化生产要求
固定条数窗口（[:4]）按 Token 预算动态截断（tiktoken 计数，预算内能装多少装多少）
按条数截断（锯齿效应）按对话轮成对截断，避免孤儿段
task_type 参数未使用按任务类型切换策略权重（forecast 偏工具段 / chat 偏历史）
无相关性判断规则粗筛 + embedding 语义精选两层漏斗
合并结果无 Token 统计记录每次合并后的 prompt 长度，纳入 05 篇式日志做成本审计
MacroForecastTool 返回假数据真实 API + 超时兜底（char06 惯例）

九、动手练习（巩固本篇技能）

  1. 复现锯齿效应：往 context_pool 再加一轮历史对话（问+答），跑一次看合并结果——观察哪段被裁掉、是否出现"答留问丢"。
  2. 实现按轮截断：改写第三级筛选，把 input 和 response 按"轮"配对（input 紧跟 response 为一轮），保证截断不拆散对话——对比两种截断的合并结果差异。
  3. 激活 task_type：给 dynamic_merge_context 加逻辑——task_type="forecast" 时工具段保留 2 条，task_type="chat" 时历史窗口扩到 6 条（让占位参数真正参与决策）。
  4. Token 预算版：用 len(prompt) // 2 粗略估算 Token 数（中文约 2 字符/Token），给合并函数加 max_tokens 参数，超预算时从最旧的历史开始裁。
  5. 进阶：语义精选：结合 char06 的 DashScopeEmbeddings，在第三级筛选前先算"当前提问"与各历史段的余弦相似度，只保留相似度 Top-4——对比规则窗口与语义窗口在同一份数据上的合并结果。
