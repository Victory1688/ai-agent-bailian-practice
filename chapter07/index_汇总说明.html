一、char07 在课程体系中的定位

核心命题：上下文是 Agent 系统的"数据血液"——怎么表示、怎么进出、怎么存、怎么选，决定了 Agent 的上限。

char01-06 分别解决了"调用壳、循环壳、服务壳、框架壳、图壳、检索壳"，这些壳里流动的都是"上下文"——但前六章都把上下文当作"黑盒子"用（messages 列表、历史对话），没人认真拆解过"上下文到底该长什么样、怎么管"。char07 是第一次把"上下文"本身当作独立工程对象来设计的章节，七篇完整覆盖了上下文工程的生命周期。

二、四阶段闭环：上下文工程的完整生命周期

①
进：表示 + 组装
01 五字段表示
02 四类标注组装
②
出：路由 + 分发
03 一对一路由
04 一对多融合
③
存：持久化 + 缓存
05 JSONL 日志
06 MD5 缓存
④
选：合并 + 压缩
07 三级筛选

四个阶段不是线性串联，而是围绕"上下文池"的多向操作：新段进入池子（01/02）、请求进来时路由到对应处理者（03/04）、同时落日志（05）+ 查缓存（06）、调 LLM 前从池子里挑出最有价值的段拼成 prompt（07）。

四、char07 独有的三笔"学费清单"（系列最珍贵部分）

学费 1：if/elif 顺序即隐式优先级——路由死代码谱系
篇死代码分支根因修复方式
03 多路由控制策略tool 分支子任务拆分后丢失"调用"+"工具"关键词子任务补上完整意图
04 模型分支路由hybrid 分支if/elif 顺序优先级——"综合分析"排在"政策"之后，被截胡hybrid 提升到最高优先级

共性结论：组合类分支（hybrid/tool）的关键词组常常同时包含其他分支的关键词，必须放在最高优先级。这不是路由本身的 bug，是教材写路由时没有意识到"一个 query 可能同时命中多组关键词"。

学费 2：timestamp 是性能审计的天然探针

05 篇持久化日志里，前三段的 timestamp 都是 10:18:01（毫秒级间隔，纯本地操作），response 段是 10:18:08——6.5 秒差正是 qwen-plus 调用的网络往返 + 模型生成耗时。生产系统的性能审计就是靠这种时间差定位瓶颈的：日志本身就是免费的性能探针。

学费 3：缓存的 17.7x 加速比——LLM 调用是最贵最慢的环节

06 篇连续运行两次：第一次 cache miss 调 LLM 花 13.8 秒，第二次 cache hit 直接回放花 0.78 秒——省掉了全部 LLM 调用开销。但缓存有个前提：full_prompt 字符串一字不差（MD5 精确匹配），同义改写的 prompt 永远不命中。精确缓存 ≠ 语义缓存，后者需要向量相似度匹配（char06 DashScopeEmbeddings + FAISS 可以直接实现）。

五、核心数据结构演进链

01 篇五字段：  {role, content, type, task_id, meta}          ← 内存上下文基础
02 篇 build_segment 同构：{role, content, type, task_id, meta}  ← 加上四类标注扩展
05 篇七字段：  {id, timestamp, task_id, role, type, model, content}  ← 持久化新增 id/timestamp/model
07 篇四字段：  {role, content, type, timestamp}               ← 为合并策略简化，新增 timestamp

字段不是越多越好——每个额外字段都带来存储和处理成本。01 篇的 meta 字段在 05 篇里被拆成独立的 model 字段（持久化场景下 model 比 meta 更有用），07 篇为了合并策略砍掉 task_id/meta 但补上 timestamp——字段设计跟着用途走。

七、char07 独有的设计模式

模式代表篇一句话生产升级

标注前缀拼接02/07[ROLE-TYPE] 标注让 LLM 一眼看懂信息性质同本篇（Token 成本低、注意力收益高）

八、给新人的学习路径

① 先跑 01 → 理解五字段数据结构是什么
   自测：改 role/type 字段值，观察 JSON 输出变化

② 再跑 02 → 理解四类标注怎么让 LLM 行为不同
   自测：分别去掉 system/memory/tool 标注，观察 qwen-plus 回答差异

③ 连读 03+04 → 对比 determine_route vs route_decision
   自测：给 route_decision 加"翻译"关键词路由，体会加一行扩关键词

④ 重点读 05+06 → 两种持久化的对比审计回溯 vs 性能优化
   自测：删 prompt_cache.json → 跑两次 → 计时对比 17.7x 加速比

⑤ 最后读 07 → 理解"不是所有上下文都值得塞给 LLM"
   自测：往 context_pool 再加一轮对话 → 观察哪段被裁掉 → 修复锯齿效应

⑥ 综合练习：把 07 篇三级筛选的"规则粗筛"升级为"规则粗筛 + 语义精选"
   用 char06 的 DashScopeEmbeddings + FAISS 实现——这就是三层漏斗的完整雏形
