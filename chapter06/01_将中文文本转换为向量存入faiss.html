一、先回答你的问题：这个报错是要装包吗？

不是缺包，是教材的 import 路径过时了（char03/04 同款问题）
报错原因解释
① import 路径断裂from langchain.embeddings import OpenAIEmbeddings 是 langchain 0.x 时代的写法。1.x 之后这些类被拆分到独立的包（langchain_openai / langchain_community），旧路径里根本没有这个名字——报 ImportError。装多少包都不会好，因为路径本身就错了
② 模型选型不通就算修好路径，OpenAIEmbeddings 默认直连 OpenAI 官方接口，国内环境访问不了——需要换成可用的向量化服务

改写方案：嵌入模型换百炼的 DashScopeEmbeddings（与 char05-03 同款）——向量化（本篇）和对话生成（后续篇）共用同一把 DASHSCOPE_API_KEY 钥匙，不再需要 OpenAI 的 key。依赖方面 faiss-cpu、langchain_community 都已装好（char03/05 时代就绪），无需新装任何包。

二、这份代码整体在做什么（一段话讲给新人）

本篇是第 6 章 RAG（检索增强生成）的第一块积木：把文本变成向量、存进向量数据库、按语义相似度检索。五条中文知识文本先被百炼向量模型转成 1024 维数字向量存入 FAISS 索引；查询时"什么是向量数据库？"也被转成向量，FAISS 找出语义距离最近的 4 条返回——注意排序依据是语义相似度而不是关键词匹配：查询里没有"嵌入""LangChain"这些词，但讲嵌入和向量库的文本照样排到前面。

核心概念速查表

概念是什么在本例中的角色
向量化（Embedding）把文本映射成高维数字向量，语义相近的文本向量距离近text-embedding-v3 把每条文本变成 1024 维向量
FAISSMeta 开源的向量相似度检索库（Facebook AI Similarity Search）本地向量数据库：存索引、算距离、排 top-k
DocumentLangChain 的文本标准载体（page_content + metadata）五条文本各包成一个 Document
similarity_search查询向量化后在索引里找最近邻默认 k=4，返回最相似的 4 条
DashScopeEmbeddings百炼向量模型的 LangChain 封装OpenAIEmbeddings 的国内可用替代
RAG检索增强生成：先检索知识再交给大模型生成答案本篇是 RAG 的"R"（检索），后续篇补"A"（生成）

逐段代码讲解

5.1 初始化嵌入模型（唯一的改写点）

# 原写法（注释保留）：
# embedding_model = OpenAIEmbeddings()

# 改写：
embedding_model = DashScopeEmbeddings(
    model="text-embedding-v3",        # 百炼向量模型，1024 维，中文效果好
    dashscope_api_key=api_key         # 与对话模型同一把钥匙
)

嵌入模型的选择只影响"向量质量"，FAISS 接口完全不变——换嵌入模型 = 换一行构造参数，这就是 LangChain 抽象层的价值。

5.2 入库与检索（原样保留）

vector_store = FAISS.from_documents(docs, embedding_model)   # 一次性入库+建索引
results = vector_store.similarity_search(query)               # 默认 k=4

两行是 FAISS 的标准用法。from_documents 内部干三件事：逐条调嵌入 API → 存向量 + 原文 → 建检索索引。注意查询向量必须用同一个嵌入模型——不同模型的向量空间不通用，混用等于"拿尺子的刻度去量公斤"。

两个值得品味的细节：

  • 查询里没有出现任何一条文本的关键词（"什么是向量数据库？"这七个字与五条文本没有字面重叠），但排序完全符合语义直觉——这就是向量检索 vs 关键词匹配的本质差异
  • "LangChain用于构建语言模型应用"排第 3（而不是直觉上更远）——因为"构建应用"与"数据库""转化"同属 AI 技术语义域，共享大量上下文；而"人工智能是研究人类智能的模拟技术"（学术定义句式）与查询的语义距离最远，未进前四。向量是整句语义的压缩，不是关键词的集合

生产视角

  • FAISS 是内存库：进程结束索引消失——生产要 save_local / load_local 落盘，或换持久向量库（Milvus/Chroma/PGVector）
  • 本篇只有 5 条文本：真实场景是文档切片（chunk）后批量入库，切片策略直接影响检索质量
  • k 值与召回：默认 k=4 是演示值；生产按任务调 k（太大引入噪声、太小漏答案），可配 similarity_search_with_score 看分数设阈值
  • 嵌入模型一致性：入库与查询必须同模型、同版本——模型升级要全量重建索引

动手练习

  1. 调 k 看全量：改成 similarity_search(query, k=5)——五条全召回，观察最后一名是哪条（预测：人工智能定义那条），验证语义距离排序。
  2. 看分数：换成 vector_store.similarity_search_with_score(query)，打印每条的 L2 距离分数——把"相似"变成数字。
  3. 换查询：把 query 改成"大模型能做什么？"——预测排序会怎么变，跑完对照，体会查询措辞对召回的影响。
  4. 增量入库：用 vector_store.add_texts(["RAG通过检索外部知识增强生成质量"]) 加一条新知识，再查——理解向量库是"活的"，可随加随查。
