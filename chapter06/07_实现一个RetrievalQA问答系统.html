一、这份代码整体在做什么（一段话讲给新人）

本篇是 char06 第一个显式 RAG 闭环：法律条文 → 切片 → 向量化 → FAISS 索引 → **手动检索** → **手动拼 prompt** → **手动调 LLM 生成**。与 05/06 篇的 function calling 不同，本篇是开发者写死"先检索再生成"的流程——这是 RAG 最原始、最显式的形态，也是理解 function calling 底层逻辑的最佳起点。

逐段代码讲解

4.1 LawRetrievalTool：纯类 + call() 方法（改写：去掉虚构 Tool 继承）

class LawRetrievalTool:                    # 原：class LawRetrievalTool(Tool):
    def __init__(self, chunks, embeddings): # 原：super().__init__(name=..., description=...)
        self.chunks = chunks
        dim = embeddings[0].shape[0]
        self.index = faiss.IndexFlatL2(dim)
        self.index.add(np.vstack(embeddings))

    def call(self, query: str) -> str:     # 核心检索逻辑完全原样保留
        q_vec = get_qwen_embedding([query])[0].reshape(1, -1)
        D, I = self.index.search(q_vec, k=5)   # k=5（比 05/06 的 k=3 多）
        retrieved = [self.chunks[i] for i in I[0]]
        return "\n".join(retrieved)

原写法 class LawRetrievalTool(Tool): 继承虚构 Tool 类→去掉继承，核心检索逻辑（向量化→搜 top-k→返回命中）一字未改。

4.2 build_prompt_with_context：知识即上下文（原样保留——本篇灵魂函数）

def build_prompt_with_context(query: str, context: str) -> str:
    prompt = f"""你是一名法律智能助手。请根据以下法律条文内容回答用户问题。
【法律条文】：
{context}
【用户提问】：
{query}
请结合条文内容给出明确、简洁、准确的回答。"""
    return prompt

这是 RAG 的"G"（Generation）的核心机制：把检索到的知识（context）塞进 prompt，引导 LLM 基于上下文回答而非凭空编。prompt 里明确写了"请根据以下法律条文内容回答"——这就是 RAG 防幻觉的关键：不给知识，LLM 瞎编；给了知识，LLM 只能基于知识说。

显式 RAG vs 隐式 RAG（function calling）的对照

三个步骤，两种写法
  本篇显式 RAG（开发者写死流程）：         05/06 篇隐式 RAG（function calling）：
  ┌─────────────────────────┐          ┌─────────────────────────────┐
  # Step 1: 检索              │          # Agent 循环（模型自主决策）：
  context = retrieval_tool    │          while True:
            .call(question)   │            response = model.call(...)
  # Step 2: 拼 prompt          │            if tool_calls:
  prompt = build_prompt_     │              → 模型调 search_finance()
           with_context(...) │              → 拿到 context
  # Step 3: 调 LLM             │              → context 塞进 messages
  answer = llm.call(prompt)   │            else:
                              │              → 模型直接生成回答
  └─────────────────────────┘          └─────────────────────────────┘
  ↑ 流程固定，必然走检索路径              ↑ 流程灵活，模型可能跳过检索
  ↑ 新人一眼看懂 RAG 两步                 ↑ 更优雅但藏了底层逻辑

**关键认识**：function calling 只是把本篇的三个显式步骤，交给模型在 Agent 循环里自主决策是否执行。底层逻辑完全同构——理解了本篇，function calling 就不再是黑盒。

生产视角

  • 显式 vs 隐式的选型：固定流程/必须检索用显式（本篇），灵活流程/可能跳过检索用 function calling（05/06 篇）。法律问答这种场景，"必须先查法条再回答"——显式更合适
  • prompt 注入的边界：context 塞进 prompt 后，LLM 可能被长 context 干扰（长上下文下注意力稀释）；生产用 max_tokens 限制 + 上下文窗口管理
  • 检索结果的 rerank：FAISS 返回的 top-5 里可能有无关条文（如本篇模拟条文里混了劳动法）——生产加 rerank 模型二次排序
  • 可追溯性：法律场景要求回答必须能追溯到具体法条——本篇已天然支持（检索→引用→回答），生产需加 source 字段返回

动手练习

  1. 对比显式 vs 隐式：把本篇 Step 1+2+3 改写成 function calling 版本——体会"同一个检索逻辑，两种调用姿势"。
  2. 换问题观察检索：把 question 改成"劳动合同法对订立合同有什么规定？"——预测 FAISS 会召回哪条模拟条文，跑完对照。
  3. 看检索到什么：print(retrieval_tool.call(question))——亲眼看到 Step 1 到底检索到了什么，理解"模型看到的上下文是什么样的"。
  4. 加 source 返回：改写 call() 返回结构化数据 [{"content": ..., "source": ...}, ...]，在 prompt 里引用 source——让回答能追溯到具体文档。
