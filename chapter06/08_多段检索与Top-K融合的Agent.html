一、这份代码整体在做什么（一段话讲给新人）

本篇与 07 篇结构几乎同构——同样的"显式 RAG 两步"（检索→拼 prompt→调 LLM），唯一差异是显式命名并强化了 Top-K 融合的检索策略：默认 top_k=5，FAISS 搜出 5 条最相关的政策标题，拼接成融合上下文塞进 prompt。关键认知：07 篇 k=5 但没叫"融合"，本篇是"给 k=5 起了个名字叫 Top-K 融合"——这个命名本身就是生产 RAG 的核心优化思路之一。

逐段代码讲解

4.1 MultiPassageRetrievalTool.call()：Top-K 融合的核心

def call(self, query: str) -> str:
    qvec = get_qwen_embedding([query])[0].reshape(1, -1)
    D, I = self.index.search(qvec, self.top_k)   # 搜 top_k 条
    top_passages = [self.docs[i] for i in I[0]]
    # Top-K融合策略：拼接多个片段形成更丰富上下文（本篇灵魂）
    fused_context = "\n".join(top_passages)
    return fused_context

关键一行：fused_context = "\n".join(top_passages)——把 FAISS 搜出的 top_k 条最相关段落，用换行拼接成一个长字符串，塞进 prompt 里作为"语料片段"。这就是"融合"的本质：不是让 LLM 逐条看，而是把多条知识打包成一个上下文块。

4.2 split_chunks：硬切 vs 贪婪拼接（与 04/07 篇的对照）

硬切的优点：每段长度一致，适合无标点/短文本场景。硬切的缺点：截断句子（如"GDP核算方法试行统一"→硬切可能变成"GDP核算方法试行"和"统一"两段，语义断裂）。贪婪拼接的优点：保留完整句子。贪婪拼接的缺点：每段长度不均，边界依赖标点。哪种好取决于文本类型——有标点的长文本用贪婪拼接更好。

Top-K 融合：为什么搜 top_k 比搜 top_1 好？

三个实际原因
  1. 语义匹配是近似的：向量空间里"GDP核算方法"和"研发支出核算方法"语义相近，top-1 可能召回后者，top_k=5 才能保证真正相关的"GDP核算方法"在里面——放宽召回 → 让 LLM 自己筛选，比硬卡 top-1 更稳妥
  2. 答案可能跨多条知识：本篇用户问"GDP核算方法"，模拟库里分散在两条标题里——只搜 top-1 可能只给一条，搜 top-5 两条都在 → LLM 可以综合两条给出更完整的回答
  3. 降低 FAISS 参数依赖：FAISS L2 距离的阈值不好调（太小漏掉真相关，太大召回太多噪声）——直接搜 top_k 更简单可控

但也有代价：融合后 context 变长 → 占用更多 prompt tokens → 可能稀释 LLM 的注意力（长上下文里"注意力分配"是问题）。生产通常在 Top-K 后加 rerank 重排序，选 top-2 最相关的，兼顾召回率和上下文简洁性。

生产视角

  • Top-K 的 k 值怎么选：k=3~10 之间，取决于知识库大小和查询模糊度——知识库小 k 可以小（如本篇只有 8 条，k=5 太宽了），知识库大 k 可以大。**生产加 rerank**：先粗召回 top-20，再 rerank 精排选 top-3
  • 融合策略不止 join：简单拼接只是最基础的融合；更高级的有 MapReduce（每段先让 LLM 总结→总结再合并）、递归摘要（递归把小段合成大段直到只剩一个）
  • 硬切 vs 贪婪拼接的选型：有标点的自然语言文本 → 贪婪拼接（04/07 篇）；代码/表格/无标点文本 → 硬切 + overlap（重叠片段保证语义不截断）
  • 显式 vs 隐式 RAG：本篇和 07 篇用显式，生产可能更常用 function calling 隐式——但显式是理解 RAG 底层的必经之路
