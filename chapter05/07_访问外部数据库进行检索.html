本篇核心：数据库工位的三个教学点

2.1 内存数据库 :memory: 的生命周期

conn = sqlite3.connect(":memory:")   # 每次连接都是一个全新的空库
cursor.execute("CREATE TABLE papers (...)")   # 所以节点里要重新建表
cursor.executemany("INSERT INTO papers ...")  # 重新插数据
...
conn.close()    # 连接关闭，内存库连同数据一起销毁
:memory: 内存库（本篇）真实外部数据库（生产）
数据生命周期连接打开→创建，连接关闭→销毁持久化在磁盘，连接只是"看它的窗口"
每次 invoke都要重新建表插数据（本篇节点内做）建表一次，节点只做 SELECT
多节点/多进程共享做不到（每个连接独立的库）天然共享
教学价值零配置自包含演示——演示完什么痕迹都不留—

教材注释"使用内存数据库示例"说得诚实——它是让演示自包含的手段：读者无需准备任何数据库文件就能跑通。换真库只需改 connect 参数，SQL 一字不动。

2.2 ? 占位符（SQL 注入防护，呼应 char02-06）

cursor.execute("SELECT content FROM papers WHERE keyword=?", (kw,))

与 char02-06 篇（员工数据库）同款标准写法：参数永远走占位符 + 元组传参，绝不 f-string 拼 SQL。若 kw 被恶意注入 "' OR '1'='1"，占位符会把它当纯文本匹配（查无结果），拼接写法则会把全表泄出去。

2.3 按关键词逐个查询（与 06 篇同构）

for kw in state.get("keywords", []):
    cursor.execute("SELECT content FROM papers WHERE keyword=?", (kw,))
    results.extend([row[0] for row in rows])

与 06 篇的字典 for 循环逐词检索同构——骨架复用的又一实证：把 database.get(kw, []) 换成 SQL 查询，其他节点一行不动。

本篇最有价值的发现：降级链"活着"是运气不是设计

与 06 篇的对照实验：同样的写法，06 断了，07 活着——为什么？
06 篇（断裂）07 篇（活着）
失败信号"有效文献不足""未找到相关数据"
中间工位加工截断+加省略号 → "有效文献不足..."replace("系统","智能体系统") → 信号里没有"系统"，原样通过
下游精确匹配失配 → 降级链断裂命中 → 降级链正常

本篇 conclude 与 06 篇一样用精确匹配判断失败信号——它能工作，仅仅因为 tool 工位的 replace 恰好碰不到信号里的字。做个反事实推演：若失败信号改叫"检索系统异常"，replace 会把它变成"检索智能体系统异常"→ 精确匹配立刻失效 → 与 06 篇同款断裂。

教训升华（05→06→07 三篇的完整故事线）
  • 05：信号逐级整体替换（"未找到"→"暂无可用信息"）→ 链活
  • 06：信号被格式加工（加省略号）→ 链断
  • 07：信号被加工函数放行（运气好）→ 链活

三篇合起来的结论：字符串信号在流水线里的存活是不可靠的——它取决于"下游有没有人碰巧改了它"。生产正解：失败状态走结构化通道（State 加 status 字段），文本内容随便加工，元信息永不失真。

生产视角：内存演示库 → 真实外部数据库

  • 建库搬出节点：CREATE TABLE / INSERT 移到节点外（初始化脚本或 migrations），节点只留 SELECT——现在节点里"每次 invoke 重建库"是演示便利，生产绝不允许
  • 连接管理：sqlite3.connect 直接调 → 连接池/ORM（生产环境连接的建立是昂贵操作，且要防泄漏）
  • 查询策略：关键词逐条 SELECT → 批量 IN 查询 / 全文索引（FTS5）/ 与向量检索组合成混合检索
  • 失败状态结构化：status 字段（第三节三篇故事线的最终答案）
  • 权限最小化：检索节点通常只需要只读账号——应用连接不该有 DROP/DELETE 权限

动手练习

  1. 反事实实验：把 retrieve 的失败信号改成"检索系统异常"，跑故障路径——亲眼看 replace 把它变成"检索智能体系统异常"导致 conclude 判断失效（在 07 篇亲手复现 06 篇的断裂）。
  2. 批量查询：把逐关键词 SELECT 改成一条 SQL：SELECT content FROM papers WHERE keyword IN (?,?,?,?)（占位符数量与 keywords 等长）——对比两种写法的查询次数。
  3. 持久化版：把 ":memory:" 换成文件路径（如 "papers.db"），建表插数据移到节点外只执行一次，节点只 SELECT——观察第二次 invoke 不再需要插数据。
  4. 进阶：真外部工具：把 tool 工位的 replace 换成一次 ChatTongyi 调用（对每条文献生成一句话点评），体验"字符串加工工位 → 模型工位"的升级路径。
