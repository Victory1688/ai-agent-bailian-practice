一、这份代码整体在做什么（一段话讲给新人）

本篇引入多 Agent 协作的消息传递范式：三个 Agent 节点（A 检索 → B 分析 → C 结论）之间不共享变量——A 检索完把结果"寄"给 B，B 分析完把结论"寄"给 C，每条消息都带发送方/接收方/时间戳/内容四要素。LangGraph 负责节点顺序，A2AProtocol 负责消息投递——"编排"与"通信"分离。
改写点：State(Dict) 静默失败（系列第九次）→ TypedDict。A2AProtocol、三节点、图全部原样保留。本篇有两个必讲辨析：假 A2A 协议命名（08 篇假 MCP 的续集）和实测抓到的"schema 裁剪输入键"新坑。

二、命名辨析：此"A2A"非彼 A2A（假 MCP 的续集）

协议名陷阱连续剧：08 篇假 MCP，09 篇假 A2A
教材的 "A2AProtocol"真实的 A2A（Agent2Agent Protocol）
本质同进程内的消息列表存取类Google 2025 年提出的开放协议（后捐给 Linux 基金会）
架构一个 Python 对象，所有节点直接调用分布式：不同 Agent 是独立服务，跨网络通信
消息对象自定义 dict（sender/receiver/timestamp/content）标准 Agent Card（能力发现）/ Task / Message 对象
传输函数调用（内存引用）JSON-RPC over HTTP
定位教学模拟与 MCP 是"姊妹协议"：MCP 管 Agent↔工具，A2A 管 Agent↔Agent

本篇真正教的概念：消息传递范式（message passing）——Agent 之间靠收发消息协作而非共享变量。这个范式在同进程里显得多余（State 直传更简单），但它真正的用武之地是分布式多 Agent：当 A、B、C 是三台机器上的三个服务时，唯一的协作方式就是消息传递——教材用同进程模拟把范式先建起来。

实测发现：schema 裁剪输入键——比"返回 None"更隐蔽的新坑

系列第九坑的升级形态：图正常跑完，数据悄悄丢在入口

改写初版 State 只声明了三个结果字段、漏了 query（节点里会读它）。实测结果令人意外——

invoke({"query": "LangGraph"})
  → agentA_result: '未找到相关数据'     ← db.get("") 当然查不到
  → 全链路照常跑完，没有任何报错！

原因：LangGraph 1.x 会把不在 State schema 里的输入键静默裁剪掉——query 键进不了状态，agent_a_node 里 state.get("query", "") 拿到空串。修复（TypedDict 补上 query 字段）后一切正常。
对照前 8 篇：State(dict) 无注解 → invoke 返回 None（错在出口，一眼见尸）；本篇漏字段 → 图跑完但数据丢（错在入口，结果"看起来正常"）——静默裁剪比静默失败更危险。教训：TypedDict 必须包含节点会读到的所有键，包括入口键 query。

核心概念速查表

概念是什么在本例中的角色
A2AProtocol教材命名的同进程消息总线（非真 A2A）三个 Agent 的"邮局"：send 寄信、receive 收信
消息四要素sender / receiver / timestamp / content每条消息的标准结构（真实 A2A 的 Message 同款思路）
收件箱（inbox）receive 按 receiver 过滤出的消息子集AgentB/C 各自的"信箱"
inbox[-1]取最新一条多条消息时的取舍策略（LIFO 最新优先）
消息传递范式靠收发消息协作，不共享变量A→B→C 三级接力全走 a2a，不走 State 直读
日志型外部存储append 列表，只增不清messages 跨 invoke 累积留痕（对照 08 篇的覆盖型）

逐段代码讲解

6.1 A2AProtocol（原样保留）——分布式消息总线的婴儿版

def send(self, sender: str, receiver: str, content: Dict):
    message = {"sender": sender, "receiver": receiver,
               "timestamp": time.time(), "content": content}
    self.messages.append(message)          # 日志式累积，永不覆盖

def receive(self, agent: str):
    inbox = [msg for msg in self.messages if msg["receiver"] == agent]
    return inbox                            # 按收件人过滤 = "收件箱"

接口形状（send/receive + 收件人寻址）与真实消息中间件（RabbitMQ / Kafka 消费组）同构。与 08 篇的关键差异：context_store 是字典（同 key 覆盖，存"最新状态"），messages 是列表（append 累积，存"全部通信记录"）——KV 型 vs 日志型，生产里分别是 Redis（状态缓存）与消息队列/审计日志。

6.2 三个 Agent 节点（原样保留）——注意它们"不读对方的状态"

# AgentB 的数据来源是收信，不是 state.get("agentA_result")：
inbox = a2a.receive("AgentB")
if inbox:
    data = inbox[-1]["content"].get("retrieved", "")   # 取最新一条
    ...
a2a.send("AgentB", "AgentC", {"analysis": analysis})   # 处理完再寄给下一个

inbox[-1] 的取舍：收件箱有多条时只认最新——简单但有信息丢失风险（真实 A2A 会用 Task 对象跟踪完整任务生命周期，而不是只看最后一条）。

生产视角：同进程模拟 → 真分布式多 Agent

  • 换消息中间件：A2AProtocol → RabbitMQ / Kafka / Redis Streams——send/receive 接口不变，实现换传输层
  • 换协议栈：自定义消息 dict → 真实 A2A 协议（Agent Card 声明能力 / Task 跟踪状态机）——Agent 可被任何协议客户端发现与调用
  • 什么时候才需要它：同进程多节点用 State 直传更简单；跨进程/跨机/跨组织的 Agent 协作才需要消息范式——不要为了"看起来像多 Agent"而引入分布式复杂度
  • 消息可靠性：inbox[-1] 丢历史 → 生产要有消息确认/重试/幂等设计
  • schema 纪律：State 字段 = 节点要读写的全部键（含入口键）——第三节新坑的直接教训

动手练习

  1. 复现 schema 裁剪坑：把 TypedDict 里的 query 字段删掉跑一次——亲眼看"图正常跑完但全链路未找到相关数据"，建立对这个最隐蔽坑的肌肉记忆。
  2. 收件箱策略实验：手动 a2a.send 两条不同内容的消息给 AgentB，观察 inbox[-1] 只取到哪条；再改成 inbox[0]（最旧优先）对比。
  3. 消息持久化：给 A2AProtocol 加 save_to_file/load_from_file（json 读写 messages）——让通信记录跨进程存活，接上 char02-03 持久化的思想。
  4. 进阶：真分布式雏形：把 AgentB 拆成独立 FastAPI 服务（收 POST /receive、返回 analysis），agent_b_node 里改用 requests 调它——同一范式从内存引用变成网络调用，就是真实 A2A 的第一步。
