02_使用langgraph设置节点之间的条件边 - 代码解析

对应文件：char05/02_使用langgraph设置节点之间的条件边.py | 教材出处：第5章2节 条件边（Conditional Edge） | 环境实测：langgraph 1.2.11 | 生成日期：2026-10-11

一、这份代码整体在做什么（一段话讲给新人）

上一篇的两节点图是"走到底的直线"——search 必到 generate。本篇引入 LangGraph 的第二个关键机制：条件边（add_conditional_edges）——根据当前状态的值动态选择下一个节点。场景是工单分诊：check 节点检查 query 里有没有 "urgent"，有则走 fast 快速处理路径，没有则走 normal 普通路径。两次 invoke 分别命中两条分支。
改写点与 01 篇相同：教材的 State(dict) 静默失败（invoke 返回 None），改 TypedDict 后输出与教材预期逐字符一致。

二、条件边意味着什么（从流水线到任务流的分水岭）

01 篇：固定边02 篇：条件边
执行路径入口 → A → B → 出口（唯一）入口 → 判断 → 多条路径之一 → 出口
表达能力顺序流程（SequentialChain 同级）分支/选择（if-else 图形化）
决定走哪条路的是开发者（编译期写死）运行时的状态值
本篇是 Agent 循环的直接前身（提前看一眼 char02 的对照）

char02 手写的 agent_chat 里有一段：if not tool_calls: 返回最终回答 else: 执行工具回到模型——这就是一个内联条件边。用 LangGraph 表达它：判断节点（模型节点把"是否需要调工具"写进状态）→ 路由函数（读这个键）→ 映射表（"继续"→tool 节点，"结束"→END）。本篇练的"路由三件套"，就是后面把 agent_chat 变成图的所有前置知识。

三、教材代码的问题（同 01 篇的静默失败）

实测 langgraph 1.2.11：State(dict) 下 invoke 返回 None——本篇还多一层问题
  • 与 01 篇相同：无字段注解 → 图无法构建状态 schema → 节点照常执行但状态收集不回来
  • 本篇加码：条件边的路由函数 lambda state: state["route"] 依赖 route 键——无 schema 时这个键根本不在状态定义里，路由机制本身失去依据
  • 修复：TypedDict 声明三个字段（query/route/response），其余代码逐行原样保留

四、核心概念速查表

概念是什么在本例中的角色
add_conditional_edges按状态值动态选路的 API（三参数）挂在 check 之后，按 route 值分流
路由函数读状态、返回"选择值"的函数（lambda 或具名函数）lambda state: state["route"]
映射表选择值 → 目标节点名 的字典{"fast": "fast", "normal": "normal"}
路由键（route）承载判断结果的中间状态字段check_node 写入，路由函数读取
END图的终点哨兵fast/normal 两条路径各自通向 END
多入口共享判断同一个 check 分流多个业务节点本例 1→2 分叉；还可以扩展成多级路由

五、整体执行流程图

      invoke({"query": "urgent request"})          invoke({"query": "regular request"})
                  │                                          │
                  ▼                                          ▼
   ┌──────────────────────────────┐          ┌──────────────────────────────┐
   │ check_node                    │          │ check_node                    │
   │ "urgent" in query.lower()?    │          │ "urgent" in query.lower()?    │
   │  → 是 → 写 route="fast"       │          │  → 否 → 写 route="normal"     │
   └──────────────┬───────────────┘          └──────────────┬───────────────┘
                  │ 条件边                                    │ 条件边
                  │ 路由函数读 route → "fast"                  │ 路由函数读 route → "normal"
                  │ 映射表["fast"] → fast 节点                 │ 映射表["normal"] → normal 节点
                  ▼                                          ▼
   ┌──────────────────────────────┐          ┌──────────────────────────────┐
   │ fast_node                     │          │ normal_node                    │
   │ 写 response="快速处理路径已启动" │          │ 写 response="普通处理路径已启动"  │
   └──────────────┬───────────────┘          └──────────────┬───────────────┘
                  ▼                                          ▼
                 END                                        END

   实测输出（与教材预期逐字符一致）：
   {'query': 'urgent request',  'route': 'fast',   'response': '快速处理路径已启动'}
   {'query': 'regular request', 'route': 'normal', 'response': '普通处理路径已启动'}

一个值得注意的细节：route 是中间变量，但它也留在了最终状态里（教材预期输出如此，实测一致）。LangGraph 默认让所有状态字段全程可见——这既是调试福音（能看出为什么走这条路），也提示生产中若不想暴露中间变量，需在出口做后处理。

六、逐段代码讲解

6.1 状态与路由节点（原样保留，仅 State 改 TypedDict）

class State(TypedDict):
    query: str      # 用户输入
    route: str      # 路由判断结果（中间变量）
    response: str   # 最终响应

def check_node(state: State):
    if "urgent" in state.get("query", "").lower():
        return {"route": "fast"}      # 判断结果写进状态，而不是直接决定走向
    return {"route": "normal"}

关键设计：check_node 不直接选路，它只负责"把判断写进状态"——选路由条件边负责。判断逻辑与路由逻辑解耦，是图能被重组的前提（想换判断规则只改 check_node，想换路径映射只改映射表）。

6.2 条件边（本篇核心，原样保留）

builder.add_conditional_edges(
    "check",                            # 参数1：挂在哪个节点之后
    lambda state: state["route"],       # 参数2：路由函数——读状态返回选择值
    {"fast": "fast", "normal": "normal"} # 参数3：映射表——选择值 → 目标节点
)

三参数解剖：条件边相当于把一句 if route == "fast": go("fast") elif route == "normal": go("normal") 图形化。映射表的价值：选择值与节点名解耦——路由函数可以返回语义值（"fast"），映射表决定它落到哪个节点（节点叫别的名字也行）。

6.3 图的组装与双路径验证（原样保留）

builder.set_entry_point("check")        # 入口是判断节点
builder.add_edge("fast", END)           # 两条业务路径各自通向终点
builder.add_edge("normal", END)

print(graph.invoke({"query": "urgent request"}))    # 命中 fast
print(graph.invoke({"query": "regular request"}))   # 命中 normal

两次 invoke 共用同一个编译好的图——图是无状态的（状态只在单次 invoke 内流转），可重复执行。这与 char02 的 agent_chat 形成对照：agent_chat 靠外部 memory 跨轮累积，图的跨轮记忆要用 checkpointer（后续篇）。

八、LangGraph 表达力三步走：本篇走到第二步

步骤API表达能力篇目
① 顺序图add_edge固定流水线01
② 条件图add_conditional_edges按状态分支02（本篇）
③ 循环图条件边 + 指回上游的映射Agent 的 ReAct 循环后续篇
路由三件套模式（贯穿 char05 全章的骨架）
判断节点（写状态键） → 路由函数（读键） → 映射表（分发）

后续把它用到 Agent 循环上：
llm 节点（写 need_tool 键） → 路由函数（读 need_tool） → {"是": "tool", "否": END}
                                                    ↑ tool 节点再连回 llm 节点 = 循环

本篇的三件套写法原封不动就是后面 Agent 循环的骨架——只是判断者从"字符串包含"换成大模型。这就是 char05 存在的意义：把 agent_chat 的控制流拆成图形化积木。

九、动手练习

  1. 三路分支：新增 low_node（低优先级路径），改 check_node 支持 "low" 关键词，映射表加一项——体会"加分支只动两处（判断+映射），业务节点零改动"。
  2. 复现静默失败：换回原版 State(dict) 跑一遍，观察两次 invoke 都返回 None——并思考：条件边的路由函数读不到 route 键时，理论上会发生什么？（生产里的真实风险）
  3. 路由函数解耦：把映射表键改成 {"high": "fast", "low": "normal"}，同步改 check_node 的返回值——验证"选择值与节点名解耦"的效果。
  4. 进阶：模型当路由器：把 check_node 的字符串判断换成一次真实的 ChatTongyi 调用（让它判断"这个请求是否紧急"并输出 fast/normal）——本篇图立即升级为"LLM 驱动的动态分诊"，这就是后续 Agent 图的第一块砖。
