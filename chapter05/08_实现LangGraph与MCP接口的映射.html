08_实现LangGraph与MCP接口的映射 - 代码解析

对应文件：char05/08_实现LangGraph与MCP接口的映射.py | 教材出处：第5章示例四 LangGraph与MCP接口的映射 | 环境实测：langgraph 1.2.11 | 生成日期：2026-10-11

一、这份代码整体在做什么（一段话讲给新人）

本篇演示"外部上下文存储"与图状态并行的双通道设计：一个模块级的 MCPInterface（内存字典存取器）在图外持续存在，每个节点执行时把中间产物存进去（query_ctx / retrieval_ctx），最后的 conclude 节点从外部存储读取前两步的存档拼出总结——同一份数据既走了 LangGraph State，也留了一份在外部存储里。
改写点只有 State(Dict) 静默失败（系列第八次）→ TypedDict；MCPInterface、三节点、图全部原样保留。但本篇最重要的内容不是代码，而是一个必须讲清的辨析：教材的"MCP"与真实 MCP 协议毫无关系（见第二节）。

二、命名辨析：此"MCP"非彼 MCP（本篇最重要的知识点）

同名陷阱：教材的 MCPInterface 只是"内存字典存取类"
教材的 "MCPInterface"真实的 MCP（Model Context Protocol）
本质一个 Python 类，包装了一个字典Anthropic 提出的开放协议（2024 年底发布，业界广泛采用）
架构同进程内的对象引用客户端-服务器：AI 应用(MCP 客户端) ↔ 工具服务器(MCP Server)
通信函数调用JSON-RPC（stdio / HTTP 传输）
能力存取两个 key 的上下文工具 / 资源 / 提示词三大原语的标准协议
与 LangGraph 集成本篇的"映射"langchain-mcp-adapters 库：把 MCP 服务器的工具转成 LangChain 工具再入图

新人拿"MCP"去搜索会得到完全另一回事的资料——先建立这个区分。教材借用了热门名词做教学命名（注释里的"演示外部上下文存储方案"才是真实意图），本篇真正教的概念是"节点间通过共享的外部存储交换上下文"——这个概念是真的，生产对应物是 Redis / 数据库 / 文件存储。

三、双通道上下文设计：State 与外部存储的分工（实测实证）

                    同一份数据，两条通道
  ┌─────────────────────────┐    ┌──────────────────────────────┐
  │  LangGraph State         │    │  MCPInterface.context_store   │
  │  （图内，单次 invoke 生命周期）│    │  （模块级对象，跨 invoke 存活）   │
  │                          │    │                               │
  │  invoke 1: query=LangGraph│    │  invoke 1: 三个key写入          │
  │  invoke 2: query=Agent    │    │  invoke 2: 同名key被覆盖        │
  │  （每次从零开始）           │    │  （数据跨执行存活）               │
  └─────────────────────────┘    └──────────────────────────────┘

实测实证（补充的第二组 invoke）：第一次 invoke("LangGraph") 后 context_store 三键存的是 LangGraph 数据；第二次 invoke("Agent") 后，State 里的值换成了 Agent 的，而 context_store 的三个键也全部被覆盖成 Agent 的数据——键数量不变（同 key 覆盖），数据跨执行存活。这就是两者的本质差异：State 的生命周期 = 单次 invoke；外部存储的生命周期 = 进程级（甚至更久）。

逐段代码讲解

6.1 MCPInterface（原样保留）——生产外部存储的婴儿版

class MCPInterface:
    def __init__(self):
        self.context_store = {}
    def save_context(self, key: str, value: Dict):   # 写入上下文
        self.context_store[key] = value
    def load_context(self, key: str) -> Dict:        # 读取上下文
        return self.context_store.get(key, {})

接口形状（save/load + key-value）与 Redis 客户端、Memcached 客户端完全同构——把它换成 Redis 只需改两个方法的实现，三个节点一行不动。这就是"外部存储抽象"的价值。

6.2 双写节点（原样保留）

def preprocess_node(state: State) -> State:
    query = state.get("query", "")
    mcp.save_context("query_ctx", {"query": query})   # 通道2：外部存储
    return {"query": query}                            # 通道1：LangGraph State

每个节点既更新 State 又写 mcp——教材刻意让两条通道都装同一份数据，就是为了在结尾打印 context_store 时能"看见"外部存储的积累过程。生产中通常二选一：图内传递用 State，需要跨执行/跨服务的才写外部存储（双写会有一致性负担）。

6.3 从外部存储读档的 conclude（原样保留）

def conclude_node(state: State) -> State:
    query_ctx = mcp.load_context("query_ctx")          # 从外部存储读（而不是从 state 读）
    retrieval_ctx = mcp.load_context("retrieval_ctx")
    summary = f"问题:{query_ctx.get('query')} | 检索结果:{retrieval_ctx.get('retrieved')}"
    mcp.save_context("final_ctx", {"summary": summary})
    return {"summary": summary}

注意 conclude 明明可以从 state 里拿到同样的数据（query/retrieved 都在），教材偏要从 mcp 读——为了演示"外部存储取上下文"的姿势。演示意图与工程实践的差异，读者要有分辨。

生产视角：从内存字典到真实外部存储

  • 换实现：context_store 字典 → Redis（跨进程） / PostgreSQL（带查询） / 向量库（语义检索历史上下文）——节点代码不动，只改 MCPInterface 两个方法
  • 会话隔离：教材一个全局字典 → 生产按 session_id 分键空间（呼应 char02-03/04 的 session_id 实践）
  • 生命周期管理：字典永不清理 → TTL 过期 / 显式注销（呼应 char02-04 注销机制——外部存储必须有清理策略，否则内存泄漏）
  • 一致性：双写有漂移风险 → 生产明确"State 管执行内、外部存储管执行外"，不重复存同一数据
  • 真 MCP 的位置：想让外部工具"协议化"（任何 MCP 客户端都能用），走 langchain-mcp-adapters + MCP Server——那是工具层的事，与本篇的上下文存储是两个话题

动手练习

  1. Redis 形态体验：给 MCPInterface 加一个 max_size 上限，超出时删最早的 key（模拟 LRU）——体会"外部存储必须有生命周期管理"。
  2. 会话隔离：save_context 加 namespace 参数，两次 invoke 用不同 namespace 存档——让 context_store 同时保留两次 invoke 的数据（当前同 key 覆盖只能留最后一次）。
  3. 读档节点：新增 history_node（读 final_ctx 前先检查有没有旧存档，有则在 summary 里追加"上次问题:..."）——最小化的"跨 invoke 记忆"。
  4. 进阶：真 MCP 初体验：了解 langchain-mcp-adapters 的文档结构（不必安装），画出"LangGraph 图 + MCP Server 工具"的架构草图——与本篇的"假 MCP"对照，看清协议化的真实含义。
