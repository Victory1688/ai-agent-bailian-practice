05_基于LangGraph的简单任务流 - 代码解析

对应文件：char05/05_基于LangGraph的简单任务流.py | 教材出处：第5章 基于 LangGraph 的简单任务流 | 环境实测：langgraph 1.2.11 | 生成日期：2026-10-11

一、这份代码整体在做什么（一段话讲给新人）

本篇是 01 篇两节点图的业务化扩展版：把"检索问答"搭成一条完整的四工位流水线——预处理（标准化问题文本）→ 检索（字典数据库查资料）→ 摘要（截断模拟）→ 结论（基于摘要给答案）。每个节点"读上游的键、写自己的键"，五个状态字段就是五个工位的产出。整条流水线没有大模型参与——先把骨架跑通，真实实现后续再替换进来。
改写点只有一个：教材 State(Dict) 静默失败（系列第五次）→ TypedDict。四个节点、图构建、invoke 全部原样保留。

二、四工位流水线全景

  graph.invoke({"query": "LangGraph?"})
            │
            ▼
  ┌──────────────────────┐
  │ 1. preprocess 工位     │  读: query
  │    strip + lower      │  写: query(被strip值覆盖), standardized
  │    去掉 "?"            │      = "langgraph"
  └──────────┬───────────┘
             ▼
  ┌──────────────────────┐
  │ 2. retrieve 工位       │  读: standardized
  │    字典数据库精确匹配    │  写: retrieved
  │    "langgraph" 命中!   │      = "LangGraph是一种任务图编排框架，擅长复杂流程管理"
  └──────────┬───────────┘
             ▼
  ┌──────────────────────┐
  │ 3. summarize 工位      │  读: retrieved
  │    截断20字符 + "..."  │  写: summary
  │    (本地模拟"摘要")     │      = "LangGraph是一种任务图编排框架，..."
  └──────────┬───────────┘
             ▼
  ┌──────────────────────┐
  │ 4. conclude 工位       │  读: summary
  │    拼装最终结论         │  写: conclusion
  └──────────┬───────────┘
             ▼
            END

这是"任务流（Task Flow）"的正式登场：01 篇的两节点证明了图能跑，本篇证明图能承载完整业务流程——工位数想加就加，工位内部实现想换就换。

三、教材代码的问题与教材输出的问题

问题1：State(Dict) 静默失败（系列第五次）

from typing import Dict + class State(Dict): pass——比前几篇多绕了一层（Dict 而非 dict），本质相同：无字段注解 → 图无法构建状态 schema → invoke 返回 None。修 TypedDict 五字段（query/standardized/retrieved/summary/conclusion）。

问题2（有趣发现）：教材的"预期输出"是手写估算，不是真跑结果

教材预期 summary: 'LangGraph是一种任务图编排框...'——实测却是 'LangGraph是一种任务图编排框架，...'。为什么？content[:20] 按字符截断：LangGraph 占 9 个字符，"是一种任务图编排框架"占 10 个，第 20 个字符是"，"——所以截断点带着逗号。教材预期少算了一个"架"字和逗号，说明这段输出是作者估算的，没实际运行。教训：一切以实测为准（本篇实测输出已写进改写文件的注释里）。

四、核心概念速查表

概念是什么在本例中的角色
任务流按固定顺序依次执行的节点流水线本篇四工位单线图（01 篇的扩展）
状态五字段TypedDict 声明的五个产出槽位每个工位读上游键、写自己的键
键改写节点返回已有键会覆盖原值preprocess 用 strip 后的 query 覆盖原始输入
精确匹配检索字典 get 的完全相等查找standardized 恰好等于 "langgraph" 才命中
降级链失败信号逐级传递+逐级翻译"未找到文献"→"暂无可用信息"→"未能得到支持性资料"
模拟工位占位实现（截断当摘要）先验证骨架，真实实现（LLM/向量检索）后续替换

五、逐段代码讲解

5.1 预处理节点（原样保留）——节点可以改写上游键

def preprocess_node(state: State) -> State:
    query = state.get("query", "").strip()
    standardized = query.lower().replace("?", "")
    return {"query": query, "standardized": standardized}   # query 被 strip 后的值覆盖

注意返回字典里的 "query": query——把"清洗过的 query"写回 query 键，覆盖了用户原始输入（"LangGraph?" 变成 "LangGraph"）。这是部分更新机制的另一面：不仅能新增键，还能改写键。本例改写是合理设计（下游不需要问号），但要意识到：原始信息已被覆盖，想留痕就得另开键（如 raw_query）。

5.2 检索节点（原样保留）——字典精确匹配 vs FAISS 相似度

database = {
    "langgraph": "LangGraph是一种任务图编排框架，擅长复杂流程管理",
    "agent": "智能体系统依赖任务调度与状态管理实现高效运行"
}
result = database.get(keyword, "未找到相关文献")

与 03 篇对照：同样的"检索工位"，03 用 FAISS 向量相似度（能容错"LangGraph 是什么"这类自然语句），本篇用字典精确匹配（只认恰好等于 "langgraph" 的标准化文本）。所以本篇的 preprocess 才如此重要——必须把 "LangGraph?" 清洗成恰好等于 key 的 "langgraph"。这个依赖关系正是真实系统里"预处理"存在的意义：把混乱的输入规整成下游能消费的形状。

5.3 摘要与结论节点（原样保留）——模拟实现 + 兜底判断

def summarize_node(state: State) -> State:
    content = state.get("retrieved", "")
    if content == "未找到相关文献":          # 兜底判断：上游失败的信号我接住了
        summary = "暂无可用信息"
    else:
        summary = content[:20] + "..."      # 模拟"摘要"：真实场景换成 LLM 生成
    return {"summary": summary}

每个工位都先检查上游有没有给有效内容——失败就产出自己的"失败信号"（措辞逐级变化）。

5.4 图构建（原样保留）

builder.set_entry_point("preprocess")
builder.add_edge("preprocess", "retrieve")   # 四条固定边，单线到底
builder.add_edge("retrieve", "summarize")
builder.add_edge("summarize", "conclude")
builder.add_edge("conclude", END)

六、真实运行输出

已在本机实际运行验证（langgraph 1.2.11，无 LLM 调用）
{'query': 'LangGraph?', 'standardized': 'langgraph',
 'retrieved': 'LangGraph是一种任务图编排框架，擅长复杂流程管理',
 'summary': 'LangGraph是一种任务图编排框架，...',
 'conclusion': '基于文献摘要可得: LangGraph是一种任务图编排框架，...'}

五个字段按工位顺序齐全，状态累积完整可见——与教材预期结构一致，仅 summary 截断点按真实字符数计算（见第三节问题2）。

七、本篇最有价值的对照：值传递兜底 vs 条件边分流（02 篇 vs 本篇）

02 篇：条件边分流本篇：值传递兜底
失败怎么处理路由函数把流量引到别的分支（换路走）失败信号写进状态，下游逐级判断翻译（同一条路都走完）
执行路径只走命中的一条四个工位全部执行
失败信息失败分支自己产出逐级翻译："未找到文献"→"暂无可用信息"→"未能得到支持性资料"
适合场景失败后彻底换流程统一流程里逐段降级、最终口径统一

两种写法都是"处理异常"的合法姿势——条件边适合"分流"，值传递适合"降级"。看懂这个区别，就同时掌握了 char05 前半章的两把刷子。

八、生产视角：模拟工位 → 真实实现 的替换清单

  • retrieve 工位：字典 get → FAISS/向量库相似度检索（03 篇已给过真实现）
  • summarize 工位：截断 20 字符 → ChatTongyi 生成真摘要（注意"截断"会腰斩语义，LLM 摘要保留完整语义）
  • conclude 工位：字符串拼接 → LLM 基于摘要生成结论（或直接让 03 篇的 RetrievalQA 一站式完成）
  • preprocess 工位：lower+去问号 → 真实清洗规则（分词/纠错/改写），或干脆删掉换向量检索的容错性
  • 架构不变：四个节点、五字段状态、四条边——工位内部实现全部替换，骨架一行不动。这就是"先建骨架再换实现"开发法的教科书示范

九、动手练习

  1. 体验降级链：invoke({"query": "Redis"})（数据库里没有的词）——观察三个工位如何逐级翻译失败信号，最终 conclusion 是什么。
  2. 验证精确匹配的脆弱：把 query 改成 "langgraph is good"——即使包含 langgraph 也查不到（standardized 不恰好等于 key）。体会为什么 03 篇要用向量相似度。
  3. 保护原始输入：新增 raw_query 键（TypedDict 加字段 + preprocess 覆盖前先写入），让最终状态能同时看到原始输入和清洗后输入。
  4. 进阶：条件边升级版：把 summarize/conclude 里的 if 判断拆掉，用 02 篇的 add_conditional_edges 改造——"未找到"时绕过摘要直连一个专门的兜底节点。改造后对比两种形态的代码可读性。
