03_LangChain的检索工具与LangGraph集成 - 代码解析

对应文件：char05/03_LangChain的检索工具与LangGraph集成.py | 教材出处：第5章示例一 LangChain检索工具与LangGraph集成 | 环境实测：langgraph 1.2.11 / faiss-cpu 1.15.0 / langchain-community 0.4.2 | 生成日期：2026-10-11

一、这份代码整体在做什么（一段话讲给新人）

char05 到本篇第一次接上真实模型与向量库：用 FAISS 存两段知识文本，用百炼的向量化模型（DashScopeEmbeddings）建索引，用 RetrievalQA 链把"检索 + 让 qwen-plus 基于检索结果生成答案"打包成一个整体，再把这个链作为一个节点塞进 LangGraph 图。问"LangGraph是什么？"，图调起链，链先检索再生成——这是一个最小 RAG 流水线。
改写点有四：import 断裂、OpenAIEmbeddings 换百炼向量化、llm=None 伪代码修复（本篇最重的发现）、State(dict) 静默失败（系列第三次）。

二、教材代码的四类问题（本篇是 char05 问题最重的一篇）

#问题原写法改写
1import 路径断裂langchain.chains / langchain.vectorstores / langchain.embeddingslangchain_classic.chains / langchain_community.vectorstores / langchain_community.embeddings
2向量化模型不可用OpenAIEmbeddings()（需 OPENAI_API_KEY，国内无法直连）DashScopeEmbeddings()——百炼平台向量化模型，与聊天模型共用同一把 DASHSCOPE_API_KEY
3llm=None 伪代码（最重）RetrievalQA.from_chain_type(llm=None, ...)llm=ChatTongyi(qwen-plus)。RetrieQA 的职责是"检索 + 让 LLM 基于检索结果生成答案"——没有 LLM 这条链根本无法工作（run 时必然报错）
4State(dict) 静默失败class State(dict): pass（无注解）TypedDict（question/answer 两字段）——01/02 篇同款修复，系列第三次出现
为什么 llm=None 一眼就能断定是伪代码

看 RetrievalQA 的名字：Retrieval（检索）+ QA（问答）。它的内部流程是：问题 → 检索器找相关文档 → 把文档塞进提示词 → LLM 生成答案。检索只负责"找资料"，资料找来了总要有人读——LLM 就是那个读资料写答案的人。教材给 llm=None 相当于"组建了一个只有图书馆没有研究员的研究团队"。凡是不给 LLM 的 QA 链，都跑不起来。

三、核心概念速查表

概念是什么在本例中的角色
FAISSFacebook 开源的向量相似度检索库存两段知识文本的向量索引，本地运行（faiss-cpu）

RetrievalQA"检索 + 生成"组合链（char04-01 链式思想的 RAG 特化版）本篇被塞进图节点的职能单元

注意答案内容："LangGraph 是一个任务编排框架。"——与知识库文本几乎逐字一致。qwen-plus 自己当然也"知道" LangGraph，但这个答案的措辞直接来自检索命中——答案有出处，是 RAG 的核心价值（模型不知道或会过时的内容，也能答对）。

五、逐段代码讲解

5.1 检索工具初始化（三处改写）

db = FAISS.from_texts(
    ["LangGraph是一个任务编排框架", "LangChain是一个工具链框架"],
    DashScopeEmbeddings()                        # 原写法 OpenAIEmbeddings() → 百炼向量化
)
retriever = db.as_retriever()                    # 原样保留：统一检索器接口
qa_tool = RetrievalQA.from_chain_type(
    llm=llm,                                     # 原写法 llm=None → 修复为真模型
    retriever=retriever,
    chain_type="stuff"
)

要点：建索引和查询必须用同一个向量化模型——两段文本用 DashScopeEmbeddings 向量化入库，用户问题也用它向量化后去比对。换模型 = 索引全部重建（向量空间不同，没有可比性）。

5.2 节点与图（原样保留）

class State(TypedDict):
    question: str
    answer: str

def query_node(state: State):
    result = qa_tool.run(state["question"])      # 链对图就是一个普通函数
    return {"answer": result}

builder = StateGraph(State)
builder.add_node("query", query_node)
builder.set_entry_point("query")
graph = builder.compile()
print(graph.invoke({"question": "LangGraph是什么？"}))

链入图的哲学：图的节点接口（入参整个状态、返回部分更新）对内容零要求——纯函数（01/02 篇）、链（本篇）、后续的模型调用都能放。char05 建立的这套"图编排层"与 char04 的"链职能层"在这里完成合体：链管怎么干活，图管什么时候干活、干完去哪。

与 char03（Embeddings 和向量数据库）的呼应

char03 时代你见过 FAISS 与向量检索（chatpdf-faiss 等），那时检索和生成是两段分开的代码。本篇用 RetrievalQA 把它们打包成一个链，再用 LangGraph 把链变成可编排的节点——同样的技术积木，组织方式在不断进化：函数 → 链 → 图节点。这一进化的方向就是"让复杂系统的每一层都能被替换和重组"。

八、生产视角：教学版离上线的差距

  • 知识库规模：两句话的内存 FAISS → 生产是持久化向量库 + 分块 + 批量入库 + 索引重建策略
  • 检索质量：默认 top-4 相似度检索 → 加 score_threshold / rerank / 混合检索（BM25+向量）
  • 答案可溯源：RetrievalQA.run 只返回答案字符串，丢掉了命中文档 → 用 return_source_documents=True 或改用 LCEL 链自组输出结构
  • 废弃 API：RetrievalQA / Chain.run 都是 2.0 待移除项——生产用 create_retriever_tool + create_agent，或 LCEL（retriever | prompt | llm）自组
  • 单节点图的局限：本篇图只有一个节点，图的编排价值还没发挥——下一课的多节点（检索→判断→生成）才是图的真正用武之地

九、动手练习

  1. 验证 RAG 的出处价值：把知识文本换成一段 qwen-plus 大概率不知道的虚构知识（如"张三公司的内部报销系统叫报销侠"），再问"报销侠是什么"——模型只能靠检索命中作答，这就是"模型不知道的知识也能答对"的实证。
  2. 复现教材伪代码的报错：临时把 llm 改回 None 跑一次，看 RetrievalQA 在哪一步炸——记住这个报错长相，以后 review 代码时能一眼识破同类伪代码。
  3. 检索器参数：db.as_retriever(search_kwargs={"k": 1})——只取最相似的 1 条，观察答案变化；再把 k 调大试试。
  4. 进阶：两节点 RAG 图：把 RetrievalQA 拆开——节点1 retrieve（只检索，把文档写进状态 docs 键），节点2 generate（拿 docs 调 qwen-plus 生成）——体会"链拆成图后，每一步都可见可替换"，这是第 5 章后面所有篇章的写法。
