一、这份代码整体在做什么（一段话讲给新人）

05 篇是"单关键词流水线"，本篇升级为五工位的科研助手：预处理（关键词提取）→ 文献检索（多关键词批量查库）→ 文献筛选（去重过滤——05 篇没有的加工工位）→ 生成摘要（截断模拟）→ 汇总结论。查询 "Graph Agent Research" 会提取出 graph/agent/research 三个关键词，批量检索出 4 篇文献，去重后逐篇摘要，最后拼装结论。
改写点：State(Dict) 静默失败（系列第六次）→ TypedDict 六字段；外加修复一个隐蔽的降级链断裂 bug（见第三节，本篇最大发现）。

三工位升级对照：05 篇 → 06 篇

能力05 篇06 篇
关键词提取整句标准化（lower+去问号）分词 + 停用词过滤（len>3）+ 小写
检索方式单关键词精确匹配（命中一条）多关键词批量检索（每个词带一批文献 extend 进列表）
结果加工无（直接进摘要）新增 filter 工位：过滤无效项 + 集合去重
数据形态全程字符串全程列表（keywords/retrieved_docs/filtered_docs/summaries）
降级链逐级翻译（正常工作）断裂 bug（被中间工位加工失真）

本篇最大发现：降级链断裂 bug（实测实锤）

一个"跑正常路径永远发现不了"的静默逻辑 bug

故障路径的信号传递链：

filter 失败 → filtered_docs = ["有效文献不足"]     （6 个字符）
       ↓
summarize: doc[:15] + "..."  →  ["有效文献不足..."]  ← 不足15字不截断，但省略号照加！
       ↓
conclude:  if "有效文献不足" in summaries:          ← 精确匹配列表元素
           "有效文献不足..." != "有效文献不足"        ← 永远失配！
       ↓
走 else 分支 → conclusion = "基于现有文献分析：有效文献不足..."
                                        ↑ 失败被当成正常分析结果输出！

实测铁证：查 "Quantum Research"（库里没有），修复前 conclude 输出"基于现有文献分析：有效文献不足..."——把失败信号当文献分析给了用户。

修复方案与更深层的教训

最小修复：conclude 的判断从精确匹配改子串匹配 any("有效文献不足" in s ...)（原写法注释保留）。但更普适的教训是：失败信号是"元信息"，不应该和正常数据混在同一条管道里靠字符串比对区分——中间任何工位对内容做格式加工（截断/拼接/翻译），都可能让下游的信号识别失效。生产做法是加独立的状态字段（如 status: "ok" | "no_docs"），让失败状态走结构化通道，与文本内容彻底解耦。

对照 05 篇：为什么 05 的降级链没断？

05 篇 summarize 对失败信号是整体替换（"未找到相关文献"→"暂无可用信息"，替换前后都是"完整信号"），06 篇是格式加工（截断+加省略号，信号被变形）。一个字之差：替换保留语义完整性，加工破坏信号结构。当你准备"顺手处理"一个可能是失败信号的字符串时，先问一句：下游有没有人在精确匹配它？

逐段代码讲解（只讲关键差异点）

6.1 关键词提取（原样保留）

keywords = [word.lower() for word in query.split() if len(word) > 3]

三个动作一行写完：按空格分词、小写归一（匹配数据库的 key）、长度>3 过滤短词。实测 "Graph Agent Research" → ["graph", "agent", "research"]——research（8字符）也被保留，但库里没有这个词，get 返回空列表。多关键词检索的细节：没命中的词不报错，安静地带回空。

6.2 多关键词批量检索（原样保留）

results = []
for kw in state.get("keywords", []):
    results.extend(database.get(kw, []))     # 每个词一批文献，合并进列表
return {"retrieved_docs": results if results else ["未找到相关文献"]}

6.3 集合去重（原样保留，实测发现顺序副作用）

filtered = list({doc for doc in docs if "未找到" not in doc})

实测实证：4 篇文献进 filter 出来后顺序变了（"图式化逻辑..." 排到了第一）。set 的迭代顺序由哈希决定，不保插入序——去重成功了，顺序牺牲了。保序去重写法：list(dict.fromkeys(doc for doc in docs if "未找到" not in doc))。

6.4 结论生成（bug 修复处）

# 修复后（原写法见文件注释）：
if any(("有效文献不足" in s) or ("未找到" in s) or (s == "暂无摘要") for s in summaries):
    conclusion = "未能生成可靠的科研结论"

生产视角：模拟五工位 → 真实科研助手

  • 检索工位：字典 → 向量库 top-k 检索；关键词级检索在生产叫"稀疏检索"（BM25），与向量检索组合成混合检索
  • filter 工位：生产还需要相关性重排（rerank）——去重只解决重复，不解决"检索到了但不相关"
  • summarize 工位：截断 → LLM 生成摘要；截断是"保证不超长"，LLM 是"保留语义"
  • 失败状态结构化：加 status 字段（见第三节教训）——生产流水线的每一步都应该有机器可读的成功/失败标志
  • 图已就绪：五节点骨架与 05 篇同构，替换实现不动架构——char05 前 6 篇反复演示的就是这一件事

动手练习

  1. 复现降级链断裂：把 conclude 改回精确匹配（原写法），跑 "Quantum Research"——亲眼看"失败被当正常结果"的荒诞输出，再看一眼 set 去重后 document 顺序变化。
  2. 结构化失败状态：State 加 status 键（"ok"/"no_docs"），retrieve/filter 失败时写 status 而不是往文档列表里塞信号字符串——体会"元信息走结构化通道"的清爽。
  3. 保序去重：用 dict.fromkeys 改写 filter 的去重，验证 filtered_docs 顺序与 retrieved_docs 一致。
  4. 进阶：真 LLM 工位：把 summarize 的截断换成 ChatTongyi 真摘要（每篇一次调用），并给 conclude 的判断加上 LLM 版失败识别——结合 char05-03 的链入图方式，把本篇升级成"真模型科研助手"。
