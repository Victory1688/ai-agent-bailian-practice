一、这份代码整体在做什么（一段话讲给新人）

这是 char05 的开篇——全书代码第一次不调用大模型。两个节点（search / generate）都是普通 Python 函数（"检索"/"生成"只是字符串拼接），教学目标是把 LangGraph 的最小图骨架立起来：节点=函数，边=顺序，状态=流转的字典。跑通后你将看到两个节点接力工作、状态逐步累积的完整画面——这是后面所有"智能体编排"的地基。
改写点只有一个：教材的 class State(dict) 在 langgraph 1.x 下不报错但 invoke 返回 None（静默失败），改用标准的 TypedDict 后一切正常。

三、教材代码为什么"跑得通但结果错"（本篇的静默失败）

实测 langgraph 1.2.11：原代码不报错、不崩溃，但 graph.invoke() 返回 None
  • 教材预期：invoke 返回 {'query': 'LangGraph', 'retrieved': '检索到与 LangGraph 相关的信息', 'answer': '...'}
  • 实际输出：None——两个节点都执行了，但状态收集不回来
  • 根源：LangGraph 1.x 靠 State 类的字段类型注解（__annotations__）构建状态 schema。class State(dict): pass 没有任何字段注解，图无法定义"状态有哪些键、如何合并"，invoke 只能返回 None
  • 系列呼应：这是继 char04-07（memory_key 静默断忆）之后第二个"静默失败"案例——AI 应用代码里，不抛异常的 bug 才是最危险的 bug，因为它让你以为程序是对的

修复方式：TypedDict + 字段注解（LangGraph 1.x 标准 State 写法）

# 原写法（注释保留）：
# class State(dict):
#     pass

# 改写：
from typing import TypedDict

class State(TypedDict):
    query: str
    retrieved: str
    answer: str

三个字段对应三段数据：用户查询 → 检索结果 → 最终答案。TypedDict 不是运行时类，它的价值全在"给框架看的字段清单"——这正是 LangGraph 构建 schema 依赖的东西。

四、核心概念速查表

概念是什么在本例中的角色
节点（Node）接收完整状态、返回部分更新的普通函数search_node / generate_node
边（Edge）节点间的固定跳转关系add_edge("search", "generate")——search 完必到 generate
状态（State）在节点之间流转的字典TypedDict 定义三字段：query/retrieved/answer
StateGraph图构建器add_node 注册节点、add_edge 连线
compile()把构建器编译成可执行图builder.compile() → CompiledStateGraph
invoke()从入口跑一遍图，返回最终状态graph.invoke({"query": "LangGraph"})
部分更新（Partial Update）节点只返回要改的键，不返回整个状态return {"retrieved": ...}——query 自动保留
entry / finish point图的入口与出口set_entry_point("search") / set_finish_point("generate")

六、逐段代码讲解

6.1 状态定义（唯一的改写点）

from typing import TypedDict

class State(TypedDict):
    query: str       # 输入：用户查询
    retrieved: str   # 中间：search_node 的产出
    answer: str      # 输出：generate_node 的产出

6.2 两个节点（原样保留）

def search_node(state: State):
    query = state.get("query", "")
    return {"retrieved": f"检索到与 {query} 相关的信息"}
    # 返回部分更新——只写 retrieved，query 自动保留在状态里

def generate_node(state: State):
    info = state.get("retrieved", "")
    return {"answer": f"基于{info}生成最终答案"}

节点的接口约定是 LangGraph 的灵魂：入参 = 整个状态（只读），出参 = 部分更新（增量写）。所有节点长得一样，所以可以随意重组——加节点、换顺序、加条件分支，都不用改节点本身。这比 char04-01 SequentialChain 的 input_variables 接线更自由（后者要求占位符精确对齐，本例只需要键名约定）。

6.3 图的构建与执行（原样保留）

builder = StateGraph(State)
builder.add_node("search", search_node)      # 注册节点：起名 + 挂函数
builder.add_node("generate", generate_node)

builder.add_edge("search", "generate")       # 定边：search 完必到 generate
builder.set_entry_point("search")            # 入口
builder.set_finish_point("generate")         # 出口（旧式 API，新式为 add_edge("generate", END)）

graph: CompiledStateGraph = builder.compile() # 编译成可执行图
result = graph.invoke({"query": "LangGraph"}) # 跑一遍
print(result)

API 演化说明：set_entry_point/set_finish_point 是旧式写法（教材风格），langgraph 1.x 中仍可用；新式写法是 add_edge(START, "search") 与 add_edge("generate", END)——import 里那个 END 就是给新式出口准备的。两种都能跑，读别人的代码两种都要认识。

三个键按执行顺序依次出现，完整呈现"状态累积"过程。对照实验（改写前的原版 State(dict)）输出 None——建议自己跑一遍原版感受静默失败（动手练习 1）。

能力API本篇是否涉及

本篇与 char02 agent_chat 的预告式呼应

char02 手写的 agent_chat 循环，用 LangGraph 表达就是一个环形图：llm 节点 →（有 tool_calls？）→ tool 节点 → 回到 llm 节点；→（无 tool_calls？）→ END。char02-01 的 while True 在这里变成图上的回路。后续篇章会把这条环形线真正搭出来——本篇先记住：图的三要素（节点/边/条件）足以表达从流水线到 Agent 循环的一切。
