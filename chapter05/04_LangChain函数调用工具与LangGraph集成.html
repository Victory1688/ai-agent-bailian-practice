一、这份代码整体在做什么（一段话讲给新人）

本篇与 03 篇配对：03 是"链入图"（RetrievalQA 当节点），04 是"工具入图"（@tool 工具当节点逻辑）。场景极简：一个 calc 节点拿到状态里的 x=7、y=8，调用 @tool 包装的 multiply 工具算出 56 写回状态。教学核心是示例注释里的那句话：LangChain 负责工具封装，LangGraph 负责编排调度。
但本篇教材代码"伤势不轻"：实测两处必炸（@tool 无 docstring 直接 ValueError、工具对象当函数调用 TypeError）+ State(dict) 静默失败（系列第四次）。另外要诚实说：标题里的"函数调用"是手动调用工具，没有大模型参与决策——真正的 Function Calling 循环见后续篇章。

二、教材代码为什么跑不起来（四类问题，两处实测必炸）

#问题原写法实测结果改写

3工具对象当函数调（节点处必炸）multiply(a=state["x"], b=state["y"])TypeError: 'StructuredTool' object is not callablemultiply.invoke({"a": ..., "b": ...})
4State(dict) 静默失败class State(dict): passinvoke 返回 None（不报错）TypedDict（x/y/product）——系列第四次
两处必炸的深层原因（都是"工具三要素"没配齐）
  • docstring 就是工具说明书：@tool 装饰器把"函数"升级成"StructuredTool 工具对象"——这个对象要能被模型看懂，必须有 description（模型靠它决定用不用这工具）。docstring 是 description 的默认来源，没有就拒绝定义。教材漏掉的这一行，恰恰是工具最灵魂的部分。
  • @tool 返回的不是函数：装饰器把 multiply 重新绑定为 StructuredTool 实例。它长着函数的名字，但本体是"带说明书的可调用工具对象"，标准调用方式是 .invoke(参数字典)。想直接摸到底层函数，得访问 multiply.func——但生产代码永远用 invoke。

五、逐段代码讲解

5.1 工具定义（改写：补 docstring）

@tool
def multiply(a: int, b: int) -> int:
    """计算两个整数的乘积"""          ← 教材缺失的关键行（工具 description）
    return a * b

对照 char03-06 的 Function Calling 三件套（执行函数 + tools 说明书 + 注册表），@tool 装饰器把三件事压缩成"一个函数 + 一个装饰器"：类型注解自动生成 parameters JSON Schema，docstring 自动变成 description，函数体就是执行逻辑。这正是 05 篇（char04）说"@tool 是 1.x 推荐写法"的原因——声明少了，说明书一点不少。

5.2 节点函数（改写：标准调用方式）

def calc_node(state: State):
    # 原写法：result = multiply(a=state["x"], b=state["y"])   → 实测 TypeError
    result = multiply.invoke({"a": state["x"], "b": state["y"]})
    return {"product": result}

.invoke(参数字典) 是所有 LangChain 可调用组件的统一入口——工具、链、模型、图全都是它。记住这一个动词，整套框架的调用方式就统一了。

5.3 图构建（原样保留）

builder = StateGraph(State)
builder.add_node("calc", calc_node)
builder.set_entry_point("calc")
graph = builder.compile()
print(graph.invoke({"x": 7, "y": 8}))

七、"函数调用"辨析：本篇不是 Function Calling（诚实地图）

本篇：工具手动入图真正的 Function Calling（char03-06 / char02 系列）
谁决定调工具开发者写死在节点里（calc_node 必调 multiply）模型自主决策（模型看 tools 说明书后输出 tool_calls）
模型参与吗完全不参与核心参与者
tools 说明书给谁看没人看（只是包装规范化）给模型看（决策依据）
适合场景固定步骤的业务节点模型按需取用能力
本篇的真实教学价值：工具 = 图的标准积木

别被标题误导而失望——本篇的价值在于确立一个模式：@tool 工具（带说明书、带参数校验）可以直接当节点逻辑。后续篇章会把这个模式升级：节点里放一个"模型决策器"，模型看着工具说明书自主挑工具——手动调用升级为 Function Calling，本篇的工具定义方式原封不动复用。工具怎么定义本篇已教完，模型怎么用它后续教。

八、03 vs 04：图节点里能放什么的两种答案

03 篇：链入图04 篇：工具入图

两条路线在后续篇章会合流：先用工具模式拆细（检索节点、生成节点各占一格），再在关键节点放模型决策（条件边路由）——这就是完整 Agent 图的组装过程。

九、动手练习

  1. 复现两处必炸：删掉 docstring 跑一次（ValueError），恢复后再把 invoke 改回直接调用跑一次（TypeError）——把两个报错长相刻进肌肉记忆。
  2. 体验参数校验：故意传 multiply.invoke({"a": "abc", "b": 8})——StructuredTool 会抛参数校验错误。这正是"类型注解=参数 schema"的运行时体现。
  3. 加第二个工具节点：定义 @tool divide（注意除零处理），图改为 calc → divide 两节点串联（x 除以 product 或自定规则）——体会工具节点如何串联。
  4. 进阶：模型决策版：在 calc_node 里先用 ChatTongyi 判断"x*y 是否超过 100"（Function Calling 或 JSON 输出），超 100 才调 multiply，否则直接写提示语——把本篇的"手动调用"升级成"模型决策调用"，呼应第七节的对照表。
