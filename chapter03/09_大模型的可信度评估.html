09_大模型的可信度评估 - 代码讲解

位置：AI Agent Development Code/aiTest/char03 | 教学主题：幻觉（Hallucination）与基于生成概率的置信度评估 | 技术栈：原本地 output_scores 逐 token 概率 → 改写为 dashscope OpenAI 兼容模式 logprobs | 已验证可运行（两组对比实验：熟悉领域 avg=0.9365 / 生造问题 avg=0.8763 且 6 个低置信 token 恰在下断言处）

一、这段代码要做什么

回答用户问题的同时，把模型生成每一个 token 时的"内心确信程度"也抓出来：每个位置上模型候选了哪些词、各自概率多少、最终选中的那个词概率多高。原理一句话：生成概率越低的内容，模型越不确定，幻觉的可能性越大——就像人说话，滔滔不绝说得溜的部分通常靠谱，支支吾吾、磕磕绊绊的地方往往在瞎编。有了这份逐 token 概率，就能给每条回答算出一个"可信度分数"，交给下游决定：直接展示 / 加"仅供参考"标注 / 人工复核。

为什么"概率"能反映"可信度"？

大模型每生成一个 token，本质是在词表上做一次概率分布（softmax）。训练数据里反复出现的事实（"LangChain 是框架"），模型见过成千上万次，分布高度集中——选中的词概率接近 1.0；而它没见过、在硬编的内容，分布扁平分散——选中的词可能只有 0.2~0.4。概率分布的"尖锐程度"就是模型的自我确信度。它不完美（有幻觉时模型也可能"自信地错"），但是目前最廉价、最通用的不确定性信号。

二、本地实现 vs 云端实现：逐项能力映射（改写的核心）

能力环节原写法（本地 GPU）改写后（dashscope 兼容模式）
拿每步原始分数model.generate(output_scores=True) 返回每步 logits请求参数 "logprobs": true
取前 k 个候选torch.topk(probs, k=req.top_k)请求参数 "top_logprobs": req.top_k（服务端直接返回 top-k）
logits → 概率F.softmax(scores[0], dim=-1)返回的已是 log 概率，math.exp(logprob) 还原为 0~1 概率
候选词解码tokenizer.decode([idx.item()])服务端直接返回 token 文本，无需本地 tokenizer
角色拼接build_prompt 手动拼 [用户]：/[助手]：messages 直接透传（同 05~08）
本篇最关键的工程知识：为什么要走"兼容模式"？

dashscope 原生 SDK（dashscope.Generation.call，char02~03 前面所有篇用的那扇门）不返回 logprobs——你拿不到逐 token 概率，本篇的需求就实现不了。而 dashscope 的 OpenAI 兼容模式（https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions）支持 logprobs / top_logprobs 参数。同一个平台的两扇门：原生 SDK 简单易用但能力子集，兼容模式功能完整且说行业通用方言——这再次验证了 char03-05 的教学点：OpenAI 协议是行业协议，高级能力（logprobs、工具调用、流式）都定义在这套协议里。以后遇到"原生 SDK 缺某个能力"时，第一反应就该是：去兼容模式找找。

三、一次请求的数据流转

客户端 POST /v1/chat/with_confidence
  {"messages": [{"role": "user", "content": "请解释一下LangChain的核心组件"}], "max_tokens": 32, "top_k": 5}
  │
  ▼
兼容模式请求（requests.post + Authorization 头）
  json: {model: "qwen-plus", messages: [...],
         logprobs: true,          ← 每个生成 token 的对数概率
         top_logprobs: 5}         ← 每步附 top-5 候选（= 原 torch.topk(k=5)）
  │
  ▼
云端返回 choice["logprobs"]["content"]：
  [{"token": "Lang", "logprob": -0.0001, "top_logprobs": [{"token": "Lang", "logprob": -0.0001}, ...]}, ...]
  │
  ▼
本地加工（改写代码的核心循环）：
  for i, item in enumerate(token_logprobs):
      chosen_prob = math.exp(item["logprob"])        # 对数概率 → 概率
      top_tokens/top_probs = 遍历 item["top_logprobs"] 逐个 exp
      → 组装成与教材相同结构的 token_confidence
  │
  ▼
本地汇总（改写新增）：
  avg_token_prob = 平均选中概率        ← 全程平均置信度
  low_confidence_ratio = 概率<0.5 的 token 占比  ← "踩薄冰"的占比
  │
  ▼
返回 {"response", "token_confidence", "confidence_summary"}

对比结论（本篇最有价值的教学数据）
  • 实验 1：前 4 步概率全在 0.9999 以上——模型对"LangChain 是……"这种常识级开场毫无犹豫，avg 0.9365，低置信占比 0
  • 实验 2：整体 avg 降到 0.8763，出现 6 个低置信 token——而且位置极其讲究：全落在"权威、可、查"这些下断言的词上。模型在说"没有任何权威可查证记录"时，每一个字都在"踩薄冰"——它自己也不确定这个否定断言是否成立。概率分布把模型的"心虚"暴露得一览无余
  • 一个诚实的观察：这次 qwen-plus 选择拒绝编造（回答"没有记录"）而不是硬编一篇论文——对齐良好的模型面对生造问题常会拒答。但低置信信号依然准确亮起：这个指标无论模型选择"拒答"还是"硬编"，都能标出它不确定的位置——拒答时告诉你"它在这几处没底"，硬编时告诉你"这段话别信"

五、token_confidence 怎么读（输出字段速查）

字段含义解读要点
step第几个生成的 token（从 0 计）定位"心虚"发生在回答的哪个位置
chosen_token模型实际选中的词对照 top_tokens 看竞争是否激烈
chosen_prob选中词的概率（0~1）< 0.5 就值得警惕；数字、专有名词、日期等"事实性 token"低概率最危险
top_tokens / top_probs该位置的 top-k 候选与概率候选差距悬殊（1.0 vs 0.0）= 稳；几家平分秋色 = 模型在猜
avg_token_prob全程平均选中概率整体可信度分数；不同任务基线不同，需自己积累阈值经验
low_confidence_ratio概率<0.5 的 token 占比占比越高，幻觉风险越大；可设阈值触发"仅供参考"标注

六、教学简化 vs 生产差距（重要：低概率 ≠ 一定是幻觉）

三个必须知道的局限
  • 概率反映的是"模型的语言习惯"，不是"事实真伪"：模型可能自信地编造（训练数据里谣言重复太多，它也说得溜），也可能在正确答案上犹豫（表达方式多样时分布天然分散）。低概率是"风险提示"，不是"错误判决"
  • 温度参数影响分布形状：temperature 越高分布越平，同样的回答置信度会系统性偏低。生产中做置信度对比必须在固定 temperature 下进行（本服务未显式传 temperature，用的是服务端默认值）
  • token 粒度 ≠ 语义粒度：中文一个词常被拆成多个 token，单个 token 低概率未必对应一个完整的"可疑断言"。生产要做聚合：把低置信 token 聚簇映射回短语/句子级再判断
生产级的幻觉检测是多种手段的组合
  • 本篇的 logprobs：零成本的第一道信号（每次请求顺手就能算）
  • RAG 事实锚定：让回答基于检索到的资料生成，从源头减少"凭记忆发挥"（char01/char02 之外最重要的配套技术）
  • 自洽性检验（Self-Consistency）：同一问题问 3~5 次，答案一致才可信——用采样多样性交叉验证
  • 裁判模型（LLM-as-Judge）：用另一个模型对着参考资料审查回答的事实性
  • 引用溯源：要求回答标注出处，无出处的断言降权展示

八、动手练习

  1. 阈值联动实验：用同一个生造问题连发 5 次（temperature 保持默认），记录每次的 avg_token_prob 和 low_confidence_ratio——观察波动范围，思考阈值该设多少（对比实验 1 的 0.9365 基线）。
  2. 事实 token 定位：问一个模型会硬编的问题（如让它介绍一个不存在的 API 函数的参数列表），检查低置信 token 是否集中在数字、参数名、版本号等事实性 token 上——验证"事实性 token 低概率最危险"这条经验。
  3. 温度对照：给请求加 "temperature": 0.0 和 "temperature": 1.2 各测一次同一问题，对比 confidence_summary——直观感受温度对分布形状的影响（第六节局限 2 的实证）。
  4. 降级策略：在端点里加一个逻辑——low_confidence_ratio > 0.3 时，在返回里附加 "warning": "本回答置信度较低，仅供参考"。这就是生产系统"仅供参考"标注的原始形态。
  5. 思维题：为什么 top_logprobs 的候选列表能帮你判断"模型是在背事实还是在猜"？如果某个位置 top_tokens 是 ["北京", "上海", "广州"] 且概率接近平均分配，这通常说明什么？（提示：分布的形状 vs 单个词的对错）
