04_模拟支持多线程并发的GPU推理系统 - 代码讲解

位置：AI Agent Development Code/aiTest/char03 | 教学主题：多实例并发调度架构 + 吞吐对比实验 | 技术栈：原 torch + threading 本地多 GPU → 改写为 threading + dashscope 云端并发 | 已验证可运行（串行 13.11秒 vs 并发 3.92秒，加速比约 3.3 倍）

一、这段代码要做什么

原教材演示的是多 GPU 多实例推理系统——检测有几张 GPU、每张加载一个模型副本、用多线程把请求轮询分发到各 GPU 实例上并行推理。这是推理服务架构的经典范式。因为电脑没有 GPU（torch.cuda.device_count() 返回 0，原代码会 assert 失败），所以改写为云端并发调用——保留多线程调度架构（这才是本篇灵魂），把"GPU 上的模型副本"换成"云端 API 调用"，并增加了串行 vs 并发的真实耗时对比实验——没有 GPU 也能亲眼看到并发如何提升吞吐。

本篇的核心教学价值：并发调度架构

你可能以为本篇在教"GPU 推理"——其实不是。GPU 只是承载"多实例"的物理介质，真正要理解的是：一个推理服务怎么同时服务多个请求而不互相阻塞。这个架构在云端、本地、甚至 CPU 上都一样成立——只是"实例"从"GPU 上的模型副本"变成了"云端 API 调用"。把教学焦点从"硬件"转到"架构"，才是改写的真正意义。

四、核心概念速查表（本篇独有的 3 个）

概念代码中的实现一句话解释
多实例部署原版：每张 GPU 一个模型副本；改写版：云端弹性实例同一模型加载 N 份副本，同时服务 N 个请求——提升并发吞吐
轮询分发idx % len(device_ids)把第 idx 个请求路由到第 (idx % N) 个实例上——最简单的负载均衡策略
join 等待for thread in threads: thread.join()主线程阻塞，直到所有子线程执行完毕——并发调度的收尾动作
IO 密集 vs CPU 密集改写版是 IO 密集（HTTP 请求等待），原版是 GPU 密集（CUDA 计算）并发对 IO 密集型任务提升巨大（HTTP 等待时间可以重叠）；对 CPU 密集型提升有限（受物理核心限制）

五、逐段讲解（4 个代码块）

块 1：run_inference —— 推理函数（签名不变，实现换了）

# 原版（本地 GPU）：
def run_inference(device_index, input_text):
    tokenizer = tokenizers[device_index]            # 从列表取对应 GPU 的 tokenizer
    model = models[device_index]                    # 从列表取对应 GPU 的模型副本
    input_ids = tokenizer(input_text, ...).input_ids.to(f"cuda:{device_index}")
    with torch.no_grad():
        output = model.generate(input_ids=input_ids, max_new_tokens=128, ...)
    decoded = tokenizer.decode(output[0], skip_special_tokens=True)
    del input_ids, output
    torch.cuda.empty_cache()                        # GPU 显存清理

# 改写版（云端）：
def run_inference(instance_index, input_text):
    start = time.time()
    response = dashscope.Generation.call(           # 一个函数调用 = 一次 HTTP 请求
        model='qwen-plus',
        messages=[{"role": "user", "content": input_text}],
        max_tokens=128,                             # 与原版 max_new_tokens=128 语义一致
        temperature=0.7,                            # 与原版 do_sample=True + temperature=0.7 语义一致
        result_format='message')
    decoded = response.output.choices[0].message.content.strip()
    print(f"[实例-{instance_index}] 推理耗时：{round(time.time() - start, 2)}秒")
    # 没有 del / empty_cache —— 云端无本地显存占用

块 2：多线程调度架构（本篇灵魂，逐行保留）

threads = []
for idx, prompt in enumerate(prompts):
    # 关键：idx % len(INSTANCE_IDS) 把 4 个请求轮询分发到 2 个实例槽位
    thread = threading.Thread(
        target=run_inference,                       # 目标函数（签名不变）
        args=(idx % len(INSTANCE_IDS), prompt)      # 参数：槽位编号 + 文本
    )
    threads.append(thread)
    thread.start()                                  # 启动子线程，不阻塞主线程

for thread in threads:
    thread.join()                                   # 主线程等所有子线程完成
为什么"轮询分发"这么简单却有效？

假设 2 个实例槽位、4 个请求：请求 0 → 槽位 0；请求 1 → 槽位 1；请求 2 → 槽位 0；请求 3 → 槽位 1。两个槽位各分到 2 个请求，并行处理。这就是经典的"轮询负载均衡"——生产级服务（如 Nginx）的默认策略之一。更复杂的策略有"最少连接数优先""加权轮询"等，但核心思想一样：把请求均匀铺到 N 个实例上。

块 3：对照实验 A —— 串行执行（基准线）

def run_serial():
    for idx, prompt in enumerate(prompts):
        run_inference(0, prompt)     # 全部路由到槽位 0，一个接一个
    # 串行总耗时 ≈ 4 × 单次请求耗时（因为完全不能重叠）

块 4：对照实验 B —— 并发执行（原 Step 5 架构）

def run_concurrent():
    threads = []
    for idx, prompt in enumerate(prompts):
        thread = threading.Thread(target=run_inference,
            args=(idx % len(INSTANCE_IDS), prompt))
        threads.append(thread)
        thread.start()
    for thread in threads:
        thread.join()
    # 并发总耗时 ≈ max(各实例处理时间)（因为实例并行处理，谁慢等谁）

为什么加速比超过了实例槽位数？

理论上 2 个实例槽位最多 2 倍加速，但实际跑出了 3.3 倍——原因是：① 云端 API 本身有并发优化（百炼可能内部做了请求合并或路由到更多弹性实例）；② 线程调度开销远小于网络等待时间（IO 密集型并发的红利被吃满了）。这恰好印证了改写版的价值——没有 GPU，也能看到并发的威力。

八、教学简化 vs 生产差距

  • 轮询分发太简单：生产级推理服务不会用裸 idx % N，而是用专业负载均衡器（Nginx / LVS / 服务网格）支持最少连接数优先、加权、熔断等策略
  • 无请求队列与限流：4 个请求同时发出没问题，400 个会怎样？dashscope 有 RPM/TPM 限制，超过会返回 429。生产应加队列缓冲 + 令牌桶限流
  • 无异常隔离：某个线程的推理失败不影响其他线程，但当前没有重试机制。生产要加 per-request 重试 + 熔断（某个实例连续失败就暂时摘掉）
  • 无批处理（Batching）：原版 GPU 推理可以把多个请求拼成一个 batch 一次过 GPU（GPU 并行吞吐更高），云端 API 是单次请求单次调用，没吃到 batch 红利。vLLM 等本地推理框架的核心优化就是 continuous batching
  • 线程数 = 请求数：当前 4 个请求 = 4 个线程，请求量上来后线程创建/销毁开销巨大。生产用线程池（ThreadPoolExecutor）复用线程，或用 asyncio 协程（比线程更轻量）

九、动手练习

  1. 改实例槽位数：把 INSTANCE_IDS = [0, 1] 改成 [0, 1, 2, 3]（4 个槽位），重跑看加速比变化——理解"实例数增加"和"吞吐提升"的关系（注意：云端不保证你多开槽位就多分配资源，这和本地多 GPU 不同）。
  2. 加异常隔离：故意让某个请求触发限流（连续发 20 个并发请求），观察哪些成功哪些失败，然后给失败的加重试逻辑——理解"并发不等于无限制"。
  3. ThreadPoolExecutor 版：用 from concurrent.futures import ThreadPoolExecutor 替换裸 threading，对比代码简洁度——理解线程池 vs 裸线程的工程化优势。
  4. asyncio 协程版：用 asyncio + httpx.AsyncClient 实现真正的异步并发，对比线程版和协程版的代码复杂度和资源占用——理解 IO 密集型任务为什么协程比线程更轻。
  5. 思维题：如果你的服务要同时处理 1000 个用户请求，每个请求耗时 3 秒。用串行？多线程？多 GPU？云 API 并发？各自总耗时和硬件成本大概是多少？
