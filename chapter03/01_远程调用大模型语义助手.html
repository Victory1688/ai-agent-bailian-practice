01_远程调用大模型语义助手 - 代码讲解

位置：AI Agent Development Code/aiTest/char03 | 教学主题：大模型远程调用的工程化基础 | 技术栈：dashscope SDK + temperature / max_tokens 参数控制 + 批量推理 | 已验证可运行（5 个成语批量请求全部成功返回完整典故）

一、这段代码要做什么

实现一个成语解释语义助手：输入"破釜沉舟"，返回这个成语的典故来历、出处和含义——全部由大模型生成，不查任何本地数据库。核心教学点有三个：消息角色的结构化构造（system 锚定角色 + user 放具体请求）、生成参数的调控（temperature 控制随机性、max_tokens 控制篇幅）、批量推理的循环调用（一个函数封装 + 一个 for 循环 = 批量任务）。

char01 → char03 的知识延续
  • char01-01 教了"提示词三要素 + 最小调用闭环" → 本篇在此基础上加了 temperature / max_tokens 两个工程参数
  • char01-05 教了"system / user 消息角色" → 本篇把它抽成 build_message 独立函数，结构更清晰、可复用
  • 本篇新增 批量推理（一个 for 循环里反复调同一个函数）和 错误兜底（try/except 返回错误字符串而非崩掉）——这两个是"写函数脚本"和"做生产级调用"之间的分界线

二、原教材代码的问题

两类问题

第 1 类：SDK 版本与网络环境：openai.ChatCompletion.create 是 OpenAI Python SDK 的老版本调用方式（v0.x），新版 v1.x 已改为 openai.chat.completions.create；更关键的是国内无法直连 OpenAI 服务，必须换成本地/国内平台。改写为 dashscope，模型名换 qwen-plus。

第 2 类：好逻辑被绑死：build_message 的消息角色设计、temperature / max_tokens 的参数传递、try/except 的兜底、batch_inference 的批量循环——这些业务逻辑完全正确，和任何框架无关。改写时原样保留。

四、核心概念速查表

概念代码中的实现一句话解释
build_message返回 [{"role": "system", ...}, {"role": "user", ...}]把"角色设定"和"具体请求"拆成两条独立消息——结构化构造
system 角色"你是一位语言学家，擅长解释中文成语的典故、来历与含义"锚定模型的身份和能力边界，让它只在"成语解释"这个领域内发挥
temperature默认值 0.5（可调参数）0-2 之间，越低越确定性（每次输出差不多），越高越有创造性（可能跑偏）
max_tokens默认值 300（可调参数）单次回复的最大 token 数上限，防止模型滔滔不绝浪费额度
批量推理for idiom in idioms: chat_with_llm(...)同一个函数反复调，每次换一个 prompt——最简单的"批量任务"写法
错误兜底try/except 里 return f"调用失败: {str(e)}"调用函数永不抛异常，失败也返回字符串——批量任务不会因为一个挂就全挂

五、逐段讲解（4 个代码块）

块 1：build_message —— 消息的结构化构造

def build_message(user_prompt: str) -> List[Dict[str, str]]:
    return [
        {"role": "system", "content": "你是一位语言学家，擅长解释中文成语的典故、来历与含义"},
        {"role": "user", "content": user_prompt}
    ]
为什么拆成两条消息而不是一条大 prompt？

因为消息列表是按条累加的——多轮对话时，模型能"看到"历史上所有的 system / user / assistant 消息。把"身份设定"独立成 system 消息，多轮时它始终在最前面，不会被 user 的具体请求冲掉。这和 char02 里 Agent 循环的 memory 列表是同一个数据结构。

块 2：chat_with_llm —— 远程调用的核心封装

def chat_with_llm(prompt: str, temperature: float = 0.5, max_tokens: int = 300) -> str:
    messages = build_message(prompt)           # ① 构造消息列表
    try:
        response = dashscope.Generation.call(   # ② 发起远程请求（网络 I/O）
            model='qwen-plus',
            messages=messages,
            temperature=temperature,
            max_tokens=max_tokens,
            result_format='message')
        reply = response.output.choices[0].message.content   # ③ 取纯文本回复
        return reply.strip()
    except Exception as e:
        return f"调用失败: {str(e)}"            # ④ 失败也返回字符串，永不抛异常

这个函数是 "远程调用的最小生产级封装"——它做了四件事：构造消息、发起网络请求、提取回复、异常兜底。之后所有"调大模型"的代码都应该长成这个样子，而不是把 API Key 硬编码、把异常直接往外抛。

块 3：temperature 和 max_tokens —— 两个最常用的生成参数

# temperature 越低越确定性，越高越有创造性
chat_with_llm("请解释成语"破釜沉舟"", temperature=0.1)   # 低随机性：每次解释差不多
chat_with_llm("请写一首关于春天的诗", temperature=1.2)   # 高随机性：每次诗都不一样

# max_tokens 控制篇幅
chat_with_llm("请解释成语", max_tokens=100)     # 要精简版
chat_with_llm("请解释成语", max_tokens=800)     # 要详细版
教学简化：本篇只调一个模型

真实项目里 temperature / max_tokens 之外，还有 top_p（核采样阈值）、stop（停止序列）、presence_penalty（重复惩罚）等十几个参数。本篇聚焦两个最常用的，其余知道名字就行，按需查 SDK 文档。

块 4：batch_inference —— 批量推理的最简单写法

def batch_inference():
    idioms = ["破釜沉舟", "卧薪尝胆", "指鹿为马", "望梅止渴", "画龙点睛"]
    results = {}
    for idiom in idioms:
        reply = chat_with_llm(f"请解释成语"{idiom}"的来历和含义")
        results[idiom] = reply     # 成语 → 解释 的映射字典
    return results

教学重点：一个 for 循环就是批量推理。但注意——大模型调用是网络 I/O，这 5 次调用是串行的（前一个完了才调后一个），如果批量很大（如 1000 条），等待时间会非常长。生产级做法用 并发（线程池 / asyncio）同时发多个请求，char03 后续可能会涉及。

七、OAI → dashscope 的参数映射（给有 OpenAI 基础的新人）

OpenAI v0.x 老写法dashscope 对应写法备注
openai.api_key = "xxx"dashscope.api_key = os.getenv('DASHSCOPE_API_KEY')Key 都走环境变量，不写死
openai.ChatCompletion.create(model="gpt-3.5-turbo", messages=[...])dashscope.Generation.call(model='qwen-plus', messages=[...])模型名换了，函数签名类似
response['choices'][0]['message']['content']（字典式取值）response.output.choices[0].message.content（对象式取值）dashscope 用了 result_format='message' 后是对象；默认格式是字典
temperature=0.5, max_tokens=300完全相同生成参数语义一致
model="gpt-3.5-turbo"model='qwen-plus'平台不同，模型名列表不同；百炼的 qwen-plus/ qwen-max/ qwen-turbo 是主力

八、教学简化 vs 生产差距（4 件事没做）

这套代码离生产还差的四件事
  • 无并发：5 次调用串行执行，大批量（如 1000 条）时总耗时 = N × 单次耗时。生产用 asyncio + httpx 或线程池并发发请求
  • 无重试与限流：dashscope 有请求频率限制（RPM），超过会返回 429；网络超时也可能被吞。生产要加 tenacity 重试 + time.sleep 限流
  • 响应未持久化：results 字典 print 完就没了。生产要写数据库/CSV/JSON 文件，防止程序崩溃丢数据
  • temperature / max_tokens 写死：作为函数默认值可以调，但批量任务通常需要统一参数。生产把参数放进配置文件/环境变量

九、动手练习

  1. 调参对比：把 temperature 改成 0.1 和 1.5，分别跑一次"画龙点睛"，对比两次输出的内容差异和句式差异。体会"确定性 vs 创造性"。
  2. 换模型：把 model 换成 'qwen-turbo'（免费但能力弱）和 'qwen-max'（最强但贵），对比同一成语的解释质量和响应速度。
  3. 加并发：用 from concurrent.futures import ThreadPoolExecutor 把 batch_inference 的 for 循环改成并发版本——体会从"串行几分钟"到"并发几十秒"的差距。
  4. 加持久化：把 results 字典存成 JSON 文件 idiom_explanations.json，失败的成语单独收集成一个列表输出到控制台——批量任务的"容错 + 存档"实践。
