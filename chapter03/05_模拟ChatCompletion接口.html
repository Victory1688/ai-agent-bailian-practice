05_模拟ChatCompletion接口 - 代码讲解

位置：AI Agent Development Code/aiTest/char03 | 教学主题：OpenAI 兼容接口协议（/v1/chat/completions）| 技术栈：FastAPI + Pydantic + SSE 流式 + dashscope 云端调用 | 已验证可运行（非流式 200 + 流式 44 个 SSE 块 + [DONE] 结束标记）

一、这段代码要做什么

用 FastAPI 搭一个和 OpenAI 接口协议完全兼容的对话服务——任何"会说 OpenAI 方言"的客户端（openai SDK、LangChain、ChatBox 等第三方工具）只要把 base_url 指向你这个服务，就能无缝使用。这是本篇的核心教学点：协议即标准。改写后，本地模型推理（需 GPU）替换为百炼云端调用，FastAPI / Pydantic / OpenAI 响应格式全部保留，并把原版的"假流式"升级为真流式。

为什么"模拟 ChatCompletion 接口"是重要的工程能力？
  • 客户端零改造：整个生态都在说 OpenAI 方言——你的服务实现了这个协议，就自动接入了整个生态
  • 透明换后端：客户端不关心你后面是 Qwen、DeepSeek 还是自己训练的模型——协议一样，体验一样
  • 企业落地常见形态：公司内部网关、模型中转站、私有化部署服务的对外接口，都是这个模式

三、一次请求的完整生命线

客户端 POST /v1/chat/completions
  │  {"model": "qwen-plus", "messages": [...], "stream": false}
  ▼
FastAPI 收到请求 → Pydantic 校验（ChatRequest：缺字段/类型错直接 422）
  │
  ├─ stream=false（非流式）
  │    build_messages(req) → dashscope.Generation.call（等整段生成完）
  │    → 包装成 OpenAI 格式 {"id": "cmpl-local-001", "object": "chat.completion", ...}
  │    → 一次性返回完整 JSON
  │
  └─ stream=true（流式）
       StreamingResponse(media_type="text/event-stream")
       → dashscope stream=True + incremental_output=True
       → 模型每生成一段 → yield "data: {\"delta\": {\"content\": \"新增片段\"}}\n\n"
       → 客户端边收边拼（打字机效果）
       → 生成完毕 → yield "data: [DONE]\n\n"

四、逐段讲解（6 个 Step）

Step 1：模型加载 → 云端配置（唯一被替换的环节）

# 原写法（需 GPU，本地加载 3.6GB 权重常驻显存）：
tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen-1.8B", ...)
model = AutoModelForCausalLM.from_pretrained(...).cuda().eval()

# 改写（云端调用，本地零加载）：
api_key = os.environ.get('DASHSCOPE_API_KEY')
dashscope.api_key = api_key

Step 2：ChatRequest 数据结构（OpenAI 请求协议的代码化，原样保留）

class Message(BaseModel):
    role: str          # "system" / "user" / "assistant"
    content: str

class ChatRequest(BaseModel):
    model: str                      # 客户端想用的模型名
    messages: list[Message]         # 对话历史（含角色）
    temperature: float = 0.7        # 随机性
    max_tokens: int = 256           # 回复长度上限
    stream: bool = False            # 是否流式

Pydantic 的价值：请求校验免费获得——客户端漏传 model、传错类型，FastAPI 自动返回 422 错误，不用手写校验代码。

Step 3：build_prompt 的消失（本篇最有意思的教学点）

# 原写法：本地基座模型不认识 messages 数组，必须手动拼成带角色标记的大字符串
def build_prompt(messages):
    history = []
    for msg in messages:
        if role == "system":  history.append(f"[系统提示]：{content}")
        elif role == "user":  history.append(f"[用户]：{content}")
        ...
    return "\n".join(history) + "\n[助手]："    # 用"[助手]："标记让模型接着说

# 改写：dashscope 原生支持 messages 数组，直接透传
def build_messages(req):
    return [{"role": m.role, "content": m.content} for m in req.messages]
为什么这一步"消失"了？

原代码手动拼接角色标记，是因为裸的基座模型（base model）只是个"文字接龙机器"，不理解对话结构。而云端 Chat 模型（qwen-plus）是指令对齐过的对话模型，服务端天然理解 role/content 结构。你调的接口越智能，需要在客户端做的格式工程就越少——这正是 Chat Completion 协议比 Completion 协议先进的地方。

Step 4：假流式 → 真流式（本篇第二个重点升级）

# 原写法："假流式"——等整段生成完，再切成 10 字符一片，sleep 模拟打字机
def stream_response(prompt, max_tokens, temperature):
    ...model.generate(...)                      # 先整段生成（客户端干等）
    for i in range(0, len(response), 10):
        yield json.dumps({"choices": [{"delta": {"content": response[i:i+10]}}]}) + "\n"
        time.sleep(0.05)                        # 人为放慢，装成在生成

# 改写："真流式"——模型每生成一段就实时推送
def stream_response(messages, max_tokens, temperature):
    responses = dashscope.Generation.call(
        model='qwen-plus', messages=messages,
        stream=True, incremental_output=True)   # 增量流式
    for response in responses:
        chunk = response.output.choices[0].message.content or ""
        if chunk:
            yield f"data: {json.dumps({'choices': [{'delta': {'content': chunk}}]}, ensure_ascii=False)}\n\n"
    yield "data: [DONE]\n\n"                    # OpenAI 协议结束标记
假流式 vs 真流式的本质区别

假流式的首字延迟 = 整段生成时间（长回答用户要干等十几秒才看到第一个字）；真流式的首字延迟 = 第一个 token 的生成时间（通常 1 秒内）。原代码还漏了 data: 前缀和 [DONE] 标记——标准 OpenAI 客户端会解析失败。改写版补齐了这两处，做到真正协议兼容。

Step 5：主接口（一个端点两种模式）

@app.post("/v1/chat/completions")
async def chat_completion(req: ChatRequest):
    messages = build_messages(req)
    if req.stream:
        return StreamingResponse(stream_response(...), media_type="text/event-stream")
    else:
        response = dashscope.Generation.call(...)
        result = response.output.choices[0].message.content
        return {"id": "cmpl-local-001", "object": "chat.completion",
                "choices": [{"message": {"role": "assistant", "content": result}}]}

注意返回结构刻意保持 id / object / choices 的 OpenAI 格式——即使换了云端后端，对客户端暴露的协议纹丝不动。这就是"模拟 ChatCompletion 接口"的意义。

六、客户端怎么用你的服务（生态接入演示）

# 用 openai SDK 对接你的本地服务（base_url 指向自己）
from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:8080/v1", api_key="not-needed")

resp = client.chat.completions.create(
    model="qwen-plus",
    messages=[{"role": "user", "content": "请解释一下LoRA技术的基本原理"}]
)
print(resp.choices[0].message.content)

# 流式版本
stream = client.chat.completions.create(
    model="qwen-plus",
    messages=[{"role": "user", "content": "讲个故事"}],
    stream=True
)
for chunk in stream:
    print(chunk.choices[0].delta.content or "", end="")

这段客户端代码一行都不用改就能切换到真正的 OpenAI 或任何兼容服务——只需要换 base_url。这就是协议兼容的价值。

七、教学简化 vs 生产差距

  • 无鉴权：OpenAI 用 Bearer Token 鉴权，本服务任何请求都能过。生产要加 API Key 校验中间件
  • 无模型路由：请求体里的 model 字段被忽略了（无论传什么都调 qwen-plus）。生产应做模型名映射与多后端路由
  • 无用量统计：OpenAI 响应带 usage 字段（prompt_tokens / completion_tokens），本服务没返回——计费与限流都依赖它
  • 无并发保护：多请求同时打进来，全靠 dashscope 的 RPM/TPM 限额兜底，生产要加信号量/队列
  • CORS 未配置：浏览器前端直调会被跨域拦截（对比 char02-08 加过 CORSMiddleware）
  • 异常处理缺失：dashscope 调用失败会直接 500，生产应捕获后返回 OpenAI 风格的错误 JSON（{"error": {...}}）
