06_支持Qwen模型函数调用标准结构 - 代码讲解

位置：AI Agent Development Code/aiTest/char03 | 教学主题：Function Calling 协议的服务化实现 | 技术栈：原 FastAPI + 假关键词匹配 → 改写为 FastAPI + 真 dashscope Function Calling 循环 | 已验证可运行（3 种场景：模型自主调天气 / 自主调求和 / 自主决定不调函数）

一、这段代码要做什么

用 FastAPI 搭一个支持 Function Calling 的对话服务——客户端把消息和可用工具发过来，模型自主决策要不要调函数、调哪个、参数填什么。改写前原代码的 FastAPI 骨架、function_registry、dispatch_function 都是好教材，但"函数调用提取"是假的——用关键词匹配（"调用函数" / "get_weather"）硬编码返回固定结构，模型根本没看到工具说明书，换个输入就对不上。改写的核心动作是补齐真正的 Function Calling 循环：tools 说明书 → 模型自主决策 → 本地 dispatch → 结果回传。

本篇在 char03 的定位

char03 前 5 篇教了"远程调用推理 / 本地 vs 云端 / LoRA 微调 / 并发调度 / ChatCompletion 协议"——全是模型本身的事。本篇首次引入 Function Calling，把模型从"只会说话"升级到"能调用外部工具"——这是 char02 Agent 能力的源头。如果你理解了本篇的 Function Calling 循环，char02 的 8 篇代码（骨架→状态→持久化→注销→API→数据库→文件→服务化）就全通了。

二、假 Function Calling vs 真 Function Calling（改写的本质）

对比维度原代码（假的）改写后（真的）
模型看到了什么只有 prompt 文本，完全没看到工具说明书messages + tools（完整的 JSON Schema 格式说明书）
谁决定调哪个函数硬编码 if/elif：输出含"北京"就返回 get_weather模型自主决策：看说明书 → 判断用户意图 → 选最合适的工具
参数从哪来硬编码：{"city": "北京", "a": "8", "b": "12"}模型根据用户输入自主提取：用户说"上海"就填 city="上海"
容错能力换个输入就崩：用户说"帮我查深圳天气"→ 硬编码只认"北京"自适应：不管用户说"深圳""广州""成都"，模型都能正确填参数
不调函数怎么办硬编码最后 return {"response": output_text}模型自主判断："这个问题不需要工具"→ 直接返回自然语言
技术本质prompt 工程 + 正则匹配（模型只是文案生成器）Function Calling 协议（模型是决策者，有工具使用能力）

四、逐段讲解（4 个代码块）

块 1：tools 说明书（改写的关键——原代码完全没有）

# 原代码的 function_registry（只有描述和参数名，不是真正的 JSON Schema）：
function_registry = {
    "get_weather": {"description": "获取城市天气", "parameters": ["city"]},
    "calculate_sum": {"description": "计算两个数字的和", "parameters": ["a", "b"]}
}

# 改写：完整的 OpenAI Function Calling 协议格式
tools = [
    {"type": "function", "function": {
        "name": "get_weather",
        "description": "获取指定城市的当前天气",
        "parameters": {"type": "object", "properties": {
            "city": {"type": "string", "description": "城市名称，如 北京、上海、深圳"}
        }, "required": ["city"]}
    }},
    {"type": "function", "function": {
        "name": "calculate_sum",
        "description": "计算两个数字的和",
        "parameters": {"type": "object", "properties": {
            "a": {"type": "number", "description": "第一个数字"},
            "b": {"type": "number", "description": "第二个数字"}
        }, "required": ["a", "b"]}
    }},
]
为什么 JSON Schema 格式如此重要？

模型不是"看懂"这份说明书的文字——它是结构化地解析这份 JSON Schema。"type": "string" 告诉模型 city 参数必须是字符串，"required": ["city"] 告诉模型这个参数不能缺。如果说明书格式不对，模型可能填错类型或漏参数——这就是为什么改写版必须把原代码的简陋格式换成完整 JSON Schema。

块 2：Function Calling 循环（本篇核心，char02 的 Agent 循环就是这个）

def run_function_call(messages_list):
    # 第 1 轮：让模型看 tools，自主决策
    response = dashscope.Generation.call(
        model='qwen-plus', messages=messages_list,
        tools=tools,                                     # ← 原代码没有！
        temperature=0.3, max_tokens=512, result_format='message')
    message = response.output.choices[0].message
    tool_calls = getattr(message, 'tool_calls', None)

    # 模型决定不调函数 → 直接返回自然语言回答
    if not tool_calls:
        return {"response": message.content, "tool_calls": []}

    # 模型决定调函数 → 本地执行 + 结果回传 + 第 2 轮让模型生成最终回答
    messages_list = messages_list + [message]
    for call in tool_calls:
        fn_name = call['function']['name']
        fn_args = json.loads(call['function'].get('arguments') or '{}')
        fn = tool_registry.get(fn_name)
        tool_result = fn(**fn_args) if fn else f"未注册的函数: {fn_name}"
        messages_list = messages_list + [{
            "role": "tool", "content": tool_result,
            "name": fn_name, "tool_call_id": call.get('id', fn_name)
        }]

块 3：dispatch_function 的升级（if/elif → 字典查表）

# 原写法：if/elif 链（加新函数必须改这个函数）
def dispatch_function(name, args):
    if name == "get_weather":       return get_weather(args["city"])
    if name == "calculate_sum":     return calculate_sum(args["a"], args["b"])
    return "未知函数"

# 改写：字典查表（加新函数只需在 tool_registry 里加一行，不用改 dispatch）
tool_registry = {"get_weather": get_weather, "calculate_sum": calculate_sum}
fn = tool_registry.get(fn_name)
tool_result = fn(**fn_args) if fn else f"未注册的函数: {fn_name}"

字典查表比 if/elif 更"开放"——新增函数只需在 tool_registry 里加一行，不需要改 dispatch 逻辑。这是"开闭原则"（对扩展开放，对修改关闭）的体现。

3 个测试的教学价值

这 3 个场景完美证明了真 Function Calling 和假关键词匹配的本质区别：原代码遇到"帮我算 8 加 12"会硬编码返回 a="8", b="12"——但如果用户说"帮我算 88 加 112"，硬编码就对不上了；而改写版的模型能正确提取 a=88, b=112，因为是模型在理解用户输入，不是 if/elif 在匹配关键词。

七、Function Calling 三件套（贯穿 char02 + char03-06 的统一模式）

┌─────────────────────────────────────────────────────────┐
│  Function Calling 三件套（任何场景都离不开）              │
│                                                           │
│  1. 工具注册表 (tool_registry)                            │
│     函数名 → 执行体（本地跑的 Python 函数）               │
│     {"get_weather": get_weather, "calculate_sum": ...}    │
│                                                           │
│  2. 工具说明书 (tools)                                    │
│     给模型看的 JSON Schema（OpenAI 协议格式）              │
│     model 看这份说明书 → 自主决策                         │
│                                                           │
│  3. Function Calling 循环                                 │
│     while True:                                           │
│       response = call(tools=tools)                        │
│       if response 里有 tool_calls:                        │
│         本地执行 → 结果回传 → continue                     │
│       else:                                               │
│         返回自然语言 → break                               │
└─────────────────────────────────────────────────────────┘

char02 的 8 篇代码只是给这三件套"加了壳"——有的加了记忆（03），有的加了状态追踪（02），有的加了服务化（08）。但三件套本身在所有文件里长得一模一样。理解了本篇的三件套，char02 八篇代码就是这三件套的 8 种不同包装方式。

八、教学简化 vs 生产差距

  • 无多轮记忆：当前每次 POST 都是独立请求，没有 session 追踪。生产应加 session_id 参数 + Redis/数据库存储每个会话的 messages 历史（参考 char03-03 的 PersistentJSONMemory）
  • 无多次工具调用循环：当前只处理一轮 tool_calls（模型可能连续调多个工具，甚至第一轮调一个，拿到结果后再调另一个）。生产应改成 while True 循环直到模型不再返回 tool_calls
  • 无鉴权与限流：同 char03-05，任何请求都能过
  • dispatch 无异常隔离：tool_registry 里的函数抛异常会直接崩掉。生产应 try/except 包裹，错误也返回字符串给模型（参考 char02-05 的四层防御）
  • tools 说明书无动态注册：当前 tools 是硬编码列表。生产应支持动态注册——启动时扫描某个目录下的所有工具自动生成 tools 列表

九、动手练习

  1. 加第三个工具：在 tool_registry 和 tools 里加一个 translate_text(text, target_lang)（直接返回"翻译结果：xxx"即可），然后问模型"帮我把 Hello World 翻译成法语"——观察模型是否自主选择新工具。
  2. 多工具串联：加一个 get_weather + calculate_sum 的组合场景——让模型先查北京天气（比如返回"晴 25°C"），然后算 25 的一半是多少——体会模型连续调两次工具、第二次调用的输入依赖第一次结果的串联逻辑。
  3. 多轮记忆版：给 ChatRequest 加 session_id 字段，用 Redis 或 char03-03 的 JSON 文件存储每个 session 的 messages 历史，实现同一 session 下的多轮对话。
  4. 思维题：为什么 Function Calling 需要"两轮"（第一轮模型说"我要调 get_weather"，第二轮模型才生成最终回答）？能不能让模型一步到位，直接在第一次回复里同时给出函数调用和最终回答？（提示：看模型的输出格式约束）
  5. 对比练习：用原代码的假关键词匹配逻辑重跑测试 2（"帮我算 88 加 112"），观察硬编码的 a="8", b="12" 如何失效——直观体会"真 Function Calling 为什么不可替代"。
