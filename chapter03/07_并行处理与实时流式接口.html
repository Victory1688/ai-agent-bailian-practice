07_并行处理与实时流式接口 - 代码讲解

位置：AI Agent Development Code/aiTest/char03 | 教学主题：批处理（Batch）与流式传输（Streaming）两种推理服务模式 | 技术栈：原 GPU batch + 假流式 → 改写为 ThreadPoolExecutor 并发批处理 + dashscope 真流式 | 已验证可运行（批处理 2 路并发 4.29秒；流式首块 0.43秒到达，25 个 SSE 块 + [DONE]）

一、这段代码要做什么

一个 FastAPI 服务暴露两个端点，演示推理服务的两种经典优化模式：

端点模式核心思想适用场景
POST /v1/chat/batch批处理（Batch）多个独立请求并行处理，全部完成后一次性返回——追求吞吐量离线任务、大规模数据处理（如批量标注、批量摘要）
POST /v1/chat/stream流式传输（Streaming）模型每生成一段就立即推送——追求低感知延迟实时聊天、AI 助手（用户看着字一个个蹦出来）

改写前：批处理依赖本地 GPU 的 batch generate（一次前向算多组输入），流式是"假流式"（整段生成完再切片模拟）。改写后：批处理变为线程池并发调用，流式升级为真流式——两个模式的核心教学思想全部保留。

二、批处理 vs 流式的本质区别（本篇总纲）

【批处理 Batch】——"一堆活一起干，干完一起交"
  请求A ──┐
  请求B ──┼─→ [并行推理] ─→ 全部完成 ─→ 一次性返回 [结果A, 结果B]
  请求C ──┘
  关注指标：总吞吐量（每秒处理多少请求）
  用户体验：慢（要等最慢的那个），但单位时间处理量大

【流式 Streaming】——"干一点交一点"
  请求 ──→ [推理中] ─→ chunk1 ─→ chunk2 ─→ chunk3 ─→ ... ─→ [DONE]
                        ↓        ↓        ↓
                      客户端实时渲染（打字机效果）
  关注指标：首字延迟（TTFT, Time To First Token）
  用户体验：快（0.43 秒就看到第一个字），总时间不变但"感觉"快得多
一句话记住两者的分工

批处理优化的是"机器的效率"，流式优化的是"人的感受"。同样是 3 秒生成完的回答：批处理让用户干等 3 秒；流式让用户 0.4 秒就开始看到内容——总时间一样，但后者的体验碾压前者。这就是为什么所有聊天产品（ChatGPT / 通义 / Kimi）全是流式输出。

三、逐段讲解（5 个代码块）

块 1：两种请求的数据结构（原样保留）

class BatchRequest(BaseModel):
    model: str
    messages_list: list[list[ChatItem]]   # 注意：两层嵌套 = 多组对话（"批"批在这里）
    max_tokens: int = 128

class StreamRequest(BaseModel):
    model: str
    messages: list[ChatItem]              # 一层 = 单组对话
    max_tokens: int = 128
    temperature: float = 0.7

list[list[ChatItem]] 的两层嵌套是批处理协议的关键——每组对话独立完整，组与组之间没有依赖（这是能并行的前提）。

@app.post("/v1/chat/batch")
async def batch_chat(req: BatchRequest):
    all_messages = [...]
    # submit 立即返回 Future（不阻塞），所有请求同时发出
    futures = [_executor.submit(infer_one, msgs, req.max_tokens) for msgs in all_messages]

    return {"results": results}
GPU batch 和线程池并发的区别与联系
  • GPU batch：一次前向计算同时算多组输入——计算层面的并行，吃 GPU 的矩阵运算能力
  • 线程池并发：多个 HTTP 请求同时在飞——IO 层面的并行，吃网络等待的重叠
  • 共同思想：多个独立请求不排队，一起处理——这就是"并行处理"的教学本质
  • 云端 API 没有 batch 接口（单次调用单组输入），所以改写版用 IO 并发模拟同样的吞吐效果

块 4：假流式 → 真流式（同 char03-05 的升级）

# 原写法（假流式）：先整段生成完，再切成 8 字符一片 + sleep 模拟
def stream_generator(prompt, max_tokens, temperature):
    output_ids = model.generate(...)                       # 客户端干等整段生成
    output_text = tokenizer.decode(...).split("[助手]：")[-1].strip()
    for i in range(0, len(output_text), 8):
        yield json.dumps({"choices": [{"delta": {"content": output_text[i:i+8]}}]}) + "\n"
        time.sleep(0.05)                                   # 人为放慢装作在生成

# 改写（真流式）：模型每生成一段就实时推送
def stream_generator(messages_list_of_dicts, max_tokens, temperature):
    responses = dashscope.Generation.call(
        ..., stream=True, incremental_output=True)         # 增量流式
    for response in responses:
        chunk = response.output.choices[0].message.content or ""
        if chunk:
            yield f"data: {json.dumps({'choices': [{'delta': {'content': chunk}}]}, ensure_ascii=False)}\n\n"
    yield "data: [DONE]\n\n"

五、假流式 vs 真流式的时间线对比

【假流式（原代码）】用户视角
  0s          2.5s                    3.5s
  ├───────────┼───────────────────────┤
  干等...干等...│ 整段生成完才开始切片推送 │ 切片放完
  ↑ 用户看到第一个字要等 2.5 秒（= 整段生成时间）

【真流式（改写后）】用户视角
  0s    0.43s            2.65s
  ├─────┼────────────────┤
  发出请求│ 第一个字出现      │ 生成完毕
         ↑ 用户 0.43 秒就看到内容，边生成边看

六、什么时候用批处理，什么时候用流式

决策因素选批处理选流式
请求来源程序/系统（无人盯着屏幕）真人用户（在等回复）
数量级成百上千条（批量摘要/标注/翻译）一次一条（对话）
时效要求几小时后要结果也行秒级必须开始响应
成本敏感度高（吞吐大 → 单位成本低）低（单次请求为主）
典型产品数据清洗管道、知识库预处理的 Embedding 批量生成ChatGPT 类聊天界面、客服机器人

生产系统常常两者都要：用户对话走流式接口，后台知识库构建走批处理——本篇把它们放进同一个服务，正是这个思路的雏形。

七、教学简化 vs 生产差距

  • 批处理无失败隔离：某个请求失败会通过 f.result() 抛异常毁掉整批。生产应逐个 try/except，失败的槽位返回错误标记（参考 char03-01 的"永不抛异常"原则）
  • 无批大小与限流控制：客户端传 1000 组对话就会打爆线程池和 RPM 限额。生产应限制单批最大组数 + 分片提交
  • 流式无心跳与断线处理：客户端中途断开，服务端生成器会收到 GeneratorExit（dashscope 侧请求也应取消，避免白烧 token）
  • 流式无 usage 统计：OpenAI 流式协议最后一块可带 usage 字段，本服务未实现——计费需要它
  • 线程池 vs 协程：8 worker 的线程池并发上限低；生产高并发场景用 asyncio + httpx.AsyncClient 更轻量（同 char03-04 的练习方向）

九、动手练习

  1. 批大小压测：把 messages_list 扩到 5 组 / 10 组对话，观察总耗时变化（是否仍 ≈ 单次耗时？什么时候开始排队？线程池 8 个 worker 的上限在哪？）。
  2. 失败隔离：在 infer_one 里加一个"指定内容抛异常"的模拟（如 content 含 "boom" 就失败），再给 batch_chat 加逐个 try/except——验证一批里某条失败不影响其他条。
  3. 前端打字机：写一个 20 行的 HTML 页面，用 fetch + ReadableStream 读取 /v1/chat/stream 的 SSE，实时渲染到页面上——亲眼看到打字机效果（这是所有聊天产品前端的原理）。
  4. asyncio 版：把批处理端点改写为 async def + asyncio.gather + httpx.AsyncClient，对比线程池版的代码结构和并发能力。
  5. 思维题：一个"批量翻译 1 万条商品标题"的任务和一个"客服机器人"产品，分别该用本篇哪个端点？如果批处理任务跑到一半某条请求 429 限流了，重试策略该怎么设计（全批重试 vs 单条重试）？
