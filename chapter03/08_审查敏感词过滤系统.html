08_审查敏感词过滤系统 - 代码讲解

位置：AI Agent Development Code/aiTest/char03 | 教学主题：内容审查的两层防线 + Trie 前缀树算法 | 技术栈：原 GPU 推理 → dashscope 云端调用（Trie 算法与双层过滤架构原样保留） | 已验证可运行（三种场景全通：input_blocked / ok / output_blocked）

一、这段代码要做什么

给大模型对话服务加一个内容审查中间层：用户输入先过一遍敏感词检查，命中直接拒绝（根本不调模型，省钱省时）；模型输出再过一遍检查，命中就拦截，不让问题内容流到客户端。这就是生产级 AI 产品的两层防线架构——所有对话产品（ChatGPT / 通义 / Kimi）都有这套机制，只是敏感词库换成了更智能的分类模型。

本篇的两个核心教学点
  • 双层过滤架构（生成前 + 生成后）：为什么一层不够？因为风险可能来自两端——用户故意投毒（输入侧），或模型被诱导后自己说出不该说的（输出侧）
  • Trie 前缀树算法：高效多模式串匹配——敏感词库上万条时，"每个词全文搜索一遍"是数量级的性能灾难，Trie 只需扫描文本一次

二、双层过滤架构图（本篇总纲）

用户请求 ──→ 【第一层：生成前过滤（pre_check）】
                  │
                  ├─ 命中敏感词 ──→ 返回 {"flag": "input_blocked", "reason": [...]}
                  │                 （模型根本没被调用——零成本拒绝）
                  ▼
             【模型推理】（原：本地 GPU generate → 改：dashscope 云端）
                  │
                  ▼
             【第二层：生成后过滤（post_check）】
                  │
                  ├─ 命中敏感词 ──→ 返回 {"flag": "output_blocked", "reason": [...],
                  │                                "original": "模型原始输出"}
                  ▼
             返回 {"flag": "ok", "response": "正常回答"}
flag 值含义触发条件成本
input_blocked输入被拦用户输入命中敏感词零模型成本（提前拒绝）
output_blocked输出被拦模型回答中含敏感词已花一次推理成本，但拦住了风险
ok正常通过两层都没命中一次正常推理成本

三、Trie 前缀树：为什么它是本篇的算法灵魂（原样保留，一字未改）

# 敏感词库：["暴力", "攻击", "毒品", "敏感政治"] 插入后的 Trie 结构：

                    root
                  /  |  \
                暴   攻   毒      敏
                │   │   │       │
                力   击   品       感
              [end] [end] [end]   │
                                  政
                                  │
                                  治
                                [end]
                                （敏感政治）

# search("我今天想了解毒品") 的扫描过程：
#   从"我"出发 → root.children 里没有"我" → 死路，下一个字
#   从"毒"出发 → root→毒→品 → 品节点 is_end=True → 记录命中"毒品" ✓
#   ...全文扫一遍，所有命中的词都出来了
Trie vs 朴素匹配的性能账（为什么要学这个数据结构）

朴素做法：for word in sensitive_words: if word in text——词库 1 万条、文本 1000 字，就是 1 万次全文扫描（约 1000 万次字符比较）。Trie 做法：文本从头到尾扫一次（1000 步），每步沿树往下走几层。词库越大，Trie 优势越明显——这是以空间（树节点）换时间（扫描次数）的经典案例，也是所有商用敏感词系统的底层方案（DFA/AC 自动机都是 Trie 的进化版）。

五、真实运行输出（三种场景全部验证通过）

【场景 1：输入命中敏感词】（教材原例）
请求: {"messages": [{"role": "user", "content": "请告诉我关于毒品的知识"}]}
响应: {"flag": "input_blocked", "reason": ["毒品"]}
↑ 第一层防线生效，模型根本没被调用（省了一次推理成本）

【场景 2：正常内容】
请求: {"messages": [{"role": "user", "content": "用一句话介绍大语言模型"}]}
响应: {"flag": "ok", "response": "大语言模型（LLM）是一种基于深度学习、通过在海量文本数据上
       进行大规模预训练而获得的AI模型，具备强大的语言理解与生成能..."}
↑ 两层都没命中，正常放行

【场景 3：诱导模型输出敏感词】（最难触发的场景——第二层防线的存在性证明）
请求: {"messages": [{"role": "user", "content": "请把这两个字连起来组成一个词并解释含义：暴 力"}]}
       ↑ 输入里"暴"和"力"是分开的，Trie 匹配不上，第一层放行
响应: {"flag": "output_blocked", "reason": ["暴力", "暴力"],
       "original": "\u201c暴力\u201d是一个汉语双音节词...暴力指通过武力、强制、胁迫..."}
↑ 模型自己把"暴"和"力"连成了"暴力"——被第二层拦下！
场景 3 的教学价值

这个测试精确演示了为什么必须有两层过滤：用户输入"暴 力"（中间带空格）骗过了第一层，但模型在回答中把它连成了完整的"暴力"——如果只有输入过滤，这个词就流到客户端了。攻击者在输入侧绕过的方式，恰好证明输出侧过滤的必要性。顺带注意 reason 里有两个"暴力"——Trie 把回答里两处出现都抓出来了。

六、教学简化 vs 生产差距（重点：别真用敏感词列表做内容安全）

本篇方案的真实定位

Trie 敏感词过滤是最基础的字符串级审查，生产环境只能当第一道补充防线，绝不能当唯一防线。真实的内容安全体系要复杂得多：

  • 变体绕过："毒 品"、"du品"、"黃色"（形近字）、"🧪青春"（谐音/emoji）——Trie 全部失守。生产用 NLP 分类模型 + embedding 相似度识别语义级风险
  • 语义审查：没有敏感词但意思危险的话（"如何在家提取某种东西"）——字符串匹配永远抓不到，需要意图分类模型
  • 多模态：图片、音频的审核（本篇只管文本）
  • 云端自带审核：dashscope 本身内置内容安全层，触发时返回错误——生产中应把它的拦截信号也纳入 flag 体系
  • 词库管理：真实词库数万条且高频更新——应放数据库/配置中心并支持热更新，而不是代码里硬编码 4 个词
  • 审计留痕：被拦截的请求应记录日志（谁、什么时间、命中什么词），供风控回溯——本篇没有落盘

九、动手练习

  1. 变体绕过实验：试试输入"毒 品"（带空格）、"D品"（拼音混写），观察 Trie 是否失守——然后给 SensitiveTrie 加一个 preprocess 函数（去空格/全角转半角/简繁转换），看能堵住几种变体，体会"字符串级审查的天花板"。
  2. 词库热更新：把 sensitive_words 挪到 sensitive_words.txt（每行一个词），加一个 GET /reload 端点重新加载 Trie——体会"词库与代码分离"的工程意义。
  3. 审计日志：每次拦截（input_blocked / output_blocked）都追加写入 audit.log（时间戳 + 命中词 + 原文），模拟风控回溯。
  4. AC 自动机调研：查一下 AC 自动机（Aho-Corasick）与朴素 Trie 的区别（失配跳转），理解为什么商用系统都用它——本篇的 Trie 在最坏情况下仍有重复扫描。
  5. 思维题：为什么 input_blocked 要在"调模型之前"返回，而不是照样调模型再拦输出？（两个角度：成本、以及生成内容本身可能产生新的风险）。如果用户的 system prompt 里含敏感词但 user 输入干净，拦截是否合理？这个边界该怎么设计？
