9 篇文件不是平铺的列表，而是一个推理服务从下到上的四个楼层：先解决"模型从哪来"（供给层），再解决"流量怎么扛、结果怎么送"（交付层），再解决"对客户承诺什么接口、什么质量"（协议层），最后解决"内容安全与可信"（治理层）。逐层向上学，每层都有可运行的代码对应。

五、贯穿 9 篇的三条不变式（新人最先要认出来的模式）

  1. 统一的钥匙与改写范式：9 篇原教材全部依赖本地 GPU（transformers + .cuda()）或虚构 API，无法在无 GPU 环境运行。改写范式统一为三步：原代码注释保留（对照学习）→ 环境变量读 DASHSCOPE_API_KEY → 推理调用替换为 dashscope 云端（或兼容模式）。改写只动"模型怎么调"，从不动业务逻辑与架构。
  2. build_prompt 的消失：01~09 里凡是手动拼 [用户]：/[助手]： 角色标记的函数，改写后全部变成"messages 直接透传"。原因：云端 Chat 模型原生理解 role/content 结构——你调的接口越智能，客户端的格式工程越少。
  3. 一平台两扇门：dashscope 原生 SDK（Generation.call，01/02/03/04 等篇用）简单但能力子集；OpenAI 兼容模式（compatible-mode/v1/chat/completions，05/06/09 篇用）功能完整（logprobs、工具协议、标准流式）。遇到原生 SDK 缺能力，第一反应去兼容模式找。

六、核心概念自测清单（学完应能不看资料回答）

  1. temperature 和 max_tokens 各控制什么？改大改小分别什么效果？（01）
  2. 本地部署和云端调用在硬件、数据隐私、成本、弹性上各差在哪？（02）
  3. LoRA 为什么"训练快、权重小"？本地 LoraConfig 的 r 和云端 hyper_parameters 怎么对应？（03）
  4. 为什么多线程并发 2 个实例能跑出 3.3 倍加速（超过 2 倍理论值）？串行是"求和"、并发是"取 max"指什么？（04）
  5. OpenAI ChatCompletion 协议的请求体和两种响应格式（非流式/流式 SSE）长什么样？[DONE] 是干嘛的？（05/07）
  6. 真 Function Calling 三件套是什么？为什么说 char02 八篇都是这三件套的包装？（06）
  7. 批处理和流式各自优化什么？为什么所有聊天产品都是流式？（07）
  8. 内容审查为什么要两层（生成前+生成后）？Trie 比朴素匹配快在哪？（08）
  9. 为什么生成概率低意味着幻觉风险大？这个指标的三条局限是什么？（09）
  10. dashscope 原生 SDK 和兼容模式各适合什么场景？（05/09）

八、新人学习路径（建议 6 步，每步带自测标准）

  1. 第 1 步：会调模型（01→02）——能解释四组参数、能说清本地/云端取舍。自测：不看资料写出 01 的最小调用函数。
  2. 第 2 步：懂定制（03）——能画出 LoRA 注入原理、说清 r 的意义。自测：讲出"为什么 235B 模型本地跑不动而 LoRA 权重却很小"。
  3. 第 3 步：能扛流量（04→07）——理解并发思想与批/流取舍。自测：画出串行 vs 并发时间线，说清"批处理优化机器效率、流式优化人的感受"。
  4. 第 4 步：通协议（05→06）——掌握 OpenAI 方言与 Function Calling 三件套。自测：手写 tools JSON Schema；解释为什么"换 base_url 不换代码"。
  5. 第 5 步：会治理（08→09）——理解硬边界 + 软预警。自测：说清双层过滤的必要性（用"暴 力带空格"实验举例）。
  6. 第 6 步：串成体系——重读本文第四节架构总图，把 9 篇放回四个楼层。自测：向别人复述"迷你模型服务公司"的部门分工。
与 char01 / char02 汇总的衔接
