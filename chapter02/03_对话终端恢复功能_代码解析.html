03_对话终端恢复功能 - 代码讲解

位置：AI Agent Development Code/aiTest/char02 | 教学主题：持久化记忆与中断恢复 | 技术栈：dashscope function calling + JSON 文件持久化 | 已验证可运行（4 轮对话 + 重建恢复全部正确）

一、这段代码要做什么

实现一个带"断点续聊"功能的机票预订 Agent：用户聊到一半程序崩了 / 关了，重新启动后还能从上次断点继续——之前说的"5 月 5 日去上海、早上 8 点"这些信息不会丢。

核心教学点：持久化记忆（Persistent Memory）

char02 三篇的"记忆"逐层升级：
01 → memory 是 Python 变量（程序一停就没了）
02 → memory 还是变量 + 多轮传递（程序一停还是没了）
03 → memory 写到磁盘 JSON 文件（程序重启、换终端、隔一天再来，记忆都在）

二、原教材代码的问题

原代码有两类问题

第 1 类：虚构 API（和 01/02 相同）：qwen_agent.Agent / Tool / QwenLLM / BaseTool / CompletionConfig / BaseMemory 全部不存在。

第 2 类：好代码被框架绑死：PersistentJSONMemory 类的 load/save 逻辑本身是标准 Python（json 读写），完全正确——但它继承了虚构的 BaseMemory，导致整个类被"连坐"无法导入。改写时去掉继承、保留核心逻辑即可，这是三个文件里唯一"可救活"的组件。

四、核心概念速查表

概念代码中的实现一句话解释
持久化记忆PersistentJSONMemory 类把对话历史写到磁盘文件，程序重启后还能读回来
session_id"user_20250501"会话的唯一标识，决定读哪个 JSON 文件
load()启动时调，读 JSON → messages 列表中断恢复的"读"环节
save()每轮对话结束调，messages → 写 JSON持久化的"写"环节
落盘时机每轮 agent_chat 结束统一 save 一次不是每加一条消息就落盘（减少磁盘 IO）

五、逐段讲解（5 个代码块）

块 1：PersistentJSONMemory（第 27-48 行，本文件最值得保留的部分）

class PersistentJSONMemory:
    """自定义Memory：将上下文持久化至JSON文件，支持中断后恢复"""
    def __init__(self, session_id: str, path: str = "./memory"):
        os.makedirs(path, exist_ok=True)              # 目录不存在就建
        self.session_id = session_id
        self.memory_file = os.path.join(path, f"{session_id}.json")
        self.messages = self.load()                   # 启动即恢复

    def load(self):
        if os.path.exists(self.memory_file):
            with open(self.memory_file, "r", encoding="utf-8") as f:
                return json.load(f)                  # 从 JSON 恢复列表
        return []

    def save(self):
        with open(self.memory_file, "w", encoding="utf-8") as f:
            json.dump(self.messages, f, ensure_ascii=False, indent=2)  # 中文不转义
改写亮点：去掉继承，保留核心

原代码 class PersistentJSONMemory(BaseMemory) 继承了虚构的 BaseMemory。改写后去掉继承，但 load/save/add_message/get 四个方法原样保留——因为它们本来就是标准 Python，和框架无关。这是三个文件里唯一"救活"的组件。

块 3：build_agent（第 73-82 行）

def build_agent(session_id: str):
    config = {
        "name": "SessionRecoveryAgent",
        "model": "qwen-plus",
        "temperature": 0.3,
        "max_tokens": 512,
        "system_message": SYSTEM_MESSAGE
    }
    memory = PersistentJSONMemory(session_id=session_id)   # 同 ID → 恢复同一份记忆
    return config, memory

关键：同一个 session_id 两次调用 build_agent，拿到的 memory 对象指向同一个 JSON 文件。第二次 build 时 load() 自动恢复历史——这就是"中断恢复"的实现方式。

落盘时机：每轮对话结束统一 save 一次

原写法 add_message 每加一条消息就 save 一次（高频小 IO）。改写为每轮对话结束统一 save 一次（低频大 IO）。两种都正确，后者性能更好。生产环境可进一步改为"定时落盘 + 对话结束落盘"双保险。

块 5：simulate_session（第 123-152 行，演示中断恢复）

def simulate_session():
    session_id = "user_20250501"

    # 首次启动前先清旧文件（让演示可重复运行）
    memory_file = os.path.join("./memory", f"{session_id}.json")
    if os.path.exists(memory_file):
        os.remove(memory_file)

    agent_config, memory = build_agent(session_id)

    print(agent_chat(agent_config, "我想订一张5月5日去上海的机票", memory))
    print(agent_chat(agent_config, "时间大约是早上8点左右", memory))
    print(agent_chat(agent_config, "帮我记录这个需求", memory))

    print("\n模拟中断后重新启动...\n")

    # 关键：同一个 session_id → load() 从磁盘恢复全部历史
    agent_config2, memory2 = build_agent(session_id)

    print(agent_chat(agent_config2, "现在继续，出发地是北京", memory2))

脚本开头 os.remove(memory_file) 是为了让演示每次都从干净状态开始，否则第二次运行会把上次的对话也带上——持久化本身是对的，只是演示需要可控的起点。

八、持久化 vs 非持久化：为什么需要落盘

场景非持久化（01/02）持久化（03）
程序运行中多轮对话OK（变量在）OK
程序崩溃后重启失忆恢复
隔一天再来聊失忆恢复
换一台设备聊失忆需 JSON 文件同步到新设备
服务器重启失忆恢复

生产级 Agent（如 ChatGPT、讯飞星火）都有持久化记忆——用户关掉浏览器第二天打开，还能看到之前的对话。03 篇就是这个能力的最小实现。
