05_查询外部天气API - 代码讲解

位置：AI Agent Development Code/aiTest/char02 | 教学主题：调用 Web API 与插件机制 | 技术栈：dashscope function calling + wttr.in 免费天气 API | 已验证可运行（3 轮真实天气查询全部通过）

一、这段代码要做什么

实现一个天气查询 Agent：用户问"北京现在天气怎样"，模型自动决定调用 get_weather 工具，工具执行体里发起真实的 HTTP 请求访问 wttr.in 免费天气服务，拿到实时数据后回传给模型，模型再组织成自然语言回答。

char02 五篇收官篇：能力边界的突破

01-04 篇的工具都是本地函数（返回固定字符串或简单拼接），模型只是在"自导自演"。
05 篇是唯一一个工具执行体里有真实 HTTP 请求的——requests.get("https://wttr.in/{city}?format=j1") 访问的是互联网上的真实服务，返回的是实时天气数据。
这正是本篇标题"调用 Web API 与插件机制"的含义：智能体从"单一对话"跨越到"执行任务"。

四、核心概念速查表

概念代码中的实现一句话解释
Web API 调用requests.get("https://wttr.in/{city}?format=j1")工具执行体访问互联网上的真实服务
插件机制tools 说明书 + tool_registry 注册表新增能力 = 新增一个函数 + 一段说明书，即插即用
wttr.in免费天气 API，无需注册 Key教学友好的真实外部服务（生产环境可用高德/和风）
参数抽取arguments: '{"city": "北京"}'模型把"北京现在的天气"自动抽成 JSON 参数
超时与异常兜底timeout=5 + try/except外部服务不可靠，必须设超时和兜底返回

五、逐段讲解（4 个代码块）

块 1：get_weather 工具函数（第 27-55 行，本文件的灵魂）

def get_weather(city: str) -> str:
    """工具执行体：调用 wttr.in 接口获取城市天气"""
    city = city.strip()                    # 防御：去掉首尾空格
    if not city:
        return "请输入有效的城市名"          # 防御：空参数校验
    try:
        url = f"https://wttr.in/{city}?format=j1"
        resp = requests.get(url, timeout=5)     # timeout=5：外部服务必须设超时！
        if resp.status_code != 200:
            return f"查询失败，状态码：{resp.status_code}"   # HTTP 层错误兜底
        data = resp.json()
        current = data["current_condition"][0]
        temp = current["temp_C"]                # 温度（字符串 "27"）
        humidity = current["humidity"]          # 湿度
        desc = current["weatherDesc"][0]["value"]   # 天气描述
        return f"{city}当前天气：{desc}，温度：{temp}℃，湿度：{humidity}%"
    except Exception as e:
        return f"调用天气API出错：{str(e)}"       # 网络层异常兜底
这段函数是"生产级工具函数"的模板（四层防御）
  • 参数校验：strip + 空值判断（模型抽的参数不一定靠谱）
  • 超时控制：timeout=5（外部服务可能挂起，不设超时会卡死整个 Agent）
  • HTTP 错误兜底：status_code != 200 时返回明确错误信息（而不是崩掉）
  • 异常兜底：try/except 兜住网络超时、JSON 解析失败等一切异常

注意：错误也以字符串形式返回给模型（而不是抛异常），让模型能向用户解释"查询失败"——工具函数永不抛异常，是 Agent 工程的重要约定。

块 2：工具注册（第 58-72 行）

tool_registry = {"get_weather": get_weather}

tools = [
    {"type": "function", "function": {
        "name": "get_weather",
        "description": "获取指定城市的实时天气信息",
        "parameters": {"type": "object", "properties": {
            "city": {"type": "string", "description": "城市名称"}},
            "required": ["city"]}}
    }}
]

description 写得好坏直接影响模型会不会用这个工具——"获取指定城市的实时天气信息"比"查天气"信息量大，模型对何时调用、传什么参数的判断会更准。

块 3：agent_chat 循环（第 75-106 行）

同 02/03/04 篇的 while True 模式，无新知识点。唯一的差异是没有持久化——天气查询是无状态任务，不需要记住历史，每轮独立。

块 4：run_weather_query（第 109-126 行）

def run_weather_query():
    config = build_weather_agent()
    memory = None

    reply, memory = agent_chat(config, "请告诉我北京现在的天气", memory)
    print(">>", reply)
    reply, memory = agent_chat(config, "上海的天气怎么样？", memory)
    print(">>", reply)
    reply, memory = agent_chat(config, "请查询一下东京的当前温度和湿度", memory)
    print(">>", reply)

三轮查询覆盖三种问法：完整句 / 口语化短句 / 明确要两个字段——模型都能正确抽取 city 参数并发起调用。

六、真实运行输出（已验证）

>> 北京当前天气为烟雾霾（Smoky haze），气温为27℃，相对湿度为23%。
   空气较为干燥，建议注意补水，并关注空气质量，减少户外长时间活动。

>> 上海当前天气为局部有雨（Patchy rain nearby），气温25℃，相对湿度60%。
   建议外出携带雨具，注意道路湿滑...

>> 东京当前天气晴朗（Sunny），气温为26℃，相对湿度为34%。
   空气较为干燥，阳光充足，适宜户外活动...
观察两个关键现象
  • 数据是实时的：温度湿度是 wttr.in 当时返回的真实值，不是模型编的（模型的训练数据里不可能有"今天的北京天气"）
  • 模型会"加戏"：工具只返回了天气数据，但模型的回答里多了"建议补水""携带雨具"等建议——这是 LLM 在工具结果之上的增值，也是 Agent 比 API 强的地方

八、外部 API 工具的工程化增强方向

当前实现（教学版）生产版增强为什么
同步 requests.get异步 aiohttp / 连接池复用多用户并发查询时同步会阻塞

九、动手练习

  1. 换城市试试：把三轮查询的城市换成广州、深圳、成都，观察模型抽参和 API 返回。
  2. 破坏实验（超时）：把 timeout=5 改成 timeout=0.001，运行——几乎所有请求都超时，观察 try/except 兜底如何让 Agent 优雅报错而不是崩掉。
  3. 破坏实验（断网）：断开网络运行，观察 ConnectionError 被兜底成"调用天气API出错：..."返回给模型，模型向用户解释。
  4. 加第二个工具：新增 get_time(city) 工具（用 wttr.in 返回里的 localObsDateTime 字段），看模型能否根据用户问题在两个工具间正确选择。
  5. 思考题：如果用户问"北京和上海哪个更热"，模型需要调几次工具？为什么？（提示：get_weather 一次只查一个城市，模型需要两次调用后对比——这正是 while True 循环的价值）
