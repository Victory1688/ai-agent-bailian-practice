08_基于FastAPI的UI中间API接口系统 - 代码讲解

位置：AI Agent Development Code/aiTest/char02 | 教学主题：把 Agent 封装成 HTTP 服务（UI 中间 API） | 技术栈：dashscope function calling + FastAPI / Pydantic / uvicorn | 已验证可运行（uvicorn 启动 + GET / + POST /chat 真实调用成功）

一、这段代码要做什么

把记账 Agent 从"命令行脚本"升级成HTTP 网络服务：用户说"刚刚买菜花了20元"，这个请求不再来自 input()，而是来自一条 HTTP POST 请求；Agent 的回答也不再 print，而是以 JSON 返回给调用方。从此任何能发 HTTP 请求的东西——网页、App、小程序、curl——都能调用这个智能体。"UI 中间 API"的含义就是：它是夹在前端界面和智能体之间的中间层。

三段式架构：UI ↔ 中间 API ↔ 智能体
前端 UI（网页/App）          中间 API 层（本文件）            智能体
┌────────────┐   HTTP    ┌──────────────────┐   函数调用   ┌─────────────┐
│ 聊天窗口/表单 │ ───────→ │ FastAPI 路由+校验  │ ─────────→ │ dashscope    │
│ 显示回复     │ ←─────── │ Pydantic 模型+CORS │ ←───────── │ + add_record │
└────────────┘   JSON    └──────────────────┘   返回文本   └─────────────┘

为什么中间要垫一层 API，而不是前端直接调大模型？API Key 不能暴露在前端、业务逻辑（工具、数据库）在服务端、且前端换壳（网页换 App）时服务端不用改——这是真实项目的标准分层。

五、逐段讲解（4 个代码块）

块 1：Pydantic 请求/响应模型（API 的"合同"）

class ChatRequest(BaseModel):      # 前端必须按这个格式发请求
    session_id: str                # 会话标识（本篇预留，暂未使用——见下文）
    message: str                   # 用户说的一句话

class ChatResponse(BaseModel):     # 服务端承诺按这个格式回响应
    session_id: str
    reply: str                     # Agent 的最终回答
类型校验的价值：把错误挡在业务逻辑之前

如果调用方漏发 message 或把 message 发成数字，Pydantic 在进函数前就返回 422 错误并附明细——chat_with_agent 里一行校验代码都不用写。前端同学拿到这份模型定义，就知道该怎么对接，这就是"合同"。

块 2：add_record 工具（唯一的新工具，逻辑最简单）

def add_record(category: str, amount: str) -> str:
    """工具执行体：记录一笔消费信息（原 AddRecordTool.run 逻辑全部保留）"""
    return f"已记录消费：{category} - {amount}元"

tool_registry = {"add_record": add_record}
tools = [{"type": "function", "function": {
    "name": "add_record",
    "description": "记录一笔消费信息",
    "parameters": {"type": "object", "properties": {
        "category": {"type": "string", "description": "消费类别"},
        "amount": {"type": "string", "description": "金额（单位：元）"}
    }, "required": ["category", "amount"]}
}}]

注意模型干了什么：用户输入"刚刚买菜花了20元"是一句自由文本，模型自己抽出 category="买菜"、amount="20元" 填进参数。真实业务里这里会接 06 篇的 sqlite3 写库——本篇用字符串返回保持教学聚焦。

块 3：FastAPI 应用 + CORS 中间件

app = FastAPI()
agent_config = build_agent()       # 原写法 agent_instance = build_agent()

# CORS 允许跨域（用于网页调用）
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],           # 任何网站都可以调（教学方便；生产要收紧）
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"]
)

CORS 解决什么问题？浏览器默认禁止"网页 A 的 JS 去请求网站 B 的接口"（同源策略）。没有这段中间件，本地 HTML 页面里的 fetch("http://localhost:8080/chat") 会被浏览器拦下。加了它，网页前端才能直连这个 API。

块 4：两个路由 + Agent 接线

@app.get("/")
def index():
    return {"message": "Agent API 运行中"}        # 健康检查接口

@app.post("/chat", response_model=ChatResponse)
def chat_with_agent(req: ChatRequest):
    # 原写法：reply = agent_instance.chat(req.message)   ← 虚构框架黑盒
    # 改写：调 agent_chat 循环（返回的 memory 本篇暂不使用）
    reply, _memory = agent_chat(agent_config, req.message)
    return ChatResponse(session_id=req.session_id, reply=reply)
教学留白：session_id 收了却没用

请求里带着 session_id，但原代码（和改写版）都没用它做记忆——每次 POST 都是一次全新对话，Agent 不记得这个 session 上一句说过什么。这是无状态服务的典型样子，也是教材故意留的练习：怎么结合 03 篇的 PersistentJSONMemory 让同一 session_id 的多轮请求共享记忆？（见第九节练习 1）

八、工程化方向：从"能跑的演示"到"能上的服务"还差四件事

  • 1. 会话记忆：session_id 收了没用，每次请求都是失忆的。生产做法：服务端维护 dict[session_id, memory]（或落盘成 03 篇的 JSON 文件），同一会话的多轮请求共享上下文，并加过期清理防止内存膨胀。
  • 2. 收紧 CORS：allow_origins=["*"] 等于大门全开。生产改成具体域名白名单（如 ["https://myapp.example.com"]）。
  • 3. 鉴权与限流：现在任何知道地址的人都能白嫖你的大模型额度。生产要加 API Key / 登录态校验 + 请求频率限制（如每 session 每分钟 N 次）。
  • 4. 部署形态：--reload 只用于开发；生产用 --workers 4 多进程、Nginx 反向代理 + HTTPS、容器化部署；DASHSCOPE_API_KEY 通过环境变量注入（本篇已做到，不要写死在代码里）。
隐藏福利：自动生成的交互式 API 文档

FastAPI 会根据 Pydantic 模型自动生成两套文档：服务运行时打开 http://localhost:8080/docs（Swagger UI）或 /redoc，可以直接在网页上填参数、发请求、看响应——不用写任何文档代码。这就是"Pydantic 是合同"的另一半价值：合同同时生成了说明书。
