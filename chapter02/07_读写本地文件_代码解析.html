一、这段代码要做什么

实现一个文件与代码执行 Agent：用户用自然语言说"把这段话写进 test.txt"，模型自动调用 write_file 工具——工具执行体里用 open(path, "w", encoding="utf-8") 把内容真的写到磁盘上；说"读取 test.txt"，模型调用 read_file 把文件内容读回来；说"运行 a = 5、b = 3、c = a * b"，模型调用 exec_code 工具，exec() 动态执行这段代码并把变量结果返回。智能体第一次拥有了直接操作本地世界（文件 + 代码）的双手。

二、原教材代码的问题

两类问题（同 char02 前 6 篇）

第 1 类：虚构 API：qwen_agent.Agent / Tool / QwenLLM / BaseTool / CompletionConfig 全部不存在，运行第一行 import 就报 ImportError。

第 2 类：好代码被框架绑死：三个工具类 run() 方法里的核心逻辑——文件存在性检查（os.path.exists）、带编码的文件读写（open(..., encoding="utf-8")）、动态执行与异常截取（exec(code, {}, local_vars) + traceback.format_exc(limit=2)）——完全正确，都是 Python 标准库的标准用法，和任何框架无关。改写时把 run() 函数体原样搬进普通函数，一个字符都没改。

  │           os.path.exists → True

  │
  └─ 第 3 轮: "请运行如下代码：a = 5\nb = 3\nc = a * b"
        │

第 3 轮隐藏的难点：参数抽取

注意用户消息是自然语言 + 多行代码混在一起的。模型必须自己从句子里"剥离"出纯代码部分（去掉"请运行如下代码："前缀），再以 JSON 字符串形式填进 arguments。这就是 function calling 的参数抽取能力——也是为什么要给工具写清晰的 description 和 parameters 说明。

四、核心概念速查表

概念代码中的实现一句话解释
写文件open(path, "w", encoding="utf-8")"w" 模式：文件不存在则创建，存在则整个覆盖
读文件open(path, "r", encoding="utf-8") + f.read()一次读出全部内容为字符串
存在性检查os.path.exists(path)读之前先检查，不存在的文件直接返回友好提示而非报错
显式编码encoding="utf-8"Windows 教学重点：不写的话默认 GBK，中文读写可能乱码
动态执行exec(code, {}, local_vars)把字符串当代码跑；第 2、3 个参数决定变量被收集到哪个字典
异常截取traceback.format_exc(limit=2)只取堆栈最后 2 层，错误信息精简地返回给模型（不抛出、不刷屏）

五、逐段讲解（4 个代码块）

块 1：三个工具函数（本文件的教学核心）

def read_file(filepath: str) -> str:
    if not os.path.exists(filepath):        # 先检查再读，给模型友好提示
        return f"文件不存在：{filepath}"
    try:
        with open(filepath, "r", encoding="utf-8") as f:
            return f.read()                 # 读到的内容整个返回给模型
    except Exception as e:
        return f"读取失败：{str(e)}"         # 错误也返回字符串，不抛异常

def write_file(filepath: str, content: str) -> str:
    try:
        with open(filepath, "w", encoding="utf-8") as f:
            f.write(content)                # 内容真的落盘
        return f"内容已成功写入文件：{filepath}"
    except Exception as e:
        return f"写入失败：{str(e)}"

def exec_code(code: str) -> str:
    try:
        local_vars = {}
        exec(code, {}, local_vars)          # 动态执行，变量收集到 local_vars
        return "执行成功，输出变量：" + str(local_vars)
    except Exception:
        return "执行出错：" + traceback.format_exc(limit=2)
延续系列原则：工具函数永不抛异常

三个工具全部用 try/except 把错误转成字符串返回。模型收到"读取失败：xxx"这样的文字后，可以自己决定向用户解释或换个方式重试。如果工具直接抛异常，Agent 循环会整个崩掉，模型就失去了"纠错机会"。

块 2：exec 的工作机制（为什么变量出现在 local_vars 里）

local_vars = {}
exec(code, {}, local_vars)
# exec 的三个参数：
#   第 1 个：要执行的代码字符串，如 "a = 5\nb = 3\nc = a * b"
#   第 2 个：globals 字典（这里传空 dict）
#   第 3 个：locals 字典（这里传 local_vars）
# exec 执行赋值语句时，变量 a、b、c 会写进第 3 个参数的字典：
#   local_vars == {'a': 5, 'b': 3, 'c': 15}
# 把 local_vars 转成字符串返回 → 模型"看得见"代码算出了什么

这是"给模型开一只眼睛"的经典手法：代码在本地真实执行，执行产生的可观察结果以文本形式回流给模型，模型再组织成人类能读的回答。

块 3：工具说明书 tools + 注册表 tool_registry（三工具版）

tool_registry = {
    "read_file": read_file,
    "write_file": write_file,
    "exec_code": exec_code,
}

tools = [
    {"type": "function", "function": {
        "name": "read_file",
        "description": "读取指定文件内容",
        "parameters": {"type": "object", "properties": {
            "filepath": {"type": "string", "description": "文件路径"}
        }, "required": ["filepath"]}
    }},
    # write_file：required 含 filepath 和 content 两项
    # exec_code：required 只含 code 一项
]
从单工具到多工具，模型多了"选哪个"的决策

01 篇只有 2 个零参工具、06 篇 2 个数据库工具，本篇 3 个工具且职责完全不同（读/写/执行）。模型每轮要独立判断该调哪个工具、传什么参数——这就是"决策权在模型，执行权在本地"的完整形态。registry 里"函数名 → 函数对象"的映射保证模型选中的名字能找到真正的执行体。

块 4：agent_chat 循环 + run_demo 演示流程

def agent_chat(config, user_input, memory=None):
    if memory is None:                          # 首轮注入 system 提示词
        memory = [{"role": "system", "content": config["system_message"]}]
    memory = memory + [{"role": "user", "content": user_input}]
    while True:                                 # 工具调用可能多轮，循环到模型给出最终回答
        response = dashscope.Generation.call(
            model=config["model"], messages=memory, tools=tools,
            temperature=config["temperature"], max_tokens=config["max_tokens"],
            result_format='message')
        message = response.output.choices[0].message
        tool_calls = getattr(message, 'tool_calls', None)
        if not tool_calls:                      # 无工具调用 → 最终回答
            ...
        # 有工具调用 → 查 registry 执行 → role="tool" 回传 → 继续循环

def run_demo():
    if os.path.exists("test.txt"):              # 演示可重复：先删掉上次的文件
        os.remove("test.txt")
    config = build_agent()
    memory = None
    reply, memory = agent_chat(config, "请将以下内容写入文件test.txt：你好，这是智能体写入的内容", memory)
    print(">>", reply)
    reply, memory = agent_chat(config, "读取文件test.txt中的内容", memory)      # memory 跨轮传递
    print(">>", reply)
    reply, memory = agent_chat(config, "请运行如下代码：a = 5\nb = 3\nc = a * b", memory)
    print(">>", reply)

八、安全警示：exec 是"最危险的工具"

为什么这么说

exec() 可以执行任意 Python 代码——包括删文件、读敏感信息、发起网络请求。假如模型被提示词注入（用户诱导它"帮我清理磁盘"），它可能生成并执行 os.system('rd /s /q D:\\') 这样的代码。原教材在工具描述里写了"仅限受控环境"，就是在提醒这一点——但"受控"二字在真实工程里要靠机制保证，不能靠自觉。

生产环境的正确姿势（教学版 exec 的四条升级路）
  • 沙箱隔离：把 exec 换成"子进程 + 资源限制"（超时杀进程、限内存、限网络），最彻底的是跑在 Docker 容器里——炸了也只炸容器
  • 代码白名单检查：执行前用 ast.parse 解析代码，禁止 import 危险模块（os / sys / subprocess / socket）
  • 文件路径白名单：read/write 工具应限制只能操作指定工作目录内的文件，防止模型读写 C:\Users\...\ 等敏感路径（目录穿越攻击）
  • 最小权限：Agent 进程用低权限账号运行，天然读不到高权限文件

类比：05 篇的天气工具像"只准递纸条给前台"；06 篇像"只准往一个抽屉里放纸"；本篇 exec 像"把整栋楼的万能钥匙交给访客"——方便，但得先装门禁（沙箱）。

  1. 防覆盖写入：给 write_file 增加保护——若文件已存在则不写入，返回"文件已存在，请先确认"。提示：用 os.path.exists（参考 read_file 的写法）。
