位置：AI Agent Development Code/aiTest/char02 | 教学主题：对话状态追踪（State Tracking） | 技术栈：dashscope function calling | 已验证可运行（4 轮对话全部正确）

一、这段代码要做什么

实现一个会议助手 Agent：用户用 4 轮自然语言对话，逐步把"会议主题 → 时间 → 与会人员"三项信息设置好，最后让 Agent 总结。代码要演示的核心概念是——

对话状态追踪（State Tracking）

智能体在多轮交互中保持"记忆"和"逻辑"的机制：跟踪任务进度、存储中间变量，确保交互的连贯性。通俗类比：填一张登记表——用户每次说的信息，Agent 都要记到表里；用户最后问"填了啥"，Agent 照着表答。

二、原教材代码的问题（为什么必须改写）

原代码使用的是虚构 API，无法运行

原文件导入的 qwen_agent.Agent / Tool / ChatMessage / QwenLLM / SimpleMemory / CompletionConfig / BaseTool 在真实的 qwen-agent 包里全部不存在（已实测 ImportError）。教材（或 AI 生成的教材）臆造了一套不存在的框架 API。

四、核心概念速查表

概念代码中的实现作用
任务状态（State）task_state = {"topic": None, "time": None, "attendees": None}跨轮存储中间变量的字典，工具执行时写入
对话记忆（Memory）memory 消息列表，每轮 agent_chat(..., memory) 传入传出让模型"记得"之前聊过什么（对话连贯性）
工具说明书tools 列表（type/name/description/parameters）告诉模型有哪些工具可调、参数长什么样
工具注册表tool_registry = {"set_topic": set_topic, ...}函数名 → 执行体。模型只发"指令"，本地负责执行
Agent 循环while True + tool_calls 判断模型可以连续调工具，直到它认为信息足够才给最终回答

五、逐段讲解

5.1 状态字典（第 27-28 行附近）

# 原写法用 SimpleMemory() 存状态；改写为显式的 task_state 字典——
# 工具执行时把信息写进来，这就是状态追踪
task_state = {"topic": None, "time": None, "attendees": None}

三个键对应会议登记表的三栏，初始都是 None。运行时你会看到它们被逐轮填充：None → AI发展 → 5月3号上午10点 → 张三、李四、王五。

5.2 三个工具（函数 + 说明书 + 注册表）

def set_topic(topic: str) -> str:
    """工具1执行体：设置会议主题，并写入任务状态"""
    task_state["topic"] = topic          # 关键：执行的同时写状态
    return f"会议主题已设置为：{topic}"    # 回传给模型的结果

注意与 char02/01 的差异：01 的工具无参数，本例的工具带参数。所以模型返回的 arguments 是一段 JSON 字符串，需要解析：

fn_args = json.loads(call['function'].get('arguments') or '{}')
tool_result = fn(**fn_args)     # 例如 fn(topic='AI发展')

tools 说明书里每个工具都声明了 required: ["topic"] 等必填项，模型据此知道传什么参数。

5.3 Agent 循环（本文件的灵魂）

while True:
    response = dashscope.Generation.call(model, messages=memory, tools=tools, ...)
    message = response.output.choices[0].message
    tool_calls = getattr(message, 'tool_calls', None)

    if not tool_calls:                       # 模型不再要工具 → 给出最终回答
        return message.content, memory + [...]

    memory = memory + [message]              # 记住"模型想调工具"这一步
    for call in tool_calls:
        fn_name = call['function']['name']   # 注意：dashscope 返回 dict，用字典取值
        fn_args = json.loads(call['function'].get('arguments') or '{}')
        tool_result = fn(**fn_args)          # 本地执行
        memory = memory + [{"role": "tool", "content": tool_result, ...}]   # 结果回传
为什么是 while True 而不是 if？

模型可能连续调用多个工具（比如一句话里同时给主题和时间）。循环让模型每次调完工具、看到结果后，自己决定"继续调"还是"回答"。这就是 Agent 与普通对话程序的本质区别：决策权在模型，执行权在本地。

5.4 多轮对话的记忆传递

reply, memory = agent_chat("我要安排一个关于AI发展的会议", memory)   # 首轮，memory=None
reply, memory = agent_chat("会议时间定在5月3号上午10点", memory)      # 带上上一轮的 memory
reply, memory = agent_chat("参加人包括张三、李四和王五", memory)
reply, memory = agent_chat("请总结一下目前的会议信息", memory)

每一轮都把更新后的 memory 传给下一轮——第 4 轮模型能总结出全部信息，靠的就是前三轮的消息全在 memory 里。删掉这个参数传递，模型就会"失忆"。

观察三个关键现象
  • 状态逐轮填充：task_state 从全 None 到三项就位，每轮打印可见
  • 模型自动提参数："5月3号上午10点" 这句自然语言被模型自动抽成 JSON 参数传给工具
  • 第 4 轮不调工具：模型判断信息已全，直接总结——Agent 循环的"自主决策"体现

七、两个"记忆"的分工（新人最容易混淆）

维度memory（消息列表）task_state（状态字典）
存什么完整对话历史（system/user/assistant/tool 全部消息）结构化的业务数据（主题/时间/人员）
给谁用给模型看（作为上下文输入）给程序逻辑用（可校验、可落库、可回显）
会膨胀吗会，随轮次线性增长（长对话需裁剪/摘要）不会，固定三个键
类比聊天记录登记表

生产级 Agent 里，两者都存在：memory 管对话连贯，state 管业务进度（如订票系统的"已选出发地/目的地/日期"）。

八、动手练习

  1. 破坏实验：把 agent_chat("会议时间定在...", memory) 的 memory 参数删掉，看第 3、4 轮模型是否"失忆"——体会记忆注入的作用。
  2. 加一个工具：新增 set_location(location) 工具（会议室地点），补全注册表和 tools 说明书，看模型能否自动用上。
  3. 打印 messages：在第 4 轮前把整个 memory 打印出来，数一数共有多少条消息、各自 role 是什么。
  4. 状态校验：增加一个 confirm_meeting() 工具，只有 task_state 三项都非 None 才返回成功，否则返回缺项提示——模拟真实业务的表单校验。
  5. 思考题：如果对话有 50 轮，memory 会非常大。查一下"对话历史裁剪 / 滑动窗口 / 摘要压缩"，想想哪种适合本例。
