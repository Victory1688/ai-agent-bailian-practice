一、这组代码到底想表达什么

char02 的教学主题是"智能体系统的组成结构与运行机制"。8 篇代码合起来回答一个问题：一个只会生成文字的大模型，是怎么一步步变成"能听懂任务、会调用工具、能记住历史、敢操作真实世界、最终作为一个服务被前端调用"的智能体的？

一句话概括每篇
  • 01 启动：把大模型 + 工具 + 系统提示词拼成最小可用 Agent（骨架）
  • 02 状态：工具执行的结果不止"说出口"，还要落到结构化状态字典里（会办事）
  • 03 恢复：对话历史写进 JSON 文件，程序重启后接着聊（会记忆）
  • 04 注销：任务结束时把资源干干净净释放掉（会收尾）
  • 05 联网：工具执行体里发起真实 HTTP 请求，突破模型知识边界（会联网）
  • 06 落库：工具执行体里读写 SQLite，数据结构化持久（会改数据库）
  • 07 本地世界：读写任意文件 + 动态执行 Python 代码（能力最强、风险最高）
  • 08 服务化：套上 FastAPI，智能体变成任何前端都能调的 HTTP 接口（交付形态）

二、大模型应用开发架构总图（8 篇文件各自落在哪一层）

任何一个生产级大模型应用，都可以拆成下面六层。char02 的 8 篇正好由内向外逐层点亮这张图：

┌─────────────────────────────────────────────────────────────────┐
│  交互交付层  08: FastAPI HTTP 接口 ← 网页/App/小程序/curl 都从这里进来  │
├─────────────────────────────────────────────────────────────────┤
│  编排决策层  01/02: agent_chat 循环 —— 模型决定"调哪个工具、传什么参"   │
│             决策权在模型，执行权在本地（Function Calling 核心）         │
├─────────────────────────────────────────────────────────────────┤
│  记忆状态层  02: 状态字典 │ 03: JSON 持久化 │ 04: 注销清理              │
├─────────────────────────────────────────────────────────────────┤
│  能力工具层  工具执行体（每篇的"变"量所在）：                          │
│             01 自检/时间 → 05 HTTP API → 06 SQLite → 07 文件/exec      │
├─────────────────────────────────────────────────────────────────┤
│  模型服务层  dashscope.Generation.call（阿里百炼 qwen-plus）           │
│             所有篇共用，API Key 走环境变量                              │
├─────────────────────────────────────────────────────────────────┤
│  存储介质层  Python 变量 → JSON 文件 → SQLite 数据库 → 任意本地文件     │
└─────────────────────────────────────────────────────────────────┘

读图要点：模型服务层从头到尾没变过（都是同一个 dashscope 调用）；变的是能力工具层（每篇换一种"手"）和记忆状态层（每篇加一层"记性"），最后用交互交付层把这一切暴露给外部世界。这就是大模型应用开发的分层本质：模型是稳定的内核，能力是可插拔的外设，服务是交付的出口。

四、统一代码骨架：8 篇"变与不变"的架构秘密

把 8 个文件叠在一起看，会发现80% 的代码一模一样。这不是巧合，而是本组课件最想传递的架构思想：

不变的骨架（每篇都有，照抄即可）
# 1. 环境配置：API Key 永远走环境变量，不写死在代码里
api_key = os.environ.get('DASHSCOPE_API_KEY')
dashscope.api_key = api_key

# 2. 工具三件套：执行体 + 注册表 + 说明书
def some_tool(arg: str) -> str: ...          # 执行体：普通函数，永不抛异常
tool_registry = {"some_tool": some_tool}     # 注册表：函数名 → 函数对象
tools = [{"type": "function", "function": {  # 说明书：给模型看的"合同"
    "name": ..., "description": ..., "parameters": {...}}}]

# 3. Agent 循环（编排核心，决策权在模型）
while True:
    response = dashscope.Generation.call(model=..., messages=memory,
        tools=tools, temperature=..., max_tokens=..., result_format='message')
    message = response.output.choices[0].message
    tool_calls = getattr(message, 'tool_calls', None)
    if not tool_calls:                       # 模型不再要工具 → 最终回答
        return message.content, memory
    memory = memory + [message]              # 记下"模型要调工具"这件事
    for call in tool_calls:                  # 本地执行 → role="tool" 回传
        fn = tool_registry[call['function']['name']]
        result = fn(**json.loads(call['function']['arguments']))
        memory = memory + [{"role": "tool", "content": result, ...}]
变的只有一处：工具执行体（以及记忆怎么存）
  • 02：执行体更新一个 task_state 字典
  • 05：执行体发 HTTP 请求
  • 06：执行体跑 SQL
  • 07：执行体操作文件 / 跑 exec
  • 03/04：不动工具，改"记忆怎么存怎么删"
  • 08：不动 Agent，改"从哪进从哪出"（input/print → HTTP）

结论（新人请记住这句话）：大模型应用开发 = 一套固定编排骨架 + 一批可插拔的工具执行体。学会骨架只需要一遍，之后的全部工作是把业务能力封装成"永不抛异常、返回字符串"的工具函数。

七、教学简化 vs 生产差距（诚实的风险地图）

这套教学代码离生产还差的距离
  • 无鉴权限流（08）：接口全开放，任何人可消耗你的大模型额度
  • CORS 全开（08）：allow_origins=["*"] 仅限教学
  • exec 无沙箱（07）：任意代码执行必须换成子进程/容器隔离 + AST 白名单
  • 文件路径未限制（07）：应限制在工作目录内，防目录穿越
  • 会话记忆在内存（08）：服务重启即失忆，多 worker 部署时 dict 不共享
  • 无重试与限流保护：dashscope 调用没有处理 429/超时重试
  • 记账工具是假的（08）：返回字符串而已，应接 06 的 SQLite
但骨架是生产级的

上述差距全部是"工具执行体"和"服务配置"层面的缺口，编排骨架（Agent 循环 / 三件套 / 记忆机制）本身就是真实项目的标准形态。从教学到产品，补的是外围工程，不是推翻重学。

八、新人学习路径建议

  1. 第 1 步（读懂骨架）：精读 01，对照"_代码解析.html"把 agent_chat 循环每一行讲给自己听。自测：能白板写出"模型返回 tool_calls 之后发生了什么"。
  2. 第 2 步（动手换工具）：跑通 02 和 05，然后自己写一个新工具（如"查询现在星期几"）加入注册表。自测：理解说明书、注册表、执行体三者关系。
  3. 第 3 步（加上记忆）：跑通 03 / 04，观察 memory 目录下 JSON 文件的生成与删除。自测：说清"内存记忆、持久记忆、注销清理"三种状态。
  4. 第 4 步（接真实世界）：跑通 06 / 07，体会"工具的副作用"越来越大，同时理解参数化 SQL 和 exec 风险两处安全设计。自测：能列出 07 的四条生产升级路。
  5. 第 5 步（交付成服务）：启动 08，用浏览器打开 /docs 发请求，再用练习补上 session_id 会话记忆。自测：画出"前端 → FastAPI → Agent → 工具 → 响应"全链路图。
  6. 第 6 步（综合验收）：完成 08 的练习 2——把 add_record 接上 SQLite 并新增 GET /records 接口。做完这一题，等于把 01-08 串成了一个真实的小产品。
