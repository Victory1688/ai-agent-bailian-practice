04_langchain的Memory使用 - 代码解析

对应文件：char08/04_langchain的Memory使用.py | 教材出处：第8章 单智能体系统构建实战 例8-4 | 环境实测：LangChain 1.3.18 + langchain_classic + ConversationBufferWindowMemory(k=3) + qwen-plus | 生成日期：2026-10-12

一、这份代码整体在做什么（一段话讲给新人）

本篇是 char08 第四篇——正式引入 LangChain 的 Memory 机制。前 01-03 篇的"记忆"全是手写的（history 列表、status 字段），本篇用 LangChain 提供的标准 Memory 组件 ConversationBufferWindowMemory(k=3) 来管理多轮对话历史：只保留最近 3 轮（6 条 message），老的自动从窗口视图里消失。核心循环是"取历史 → 拼 prompt → 调 LLM → 回写 memory"，这和 char04-03 的 BufferMemory 是同一家族，但用 LangChain 框架组件替代了手写实现。

二、LangChain Memory 三种类型速查表（教材重点）

类型存储策略适用场景截断触发
ConversationBufferMemory全量存储不截断短对话 / 对完整历史有强依赖永不截断 → Token 预算会爆
ConversationBufferWindowMemory（本篇）只保留最近 k 轮长对话 / Token 预算有限（最常用）每次 load_memory_variables 时窗口截断
ConversationSummaryMemoryLLM 摘要压缩存储超长对话 / 历史信息密度低超过阈值后让 LLM 写摘要替换旧消息
三种 Memory 的核心 trade-off

Buffer：不丢信息但 Token 线性增长 → 适合只聊 2-3 轮就结束的场景。

Window：只留最近 k 轮，老信息直接丢弃 → 适合长对话但用户意图主要在最近几轮的场景。这是本篇的选择，也是生产中最常用的类型。

Summary：让 LLM 把旧历史压缩成一段摘要 → 适合超长对话且需要保留历史"大意"的场景，但摘要本身需要额外 LLM 调用（成本翻倍）。

四、逐段代码讲解

4.1 ConversationBufferWindowMemory(k=3, return_messages=True)：两个关键参数

memory = ConversationBufferWindowMemory(k=3, return_messages=True)
  • k=3：只保留最近 3 轮对话（1 轮 = 1 user + 1 AI = 2 条 message），窗口上限 6 条
  • return_messages=True：让 load_memory_variables({})['history'] 返回 AIMessage/HumanMessage 对象列表；如果是 False（默认），返回拼接的字符串

4.2 窗口截断的"两视图"设计（核心认知）

ConversationBufferWindowMemory 有两个视图，这是理解其行为的关键：

# 视图 A：原始存储（chat_memory.messages）
# —— 永远累积全部消息，永不截断
# —— 直接访问会绕开 k 窗口！（原代码的 bug）
len(memory.chat_memory.messages)  # 4 轮后 = 8 条（全量）

# 视图 B：窗口视图（load_memory_variables({})['history']）
# —— 只返回最近 k 轮，自动截断
len(memory.load_memory_variables({})['history'])  # 4 轮后 = 6 条（窗口）

这不是"先存后删"的物理截断，而是"先存后滤"的读时过滤。chat_memory 永远满的，load_memory_variables 在读取时做窗口裁剪。好处是存储逻辑极简（只管追加），坏处是内存占用随对话轮次线性增长（实际生产中如果对话很长，需要物理清理）。

4.3 ask() 的四步循环（LangChain Memory 的标准用法）

def ask(self, user_input):
    # 1. 取窗口视图（不是 chat_memory.messages！）
    windowed = self.memory.load_memory_variables({})['history']
    
    # 2. 拼 prompt + 调 LLM
    response = dashscope.Generation.call(qwen-plus, ...)
    
    # 3. 回写 memory（原始存储）
    self.memory.chat_memory.add_user_message(user_input)
    self.memory.chat_memory.add_ai_message(result_content)
    
    return response

这是 LangChain Memory 的标准使用模式——即使不通过 ConversationChain 框架直接用，也应该遵循这个四步循环。原代码的 bug 是把第 1 步写成了 chat_memory.messages，绕开了窗口视图，导致 k 参数形同虚设。

4.4 FakeDataFetcher：注册了但从未调用（死代码谱系）

原代码在 LangChainQwenAgent.__init__ 里初始化了 FakeDataFetcher()，并注册给虚构的 qwen_agent.Agent，但 ask() 方法里从未显式调用它——LLM 回答完全靠自己的预训练知识。这是 char07-03/04 路由死代码谱系的延伸：

篇死代码根因

char07-04hybrid 路由分支if/elif 顺序截胡
char08-04（本篇）FakeDataFetcher 工具注册了但从没被调用

五、实测数据：窗口截断真的生效了吗？

修复后实测：原始存储 vs 窗口视图（Round 4 时 Round 1 被裁掉）
[Round 1]  用户:2022年GDP → AI → 原始存储 2 | 窗口视图 2 ✓
[Round 2]  用户:那2023年呢 → AI → 原始存储 4 | 窗口视图 4 ✓
[Round 3]  用户:2024年增长更快？ → AI → 原始存储 6 | 窗口视图 6 ✓ (k*2=6 到上限)
[Round 4]  用户:依据是什么？ → AI → 原始存储 8 | 窗口视图 6 ✓ (Round 1 被窗口裁掉!)

4 轮设计是故意的：k=3 意味着 Round 4 时窗口只能看到 Rounds 2+3+4（6 条），Round 1 的"2022年GDP"查询和回答从窗口视图中消失。这正是"窗口存储"的本质——只关注最近几轮的上下文。

原代码的 bug：chat_memory.messages 绕开了窗口截断

修复前运行（直接访问 chat_memory.messages）：

[Round 4]  原始存储 8 | 窗口视图 8 ✗（k 参数完全失效！）

修复后运行（用 load_memory_variables）：

[Round 4]  原始存储 8 | 窗口视图 6 ✓（k=3 真正生效）

这个 bug 是 LangChain Memory 的经典陷阱——很多人以为 chat_memory.messages 就是窗口化后的结果，其实不是。chat_memory 永远是全量累积，窗口截断只在 load_memory_variables 时发生。如果手动读 chat_memory.messages，就等于绕过了整个窗口机制。

LangChain 正在废弃这套 Memory 类

运行时会看到 deprecation 警告：

ConversationBufferWindowMemory was deprecated in LangChain 0.3.1 and will be removed in 2.0.0.
Use langchain.agents.create_agent instead.

LangChain 2.0 方向是：把 Memory 的能力内置到 Agent 框架（checkpoint 持久化 + Store 长期记忆），不再推荐手动使用 ConversationBufferWindowMemory 这类 Memory 类。本篇作为教学代码保留，但生产新项目应直接用 LangGraph 的 checkpoint 机制。

LangChain Memory 组件只帮你解决"怎么存"的问题，不解决"怎么用"的问题——prompt 拼接、回写时机、窗口参数，全部还是要自己管。这和 LangChain 的 Chain/Agent 框架不同（框架帮你管了全部），也是本篇选择手动四步循环而非 ConversationChain 的原因：手动模式更透明，教学时每一步都看得见。

七、架构视角：对话记忆的三种技术路线

路线代表截断策略Token 成本信息损失
全量存储char04-03 BufferMemory永不截断线性增长无（但迟早爆）
窗口截断本篇 WindowMemory(k=3)只读最近 k 轮固定上限老轮次完全丢弃
摘要压缩ConversationSummaryMemoryLLM 写摘要替换旧消息固定 + 额外摘要成本老轮次只留大意
语义检索char06 RAG + char07-07 动态合并按相似度选 Top-K 条固定上限低（语义保留）

第四行（语义检索）是 char07 系列的路线——把对话历史当"检索语料库"，每次按当前问题的语义相似度挑最相关的几条注入 prompt，比窗口截断更聪明。生产级 Agent 的记忆通常是窗口截断 + 语义检索的组合：窗口截断做粗筛（砍掉超老的轮次），语义检索做精选（从剩余里挑最相关的）。

九、动手练习（巩固本篇技能）

  1. 对比两种访问方式：把 ask() 里的 load_memory_variables 改回 chat_memory.messages，跑 4 轮观察窗口视图从 6 变成 8——亲手复现原代码的 bug。
  2. 改 k 值看截断效果：把 k=3 改成 k=2，跑 4 轮——Round 4 时窗口视图应该只剩 Rounds 3+4（4 条），验证 k 参数真的生效。
  3. 让 FakeDataFetcher 真被调用：在 ask() 里加"先用 FakeDataFetcher 取数据，再拼进 prompt"——体会"注册了工具但没调用"和"真调用"的区别，以及 char07 死代码谱系的修复思路。
  4. 升级为摘要压缩：让 ask() 在回写前检查 chat_memory 长度，超过 6 条时调 LLM 把 Round 1-2 压缩成摘要（如"用户问 2022/2023 GDP，AI 分别回答了 3.0%/5.2%"），替换掉原始消息——实现 SummaryMemory 的极简版。
  5. 跨会话持久化：把 ask() 开头的 memory 改成从 JSON 文件读，结尾写回——让脚本第二次运行时还能记住第一次的对话历史（char07-05 JSONL 日志同源技术）。
