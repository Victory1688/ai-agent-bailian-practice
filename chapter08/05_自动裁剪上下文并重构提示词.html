一、这份代码整体在做什么（一段话讲给新人）

本篇是 char08 第五篇——显式引入 Token 预算管理的剪辑策略。04 篇的 Memory 窗口是"按轮数截断"（k=3），本篇升级为"按 Token 预算装填"：dynamic_clip_context() 给每段上下文估一个 token 成本（length 字段），按优先级 + 新鲜度排序后贪心装填——预算内能装多少装多少，装不下的直接丢弃。这是从"规则窗口"到"预算装填"的算法跃迁，与 char07-07 的三级筛选合并形成上下文压缩的两个互补流派。

四、逐段代码讲解

4.1 dynamic_clip_context：贪心装填算法（本篇核心教学资产，原样保留）

def dynamic_clip_context(segments, token_limit=150):
    # 1. 排序：优先级降序 + 时间戳降序
    segments.sort(key=lambda x: (-x["priority"], -x["timestamp"]))

    # 2. 贪心装填：预算内尽量多装
    total = 0
    clipped = []
    for seg in segments:
        if total + seg["length"] <= token_limit:
            clipped.append(seg)
            total += seg["length"]

    # 3. 拼接 [ROLE-TYPE] 标注
    merged = ""
    for seg in clipped:
        merged += f"[{seg['role']}-{seg['type']}] {seg['content']}\n"
    return merged

三步式：排序 → 装填 → 拼接。注意两个细节：

  • 排序用双重 key：(-priority, -timestamp)——先按优先级（system 永远排最前），同优先级内按时间（最新的在前）。负号是 Python 排序"降序"的惯用技巧。
  • 装填是"跳过"不是"终止"：装不下的段被跳过后，循环继续——后面可能有更短的段能塞进剩余空间。这是背包问题的贪心解法特征：不保证全局最优，但保证高价值段优先入选。

4.2 length 的粗估：len(content) // 2（原样保留）

用"字符数除以 2"模拟 token 数——对中文内容这是个粗略估计（qwen 系 tokenizer 大约 1 汉字 ≈ 0.6-1 token，取决于内容）。教学场景够用，但生产系统必须用真实 tokenizer（tiktoken / transformers tokenizer）计数。粗估的风险：估少了 → 超预算被 API 拒绝；估多了 → 白白丢弃有价值的内容。

注意 62-63 行：用户问"那2023年呢？"，assistant 回答的却是"2025年为5.2%"——问 2023 答 2025，明显是教材笔误（response 内容与提问轮次错位）。改写时保留原样并在注释里标注，因为这不影响本篇的教学重点（剪辑算法），但新人读上下文时会困惑，需要点破。

4.4 与 04 篇 WindowMemory 的对比（重要认知）

维度04 篇 ConversationBufferWindowMemory(k=3)本篇 dynamic_clip_context
截断单位轮（1 轮 = 1 user + 1 AI）段（任意粒度，system/tool/input/response 各自独立）

本篇的剪辑策略本质上是一个微型的"上下文价值函数"实现：priority（重要性）× timestamp（新鲜度）× length（成本）三维度综合决策。这三个维度正是所有上下文压缩算法的核心变量——后面 06 篇如果有更高级的策略，也只是在这三个维度上做文章。

五、实测验证：贪心装填的真实剪出效果

实测：token_limit=100，9 段进 9 段出（预算刚好够）
--- 剪辑后上下文结构 ---
[system-system] 你是资深经济顾问，语言需精准、简洁    ← priority=1.0，排最前
[user-input] 主要依据有哪些？                        ← 最新，时间降序开始
[assistant-response] 预计增长可达5.4%
[user-input] 2026年会不会更高？
[tool-tool] [DeepSeek-V1] 分析完成：2026年预测...
[assistant-response] 2025年为5.2%
[user-input] 那2023年呢？
[assistant-response] 2024年增长为3.0%
[user-input] 2024年GDP是多少？                      ← 最老，排最后

--- Qwen3.0 响应输出 ---
2024年GDP总量为126.06万亿元（人民币，初步核算值）。

排序完全符合预期：system 段优先级最高排第一，其余段按时间新→旧。9 段总 token 数（粗估）约 94，在 100 预算内全部装入——预算宽松时贪心装填 = 全量保留，只有预算紧了才会看到"跳过"效果。

把 token_limit 收紧到 30，观察"跳过"效果

预算 30 时，system 段（约 11 token）+ 最新两三段就满了，老段全部被跳过——注意被跳过的可能是中间某段而非尾部（因为贪心是逐段判断，不是一刀切）。动手练习第 1 题让你亲手跑这个实验。

九、动手练习（巩固本篇技能）

  1. 收紧预算看"跳过"：把 token_limit=100 改成 30，跑一次——观察哪些段被跳过、system 段是否依然保留，验证贪心算法的"跳过不终止"特性。
  2. 真实 tokenizer 计数：用 tiktoken.get_encoding("cl100k_base") 替换 len(content)//2，对比两种估算的差距——体会"粗估"在真实 tokenizer 面前误差有多大。
  3. 按价值密度装填：把排序 key 改成 -priority/length（价值密度 = 每单位 token 换取的优先级），对比原排序在 token_limit=30 下的装入结果——体验背包问题"按密度贪心"的经典改进。
  4. 给 04 篇 WindowMemory 加优先级：把本篇的 build_segment（带 priority/length）套进 04 篇的对话循环，实现"system + 最近 2 轮 + 高优先级段"的混合剪辑——完成从"窗口"到"价值"的升级。
  5. 接上 03 篇状态机：给剪辑过程加状态——排序阶段转 RUNNING、装填阶段转 WAITING_TOOL（如果 tool 段需要实时生成）、拼接完成转 COMPLETED——融合 char08 前五篇的全部技能。
