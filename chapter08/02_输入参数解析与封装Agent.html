一、这份代码整体在做什么（一段话讲给新人）

本篇是 char08 第二篇——解决"人说人话、工具要结构"的翻译问题。用户说的是自然语言（"请预测2026年美国的GDP增长趋势"），工具 API 吃的是结构化参数（{"region": "美国", "year": 2026, "focus": "GDP"}），两者之间需要一座桥——parse_input() 规则解析器。本篇完整演示了这条链：自然语言 → 规则解析 → 结构化参数 → 工具执行 → LLM 综合解读。这正是 function calling 的"规则版前传"——在 LLM 自主选参之前，工程师先用硬编码规则做参数提取。

三段解析规则速查表（parse_input 的全部逻辑）

参数解析方式默认值匹配规则本例结果
year分词 + 后缀判断2026token 以"年"结尾且前缀是纯数字2026（命中"2026年"）
region关键词包含中国"美国" 优先于 "欧盟"（if/elif 顺序）美国
focus关键词包含GDP"CPI" 优先于 "PMI"（if/elif 顺序）GDP（未命中 CPI/PMI）
三层兜底设计：每个参数都有默认值

注意 parse_input 的开头——三个变量先赋默认值，解析命中就覆盖，没命中就保留默认。配合工具侧的 params.get("region", "中国") 双重默认值，这条链永远不会因为参数缺失而崩溃。这是"宽容输入"设计：解析器尽力提取，提取不到就给合理默认，工具再兜一层底。

四、逐段代码讲解

4.1 parse_input：三段式规则解析（本篇核心教学资产，原样保留）

# 年份解析：分词 + 后缀判断
for token in user_text.split():
    if token.endswith("年") and token[:-1].isdigit():
        year = int(token[:-1])

# 区域解析：if/elif 优先级
if "美国" in user_text:
    region = "美国"
elif "欧盟" in user_text:
    region = "欧盟"

# 指标关键词：if/elif 优先级
if "CPI" in user_text:
    focus = "CPI"
elif "PMI" in user_text:
    focus = "PMI"

三种典型的规则提取手法：分词+后缀（结构化程度高的"数字年"）、子串包含（"美国"藏在句子里任何位置都能命中）、if/elif 优先级（同时命中多个时取先判断的——和 char07-03/04 的路由函数同一套写法）。整段零依赖、纯 Python，是"不调 LLM 做参数提取"的最小样板。

4.2 EconomicForecastTool：Dict 签名 + 双层默认值

def call(self, params: Dict[str, Any]) -> str:
    region = params.get("region", "中国")   # 工具侧兜底
    year = params.get("year", 2026)
    focus = params.get("focus", "GDP")

注意 call 的签名是 params: Dict[str, Any] 而非 str——与 char07-04 的 HybridAnalysisTool 同款设计（结构化输入比单字符串表达力强）。.get(key, default) 的默认值机制让工具对"参数缺失"免疫：解析器漏提一个字段，工具照样能跑（用默认值），只是结果可能不符合用户本意。不崩溃 ≠ 正确，这是宽容输入的代价。

4.3 主流程：解析→工具→LLM 的三段式

structured_params = parse_input(user_input)     # 第一段：NL → 结构化
tool_output = forecast_tool.call(structured_params)  # 第二段：结构化 → 工具结果
prompt = f"工具输出：{tool_output}\n问题原文：{user_input}\n..."  # 第三段：结果 → LLM 解读

第三段 prompt 里同时塞了工具输出和问题原文——这是个好习惯：LLM 既知道工具算出了什么，也知道用户原始意图是什么，能校验两者是否对齐（比如工具把"2026"解析错成"2020"，LLM 对比原文能发现）。

4.4 本篇与 function calling 的关系（重要认知）

本篇的 parse_input 是工程师手写的参数提取；char02-06/03-06 的 function calling 是LLM 自主的参数提取（模型输出 tool_calls JSON）。两者解决同一个问题（NL→结构化参数），但路线不同：

维度规则解析器（本篇）function calling（char02-06）
提取者工程师写死的规则LLM 按工具 schema 生成
成本零（纯本地计算）一次 LLM 调用（token 费用 + 延迟）
覆盖面只覆盖预想到的表达（"2026年"能提取，"明年"不能）泛化强（"明年"、"下个季度"都能理解）
确定性100% 可复现有随机性（temperature>0）
适用场景格式固定的查询（报表年份、已知区域列表）开放域自然语言（用户想怎么说就怎么说）

生产系统常用混合策略：先用规则解析器快速试（成本低、命中就走），规则没命中再升级到 LLM 解析（成本高、但泛化强）——这就是"规则优先，模型兜底"的两级漏斗。

year: 2026           ← 分词提取"2026年"

三个参数全部提取正确，工具按结构化参数生成了结果，qwen-plus 以政策分析师视角给出了专业解读（还主动对比了历史均值和 IMF 基准——工具输出与问题原文同时入 prompt 的收益）。

规则解析器的盲区实测提示

试试这几句，观察 parse_input 的表现：

  • "请预测明年美国的GDP" → year 保留默认 2026（"明年"没有"数字+年"结构，提取失败但静默用默认值——不报错但可能不是用户本意）
  • "请预测2026年欧盟和美国的GDP" → region=美国（if/elif 顺序，"美国"优先命中，欧盟被忽略——多区域只能取一个）
  • "请预测2026年美国的cpi"（小写） → focus=GDP（"CPI" 大小写敏感匹配失败——需要 upper() 归一化）

这三条盲区就是"规则优先，模型兜底"两级漏斗存在的理由——动手练习第 2 题会让你亲手复现。

七、架构视角：参数提取的三代技术

代际技术成本泛化代表
第一代正则/分词规则零差（只认预设模式）本篇 parse_input、char03-08 Trie 敏感词
第二代专门 NLU 模型（意图分类+槽位填充）低（小模型推理）中（需标注数据训练）RASA、科大讯飞 NLU
第三代LLM function calling高（大模型推理）强（开放域理解）char02-06、char03-06、OpenAI tools

三代不是替代关系，是成本-泛化的梯度：高频简单查询走第一代（零成本），复杂长尾走第三代（高成本高泛化）。本篇教的规则解析器是整个梯度里"免费档"的基石。

八、教学版 vs 生产版差距

教学简化生产要求
三个参数硬编码解析参数 schema 声明式定义（JSON Schema），解析器按 schema 自动生成
规则未命中静默用默认值未命中时显式向用户确认（"您是指明年(2027)吗？"）或升级 LLM 解析
区域/指标只有 2-3 个枚举值完整枚举表 + 别名映射（"美国/USA/US" 同义）
大小写敏感匹配统一 lower()/upper() 归一化后再匹配
EconomicForecastTool 返回假数据真实 API + 参数校验（year 超范围直接报错而非静默）
解析结果无日志留痕解析输入/输出/命中规则全部落日志（char07-05 惯例），便于审计解析质量
