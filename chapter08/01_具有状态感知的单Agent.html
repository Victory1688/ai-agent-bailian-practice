01_具有状态感知的单Agent - 代码解析

对应文件：char08/01_具有状态感知的单Agent.py | 教材出处：第8章 单智能体系统构建实战 例8-1 | 环境实测：qwen-plus 真实调用 + 六态状态机完整流转 | 生成日期：2026-10-12

一、这份代码整体在做什么（一段话讲给新人）

本篇是 char08 开篇——把状态管理引入智能体。char02-07 的 Agent 都是"一把梭"（调 LLM 拿结果返回），内部没有显式的"我现在在干什么"的意识。本篇定义了一个 AgentState 六态枚举（初始化→就绪→运行→等工具→完成/失败），StatefulAgent.execute() 在执行过程中按阶段切换状态、把每次变更记录到 history 列表，try/except 兜底把异常路径也纳入状态机（FAILED 状态）。这是"可靠 Agent"的第一步——能看见自己在干什么，出了错能恢复。

二、AgentState 六态流转速查表

状态含义谁触发下一个状态设计意图
INITIALIZED刚创建对象，task_id 已分配__init__ 自动READY对象刚出生
READY准备好接收任务execute 开头RUNNING任务开始前的预备态
RUNNING正在执行（LLM 调用阶段）工具调用前后各一次WAITING_TOOL / COMPLETED / FAILED主工作态
WAITING_TOOL正在等外部工具返回工具调用前RUNNING（工具返回后）首次承认外部依赖等待——char02-07 都没显式建模这一步
COMPLETED正常完成execute 末尾终态全部 OK
FAILED异常失败except 兜底终态任一步骤抛异常都走这里
状态机流转图
                    execute() 开头
  INITIALIZED ──────────────────► READY
                                      │
                                      ▼
                                   RUNNING ◄──┐
                                      │        │
                          工具调用前    │        │ 工具返回后
                                      ▼        │
                                  WAITING_TOOL ─┘
                                      │
                          LLM 调用正常 │   LLM/工具抛异常
                                      ▼        ▼
                                 COMPLETED  FAILED
                                  （终态）  （终态）

两条关键路径：正常路径是 INITIALIZED→READY→RUNNING→WAITING_TOOL→RUNNING→COMPLETED（五步状态变更），异常路径是任一步骤 → except → FAILED。try/except 把所有未预料的失败都纳入了状态机，这是"可靠"的核心保障。

三、整体执行流程图

StatefulAgent(task_id = uuid4)

四、逐段代码讲解

4.1 AgentState 枚举：状态机的"字典"

class AgentState(Enum):
    INITIALIZED = "initialized"
    READY = "ready"
    RUNNING = "running"
    WAITING_TOOL = "waiting_tool"
    COMPLETED = "completed"
    FAILED = "failed"

用 Python 枚举类做状态定义——好处是：① IDE 自动补全，不会写错字符串；② state.value 统一输出值（如 "running"），而 AgentState.RUNNING 是类型安全的引用，不会出现拼写错误（比如把 "running" 写成 "runing"）。六个状态覆盖了 Agent 从出生到死亡的完整生命周期。

4.2 StatefulAgent.__init__：去掉虚构 Agent，保留 self.tool

# 原写法：self.agent = Agent(tools=tools)  ← 虚构 qwen_agent
# 改写：直接删，StatefulAgent 内部直接调 dashscope
self.tool = tools[0]

原代码用 Agent(tools=tools) 做了一层"Agent 持有工具"的抽象，但 StatefulAgent 根本没用到这个抽象——execute 里直接调 self.tool.call() 和 self.agent.chat()，两个调用是平级的。改写后干脆去掉 self.agent，LLM 调用直接写在 execute 里——少一层无意义的包装，代码更扁平。

4.3 execute 方法：状态流转的骨架

def execute(self, system_prompt, user_question):
    try:
        self.update_state(AgentState.READY)        # 状态1
        # ... 拼 prompt ...
        self.update_state(AgentState.RUNNING)       # 状态2
        self.update_state(AgentState.WAITING_TOOL)  # 状态3（首次承认外部依赖）
        tool_result = self.tool.call(user_question)
        self.update_state(AgentState.RUNNING)       # 状态4
        # ... 拼 merged_prompt + 调 LLM ...
        self.update_state(AgentState.COMPLETED)     # 状态5
        return result
    except Exception as e:
        self.update_state(AgentState.FAILED)        # 异常兜底
        return f"[ERROR] {e}"

五个 update_state 调用就像五个"里程碑"——每一步做完先报状态再往下走。这个模式的好处：① 任何一步失败，FAILS 状态必然被记录，事后审计能精确定位；② 外部监控系统可以订阅状态变更事件（比如 RUNNING→WAITING_TOOL 超过 10 秒就告警工具超时）。

4.4 WAITING_TOOL：首次显式建模"外部依赖等待"

这是 char02-07 系列里第一次出现"工具调用前后的状态切换"。之前所有示例都是"调工具→拿结果→继续"，中间没有显式承认"我正在等工具"。WAITING_TOOL 状态的引入，意味着：① 工具调用可能慢（本篇 ForecastTool 就有 sleep(1)）；② 工具调用可能超时或失败；③ 可以监控"等工具等了多久"。这是从"同步一把梭"到"异步可靠 Agent"的关键一步。

五、实测数据：时间戳暴露了每一步的耗时

show_history 日志的时间戳差值就是各阶段耗时
2026-10-12 11:13:23 | ready          ← execute 开始
2026-10-12 11:13:23 | running        ← 毫秒级（拼 prompt 是字符串操作）
2026-10-12 11:13:23 | waiting_tool   ← 同上
2026-10-12 11:13:24 | running        ← WAITING_TOOL→RUNNING：+1 秒 = ForecastTool.sleep(1)
2026-10-12 11:13:37 | completed      ← RUNNING→COMPLETED：+13 秒 = qwen-plus 生成耗时

这个时间戳链的分析模式和 char07-05 的日志 timestamp 对比是同一家族——char07-05 是磁盘版 JSONL 日志，本篇是内存版 history 列表，都是"时间戳 = 免费性能探针"。区别是：05 篇日志跨运行存活，本篇 history 随对象销毁即消失。

八、教学版 vs 生产版差距

教学简化生产要求
状态记录在内存 history 列表持久化存储（char07-05 JSONL 日志同源技术），支持跨进程/跨运行状态恢复
execute 是同步单线程WAITING_TOOL 应异步化（asyncio / 线程池），工具等待不阻塞主循环
无工具超时WAITING_TOOL 超时（如 10 秒）自动转 FAILED + 重试
FAILED 只返回错误字符串区分失败类型（ToolTimeout / LLMError / ParseError），不同类型不同重试策略
try/except 兜底所有异常分层捕获：工具异常 / LLM 异常 / 系统异常分别处理，避免 ALL CATCH 吞掉关键错误
ForecastTool 返回假数据真实 API + 超时兜底（char06 惯例）

九、动手练习（巩固本篇技能）

  1. 触发 FAILED 分支：把 ForecastTool.call 改成 raise Exception("模拟工具超时")，跑一次观察 FAILED 状态是否被记录、history 日志里最后一条是否是 failed。
  2. 实现超时状态：给 AgentState 加一个 TIMEOUT 状态，在 WAITING_TOOL 阶段用 threading.Timer 计时（超过 5 秒就转 TIMEOUT），体会"状态机 = 业务流程的显式声明"。
  3. 持久化 history：把 show_history 里的 history 列表改成 char07-05 的 JSONL 追加写——每次 update_state 就落盘，这样即使脚本崩溃，已完成的状态变更也不会丢。
  4. 扩展状态机：加一个 AUTHENTICATED 状态（在 INITIALIZED→READY 之间），execute 开头先验证 API key 有效性，失败直接转 FAILED——体会"状态机可以前置业务验证"。
  5. 进阶：双工具串行：再加一个 RAGRetrievalTool（模拟检索），execute 里先调检索工具再调预测工具，状态流转变成 RUNNING→WAITING_TOOL→RUNNING→WAITING_TOOL→RUNNING——观察状态机如何自然扩展到多工具场景。
