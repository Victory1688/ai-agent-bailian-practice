例 10-4 讲解：Request-Response 机制详解

本节核心概念：Request-Response 是多 Agent 通信最基础的模式。真实 A2A 协议中，这一模式在 三层 上同时发生——协议层用 JSON-RPC 2.0 信封（Request ↔ Response），业务层用 A2A Task（message.send → working → completed + Artifact），能力层用 dashscope.Generation.call（LLM 请求 ↔ LLM 响应）。三层结构是理解所有 Agent 通信的基石。

一、本节要解决什么问题

教材例 10-1 讲 A2A 消息格式，例 10-2 讲认证与能力匹配，例 10-3 讲 A2A + MCP 组合——到了这一篇，我们要拆解所有 Agent 通信的 最基础交互单元：请求方 Agent 主动发起，响应方 Agent 处理后返回。

教材原版的问题：

  • A2AMessage 是自定义简化结构（sender / receiver / type / payload），不符合 A2A 规范
  • "type = 'request' 或 'response'" 这种做法在真实协议里不存在——协议层和业务层各有自己的"请求/响应"语义
  • responder.handle_request() 里手动拼三段 prompt 调虚构的 qwen_agent.Agent

本次改写的核心目标：用真实 A2A v1.0 + JSON-RPC 2.0 拆解 Request-Response 的三层实现。

二、三层 Request-Response 架构

L1 协议层 — JSON-RPC 2.0 信封（Request ↔ Response 信封）

所有 A2A/MCP 方法调用都包裹在 JSON-RPC 2.0 信封里，id 字段必须在响应中原样返回用于匹配。

# Request（请求方发出）
{
  "jsonrpc": "2.0",                        # 固定版本
  "id": "req-b8e6295bc24d",                # 唯一请求标识
  "method": "message.send",                # A2A 方法名
  "params": { "message": {...} }           # 业务参数
}

# Response（成功响应，响应方返回）
{
  "jsonrpc": "2.0",
  "id": "req-b8e6295bc24d",                # 原样返回 id
  "result": { ... A2A Task 对象 ... }       # 成功结果
}

# Error Response（失败响应）
{
  "jsonrpc": "2.0",
  "id": "req-b8e6295bc24d",
  "error": { "code": -32601, "message": "Method not found" }
}

L2 业务层 — A2A Task 生命周期（message.send → working → completed + Artifact）

协议层的 method = "message.send" 只是信封，业务层的真实内容是 A2A Task 对象——它封装了从收到请求到处理完成的完整生命周期。

# message.send 请求
{
  "messageId": "msg-abc123",
  "role": "user",
  "contextId": "ctx-15cee4b686e5",
  "parts": [{"kind": "text", "text": "欧洲通胀情况如何？"}]
}

# 返回的 A2A Task（completed + Artifact）
{
  "id": "task-0525adfe3c69",
  "contextId": "ctx-15cee4b686e5",        # 与请求的 contextId 相同
  "status": {
    "state": "completed",                  # working → completed
    "message": { "role": "agent", "parts": [...] }
  },
  "kind": "task",
  "artifacts": [                            # 最终产出（替代教材的 payload.answer）
    { "artifactId": "art-xyz", "name": "qa_answer",
      "parts": [{"kind": "text", "text": "结论：欧洲通胀已显著回落..."}] }
  ]
}

L3 能力层 — dashscope.Generation.call（LLM 请求 ↔ LLM 响应）

业务层要生成 Artifact 里的文本内容，必须调 LLM。dashscope 的 Generation.call 本身也是一次完整的 Request-Response。

# LLM 请求
dashscope.Generation.call(
  model="qwen-plus",
  messages=[{"role": "user", "content": prompt}],
  temperature=0.3, max_tokens=512,
  result_format='message',
)

# LLM 响应（response.output.choices[0].message.content）
"结论：欧洲通胀已显著回落，但略高于目标。
据欧盟统计局数据，2024 年 5 月欧元区调和消费者物价指数
（HICP）同比上涨 2.6%，较 2022 年 10 月峰值 10.6% 大幅下降..."

三、完整交互链路

1RequestAgent.build_request()
  L1: 生成 JSON-RPC 2.0 Request 信封（id + method + params）
  L2: params.message 里嵌 A2A Message（role + contextId + parts）
2发送给 ResponderAgent.handle_request(jsonrpc_request)
3ResponderAgent.verify_request() 验证信封格式
  jsonrpc 版本 = 2.0？ method 合法？ params.message 存在？
4ResponderAgent 提取用户问题 + contextId
5L3: dashscope.Generation.call() → 得到 LLM 文本
6L2: 构造 A2A Task（completed + Artifact）
7L1: 构造 JSON-RPC 2.0 Response（原样返回 id + result）
8RequestAgent.handle_response() 解析 Task → 提取 Artifact

四、核心组件解析

RequestAgent（请求方 Agent）

方法职责对应层
build_request(question)构造 JSON-RPC Request 信封 + A2A MessageL1 + L2
handle_response(jsonrpc_response)解析 Response：成功取 Task.Artifact，失败取 errorL1 + L2

ResponderAgent（响应方 Agent）

方法职责对应层

错误处理（JSON-RPC 标准错误码）

真实协议里错误不用 HTTP 状态码（那是传输层的事），协议层用 error.code 数字码：

错误码含义触发场景
-32700Parse Error收到的 JSON 根本解析不出来
-32600Invalid Requestjsonrpc 版本不是 "2.0"，或缺少必填字段
-32601Method Not Found请求的 method 不存在（如 nonexistent.method）
-32602Invalid Params参数缺失或类型错误（如 params 里没有 message 字段）
-32001Auth FailedA2A 层：认证失败（见例 10-2）
-32002Capability Validation FailedA2A 层：能力不匹配（见例 10-2）

七、三层架构的重要性（为什么要分三层）

解耦与独立演进

三层各司其职，可以独立替换而不影响其他层：

  • L1 协议层：如果某天 A2A 信封从 JSON-RPC 改成别的，只要 Request/Response 的语义不变，L2 和 L3 完全不用改
  • L2 业务层：Task 状态机从 7 态增加到 8 态（比如加个 "preparing"），不影响 L1 信封格式，也不影响 L3 LLM 调用
  • L3 能力层：从 dashscope 换成 Claude / GPT-5 / 本地模型，上层业务逻辑（Task / JSON-RPC）都不需要改

教材原版把三层混为一层

教材把"请求/响应"全部塞在一个 A2AMessage(type, payload) 里，这在教学上可以简化，但在工程上是致命的——因为它把"协议信封"、"业务对象"、"LLM 调用"三件完全不同的事混在一起，后续改任何一层都要全部重写。

八、动手练习

  1. 加 working → completed 两阶段返回：当前 ResponderAgent 直接返回 completed 状态。改成先返回 working 状态（带空 Artifact），处理完再返回 completed。这就是 A2A 规范里 Task 状态机的两阶段转换。
  2. 加多轮对话（contextId 复用）：第二次提问时复用第一次的 contextId，看 ResponderAgent 能不能识别多轮并把历史也传给 dashscope。A2A 规范里 contextId 是 SERVER 生成的，多轮必须复用。
  3. 加错误码覆盖测试：构造一个 jsonrpc = "1.0" 的请求（触发 -32600）、构造一个空 id 的请求（看规范要求）。把 verify_request() 扩展到覆盖规范要求的所有校验。
  4. 加 Notification 模式：JSON-RPC 还有第三种消息类型 Notification（没有 id，不需要响应）。实现一个"广播通知 Agent 上线"的功能，对比它和 Request 的区别。
