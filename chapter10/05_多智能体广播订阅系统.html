例 10-5 讲解：多智能体广播订阅系统（Pub/Sub）

本节核心概念：Request-Response（例 10-4）是"一对一"通信，而 Pub/Sub（发布-订阅）是"一对多"通信。协议层用 JSON-RPC 2.0 Notification（没有 id，不需要响应）作为广播载体；业务层用 A2A subscribeToTask + SSE TaskStatusUpdateEvent 实现订阅和推送。两者关键区别就在 id 字段。

一、本节要解决什么问题

例 10-1 到 10-4 讲的都是 一对一 通信（A 给 B 发请求，B 给 A 回响应）。但真实多 Agent 系统里经常需要 一对多 广播场景：

  • 一个 Planner Agent 创建了新 Task，通知所有相关 Agent 自己选要不要接
  • 一个 Worker Agent 处理完 Task，通知所有订阅者"我完成了，Artifact 在这"
  • 一个 Status Agent 广播"系统故障，暂停服务"，所有 Agent 收到后各自处理

教材原版的简化实现：

  • class PubSubMessage(topic, content) — 自定义的 topic 订阅消息
  • class PubSubSystem(publish, register) — 简单 topic 匹配
  • from qwen_agent import Agent, PromptEntry — 虚构框架

本次改写的核心目标：用真实 A2A v1.0 规范的 Pub/Sub 机制。

二、协议层：JSON-RPC Request vs Notification（关键区别）

这是理解 Pub/Sub 的基础——Notification 就是"不需要响应的单向广播"。JSON-RPC 2.0 规范里明确定义了三种消息类型：

Request（请求）

{
  "jsonrpc": "2.0",
  "id": "req-abc123", // ← 有 id！
  "method": "message.send",
  "params": { ... }
}

期望 Response（{id, result} 或 {id, error}）

例 10-4 用的就是这个

Notification（通知）

{
  "jsonrpc": "2.0",
  "method": "task.status", // ← 没有 id！
  "params": { ... }
}

MUST NOT 发送任何 Response

例 10-5 Pub/Sub 的广播载体

为什么 Notification 适合广播

  • 无 id：接收方收到后不需要回任何东西，Publisher 不用等响应就能继续干别的
  • 一发布多接收：Publisher 构造一个 Notification 对象，PubSubSystem 向注册表中的所有 Subscriber 分发
  • 容错天然：某个 Subscriber 挂了不影响其他 Subscriber（对比 Request 如果目标挂了会阻塞调用方）

三、业务层：A2A subscribeToTask + TaskStatusUpdateEvent

JSON-RPC Notification 只是协议层信封，业务层 A2A 规范用 subscribeToTask RPC 方法 + TaskStatusUpdateEvent 事件对象实现了完整的 Pub/Sub 语义。

A2A Pub/Sub 三阶段（对应规范 § Streaming & Async）

阶段A2A 规范元素说明
① 订阅subscribeToTask(taskId) RPCClient 声明"我想看这个 Task 的所有状态变化"
② 推送通道SSE（Server-Sent Events）流Server 建立 HTTP 长连接（Content-Type: text/event-stream），实时推送
③ 事件对象TaskStatusUpdateEvent每次 Task 状态变化都推送一个，含 state + message + artifacts

TaskStatusUpdateEvent 状态流转

1submitted → Task 已创建，等待处理
2working → Publisher 正在处理（LLM 调用中）
3completed → 处理完成，返回 Artifact
  （也可能走向 input-required / failed / canceled）

四、系统架构

A2ASubscriptionManager（订阅管理器）
├── _subscriptions: {task_id → [SubscriberAgent, SubscriberAgent, ...]}
├── subscribe(task_id, subscriber)
├── unsubscribe(task_id, subscriber)
├── get_subscribers(task_id) → List[SubscriberAgent]
└── broadcast(task_id, notification) → List[str]  ← 向所有订阅者分发

PublisherAgent（发布者）
├── create_task(description)     → 广播 task.submitted Notification
├── process_task(task_id, prompt)
│   ├── 广播 task.working Notification
│   ├── dashscope.Generation.call()
│   └── 广播 task.completed Notification（含 Artifact）
└── get_task(task_id) → Task

SubscriberAgent（订阅者）
├── subscribe_to_task(task_id, mgr)   ← 业务调用 subscribeToTask
└── on_notification(notification)     ← 接收 JSON-RPC Notification
    ├── task.submitted → 记录新任务
    ├── task.working   → 记录状态变化
    └── task.completed → 可选调 dashscope 做二次分析

五、完整交互链路（运行时实际发生了什么）

1PublisherAgent.create_task()
  → mgr.broadcast(task_id, {jsonrpc:"2.0", method:"task.status", params:{event:{state:"submitted"}}})
  → 此时订阅者还未加入，broadcast 返回空列表
2SubscriberAgent.subscribe_to_task(task_id, mgr)
  → mgr.subscribe(task_id, self) → 注册到注册表
3手动重广播 submitted（新订阅者已加入）
  → analyzer.on_notification() 收到 → 返回 "[agent:analyzer] 收到新任务: ..."
  → reporter.on_notification() 收到 → 返回 "[agent:reporter] 收到新任务: ..."
4PublisherAgent.process_task() 内部广播 working
  → analyzer: "[agent:analyzer] 状态变化: Publisher 正在处理..."
  → reporter: "[agent:reporter] 状态变化: Publisher 正在处理..."
5PublisherAgent 调 dashscope qwen-plus 生成财经分析
6PublisherAgent 广播 completed（含 Artifact）
  → analyzer: 收到后调 dashscope 做二次摘要 → "[agent:analyzer] 二次分析: ..."
  → reporter: "[agent:reporter] 任务完成，内容预览: ..."

八、与例 10-4（Request-Response）的对比

这一节是理解 Pub/Sub 模式的关键——Request-Response 和 Pub/Sub 解决的是两种完全不同的通信场景：

维度Request-Response（例 10-4）Pub/Sub（例 10-5）
通信模式一对一（点对点）一对多（发布-订阅）
协议层消息JSON-RPC Request（有 id）JSON-RPC Notification（无 id）
响应语义期望 Response（同步等待）不需要任何 Response
业务载体A2A Task（同步返回）A2A TaskStatusUpdateEvent（异步 SSE 推送）
容错性目标挂了 → 调用方阻塞/报错某个订阅者挂了 → 不影响其他订阅者
适用场景"帮我干一件事，把结果告诉我""我有新消息，所有关心的人都应该知道"
类比打电话（一对一）发朋友圈（一对多，朋友各自看）

九、动手练习

  1. 加第三个订阅者：创建一个只关心 task.failed 状态的订阅者，看看 publisher 任务失败时它会不会收到——可以让 publisher 故意抛异常触发 failed 状态。
  2. 加取消订阅：在 SubscriberAgent 里加一个 unsubscribe_from_task(task_id, mgr) 方法，验证取消后该订阅者不再收到广播。
  3. 对比 SSE 推送：当前 broadcast() 是进程内直接调用 on_notification()。改成用 HTTP + SSE 实现真正的跨进程推送——Publisher 建 HTTP Server，Subscriber 用 requests.get(stream=True) 消费 SSE 流。
  4. 加多 Task 订阅：让一个 Subscriber 同时订阅多个 Task（task-abc123 + task-def456），验证它能正确区分不同 taskId 的状态变化。
