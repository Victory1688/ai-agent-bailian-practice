三、本章核心架构模式（最小生产骨架）

POST /chat 请求全旅程（融合七篇防御）：

  客户端 ──HTTPS──▶ 接入层：API Key 恒时比较（401）
                        │
                        ▼
                    令牌桶 acquire（桶空 → 429，状态落盘 cache.json）
                        │
                        ▼
                    优先级队列 put_nowait (priority, seq)（队满 → 503）
                        │
                        ▼
                    Worker 池取任务（高优先级先出，同级 FIFO）
                        │
                        ├─▶ 记忆层：读会话历史 + MCP tools/call 知识检索
                        │        （isError → 知识置空，不炸主流程）
                        ▼
                    降级链：qwen-plus → qwen-turbo → 兜底文案
                        │     （超时 8s · 指数退避 · 熔断打开直接跳过）
                        ▼
                    finally: event.set() 回填结果（异常也回填，永不挂死）
                        │
                        ▼
                    200 响应 + request_id 日志 + /health 指标
为什么这个骨架值得背下来？它是所有 LLM API 服务的通用形态（OpenAI/Anthropic 官网同款）：闸门在前快速失败（不消耗下游资源），队列居中削峰（把洪峰摊平），降级链收尾（永不给用户报错堆栈）。换任何语言框架，这七道工序的顺序与语义都不变。

八、动手路径建议

  1. 先跑 01 + 06：把最小生产骨架立起来，观察 /health 指标与日志双通道。
  2. 压测 06：用 10 线程突发打 /chat，对照 429 出现时机与令牌恢复速率（2 个/s）。
  3. 在 05 上做故障演习：修改 FaultyBackend 参数，观察熔断打开 → 半开 → 闭合的完整流转。
  4. 给 07 加 prompts 原语：实现 prompts/list + prompts/get，体会 MCP 三大原语同构性。
  5. 串起全章：把 02 的 API Key 校验、06 的令牌桶、05 的降级链合并成一个服务——就是第四节那张骨架图的完整实现。
