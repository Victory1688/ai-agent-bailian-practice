例 12-1 讲解：Web 服务记录日志与并发

本节核心变化：char11 学了"怎么把 Agent 部署成 Web 服务"，char12 开始"部署之后怎么运维"。本篇聚焦两个运维基石：日志（出了问题怎么查）和并发（很多人同时调用怎么办）。同时修复教材的 torch.time.time() bug，并把本地 GPU 推理改为全书统一的 dashscope API 模式。

一、本节要解决什么问题

char11 的 Flask 服务是"能用"水平：一个 /ask 端点、一次调用验证。但生产环境要回答两个致命问题：

  • 出了错怎么查？——用户说"我调你的接口报错了"，没有日志你两眼一抹黑：请求什么时候来的？参数是什么？哪一步失败的？耗时多久？
  • 100 个人同时调用怎么办？——教材用本地 GPU 推理，必须 model_lock 串行化（显存只够一次跑一个）；API 化之后并发难题交给云端，但你要观测并发水位。

二、改写后的整体架构

外部客户端（APP / 网站 / 其他 Agent） │ ▼ Flask 路由层（两个端点） ├─ GET /health → 健康检查 + 并发统计 └─ POST /v1/chat/completions → OpenAI 兼容 Chat API │ ▼ 请求处理 5 步（每步都有日志） ① request_id 生成（uuid 8 位） ② JSON 解析 + 参数校验 ← 失败记 warning 日志 ③ 并发计数 +1（加锁） ← 记"请求开始"日志 ④ dashscope.Generation.call ← 失败记 error 日志 ⑤ 并发计数 -1（finally 保证） ← 记"请求完成"日志（耗时+tokens） │ ▼ LLM 后端：DashScope qwen-plus（前 10 章统一模式）

日志双通道输出

  • 控制台（StreamHandler）—— 开发时实时看
  • 日志文件（FileHandler → agent_server.log）—— 生产排查依据，UTF-8 落盘持久化

三、核心概念 1：request_id 请求链路追踪

# 每个请求生成 8 位唯一标识，日志用它能串联完整链路
request_id = uuid.uuid4().hex[:8]

# 之后所有日志都带上这个前缀：
logger.info(f"[{request_id}] 请求开始 messages={len(messages)} 并发={active_now}")
logger.info(f"[{request_id}] 请求完成 耗时={elapsed_ms}ms tokens={usage['total_tokens']}")
为什么需要 request_id？ 并发时日志是交叉的——10 个请求的日志混在一起根本分不清谁是谁。有了 request_id，grep 一下 [6c984fc8] 就能抽出这一个请求的完整生命周期。这是生产级日志的第一要素。

四、核心概念 2：并发观测与锁

教材的锁 vs 改写后的观测

维度教材（本地 GPU 推理）改写后（云端 API）
为什么处理并发model_lock 必须加——GPU 显存只够一次跑一个请求，不加锁会 OOM不需要加锁——dashscope 云端天然支持并发
并发能力串行（一次一个）受 Flask 线程数和 API 限流约束
可观测性无计数器统计 total / active / max_active
# 并发计数器：观测并发水位（加锁保护，避免竞态条件）
_stats = {"total": 0, "active": 0, "max_active": 0}
_stats_lock = threading.Lock()

# 请求开始：active +1，并刷新峰值
with _stats_lock:
    _stats["total"] += 1
    _stats["active"] += 1
    _stats["max_active"] = max(_stats["max_active"], _stats["active"])

# 请求结束：active -1（放在 finally 里，出错也必须释放）
try:
    response = dashscope.Generation.call(...)
finally:
    with _stats_lock:
        _stats["active"] -= 1
两个易错点：
① 计数 -1 必须放 finally——如果放 try 正常分支，LLM 抛异常后 active 永远不减，统计就废了。
② 读写计数必须加锁——_stats["active"] += 1 看似一行，实际是"读-改-写"三步，多线程不加锁会丢更新（竞态条件）。

max_active 的意义

max_active（同时处理峰值）是容量规划的核心指标：如果压测发现 max_active 长期顶在 Flask 默认线程上限，就该考虑 gunicorn/workers 扩容或异步队列了。

六、实测验证（4 项 self-test 全部通过）

Test 1 - GET /health：[通过] status=ok
Test 2 - 单请求：[通过] answer=2, usage={'prompt_tokens': 21, 'completion_tokens': 1, 'total_tokens': 22}
Test 3 - 并发 3 请求：[通过] 日志交叉显示 并发=1→2→3，3 个请求全部完成
Test 4 - 并发统计：total=4 max_active=3 → [通过] max_active >= 3，并发处理得到验证

Test 4 的设计意图

为什么专门校验 max_active >= 3？如果 Flask 被配置成单线程串行处理，3 个请求会排队，计数器最多到 1。max_active 达到 3 数学上证明了真并发——这比"看起来跑完了"严格得多。

八、动手练习

  1. 加日志级别区分：给 /v1/chat/completions 加 logger.debug 记录完整请求体，并把 FileHandler 级别改为 DEBUG、控制台保持 INFO——体验"文件记详细、控制台记摘要"的双级别策略。
  2. 加日志轮转：把 FileHandler 换成 logging.handlers.RotatingFileHandler(maxBytes=1_000_000, backupCount=5)，防止日志文件无限增长。
  3. 模拟慢请求：加一个 /slow 端点内部 time.sleep(5)，同时发 10 个请求，观察 max_active 变化——理解 Flask 默认线程模型的并发上限。
  4. 接入 gunicorn/waitress：用 waitress（Windows）以 4 线程启动同一个 app，对比并发能力差异。
  5. 失败请求统计：给 _stats 加 "errors": 0，LLM 调用失败时 +1，/health 里展示错误率。
