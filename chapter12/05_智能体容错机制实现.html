例 12-5 讲解：智能体容错机制实现

本节核心目标：构建"打不死"的智能体。LLM API 会限流、超时、抖动宕机——生产环境故障是常态而非例外。本篇实现容错五件套：超时控制 → 重试退避 → 自动切换 → 熔断 → 优雅降级，并用故障注入器让每一种机制都被实测触发和验证（教材只演示了 happy path，容错代码写了却从未验证过）。

一、教材原版问题

二、容错五件套总览

用户请求 ask() │ ▼ ① 熔断检查 ──打开且未冷却──▶ 跳过该后端（不再白等）→ 试下一后端 │ 允许 ▼ ② 超时控制调用 ──超过 8s──▶ 按失败处理（线程池 future.result(timeout)） │ ▼ ③ 失败重试 + 指数退避（0.5s → 1s → 2s，给故障服务喘息窗口） │ 重试耗尽 ▼ ④ 自动切换下一后端（qwen-plus → qwen-turbo → ...） │ 全部后端耗尽 ▼ ⑤ 优雅降级：返回友好兜底文案（不报错不崩溃）

五个机制各管一种故障

机制防御的故障关键参数
超时控制服务卡死不响应timeout=8s
重试+退避瞬时抖动（限流/网络闪断）max_retries=2, backoff=0.5s×2^n
自动切换单后端持续故障后端列表顺序（主 → 备）
熔断器故障后端拖慢所有新请求连续 2 次失败打开，30s 冷却半开
优雅降级全部后端不可用兜底文案

三、核心组件 1：故障注入器（让容错可验证）

class FaultyBackend:
    """故障注入后端：可控模拟故障，用于验证容错机制"""

    def __init__(self, name, fail_times=0, forever=False):
        # fail_times=1 → 第 1 次失败第 2 次成功（验证重试）
        # forever=True → 永远失败（验证切换/降级/熔断）
        self.fail_times = fail_times
        self.forever = forever
        self.calls = 0

    def call(self, messages):
        self.calls += 1
        if self.forever or self.calls <= self.fail_times:
            raise RuntimeError(f"[故障注入] {self.name} 第 {self.calls} 次调用失败")
        return "（故障后端的正常回复）"
为什么这是本篇最重要的增强？ 教材的 run_demo 只演示"一切正常时 Agent 能回复"——但容错代码的意义恰恰在"一切不正常"时。故障注入让 self-test 能精确构造每一种故障场景：第 1 次失败（验证重试）、永远失败（验证切换）、全部失败（验证降级）、连续失败（验证熔断）。没有故障注入的容错测试 = 没测。

四、核心组件 2：熔断器（CircuitBreaker）

class CircuitBreaker:
    """按后端熔断：连续 2 次失败打开，冷却 30s 后半开重试"""

    def allow(self, name) -> bool:
        st = self._state.get(name)
        if not st or not st["opened_at"]:
            return True                          # 闭合 → 放行
        if time.time() - st["opened_at"] >= self.cooldown:
            st.update(opened_at=None, fails=0)   # 冷却完毕 → 半开放行试探
            return True
        return False                             # 打开 → 拒绝（上层跳过）

    def record_failure(self, name):
        st["fails"] += 1
        if st["fails"] >= self.threshold:
            st["opened_at"] = time.time()        # 达到阈值 → 打开熔断

熔断器三态

CLOSED 闭合（正常放行） → 连续 2 次失败 → OPEN 打开（直接跳过） → 冷却 30s → HALF-OPEN 半开（放行试探） → 成功则闭合 / 失败则再打开

熔断的价值（对比无熔断）

场景无熔断（教材）有熔断（改写后）
后端已挂，第 100 个请求到来白等 2 次重试 × 8s 超时 ≈ 16s+ 才切到备用熔断已打开，0ms 跳过直接用备用
对故障服务的压力每个请求都打 2-3 次，雪崩放大熔断期间零流量，服务获得恢复窗口

五、核心组件 3：ResilientAgent 主流程

def ask(self, user_input) -> str:
    messages = [{"role": "user", "content": user_input}]
    for backend in self.backends:                     # ④ 逐个后端尝试
        if not self.breaker.allow(backend.name):      # ① 熔断跳过
            self.stats[backend.name]["skip"] += 1
            continue
        for attempt in range(self.max_retries + 1):   # ③ 重试
            try:
                answer = self._call_with_timeout(backend, messages)  # ② 超时控制
                self.breaker.record_success(backend.name)
                return answer
            except (Exception, FutureTimeout) as e:
                self.breaker.record_failure(backend.name)
                if attempt < self.max_retries:
                    time.sleep(self.backoff_base * (2 ** attempt))   # 指数退避
    return self.FALLBACK_MSG                          # ⑤ 优雅降级
注意 try/except 捕获了 FutureTimeout：超时和普通失败走同一条处理链（记录熔断 → 退避 → 重试/切换）——统一故障处理路径，代码才不会分叉成两套逻辑。教材在 _call_with_timeout 内 import TimeoutError 却没在调用处区分处理，超时和异常行为不一致。

六、实测验证（5 项 self-test 全部通过）

Test 1 - 正常路径：[通过] qwen-plus 直连成功
Test 2 - 自动切换：broken-primary 失败 2 次（熔断同步打开）→ 切换 qwen-turbo 成功
Test 3 - 重试机制：flaky 第 1 次失败 → 退避重试第 2 次成功（未切换后端）
Test 4 - 优雅降级：双后端全故障 → 各自重试耗尽 → 兜底文案"很抱歉，我暂时无法回答您的问题..."
Test 5 - 熔断器：fails=2 opened_at 已记录 → 第三问 skip=1（直接跳过）

注意一个真实系统才会出现的细节：重试第 2 次的同时熔断器已打开（阈值 2 次连败）——本次请求仍会完成切换流程，但下一个请求开始就直接跳过该后端。新旧机制平滑衔接，无竞态死角。

九、动手练习

  1. 超时故障注入：给 FaultyBackend 加 sleep_before=20 参数（先卡 20s 再返回），配合 timeout=2 的 Agent，验证超时路径被触发且 Agent 不被卡死。
  2. 熔断半开恢复：把 cooldown 设为 1s，验证"打开 → 冷却 → 半开放行 → 恢复闭合"的完整三态流转（在 Test 5 基础上补断言）。
  3. 重试策略可配：支持 retry_on=[TimeoutError] 白名单——超时才重试，4xx 参数错误直接切后端不浪费（幂等性思考）。
  4. 与 12-04 记忆组合：把 ResilientAgent 和例 12-4 的 JSONCache 结合——降级兜底时用户输入仍写历史，恢复后 Agent 能接上上下文。
  5. 健康统计端点：把 stats 暴露为 GET /health（参考 12-01），观察压测下各后端的失败率变化。
