例 12-7 讲解：模拟 MCP 服务与 Coze 调用

本节核心目标：把教材的"伪 MCP"换成真实 MCP。教材把对话历史存进 Redis 并给键加 mcp: 前缀就宣称是"MCP 协议层"——这与真实协议毫无关系。真实 MCP（Model Context Protocol）是 Anthropic 于 2024-11 发布、2025-06-18 最新修订的跨进程开放标准：JSON-RPC 2.0 信封 + initialize 生命周期握手 + tools/resources/prompts 三大原语。本篇实现一个协议最小可运行版（协议消息结构与官方 SDK 完全一致），并模拟真实扣子（Coze）Bot 通过 MCP 集成外部工具的工作流。

二、教材"伪 MCP" vs 真实 MCP（本篇核心辨析）

维度教材（伪 MCP）真实 MCP（2025-06-18 规范）
本质给 Redis 消息键加 mcp: 前缀跨进程开放标准（JSON-RPC 2.0 之上的应用协议）
角色模型无Host（如扣子/Claude Desktop）+ Client（连接器）+ Server（能力提供方）
消息格式{"role","content"} 数组JSON-RPC 2.0 信封：jsonrpc / id / method / params / error
生命周期无initialize 握手（协商 protocolVersion + capabilities）→ notifications/initialized → 运行 → 关闭
能力发现无tools/list / resources/list / prompts/list 动态拉取
错误处理无JSON-RPC 标准错误码（-32700 / -32601 / -32602）+ 工具级 isError 标记
传输层进程内函数调用stdio（本地子进程）/ Streamable HTTP（远程，2025-03 起替代旧 SSE 传输）

MCP 三大原语

原语作用本篇实现
Tools模型可调用的函数（带 JSON Schema 入参声明）search_knowledge 知识检索
Resources客户端可读取的上下文数据（URI 寻址）session://{sid}/history 会话历史
Prompts预置提示词模板（最小实现未含，结构与前两者同构）
MCP 生命周期（本篇代码完整走通）： Client Server │ ── initialize(protocolVersion, clientInfo) ──▶ │ │ ◀── protocolVersion + capabilities + serverInfo │ │ ── notifications/initialized（通知，无响应）──▶ │ │ │ ← 运行期 │ ── tools/list ──▶ 工具清单 │ │ ── tools/call(search_knowledge) ──▶ 检索结果 │ │ ── resources/read(session://x/history) ──▶ 历史 │
为什么要先握手？initialize 让双方在发任何业务请求前协商"我会什么、你支持吗"——protocolVersion 不匹配直接失败，capabilities 声明服务器有无 tools/resources 能力。教材版本没有任何协商，客户端调什么全凭猜——这就是"协议"和"函数调用"的区别。

三、核心组件 1：McpServer（JSON-RPC 2.0 单入口分发）

def handle(self, raw: str) -> str:
    """协议单入口：解析 JSON-RPC 请求 → 分发 method → 序列化响应"""
    try:
        req = json.loads(raw)
    except json.JSONDecodeError:
        return self._dump(self._error(None, -32700, "Parse error"))
    req_id, method = req.get("id"), req.get("method", "")
    if req_id is None:
        return ""       # notification（如 initialized 通知）：按规范不回包
    handler = dispatch.get(method)
    if handler is None:
        return self._dump(self._error(req_id, -32601, f"Method not found: {method}"))
    try:
        result = handler(req.get("params") or {})
    except ValueError as e:
        return self._dump(self._error(req_id, -32602, str(e)))   # 参数级错误
    return self._dump({"jsonrpc": "2.0", "id": req_id, "result": result})

两类错误要分清（真实 MCP 的规范细节）

错误类型表达方式触发场景
协议错误JSON-RPC error 字段（-32601 / -32602 / -32700）方法不存在、参数非法、请求本身解析不了——协议层听不懂
工具执行错误result 里 "isError": true + 错误文案放进 content工具跑起来了但内部失败（如 embedding 超时）——协议层懂，业务没成
为什么工具失败不用 JSON-RPC error？因为请求在协议层面完全合法——服务器理解了方法、收到了合法参数、也成功执行了分发，只是"活儿没干成"。调用方（Bot 编排层）需要区分"该重试协议请求"和"该换一种方式回答"这两种情况，所以规范把业务失败放进正常响应体里。本篇 CozeBot 的兜底逻辑正依赖这个区分。

四、核心组件 2：tools 原语（search_knowledge 工具）

SEARCH_TOOL_DEF = {
    "name": "search_knowledge",
    "description": "在 LLM 知识库中检索与查询语义最相关的知识分块",
    "inputSchema": {                      # ← 标准 JSON Schema（真实 MCP 格式）
        "type": "object",
        "properties": {
            "query":   {"type": "string"},
            "top_k":   {"type": "integer", "default": 2},
        },
        "required": ["query"],
    },
}

# tools/call 的响应格式（真实规范 CallToolResult）：
{"content": [{"type": "text", "text": "[1] RoPE（旋转位置编码）...（相似度 0.612）"}],
 "isError": false}

工具实现沿用例 12-4 模式：dashscope text-embedding-v3 生成语义向量 + 纯 Python 余弦相似度 top-k 检索，向量缓存进 cache.json（重复运行不二次计费），替代教材的 Chroma + 90MB 本地 HuggingFace 模型。

MCP 工具 vs Function Calling 的关系：Function Calling 是模型厂商的私有接口约定（模型决定"调哪个函数"）；MCP 是工具的开放发布与发现标准（任何符合协议的客户端都能动态拉取工具清单并调用）。二者互补：模型经 Function Calling 决策，运行时经 MCP 执行。2025 年 OpenAI、Google 相继宣布支持 MCP，工具生态正在统一到这一标准。

五、核心组件 3：resources 原语 + CozeBot 工作流

# resources：把会话历史作为 URI 寻址的资源暴露
resources/list  →  [{"uri": "session://a1b2/history",
                     "name": "会话 a1b2 的对话历史",
                     "mimeType": "application/json"}]
resources/read  →  {"contents": [{"uri": ..., "text": "[{role,content},...]"}]}

CozeBot：真实扣子平台的工作流模拟

CozeBot.chat(session_id, user_input) │ ▼ ① user 消息先写历史（cache.json）── 修复教材"后写"顺序 bug │ ▼ ② MCP 工具调用：tools/call search_knowledge(query) │ isError=true 或异常 → 知识置空（不炸主流程） ▼ ③ 组装上下文：system（知识增强）+ 完整会话历史 │ ▼ ④ qwen-plus 生成 → assistant 消息回写历史 → 返回

真实扣子平台的集成方式：在 Bot 中添加 MCP 扩展并填入 MCP 服务 URL（Streamable HTTP / SSE），运行时平台按 MCP 协议拉取工具清单、在对话中调用工具——与本篇 McpClient 的行为一致，只是传输层换成 HTTP。
