例 12-2 讲解：Web 服务部署环境安全架构手段

本节核心变化：例 12-1 的服务是"裸奔"状态——任何人拿到地址就能白嫖你的 LLM 额度。本篇给服务穿上四层铠甲：HTTPS 加密 → API Key 认证 → IP 限流 → 安全响应头，从外到内构成纵深防御。同时修复教材的证书缺失、ProxyFix 失效和 torch.time bug。

一、为什么需要安全加固？

教材开篇说了三个理由：防数据泄露、防模型滥用、防服务攻击。落到一个 LLM API 服务上，具体风险是：

  • 传输被窃听——HTTP 明文传输，同一 WiFi 下抓包就能看到对话内容
  • 额度被白嫖——没有认证，爬虫扫到你的端口就能无限调用，DashScope 账单替别人买单
  • 服务被打挂——没有限流，一个脚本循环发请求就能耗尽配额、拖垮服务
  • 响应被利用——缺少安全头，API 响应可能被浏览器误解析（MIME 嗅探）、被恶意页面 iframe 套用

二、纵深防御四层架构

改写后的服务从外到内叠加四层防御，任何一层被突破，下一层还能兜底：

第 1 层 · 传输加密HTTPS（TLS）
防窃听防篡改
Flask adhoc 自签名证书
第 2 层 · 认证鉴权API Key 校验
缺失/错误 → 401
恒时比较防时序攻击
第 3 层 · 速率限制flask-limiter 按 IP
超限 → 429
防滥用防 DDoS
第 4 层 · 安全响应头nosniff / DENY / CSP
防 MIME 嗅探
防点击劫持
为什么顺序是"认证在限流之前"？ 本例中限流 decorator 挂在认证外层（先执行），401 请求也会消耗限流额度——这是刻意的：暴力破解 API Key 的行为本身就应该被限流掐死。实测里 401 也计数，最终第 6 个请求触发 429。

三、第 1 层：HTTPS 传输加密（证书问题修复）

教材的死路 vs 改写的活路

# 教材：证书文件不存在，直接崩溃
context = ssl.SSLContext(ssl.PROTOCOL_TLS)
context.load_cert_chain('cert.pem', 'key.pem')   # FileNotFoundError!
app.run(port=443, ssl_context=context)

# 改写：Flask 内置 adhoc 模式，自动生成临时自签名证书（需 cryptography 库）
app.run(host="0.0.0.0", port=8443, ssl_context="adhoc")
方案适用场景说明
ssl_context="adhoc"开发/测试（本例）自动生成临时证书，零配置；客户端需 verify=False 或 curl -k
load_cert_chain(正式证书)生产Let's Encrypt 免费签发，或云厂商免费证书
反代终结 TLS生产（更常见）Nginx/云负载均衡处理 HTTPS，Flask 只跑 HTTP 内网

端口选择：教学演示用 8443（教材的 443 保留为生产值）——最小权限原则的含义就是"只开必要端口"。

四、第 2 层：API Key 认证（教材完全缺失的防线）

def require_api_key(func):
    """API Key 校验装饰器：缺失或错误返回 401"""
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        key = request.headers.get("X-API-Key") or ""
        if not key:                        # 兼容 Bearer 方式（与 A2A 对齐）
            auth = request.headers.get("Authorization") or ""
            if auth.startswith("Bearer "):
                key = auth[7:]
        if not key or not secrets.compare_digest(key, API_KEY):
            # ↑ 恒时比较，防时序攻击逐位猜 Key
            return jsonify({"error": {"code": 401, ...}}), 401
        return func(*args, **kwargs)
    return wrapper

两个安全细节

细节原理
secrets.compare_digest() 恒时比较普通 == 比较遇到第一个不同字符就返回，攻击者可通过响应时间差逐位猜出 Key（时序攻击）；恒时比较无论错在第几位耗时都相同
兼容 Authorization: Bearer与 char10 A2A 协议的 bearer 认证方案对齐，未来接 A2A Client 无需改造

Key 管理策略：环境变量 AGENT_API_KEY 优先；未设置则 secrets.token_hex(16) 随机生成并打印（每次运行都变，模拟临时凭据）。生产环境 Key 应存密钥管理服务（KMS/Vault），绝不能硬编码。

五、第 3 层：速率限制（flask-limiter）

limiter = Limiter(
    get_remote_address,              # 按客户端 IP 限流
    app=app,
    default_limits=["60 per minute"],  # 全局兜底
    storage_uri="memory://",           # 显式声明内存存储

@limiter.limit("5 per minute")
@require_api_key

存储方式的选择（重要）

存储适用特点
memory://（本例）单机、教学进程内计数，重启清零，零依赖
redis://...生产多实例多台服务器共享计数；本环境无 Redis，按项目约定不引入，代码中已留注释说明

实测限流行为（Test 4 状态码序列）

[200, 200, 200, 429, 429]   ← 精确在第 6 次触发

为什么是第 6 次？限流窗口 5 次/分钟，401 被拒的请求也计数（Test 2 消耗 1 次）+ Test 3 正常 1 次 = 已用 2 次，Test 4 连发 5 次中前 3 次把额度用满，后 2 次触发 429。这验证了两件事：限流精确生效 + 暴力破解行为会被限流掐断。

六、第 4 层：安全响应头 + 输入校验

@app.after_request
def add_security_headers(response):
    response.headers["X-Content-Type-Options"] = "nosniff"   # 禁止 MIME 嗅探
    response.headers["X-Frame-Options"] = "DENY"              # 禁止被 iframe 嵌套
    response.headers["Referrer-Policy"] = "no-referrer"       # 不泄露来源
    response.headers["Content-Security-Policy"] = "default-src 'none'"
    return response

# 输入校验（防资源滥用）
max_tokens = min(data.get("max_tokens", 512), 1024)  # 上限截断
if not messages or len(messages) > 20:                 # 条数限制
    return jsonify({...}), 400

API 服务主要是 JSON 响应，安全头的作用在浏览器直连场景（如简单前端页面）才体现——但"默认全部加上"是零成本好习惯。

九、动手练习

  1. 生成正式自签名证书：用 openssl req -x509 -newkey rsa:2048 -nodes -keyout key.pem -out cert.pem -days 365 生成证书文件，替换 adhoc 模式，对比两种方式的差异。
  2. 多 Key 管理：把单一 API Key 改成字典 {key_id: key}，支持多个客户端各自凭据，401 日志里记录 key_id 便于审计。
  3. IP 白名单：实现一个 @require_ip_whitelist 装饰器，只允许指定 IP 访问 /health 以外的端点（对应教材"最小权限·限制访问IP"）。
  4. 限流存储升级实验：阅读 flask-limiter 文档，理解 storage_uri="redis://" 的多实例共享计数场景——写一段说明文字解释为什么多台服务器必须用集中存储。
  5. HTTPS 压测：用 ab -n 100 -c 10 https://localhost:8443/health 或 Python 脚本压测，观察限流拦截后的可用性表现。
