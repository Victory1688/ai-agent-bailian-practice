例 12-6 讲解：高并发的限流与降级策略

本节核心目标：给智能体服务装上"三道防线"。当 1000 个请求同时涌进来而 LLM 每秒只能处理 2 个时，系统必须有序地"拒绝一部分、排队一部分、兜底一部分"。本篇实现：限流（令牌桶快速失败）→ 削峰（优先级队列 + Worker 池缓冲）→ 降级（后端故障链式切换）。教材三大机制全部零验证（第七节只有一行启动注释），改写后 6 项 self-test 把每一种机制都真实触发了一遍。

二、三大机制总览：一个请求的生命周期

POST /chat（{"message": "...", "priority": 0 或 1}） │ ▼ ① 令牌桶 acquire() ──桶空──▶ 429 Too Many Requests（快速失败，保护下游） │ 拿到令牌 ▼ ② 优先级队列 put_nowait ──队列满──▶ 503 背压（系统容量已满） │ 入队 (priority, seq) ▼ ③ Worker 池（2 线程）按优先级取出任务 │ ▼ ④ 降级链 generate()：qwen-plus ──失败──▶ qwen-turbo ──失败──▶ 兜底文案 │ ▼ ⑤ Event 唤醒请求线程回填结果 ──超 60s──▶ 504 处理超时

三道防线各管一种问题

防线防御的问题失败响应关键参数
限流（令牌桶）流量洪峰超过系统容量429容量 5，速率 2 个/s

限流 vs 削峰的区别（面试高频）：限流是拒之门外——超出容量的请求直接拒绝，不消耗任何资源；削峰是排队缓冲——请求都收下，但用队列把"瞬时洪峰"摊平成"匀速处理"。两者是互补关系：先限流挡掉超额部分，剩下 valid 流量进队列削峰。

三、核心组件 1：令牌桶 TokenBucket（修复教材两处 bug）

class TokenBucket:
    """令牌桶限流：容量 capacity，每秒补充 refill_rate 个，桶空则拒绝"""

    def __init__(self, capacity, refill_rate, cache_file):
        state = self._load_state()
        # 优先从 cache.json 恢复（重启不回满）；首次运行才初始化满桶
        self._tokens = state["tokens"] if state else float(capacity)  # ← bug 修复：初始满桶
        self._last_refill = state["last_refill"] if state else time.time()
        self._lock = threading.Lock()

    def acquire(self) -> bool:
        with self._lock:                     # ← bug 修复：读-扣-写全程原子
            self._refill_locked()            #    教材 get/decr 分离有并发竞态
            if self._tokens >= 1:
                self._tokens -= 1
                self._save_state()           # 落盘 cache.json（替代 Redis 持久化）
                return True
            return False                     # 桶空 → 调用方返回 429

教材两处 bug 的危害推演

bug教材代码实际后果修复
初始空桶int(get(BUCKET_KEY) or 0)服务启动后到令牌攒够之前，所有请求都被误判限流，用户体验为"新服务上线即罢工"首次运行初始化 float(capacity) 满桶
非原子扣减tokens = get() 判断后 decr()两个并发请求同时读到 1 个令牌、都判断通过、都扣减 → 桶变 -1，限流形同虚设threading.Lock 包住判断+扣减（单进程）；Redis 场景应写 Lua 脚本
重启回满（教材未考虑持久化）服务重启后桶凭空回满，攻击者可诱发重启绕过限流每次扣减落盘 cache.json，重启恢复余量
惰性补充（lazy refill）的设计：教材用后台定时任务周期性补充令牌，改写版改为每次 acquire 时按流逝时间一次性补足（tokens = min(capacity, tokens + elapsed × rate)）。好处：无需定时线程、无锁竞争点、补充精度与请求精度对齐——这是工业界令牌桶的主流实现（Guava RateLimiter 同款思路）。

四、核心组件 2：优先级队列 + Worker 池（削峰填谷）

class PriorityEntry:
    """队列条目：(priority, seq) 排序 —— 高优先级先处理，同级先进先出"""

    _seq = itertools.count()                 # 全局单调递增序号

    def __init__(self, priority, payload):
        self.priority = priority             # 0 = 高优先级 / 1 = 默认
        self.seq = next(PriorityEntry._seq)
        self.event = threading.Event()       # 请求线程等待 worker 的桥

    def __lt__(self, other):
        return (self.priority, self.seq) < (other.priority, other.seq)

为什么必须加 seq？

教材用 (priority, time.time()) 元组排序——同一秒内到达的两个同级请求 time 相同，堆排序结果不稳定（谁先出队看运气）。seq 单调递增保证：高优先级必先出队，同级严格按入队顺序（FIFO），且永远不会抛元组比较异常。这是 heapq 官方文档推荐的标准写法。

Worker 池：修复"请求挂死"

def queue_worker():
    while True:
        entry = task_queue.get()             # 阻塞取最高优先级任务
        try:
            result = service.generate(entry.payload["message"])
            entry.result = {...}
            queue_stats["processed"] += 1
        except Exception as e:
            entry.result = {...FALLBACK_MSG}  # 异常也回填兜底文案
            queue_stats["failed"] += 1
        finally:
            entry.event.set()   ← 无论成败都唤醒等待的请求线程（修复挂死）
教材第 7 个问题就在这里：worker 处理时一旦抛异常，教材代码不会 set future——对应 HTTP 请求会一直挂到客户端超时。finally: entry.event.set() 把"回填"变成无条件动作：成功回结果、失败回兜底文案，请求线程永远不会被遗忘。

五、核心组件 3：降级链与 /chat 端点

def generate(self, message) -> str:
    """带降级的 LLM 调用：主后端失败 → 备用 → 兜底文案"""
    for backend in self.backends:
        try:
            answer = self._call(backend, message)
            logger.info(f"[LLM] 由 {backend['name']} 处理成功")
            return answer
        except Exception as e:
            logger.warning(f"[降级] {backend['name']} 失败 → 尝试下一后端")
    logger.error("[降级] 全部后端不可用")
    return FALLBACK_MSG

降级链直接复用例 12-5 的"自动切换 + 优雅降级"思想，从 Agent 内部机制移植到服务层。

/chat 端点的四态响应（每个状态码都有明确语义）

状态码触发条件语义客户端该怎么做
200全链路成功正常结果—
429令牌桶为空速率超限（客户端的错）退避后重试（参考 Retry-After）
503队列已满（背压）系统容量不足（服务端的错）换低峰期或走备用通道
504等待结果超 60s处理超时重试需带幂等键
429 与 503 的区别：429 说"你请求太快了"，责任在客户端，应该指数退避；503 说"我自己满了"，责任在服务端，客户端重试也没用应该换通道。混用两者会让监控告警无法归因——生产 API 网关都会严格区分。

Test 4 优先级插队的时序设计（本篇最难验证的一项）

# 三线程错峰发出，构造"worker 全忙 + 高优先级排队"场景：
t0        低-1 到达 → worker-0 取走（假 LLM 延迟 0.5s）
t0+0.05   低-2 到达 → worker-1 取走（假 LLM 延迟 0.9s，占住 worker）
t0+0.20   高-0 到达 → 两 worker 全忙 → 高-0 在队列中等待
t0+0.50   worker-0 空闲 → 队列头是高-0（priority=0 优先于低-2 的 1）→ 插队取走
t0+0.60   高-0 完成（延迟仅 0.1s）；t0+0.95 低-2 才完成

实际处理顺序（日志）: ['低-1', '高-0', '低-2']
                       ↑ 高-0 晚到 0.15s 却排在低-2 前面 —— 插队生效
为什么 Test 4 必须精心设计时序？三个坑：① 顺序发请求时队列里永远只有 0-1 个任务在等，高优先级根本没有插队对象；② 真实 LLM 每次调用 3s+，令牌边用边补充会稀释限流效果——所以注入本地假 LLM（差异化延迟 0.5s / 0.9s / 0.1s）保证时序确定且零 API 成本；③ 断言只能读"本次运行"的日志尾部，跨次运行累积的历史记录会污染 index() 首次命中位置（这是调试中真实踩到的第三个坑）。

九、动手练习

  1. 滑动窗口限流：用时间戳双端队列实现滑动窗口计数器，与令牌桶对比——同样容量 5，突发 10 个请求时两者各放行几个？（体会令牌桶"突发容忍"、滑窗"严格均摊"的差异）
  2. 分布式限流：把 TokenBucket 状态搬回 Redis，用一段 Lua 脚本原子执行"补充 + 判断 + 扣减"三步，亲身体会教材非原子 bug 为什么必须用 Lua 解决。
  3. 背压实测：把 QUEUE_MAXSIZE 调成 2，用 20 线程并发发请求，观察 503 出现的时机——并思考为什么队满比桶空更晚发生。
  4. 同级 FIFO 验证：并发发 5 个 priority=1 请求，断言处理顺序与发送顺序一致——这依赖 seq 而非线程调度顺序（把 seq 去掉再试，观察顺序混乱）。
  5. 降级预算：给 AgentService 加"每分钟最多降级 N 次"保护——qwen-plus 长时间故障时防止全部流量压垮 qwen-turbo（熔断思想与 12-05 呼应）。
