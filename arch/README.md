# 大模型 Agent 五模块划分 —— 判定与架构图

> 判定时间：2026-10-10　|　参考依据：`architecture-reference/architecture-patterns.md`（分层模板 + ADR 范式）

## 一、结论：基本正确，但要修正两点

你的理解 **「感知 / 认知 / 执行 / 记忆 + 接口 = 5 大部分」是成立的**，也是业界常见划分之一，但它 **不是唯一的标准答案**，需要补两点：

| # | 判断 | 说明 |
|---|---|---|
| ✅ 正确 | 感知 / 认知 / 执行 / 记忆 是四大核心 | 这四块是绝大多数 Agent 文献与工程实现的共识骨架，你的表述没问题 |
| ✅ 合理 | 接口模块作为第 5 模块 | 合理，但**有争议**。很多划分把「输入接口」并入感知、「工具/输出接口」并入执行，于是只剩 4 模块 |
| ⚠️ 修正 1 | "5 大部分"不是定论 | 常见变体：4 模块（感知/记忆/规划/执行）、5 模块（+工具）、6 模块（+安全对齐或+评估）。**模块数量取决于划分粒度，不是事实问题** |
| ⚠️ 修正 2 | 缺少横切层 | 生产级 Agent 必须显式列出**横切关注点**：编排调度、安全与对齐（护栏）、可观测与评估、成本与限流。它们不占流程位置，但缺一个都不能上线 |

### 一句话回答

> 结构上**对**，口径上**不严谨**：说"通常包括这 5 个模块"不如说"常见划分之一是：认知为核心，感知/执行/记忆为支撑，接口为边界，另有安全/可观测等横切能力"。

## 二、模块职责对照表

| 模块 | 核心职责 | 工程上拆成的子能力 | 常见实现 |
|---|---|---|---|
| ① 接口模块 Interface | 与外部世界交互的边界 | 多模态输入解析、协议与工具定义适配、输出渲染分发、会话通道管理 | API Gateway、MCP / Function Calling Schema、SSE/WebSocket、IM/语音接入 |
| ② 感知模块 Perception | 理解输入、构建上下文与状态 | 多模态理解、意图与实体识别、上下文/状态构建、工具结果归一化 | 多模态模型、意图分类器、Embedding、状态机 |
| ③ 认知模块 Cognition（大脑） | 决策核心：规划 → 推理 → 反思 | 任务规划与分解、推理与工具选择、结果合成校验、反思纠错、模型路由降级 | LLM（ReAct / Plan-and-Execute）、Critic 模型、Router |
| ④ 执行模块 Action | 与工具/环境交互并产生副作用 | 函数/API 调用、代码与沙箱执行、浏览器/RPA 自动化、幂等与回滚 | MCP / Function Calling、E2B 类沙箱、Playwright、任务队列 |
| ⑤ 记忆模块 Memory（横切） | 让 Agent 拥有跨轮次、跨任务的连续性 | 短期（上下文窗口）、长期（向量库 RAG）、情景（任务轨迹）、语义（画像规则）、记忆管理（写入/检索/压缩/遗忘） | Redis + 向量库（pgvector/Milvus）、会话摘要、事件日志 |
| 横切支撑层 | 保证系统可控、可查、可算钱 | 编排与调度、安全与对齐、可观测与评估、成本与限流 | 编排框架（LangGraph 类）、护栏中间件、Tracing/Eval、Token 计量与小模型路由 |

### 📌 画图时采用的假设

- 面向**通用 LLM Agent**（对话型 + 任务型），非特定垂直场景；
- 模块编号按**数据流顺序**排：接口① → 感知② → 认知③ → 执行④，记忆⑤ 作为横切能力单独一列；
- 依据 `architecture-patterns.md` 的分层模板画法：方框=组件、实线箭头=同步调用、虚线=回灌/横切、底部单列支撑层。

## 五、下一步建议（按优先级）

1. **若用于对外汇报/文档**：直接引用本图，并在文字里把"5 模块"表述为"常见划分之一"，避免被质疑口径。
2. **若用于真实系统设计**：把「认知模块」再拆一层（Planner / Executor / Critic / Router），这是落地时最容易混淆的地方。
3. **若担心过度设计**：按 `architecture-patterns.md` 的演进路线走 —— MVP 期记忆先只做"会话摘要 + 单库检索"，不要一上来就上向量库集群。
