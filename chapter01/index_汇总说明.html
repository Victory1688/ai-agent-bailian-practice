一、这组代码到底想表达什么

char01 回答大模型应用开发的第一个问题：抛开所有框架和智能体概念，调用一个大模型最本质的形态是什么？答案就一行代码——输入一个 messages 列表，返回一段文本。大模型 = 一个输入提示词、输出文本的函数。而全部 6 篇都在回答这个"函数"怎么用好：提示词怎么设计（01）、要不要用框架管理（02）、不同类型的任务怎么建模（03/04）、接口长什么样（05）、怎么用上下文引导多步任务（06）。

一句话概括每篇
  • 01 文本摘要：提示词三要素（角色 / 任务 / 约束）+ 占位符模板 + dashscope 最小调用
  • 02 提示词驱动的 Agent：引入 LangChain——PromptTemplate 变量化管理 + LCEL 管道 template | llm | parser
  • 03 生成 SQL：生成类任务建模——自然语言转 SQL，约定 JSON 输出（sql + explanation）
  • 04 文本抽取：抽取类任务建模——从文本抽企业名和地址，用输出格式样例锚定 JSON 结构
  • 05 接口模式设计：标准对话接口契约——system/user 消息角色 + temperature / max_tokens 生成参数
  • 06 上下文引导：把"已完成步骤 / 当前阶段"写进提示词，引导模型分阶段推进多步任务

四、6 篇"变与不变"：一个调用壳，六种提示词

和 char02 的"固定骨架 + 可插拔工具"呼应，char01 的结构是"固定调用壳 + 可变提示词建模"：

不变的调用壳（01/03/04/05/06 五篇共用）
# 1. 环境配置：API Key 永远走环境变量
api_key = os.environ.get('DASHSCOPE_API_KEY')
dashscope.api_key = api_key

# 2. 封装模型响应函数：所有篇的统一出入口
def get_response(messages):
    response = dashscope.Generation.call(
        model='qwen-plus',
        messages=messages,
        result_format='message'      # 统一 message 格式，取值路径一致
    )
    return response

# 3. 组装 messages → 调用 → 取 content
messages = [{"role": "user", "content": prompt}]
response = get_response(messages)
print(response.output.choices[0].message.content)
变的只有提示词的"建模方式"
  • 01：角色 + 任务 + 约束 + {} 占位符（模板化）
  • 02：交给框架管理（PromptTemplate 的 input_variables）
  • 03：生成类建模——任务要求逐条列出（表名/字段/语法/输出格式）
  • 04：抽取类建模——给出输出 JSON 样例，让模型"照葫芦画瓢"
  • 05：消息结构建模——system 定角色边界，user 放具体请求
  • 06：上下文建模——把任务进度注入提示词，单次调用模拟多步推进

结论（新人请记住这句话）：提示词工程不是"会聊天"，而是把业务任务翻译成模型能精确执行的结构化指令。调用代码千篇一律，提示词建模才是真功夫。

五、任务建模方法论（本组代码的核心技能）

03 和 04 两篇看似只是换了场景，实际是在教两类典型任务的标准建模套路——几乎所有大模型应用需求都能归入这两类：

维度生成类任务（03：NL2SQL）抽取类任务（04：NER）
输入自然语言指令 + 表结构约束待处理原文 + 字段清单
提示词骨架角色（数据库专家）→ 要求逐条编号 → 指令注入任务说明 → 输出 JSON 样例 → 原文注入
输出约定JSON：{"sql": "...", "explanation": "..."}JSON：{"company": "...", "address": "..."}
为什么约定 JSONsql 字段要被下游程序拿去真的执行字段要被下游程序入库/展示
随机性控制需要低随机（temperature 越低越稳）同样需要确定性（抽取没有发挥空间）
结构化输出：从"能聊"到"能用"的分水岭

01 篇的摘要输出给人看，print 完就结束；03/04 篇的 JSON 输出给程序看——下游代码要 json.loads 它、拿字段值去执行 SQL、写数据库。一旦模型输出需要被代码消费，"输出格式约定"就从建议变成了契约。这是大模型应用和聊天机器人的本质区别。

七、教学简化 vs 生产差距

这套教学代码离生产还差的距离
  • 输出未校验：03/04 的 JSON 输出直接 print，生产必须 json.loads + 异常处理 + 格式不符时的重试
  • 无错误处理：网络超时、限流（429）、内容审查拦截都没有处理分支
  • 模型名写死：model='qwen-plus' 硬编码，生产应放进配置
  • 无流式输出：生产级对话产品用 streaming 逐字返回，体验差异巨大
  • 单轮调用为主：只有 06 触及上下文，真正的多轮对话管理在 char02 完成
  • 02 的组件较旧：ChatTongyi 属于 langchain_community，1.x 官方更推荐 langchain_openai 兼容层（base_url 指向百炼兼容端点）——教学取它"零新增依赖"的优势
但建模思想是通用的

上面缺的全是"工程外围"；提示词三要素、任务建模四步、输出契约、上下文引导这些方法论不随框架版本变化——换任何模型、任何 SDK 都成立。这也是为什么本组代码把调用壳压缩到最简：让注意力全部留在提示词上。

八、新人学习路径建议

  1. 第 1 步（最小闭环）：精读 01，亲手把 prompt 里的角色/任务/约束三段拆出来看。自测：不看书写出"从调用到打印"的完整 10 行代码。
  2. 第 2 步（接口契约）：读 05，给同一段 messages 分别加/去掉 system 角色，对比输出差异。自测：说清三种消息角色和两个生成参数的作用。
  3. 第 3 步（两类建模）：跑通 03 / 04，然后模仿着做一道新题（如"从订单文本抽取商品名和金额"）。自测：能独立写出"要求逐条 + JSON 样例"式提示词。
  4. 第 4 步（框架化）：读 02，把 01 的手拼模板改写成 PromptTemplate + LCEL 管道。自测：说清 f-string、PromptTemplate、LLMChain、LCEL 四者的演进关系。
  5. 第 5 步（上下文引导）：读 06，自己再造一个三步任务（如订机票：查航班→选座→付款），把进度状态写进上下文。自测：解释为什么这已经是"Agent 的雏形"。
  6. 第 6 步（进入 char02）：带着 06 的疑问读 char02-01——当模型自己决定"下一步做什么"时，提示词引导就升级成了 Function Calling。两章连起来才是完整拼图。
