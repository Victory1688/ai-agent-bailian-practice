对应文件：char04/05_多工具调用顺序管理.py | 教材出处：第4章【例4-5】多工具调用顺序管理：实现复杂任务流 | 生成日期：2026-10-11

一、这份代码整体在做什么（一段话讲给新人）

这份代码演示了多工具协同：给 Agent 配三个工具——"搜索"、"摘要"、"翻译"——让它完成一个需要多步加工的任务："用中文总结 AI Agent 的基本定义"。理想链路是一条流水线：

search_web（搜定义）→ summarize_text（做摘要）→ translate_to_zh（翻中文）→ 最终回答

与前几篇只配一两个工具不同，本篇的问题是：三个工具按什么顺序调？谁决定顺序？——这正是本篇标题"多工具调用顺序管理"要回答的。而实测结果给出了比教材预期更深刻的答案（见第六、七节）。

教材想教的是"三个工具按特定顺序协同"，但 ReAct Agent 的真实语义是：调用顺序由模型现场规划，而不是开发者写死——模型有权判断"这一步是否必要"，甚至有权跳过你点名的工具（路径 B 第 3 步）。这不是模型不听话，恰恰是 Agent 与普通程序的本质区别：模型会为结果负责地省掉冗余步骤。如果任务必须强制三步顺序（确定性流水线），正确工具不是 Agent，而是本系列 01 篇的 SequentialChain——见第七节的对照闭环。

四、核心概念速查表

概念是什么在本例中的角色
@tool 装饰器新式工具定义：函数 + docstring 直接变工具三个工具的定义方式（本篇新知识点，见 5.1）
StructuredTool@tool 装饰后生成的对象：带参数 schema 的工具search_web 等三个函数装饰后的真身，可直接进 tools 列表
docstring 即说明书@tool 方式下，函数的 docstring 自动成为工具 description"根据用户输入执行Web搜索…"——模型选工具的唯一依据
哑工具（stub）返回固定值的假实现summarize_text / translate_to_zh 都是哑工具——教学上隔离外部依赖，让注意力集中在调用顺序
temperature=0零随机性顺序规划要可复现
多工具协同多个工具按语义依赖接力（A 的输出是 B 的输入）搜索 → 摘要 → 翻译的数据流水线

五、逐段代码讲解

5.1 @tool 装饰器（本篇新知识点，与 02-04 篇的 Tool 类对照）

@tool
def search_web(query: str) -> str:
    """根据用户输入执行Web搜索，并返回摘要结果"""
    if "AI Agent" in query:
        return "AI Agent是一种基于大语言模型的自主任务执行单元，具备工具调用与上下文感知能力。"
    return f"未找到关于：{query} 的相关信息"

对比 02-04 篇的旧式写法：

维度Tool 类包装（02-04 篇）@tool 装饰器（本篇）
定义位置函数定义完再单独包装定义的同时就地变工具
说明书来源显式传 description 参数直接用函数 docstring
参数 schema无（ReAct 下输入是裸字符串）从类型注解自动生成（StructuredTool）
本系列归宿经典 API，已废弃1.x 推荐方式（与 Function Calling 时代的工具定义一脉相承）

5.2 两个哑工具（原样保留）

@tool
def summarize_text(text: str) -> str:
    """对给定文本执行摘要处理"""
    return "智能体是一种基于大模型的自主系统。"      # 不管输入是什么，固定返回

@tool
def translate_to_zh(text: str) -> str:
    """将英文摘要翻译成中文"""
    return "智能体是一种基于大模型的自主系统。"

教材的刻意设计：工具实现是假的，调用顺序是真的——把外部依赖（真搜索/真翻译 API）隔离掉，教学注意力 100% 集中在"模型如何规划多工具"。生产中把函数体换成真实实现即可（呼应 char02-05 的外部 API 工具模式）。

5.3 工具集成与 Agent 组装（原样保留）

tools = [search_web, summarize_text, translate_to_zh]   # 装饰后直接进列表，无需再包装
agent = initialize_agent(tools=tools, llm=llm, memory=memory,
    agent="zero-shot-react-description", verbose=True)
output = agent.run("用中文总结AI Agent的基本定义")

七、核心洞察：char04 的 01 与 05 正好构成"工作流 vs Agent"对照闭环

维度01 篇 SequentialChain（工作流）05 篇多工具 Agent（本篇）
调用顺序开发者写死：三段固定接力模型现场规划：可能走满、可能抄近路、可能跳过点名工具
确定性高——每次运行结构相同低——同一问题不同模型/提示词可能走出不同链路
数据传递output_key 与占位符同名匹配（框架搬运）模型在 Thought/Action Input 里手动搬运上一步 Observation
适用任务流程固定、每步必达的任务（如报告生成流水线）路径不确定、需要判断"要不要做"的任务（如开放问答）
成本可控性调用次数固定调用次数由模型决定——实测 1~2 次不等
给新人的选型口诀

步骤必须全走 → 用链（01 篇）；步骤做不做由模型判断 → 用 Agent（本篇）。本篇教材标题里的"显式地管理调用顺序"，严格说只有链做得到；Agent 管理的是"工具的可用性"，顺序永远归模型管。理解这条界线，就理解了当前业界"工作流（Workflow）"与"智能体（Agent）"之争的技术本质——04 篇 HTML 首次提出这对概念，本篇用两条实测路径完成了实证闭环。

八、生产视角：教学版离上线的差距

  • 哑工具必须换真：search_web 接真实搜索 API（SerpAPI/Bing/博查），translate 接翻译服务；且真搜索返回的是长文本列表，需要先解析再入链
  • 顺序不可控的风险：业务上"必须三步都走"的场景（如合规要求每步留痕）不该用 Agent——用 01 篇的链，或 create_agent + 强制工具路由中间件
  • 中间结果不校验：模型可能把错误内容传给下游工具——生产在每步之间加结果校验（呼应 char03-09 的置信度评估）
  • 无迭代上限：多工具任务更容易陷入循环——AgentExecutor 应设 max_iterations
  • 无多任务并发：三个工具串行调用总耗时高——独立步骤可并行（呼应 char03-07 的批处理思想）
