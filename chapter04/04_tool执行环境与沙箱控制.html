一、这份代码整体在做什么（一段话讲给新人）

这份代码演示了沙箱（Sandbox）——给 Agent 的工具套上"安全罩"。场景是让模型计算数学表达式，但工具内部用的是 Python 的 eval（一个臭名昭著的危险函数：能执行任意代码）。如果用户诱导模型把恶意命令传进来（如 os.system('rm -rf /') 删库命令），裸 eval 会真的执行它。
沙箱就是三道防线：①限时执行（最多 3 秒，防死循环）→ ②字符白名单（只放行数字和运算符，字母、分号、下划线统统拦下）→ ③空内置命名空间（eval 里找不到任何内置函数）。恶意表达式会在某一层被拦截，主系统安然无恙。

四、核心概念速查表

概念是什么在本例中的角色
沙箱（Sandbox）隔离执行环境：限制代码的权限与资源safe_eval 函数整体就是一个进程内微型沙箱
signal.SIGALRM / signal.alarmUnix 信号机制的定时器（Windows 不存在）原写法的限时实现——本篇被替换的部分
threading.Thread(daemon=True) + join(timeout)跨平台限时方案：后台线程干活，主线程限时等待改写后的限时实现，3 秒上限与原版一致
eval(expr, globals)动态执行字符串表达式；globals 参数限定可见的名字空间被保护的危险核心，{"__builtins__": {}} 掏空内置函数

daemon=True守护线程：主程序退出时自动终止，不阻塞进程保证超时的"僵尸"计算不会拖住整个 Agent
temperature=0零随机性，输出确定性最高数学计算任务的标准参数选择

五、逐段代码讲解

5.1 限时执行器（改写点：signal → 线程）

# 原写法（Unix 专属，注释保留）：
# class TimeoutException(Exception):
#     pass
# def timeout_handler(signum, frame):
#     raise TimeoutException("执行超时")
# signal.signal(signal.SIGALRM, timeout_handler)

# 改写（Windows 可用）：
EVAL_TIMEOUT_SECONDS = 3
thread = threading.Thread(target=worker, daemon=True)
thread.start()
thread.join(timeout=EVAL_TIMEOUT_SECONDS)   # 主线程最多等 3 秒
if thread.is_alive():
    return "执行超时"

原理对比：signal.alarm 是操作系统定时器中断主线程（Unix 才有）；线程版是把活儿外包给后台线程，主线程限时等待——超时不杀线程（Python 无法强杀线程），而是直接返回"执行超时"，daemon=True 保证最后不会拖住进程退出。

5.2 沙箱核心：白名单 + 空 builtins（原样保留）

allowed_chars = "0123456789+-*/(). "
if not all(c in allowed_chars for c in expression):
    return "非法表达式，包含禁止字符"
result = eval(expression, {"__builtins__": {}})

注意防线的先后顺序：白名单在前，eval 在后——绝大多数恶意输入（含字母、分号、引号）在第一关就出局，根本到不了 eval。这体现了纵深防御的经济学：最便宜、最可靠的检查放最前面。

5.3 异常与资源清理（结构保留，合并为通用 except）

except Exception as e:
    outcome["reply"] = f"执行失败：{str(e)}"
...
return outcome.get("reply", "执行失败：未知错误")

延续"工具永不抛异常"纪律：超时、非法、执行错误全部以字符串返回，Agent 循环不断。线程版把原来的 TimeoutException 分支（主线程捕获）与 Exception 分支（worker 内捕获）合并——因为线程里抛的异常主线程接不住，必须在线程内就地处理并通过共享字典传出。

七、与 char02-07 的呼应：exec 沙箱警示的"实现示范"

char02-07 读写本地文件篇的 exec_code 工具曾留下安全警示（exec 是最危险的工具，生产需沙箱/白名单/最小权限）。本篇正是那个警示的落地示范：

防线char02-07 的警示（当时指出的问题）char04-04 的实现（本篇的做法）
输入白名单"exec 能执行任意代码"字符白名单挡在 eval 之前
命名空间隔离"exec(code, {}, local_vars) 的 globals 可控"eval(expr, {"__builtins__": {}}) 掏空内置
资源限制"死循环/资源爆炸会拖垮系统"3 秒限时（线程版跨平台）
错误隔离"工具永不抛异常"异常全捕获、字符串返回
诚实的边界：进程内"微型沙箱"不是真沙箱

业界共识：eval 的空 builtins 可以被精心构造的表达式绕过（如利用对象属性链 ().__class__.__mro__... 反射出危险模块）——本例中字符白名单把这些字符全挡了，所以防线实际由白名单独自扛住。真正的强隔离是进程级（subprocess + 资源配额）或容器级（Docker/Firecracker）。教学版演示的是"最小可懂沙箱"，生产版请直接上容器。

八、生产视角：教学版离上线的差距

  • 隔离级别不够：线程内 eval 与主系统共享内存与文件系统——生产用 subprocess/Docker 容器（进程级/系统级隔离）
  • 白名单是唯一硬防线：一旦业务必须放行字母（如支持幂运算 ** 或函数），白名单就会失效——生产改用专用表达式解析器（如 ast 模块解析后白名单节点校验，或 mathexpr 这类专用库），根本不让 eval 上场
  • 超时不回收线程：超时后 worker 线程仍在后台跑——daemon=True 保证进程退出时不挂，但长驻服务里要配线程池上限
  • 无审计：被拦截的恶意请求没有留痕——生产要记录拦截日志（谁、什么表达式、哪层拦截）供安全审计（呼应 char02-04 的注销日志思想）
  • initialize_agent 已废弃：同前几篇，2.0 移除，新项目用 create_agent

九、动手练习

  1. 直测沙箱：写 5 行代码直接调用 safe_eval("1/0")、safe_eval("(1+2")、safe_eval("__import__('os')")，观察三条不同错误路径的返回（除零报错 / 括号不匹配报错 / 白名单拦截）。
  2. 限时实证：临时把白名单放宽后传入 sum(range(10**10)) 类慢表达式（需先想清楚为什么它能骗过原白名单——提示：它含字母），或直接把 EVAL_TIMEOUT_SECONDS 改成 0.001 跑测试 1，观察"执行超时"分支触发。
  3. 绕过攻防思考题：假设白名单额外放行了下划线 _，表达式 ().__class__.__bases__[0].__subclasses__() 能否掏空 builtins 的 eval 里执行？答案：能——这就是为什么生产绝不 eval 用户输入，要用 AST 白名单校验。
  4. 进程级沙箱初体验：把 safe_eval 的 eval 换成 subprocess.run([sys.executable, "-c", expression], timeout=3, capture_output=True)——体会"进程级隔离"与本篇"线程级隔离"的差异（崩溃不影响主进程，但要处理子进程输出与编码）。
