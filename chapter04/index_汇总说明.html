二、这组代码想表达什么（总定位：框架化）

char01~03 的所有 Agent 都是手写的——char02 用 200 行 Python 亲手写 agent_chat 循环，char03 亲手搭推理服务。char04 换了一种存在方式：把之前手写的一切交给 LangChain 组件。它想表达的核心命题是：

框架化的本质：用声明换控制权

手写循环（char02）：每一行消息流向都看得见，但每写一个新 Agent 都要重写骨架。框架（char04）：initialize_agent 一行拼装，但循环进了黑盒——你只控制"给什么工具、什么记忆、什么提示词"，不再控制"循环怎么转"。
本系列的教学顺序刻意如此：先手写（char02）看透原理，再用框架（char04）享受效率——直接学框架的人永远不知道黑盒里在发生什么，出了问题（如本篇 06/07 的模板与记忆 bug）完全无从下手。

7 篇沿一条递进主线展开：

01 链（固定流水线） → 02 Agent（模型决策） → 03 +记忆 → 04 +安全沙箱
                    → 05 多工具（新式定义） → 06 定制灵魂（提示词） → 07 跨轮工具链（收官）

三、"变与不变"：一个骨架、两种工具定义、一个模型适配

3.1 六篇共用的 Agent 骨架（不变项）

llm = ChatTongyi(model="qwen-plus", temperature=..., dashscope_api_key=os.environ.get("DASHSCOPE_API_KEY"))
tools = [...]
memory = ConversationBufferMemory(...)
agent = initialize_agent(tools=tools, llm=llm, memory=memory, agent="zero-shot-react-description"/CONVERSATIONAL_REACT, verbose=True)
agent.run("...")

02/03/04/05/06/07 六篇只换三样东西：工具集（变量）、agent 类型（02/05 用 zero-shot，03/04/06/07 用 conversational）、本篇的新组件（memory/沙箱/自定义 prompt）。骨架一次学完，后面每篇只增量学一个概念。

3.2 工具定义的两代同堂（char04 独有的对照）

方式篇目写法现状

3.3 模型适配层（每篇相同的两行换装）

原教材的 OpenAI/ChatOpenAI → ChatTongyi(model="qwen-plus") + 环境变量钥匙。LangChain 的模型抽象（BaseChatModel）在这里兑现价值：换模型不动任何 Agent 代码——这正是 char03-05"协议即标准"在框架层的体现。

四、教材代码质量谱系（char04 特色：bug 密度最高的一章）

7 篇里 4 篇藏着"即使环境修好也跑不通"的教材自带 bug——这份谱系本身就是最好的教学素材
篇bug 类型现象根源教学价值
01API 误用（硬错误）run() 声明 3 个输出键直接抛 ValueErrorrun() 只支持单输出键链的多输出必须用 invoke()/dict 访问
02类型错配（硬错误）"20" * 7.25 抛 TypeErrorReAct 协议的输入永远是字符串工具入参必须显式类型转换——Function Calling 的 JSON Schema 就是解药
06概念代码（最深）custom_prompt 覆盖不生效/报错该 Agent 类型工具清单预格式化，from_llm_and_tools 无 prompt 参数（查源码实证）自定义提示词的正确通道是 prefix/suffix
07静默失败（最隐蔽）不报错，但第 2 轮模型"失忆"memory_key="history" 与默认模板 {chat_history} 不匹配不抛异常的 bug 才是最危险的 bug
04平台不兼容signal.SIGALRM 在 Windows 抛 AttributeErrorUnix 专属信号机制跨平台代码不能假设 OS 能力
全部import 断裂 + 模型不可直连ImportError / 认证失败LangChain 1.x 拆分 + 网络环境共性改写范式的由来
03 / 05（无隐藏 bug）--改写后即跑

  8. 模型会"抄近路"跳过工具（05），也会"加戏"多做步骤（07）——这说明调用顺序的决定权在谁？
  9. CONVERSATIONAL_REACT 的提示词由哪四段组装？哪两段可以定制、哪一段动了会炸？（06）
