03_具备对话以及功能的agent - 代码解析

对应文件：char04/03_具备对话以及功能的agent.py | 教材出处：第4章【例4-3】Memory 记忆管理 | 生成日期：2026-10-11

一、这份代码整体在做什么（一段话讲给新人）

这份代码在前两篇基础上给 Agent 装上了记忆（Memory）：同一个 Agent 连续进行三轮对话，每轮的问答都存进 ConversationBufferMemory，让后续轮次"记得前面聊过什么"。三轮对话是精心设计的递进：

轮次用户输入记忆在起什么作用
第 1 轮"我想知道北京天气如何？"（无记忆可依赖，正常调工具）
第 2 轮"那广州呢？"输入只有三个字——没有"天气"二字，模型靠记忆知道这是在问天气，正确调了 WeatherTool
第 3 轮"那明天去哪旅游好？"模型靠记忆想起前两轮聊过北京/广州的天气，自主决策查北京天气并据此给出具体旅游推荐

一句话总结：没有 Memory，"那广州呢？"就是一句莫名其妙的话；有了 Memory，省略主语的追问才成为可能——这就是"具备连贯性的智能对话体验"的含义。

三、整体执行流程：Memory 如何跨轮积累

┌────────────────────────────────────────────────────────────────┐
│                ConversationBufferMemory（chat_history）          │
│                                                                │
│   第1轮结束后存入:   human: 我想知道北京天气如何？               │
│                      ai:   北京目前天气晴朗，气温为25°C。        │
│                                                                │
│   第2轮结束后追加:   human: 那广州呢？                           │
│                      ai:   广州当前天气为雷阵雨，气温29°C。      │
│                                                                │
│   （每轮开始前，memory 里积累的全部历史 → 拼进模型 prompt）        │
└────────────────────────────────────────────────────────────────┘
        │                    │                    │
        ▼                    ▼                    ▼
   第1轮: 查北京         第2轮: 查广州         第3轮: 查北京→旅游推荐
   （模型看到）          （模型看到记忆里       （模型看到两轮天气记录，
    "北京天气"            的北京对话，才懂        推理出"结合天气给建议"）
                          "那广州呢"=问天气）
memory 在 Agent 循环里的位置

ConversationBufferMemory 被注入 initialize_agent 后，AgentExecutor 每轮执行前自动做两件事：① 把 memory 内容按 memory_key="chat_history" 塞进 prompt；② 本轮结束后把新的问答对追加进 memory。你不需要像 char02 那样手动 reply, memory = agent_chat(...) 传参——框架托管了记忆的读写，这正是 Memory 组件的价值。

四、核心概念速查表

概念是什么在本例中的角色
ConversationBufferMemory最基础的对话记忆：把历史问答原文一条条存下来三轮对话的"记事本"，每轮问答原样追加
memory_key记忆内容注入 prompt 时用的变量名"chat_history"——与 Agent 内部 prompt 模板里的占位符对应
input_key告诉记忆组件"哪个字段算用户输入""input"——agent.run("...") 的那个字符串
Buffer（缓冲区）名字里的含义：原文全存、不做压缩优点是信息无损；缺点是轮数多了 prompt 越来越长（见第八节）
agent="zero-shot-react-description"ReAct 智能体（02 篇已详解），此处用字符串等价指定与本篇唯一的新知识 Memory 组合：ReAct + 记忆
WeatherTool字典查表的模拟天气工具验证"记忆省略主语"的标准道具

五、逐段代码讲解

5.1 模拟天气工具（原样保留）

def get_weather(city: str) -> str:
    dummy_weather = {
        "北京": "晴，25°C",
        "上海": "多云，23°C",
        "广州": "雷阵雨，29°C"
    }
    return dummy_weather.get(city, "当前城市暂无天气数据")

纯字典查表，不发真实请求（与 char02-05 的真实 wttr.in API 形成对照：教学版先隔离外部依赖）。未收录城市返回提示字符串——延续"工具永不抛异常"的纪律。

5.2 记忆初始化（本篇核心，原样保留）

memory = ConversationBufferMemory(
    memory_key="chat_history",
    input_key="input"
)

就两行，却是本篇全部魔法所在：memory_key 必须与 Agent 内部 prompt 的占位符名一致（ReAct 模板里就是 chat_history），配错名记忆就注不进去——这是实际开发中最常见的踩坑点之一。

5.3 Agent 组装（只多了一个 memory 参数，原样保留）

agent = initialize_agent(
    tools=[weather_tool],
    llm=llm,
    memory=memory,        # 与 02 篇唯一的结构差异
    agent="zero-shot-react-description",
    verbose=True
)

对比 02 篇的 initialize_agent，唯一新增就是 memory=memory——框架设计的妙处：加记忆不用改任何其他代码。

5.4 三轮对话（原样保留）

res1 = agent.run("我想知道北京天气如何？")
res2 = agent.run("那广州呢？")
res3 = agent.run("那明天去哪旅游好？")

注意同一个 agent 对象连续 run 三次——记忆存在 agent 内部引用的 memory 对象里，三轮共享。如果每次都重新 initialize_agent，记忆就断了（动手练习 3 会验证这一点）。

第 3 轮的 Thought 值得逐字品读：模型明确意识到"问题中没给城市"这个信息缺口，并在"反问用户"与"查典型城市作示例"之间做了决策——这已经不是简单的记忆复读，而是基于上下文的自主规划。同时注意一个诚实的观察：模型查到的是"今天式"天气数据（工具是模拟字典），它把"晴 25°C"当作明日天气来推荐——模拟工具的语义局限，生产中要用带日期参数的真实预报 API（见动手练习 2）。

七、三种记忆方案对比：char04-03 vs char02 系列

维度ConversationBufferMemory（本篇）显式 memory 列表（char02-01/02）PersistentJSONMemory（char02-03）
谁来管理框架托管：AgentExecutor 自动读写手动传递：reply, memory = agent_chat(...)
存在位置进程内存（Buffer 的含义）进程内存磁盘 JSON 文件
进程重启后全部丢失全部丢失从文件恢复
存的内容human/ai 问答对原文完整 messages（含 system/tool 消息）完整 messages 持久化
适合场景框架内快速起步、单进程对话想看清每一步消息流向的教学场景跨会话、中断恢复的真实产品
一个关键的认识：Memory 组件解决的是"便利性"，不是"持久性"

本篇的 ConversationBufferMemory 让"加记忆"变成一行参数，但进程一退记忆全丢。char02-03 教的 JSON 持久化才是"中断恢复"的答案。char04 的 Memory 与 char02 的记忆是同一件事的两个层次：组件化便利 vs 原理透明——先在 char02 看清原理，再在 char04 享受便利，学习顺序的价值正在于此。

八、生产视角：教学版离上线的差距

  • Buffer 无上限：对话 50 轮后 prompt 会逼近模型上下文窗口且成本线性上涨——生产换 ConversationSummaryMemory（摘要压缩）或滑动窗口策略
  • 无持久化：进程重启记忆清零——生产接 char02-03 的 JSON 落盘思路，或 LangGraph checkpoint / Store API（deprecation 警告里官方推荐的正是这两者）
  • 无会话隔离：全局一个 memory，多用户同时用会互相"看见"对方对话——生产按 session_id 隔离（呼应 char02-08 的教学留白）
  • 模拟工具无日期语义：真实旅游推荐需要带日期的天气预报 API + 地理位置理解
  • initialize_agent / ConversationBufferMemory 均已废弃：2.0 移除，新项目按官方迁移指南改用 create_agent + checkpointing

九、动手练习

  1. 验证记忆断线：把三轮对话改成每轮都重新 initialize_agent（新建 agent 对象但共用同一个 memory 变量）——观察第 2 轮"那广州呢？"模型是否还能理解。再改成每轮新建 memory——记忆彻底消失，模型会反问"你想问广州的什么？"。
  2. 工具升级：给 WeatherTool 增加日期参数（如 "北京 明天"），把字典扩成二维结构，重跑第 3 轮看推荐质量变化。
  3. 塞爆记忆实验：写一个 for 循环连问 10 轮（每轮换个城市），观察 verbose 日志里每轮 prompt 的长度增长——直观理解 Buffer 的成本曲线。
  4. 记忆内容透视：三轮结束后打印 memory.load_memory_variables({})——亲眼看看 chat_history 里到底存了什么、以什么格式。
