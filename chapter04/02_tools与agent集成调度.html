一、这份代码整体在做什么（一段话讲给新人）

这份代码演示了 LangChain 的工具（Tools）与智能体（Agent）集成：给模型配两个工具——"网页摘要器"和"汇率换算器"——然后让它自主决定用哪个工具完成任务。当你问"20 美元换算成人民币"时，模型会：

  1. 思考：换汇率需要用换算工具
  2. 选工具：USDToCNYConverter
  3. 填参数：Action Input: 20
  4. 拿到结果：本地执行返回 145.0 人民币
  5. 生成最终回答：20美元 ≈ 145.0人民币

关键区别在于：上一篇（01）的链式处理是人把流程写死（固定三段接力），而本篇的 Agent 是模型自己决定流程（它看到问题后自主选择工具）。这就是"链"与"Agent"的本质分界。

二、原教材代码为什么跑不起来（三类问题）

问题原写法说明
1. import 路径断裂from langchain.agents import Tool, initialize_agent 等 3 行LangChain 1.x 路径拆分：经典 Agent API 收纳进 langchain_classic.agents，Tool 在 langchain_core.tools；langchain.llms.OpenAI 类已移除
2. 模型不可直连llm = OpenAI(temperature=0.3)改用百炼 ChatTongyi（qwen-plus），temperature=0.3 语义不变
3. 原代码隐藏 bugconverted = round(amount * rate, 2)ReAct 型智能体的工具输入是从文本协议（"Action Input: 20.0"）解析出的字符串，字符串 × 浮点数必然抛 TypeError: can't multiply sequence by non-int of type 'float'——原代码运行必然报错，不是版本迁移问题
本篇最有价值的知识点：工具输入永远是字符串（ReAct 时代）

ReAct 是文本协议：模型输出的 "Action Input: 20.0" 本质是一段文字，框架解析后把字符串直接传给工具函数。Python 的类型注解 amount: float 只是标注不会转换——所以工具函数内部必须自己做 float(amount)。
对比 char02 系列：Function Calling 时代模型输出的是结构化 JSON，框架已按 schema 自动解析类型——这就是两种工具调用方案的本质差异（详见第七节对比表）。

用户任务："请帮我把20美元换算成人民币"

│   ┌──────────────────────────────────────────────────┐               │

        │
        ▼
最终回答："20美元 ≈ 145.0人民币（按汇率7.25）"
ReAct 是什么：让模型"边想边做"的提示词协议

ReAct = Reasoning（推理）+ Action（行动）。它不是代码结构，而是一段写在 system 提示词里的格式约定——教模型按"Thought / Action / Action Input"的格式输出，框架解析这些文本行来驱动循环。ZERO_SHOT_REACT_DESCRIPTION 的意思：零样本（无需示例）+ 依据工具的 description 来选工具。

四、核心概念速查表

概念是什么在本例中的角色
Tool工具包装器：name + func + description 三要素把两个普通函数包装成模型可调用的工具
description（工具的）给模型看的"工具说明书"模型靠它判断"哪个工具适用当前任务"——写不好模型就选错
initialize_agent经典 Agent 工厂：组装工具 + 模型 + Agent 类型拼装出完整的 AgentExecutor（已标记废弃，新项目用 create_agent）
AgentType.ZERO_SHOT_REACT_DESCRIPTIONReAct 风格智能体决定模型按 ReAct 文本协议循环
AgentExecutorAgent 的运行引擎：解析模型输出 → 执行工具 → 回流观察 → 循环"决策权在模型、执行权在本地"的框架实现
Thought / Action / Action Input / ObservationReAct 文本协议的四个关键字verbose=True 时你在日志里看到的执行轨迹
verbose=True打印 Agent 每一步的思考与行动教学必备——不开就只看到最终答案

五、逐段代码讲解

5.1 工具1：网页摘要器（原样保留）

def fetch_summary(url: str) -> str:
    try:
        resp = requests.get(url, timeout=10)
        if resp.status_code == 200:
            content = resp.text[:1000]
            return f"网页摘要：{content[:300]}..."  # 仅返回前300字
        else:
            return "无法访问网页内容"
    except Exception as e:
        return str(e)

注意它完全符合 char02 沉淀的工具函数纪律：永不抛异常、错误也以字符串返回（HTTP 非 200 返回提示、异常返回错误文本）。这个纪律在 ReAct 时代同样成立——Observation 回流给模型，模型看到错误文本才知道"换条路"。

5.2 工具2：汇率换算器（bug 修复点）

def convert_usd_to_cny(amount) -> str:
    rate = 7.25
    converted = round(float(amount) * rate, 2)   # 修复：float() 显式转换
    return f"{amount}美元 ≈ {converted}人民币（按汇率7.25）"

原代码直接 amount * rate——ReAct 解析出的字符串 "20" 乘浮点数直接炸。修复加 float()。教学点：ReAct 工具函数的第一行往往是类型转换。

5.3 Tool 包装（原样保留）

Tool(
    name="USDToCNYConverter",
    func=convert_usd_to_cny,
    description="将美元金额转换成人民币金额，适用于财务相关查询",
)

三要素缺一不可：name 是模型嘴里喊的名字（Action 行），func 是本地真正执行的函数，description 是模型选工具的唯一依据。description 的写法有讲究——"做什么 + 什么时候用"，本例两句话正好覆盖。

5.4 组装与执行（原样保留）

agent = initialize_agent(
    tools, llm,
    agent=AgentType.ZERO_SHOT_REACT_DESCRIPTION,
    verbose=True
)
response = agent.run("请帮我把20美元换算成人民币")

initialize_agent 把"工具箱 + 模型 + 协议类型"拼成 AgentExecutor；agent.run 触发 ReAct 循环直到模型输出 Final Answer。

六、真实运行输出（完整 ReAct 轨迹）

已在本机实际运行验证（qwen-plus 真实调用，ReAct 循环完整走通）
> Entering new AgentExecutor chain...
需要使用USDToCNYConverter工具将20美元换算成人民币。        ← ① Thought（模型在思考）

Action Input: 20                                           ← ③ Action Input（填了参数 20）
Observation: 20美元 ≈ 145.0人民币（按汇率7.25）            ← ④ 本地执行结果回流

==== 输出结果 ====
20美元 ≈ 145.0人民币（按汇率7.25）

这段日志是本篇最大的教学财富：模型自主完成了"选工具 → 填参数 → 拿观察 → 给答案"的全过程，而本地代码只负责解析与执行。特别注意第一轮运行时曾抛出 TypeError——正是修复前的原代码 bug 现场：模型行为完全正确，错在工具函数没做类型转换。Agent 出错不一定是模型笨，更可能是工具实现糙。

七、两代工具调用方案对比：ReAct（本篇）vs Function Calling（char02/char03-06）

维度ReAct（本篇，经典方案）Function Calling（char02 八篇 / char03-06）
协议形态文本协议：Thought/Action/Action Input 都是提示词约定的文本行结构化协议：模型原生输出 tool_calls JSON
参数类型永远是字符串，工具函数内自行转换按 JSON Schema 自动解析（数字就是数字）
解析可靠性靠正则/关键词解析文本，模型格式偶尔跑偏就解析失败协议级保证，不依赖模型遵守文本格式
适用模型任何能对话的模型（包括不支持 FC 的）需要模型原生支持 function calling（qwen 系列都支持）
Agent 循环实现框架内置 AgentExecutor，对新人是黑盒char02 手写 while True 循环，每一步可见
历史地位2022-2023 主流，教学价值高（决策过程可见）当前主流，生产首选
char04 系列内部的关系：01 是"人写流程"，02 是"模型定流程"
  • 01 链式处理：步骤顺序是开发者写死的（三段接力），适合流程固定的任务（摘要→提问→总结）
  • 02 Agent 集成：用不用工具、用哪个、用几次由模型现场决策，适合路径不确定的任务（问汇率就用换算器，问网页就开摘要器）
  • 这两者正是"工作流（Workflow）"与"智能体（Agent）"的分野——当前业界讨论 AI 应用架构时的核心概念，char04 用两篇代码就把界线划清了

八、生产视角：教学版离上线的差距

  • 汇率是写死的 7.25：真实汇率每天浮动——生产应把工具升级为"调用实时汇率 API"（正好复用 char02-05 的外部 API 工具模式）
  • initialize_agent / run() 已废弃：LangChain 1.x 推荐 create_agent（基于 LangGraph）——本篇的 ReAct 原理仍是理解一切 Agent 的地基，但新项目代码要换 API
  • 无最大迭代保护：模型若陷入"反复调工具不停"的循环会烧钱——AgentExecutor 应设 max_iterations（教学版未设）
  • 网页摘要无安全边界：fetch_summary 会请求任意 URL——生产要加域名白名单、响应大小限制、SSRF 防护
  • ReAct 解析失败风险：qwen-plus 偶尔不按 Action 格式输出会导致解析失败——生产首选 Function Calling（见第七节）

  3. 加一个工具：仿照现有写法增加第三个工具（如温度换算 CelsiustoFahrenheit），用新问题测试模型能否在三个工具中选对。
  4. 类型转换思考题：把 fetch_summary 的参数类型改成 url（字符串）没问题，但如果是"金额列表"这样的复合参数，ReAct 文本协议下该怎么传？（答案：让模型输出 JSON 字符串、函数内 json.loads——这正是 Function Calling 出现前大家的土办法，也解释了 FC 为什么是进步。）
