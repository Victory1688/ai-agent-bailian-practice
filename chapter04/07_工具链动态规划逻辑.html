一、这份代码整体在做什么（一段话讲给新人）

这份代码演示工具链的动态规划：Agent 配两个工具——"搜书"（SearchBooks）和"查详情"（GetBookDetails），两轮对话完成一条任务链：

第 1 轮："我想查几本关于人工智能的书"     → 调 SearchBooks → 返回书单
第 2 轮："请介绍第一本书的详细信息"        → 模型靠记忆知道"第一本书"是谁
                                        → 调 GetBookDetails → 返回详情

教材导语说得准确：Agent 不再被动执行单一指令，而是理解任务上下文和目标，动态判断调用的工具类型与顺序。本篇与 05 篇（多工具顺序）的差别在于：05 篇的接力发生在单轮内（模型在一条链里连调几个工具），本篇的接力是跨轮的——"第一本书"这个指代物存在于上一轮的记忆里，工具链靠 Memory + 模型规划 串起来。这实际上是 char04 系列的"05 篇 + 03 篇记忆"合体。

问题原写法说明

06 篇：维基百科超时07 篇原代码：openlibrary 超时

四、核心概念速查表

概念是什么在本例中的角色
工具链（Tool Chain）多个工具按数据依赖接力（A 的输出是 B 的输入）书名（SearchBooks 的输出）成为 GetBookDetails 的输入
动态规划（Agent 语境）调用什么工具、什么顺序，由模型按上下文现场决定第 1 轮模型自主加戏连查详情；第 2 轮自主决定调哪个工具
指代消解（Coreference）理解"第一本书"这类指代具体指什么第 2 轮的关键——完全依赖记忆注入成功
memory_key 与模板变量对齐记忆注入的名字必须与 prompt 占位符一致"history" → "chat_history" 的一字修正，决定本篇成败
静默失败（Silent Failure）不报错但功能失效的 bug变量名不匹配不抛任何异常——比 06 篇的硬错误更难察觉
输入清洗（Input Sanitization）工具对模型传入参数做规范化处理模拟版 GetBookDetails 剥书名号、去" by 作者"后缀

五、逐段代码讲解

5.1 两个工具（改写为本地模拟，返回格式与原版逐字符一致）

LOCAL_BOOKS = [
    {"title": "人工智能：一种现代方法", "author": "Stuart Russell", "year": 2020},
    {"title": "深度学习", "author": "Ian Goodfellow", "year": 2017},
    {"title": "生命3.0", "author": "Max Tegmark", "year": 2018},
]

def search_books(keyword: str) -> str:
    """调用公开API搜索图书标题（改写版：本地模拟，返回格式与原版一致）"""
    hits = [b for b in LOCAL_BOOKS if any(k in b["title"] for k in ["人工智能", "AI", "artificial", "智能"])]
    ...
    return "\n".join([f"{i+1}. {b['title']} by {b['author']}" for i, b in enumerate(hits[:3])])

原版 openlibrary 真实 API 全文注释保留。改写版刻意保持 "1. 书名 by 作者" 的返回格式——这样从模拟切回真实 API 时，模型的下游行为完全不变（模型对格式敏感，格式一变行为就变）。

5.2 输入清洗（实测催生的加固）

t = title.strip().strip("《》").strip()
if " by " in t:
    t = t.split(" by ")[0].strip()

实测发现模型传入的书名可能带书名号（《…》）或拼上" by Stuart Russell"后缀——真实 API 用 HTTP 参数化查询天然健壮，模拟版必须自己做清洗。这是一个真实工程教训的浓缩：工具入参永远不要假设格式，模型的输出是"类人文本"不是结构化数据（对照 char03-06：Function Calling 的 JSON Schema 就是这个问题的结构化解法）。

5.3 记忆修复（本篇成败的关键一字）

# 原写法：memory_key="history"   → 与默认模板 {chat_history} 不匹配，记忆静默丢失
memory = ConversationBufferMemory(memory_key="chat_history")

5.4 Agent 组装与两轮调用（原样保留）

agent = initialize_agent(tools=tools, llm=llm,
    agent=AgentType.CONVERSATIONAL_REACT_DESCRIPTION, memory=memory, verbose=True)
response_1 = agent.run("我想查几本关于人工智能的书")

三处值得品读的细节：① 第 2 轮输入只有"请介绍第一本书的详细信息"九个字——"第一本书"三个字的全部信息量都来自第 1 轮存入的记忆；② 模型复原书名时加了书名号《》——它认为自己在"指代一本书"，这是语言习惯，工具侧必须兜住（5.2 的清洗）；③ 第 1 轮的"加戏"与 05 篇的"抄近路"恰好互补：模型既会省略多余步骤，也会主动补全信息缺口——动态规划的伸缩性。

首次运行的意外收获：降级轨迹同样精彩（已随清洗加固修复）

首次运行时（清洗逻辑未加），第 2 轮模型收到两次"未找到该书籍详情"后，展现了教科书级的容错：先重试 SearchBooks 换取精确书名 → 再试一次 GetBookDetails（把"by Stuart Russell"也拼了进去）→ 仍失败后诚实降级，且准确诊断了失败原因（"书名/作者匹配存在细微偏差，例如常见译名差异"）——模型自己分析了 bug 的位置。修复清洗逻辑后，轨迹收敛为上面的干净版本。两个版本都值得教学展示：工具健壮性决定 Agent 的下限，模型韧性决定 Agent 的上限。

七、"动态规划"在本系列的三种实现形态

形态代表篇目规划者接力发生的范围
固定链01 SequentialChain开发者（写死）单次调用内，顺序确定
单轮多工具05 多工具顺序管理模型（单轮内）一条 ReAct 链内连调 N 个工具
跨轮工具链（本篇）07 工具链动态规划模型（跨轮）本轮工具的输入 = 上轮记忆中的结果
本篇在 char04 中的位置

本篇 = 05 篇的工具接力 + 03 篇的对话记忆。至此 char04 的主线清晰成型：链（01）→ Agent（02）→ 记忆（03）→ 安全（04）→ 多工具（05）→ 定制灵魂（06）→ 跨轮工具链（07）——每篇往前推一格，最后收敛到"能理解上下文、自主拆解任务"的完整智能体，正好接第 5 章（RAG 与更复杂的系统）。

八、生产视角：教学版离上线的差距

  • 数据源：模拟书库换真实 API 时注意保持返回格式稳定（模型行为对格式敏感）；openlibrary 国内不可达，生产换豆瓣/国家图书馆等可达数据源
  • 入参校验：5.2 的字符串清洗只是补丁——结构化解法是 Function Calling（char03-06 的 JSON Schema 让模型直接输出结构化参数，从根上消除格式猜测）
  • 指代消解的边界：靠全文记忆做消解，对话超过几十轮后关键信息会被稀释（Buffer 无上限问题）——生产用摘要记忆或结构化状态（char02-02 的 task_state 思路）
  • 工具永不抛异常：本篇实测反面教材（超时打崩 Agent）——所有工具必须兜底 + requests 加 timeout
  • initialize_agent 已废弃：同前几篇，新项目用 create_agent

九、动手练习

  1. 复现"静默断忆"：把 memory_key 改回教材的 "history" 重跑——观察第 2 轮模型是否反问"您指的是哪本书？"（预期：是）。这是比报错更危险的 bug 形态，亲眼见过才会防。
  2. 切回真实 API：在能访问 openlibrary 的网络环境下，取消注释真实实现重跑——对比真实 API 返回（英文书名、真实出版年份）对模型行为的影响。
  3. 指代升级：把第 2 轮改成"第 2 本书出版多少年了？"——观察模型是否正确消解"第 2 本书"（《深度学习》，2017）并自主算年份（2026-2017=9）——记忆 + 推理 + 工具的三合一。
  4. 工具健壮性攻防：故意给 GetBookDetails 传"不存在的书""半截书名""全角空格书名"，观察清洗逻辑的漏网之鱼，再想想用 Function Calling 的 enum 约束能否从根上解决。
