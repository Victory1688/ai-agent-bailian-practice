例 13-1 讲解：先定义标准的 Agent 接口层和数据结构

本节核心目标：给整个第 13 章打地基。char13 要"从零实现一个复合智能体系统"，而复合系统的第一课不是写功能，是定契约——消息长什么样、上下文怎么流转、模型怎么换。本篇定义三个组件：Message（最小消息单元）、ConversationContext（上下文容器）、ModelAdapter（模型适配器），让上层代码只依赖 call(context) 一个接口，底层 qwen 原生协议还是 OpenAI 兼容协议随意切换——这就是适配器模式 + 依赖倒置在 Agent 系统里的落地。

二、三层数据流总览：接口层的契约设计

业务层（后续篇章的工具调用 / 编排 / 复合 Agent） │ 只依赖 call(context) 契约，不知道底层是什么模型 ▼ ConversationContext（上下文容器） │ add_message() 追加 · as_dict() 导出原生格式 ▼ ModelAdapter（适配器，注册表驱动） │ protocol = native ──▶ dashscope.Generation.call（qwen-plus） │ protocol = openai ──▶ OpenAI SDK + compatible-mode（qwen-turbo / deepseek-v3） ▼ 结构化返回 {"success", "model", "response"} / {"success", "error"}

为什么"先定义接口"是复合智能体的第一步？

复合系统 = 多个 Agent + 多个模型 + 多种工具协作。如果每个组件各自调模型，协议差异（消息格式、返回结构、错误类型）会渗透到每个角落；一旦要换模型，等于全项目重写。接口层的价值：协议差异被压扁在 ModelAdapter 一层里，上层只看见统一的 call(context) → {"success", "response"} 契约。char13 后续篇章的工具路由、多 Agent 协作都建立在这份契约上。

三、核心组件 1：Message（fail fast 的最小消息单元）

class Message:
    """标准消息单元：role 白名单校验 + 序列化"""

    def __init__(self, role: str, content: str):
        if role not in VALID_ROLES:               # ← 构造时即校验（fail fast）
            raise ValueError(f"不支持的角色类型：{role}（合法值 {VALID_ROLES}）")
        self.role = role
        self.content = content

    def to_dict(self) -> dict:
        """序列化为 dashscope 原生 messages 格式的一条"""
        return {"role": self.role, "content": self.content}
校验前置的价值：教材在 to_langchain() 里才校验 role——此时坏消息已经在 messages 列表里了，报错时机晚于污染时机，排查时看到的上下文已经不干净。改写版把校验放进构造器：不合法的消息根本无法诞生，ConversationContext.messages 从此恒定干净。这是"让非法状态不可表示"的经典设计。

四、核心组件 2：ConversationContext（上下文容器）

def as_dict(self) -> list:
    """导出为 dashscope / OpenAI 双兼容的 messages 列表"""
    return [msg.to_dict() for msg in self.messages]

教材的 get_langchain_messages() 需要把每条 Message 翻译成 HumanMessage/AIMessage/SystemMessage 三种对象——而 dashscope 原生协议与 OpenAI 兼容协议恰好共用同一份字典格式 {"role", "content"}。所以改写版删掉了整个翻译层：一份 as_dict() 同时喂两种协议，适配器里不再需要任何格式转换。选对了数据格式，转换层就消失了——这本身就是一个架构决策的示范。

角色语义谁在用
system设定人格与规则业务层注入（如"你是专业 AI 助手"）
user用户输入对话入口追加
assistant模型回复调用成功后回写（下一轮的历史记忆）

五、核心组件 3：ModelAdapter + 注册表 + 适配器池

# 模型注册表：类型 → (模型名, 协议)——新增模型只改这里，不动任何调用方
MODEL_REGISTRY = {
    "qwen":     {"model": "qwen-plus",  "protocol": "native"},
    "deepseek": {"model": "qwen-turbo", "protocol": "openai"},  # 账号未开通 DeepSeek 托管
}

def call(self, context) -> dict:
    """统一调用入口：错误止于日志，堆栈不外泄"""
    try:
        answer = self._invoke(context.as_dict())
        return {"success": True, "model": self.model_name, "response": answer}
    except Exception as e:
        logger.error(f"[模型] {self.model_type} 调用失败: {e}")
        return {"success": False, "error": str(e)}

三个设计决策

决策教材做法改写做法理由
模型配置if/elif 硬编码在 _load_model注册表字典驱动新增模型 = 加一行注册，开闭原则
实例管理每轮 ModelAdapter(...) 重新构造get_adapter() 池化复用构造函数可能含重活（加载配置/建连），复用是惯例
错误处理traceback 放进返回值堆栈只进日志，返回值只带 str(e)堆栈外泄 = 信息泄露
关于 deepseek 槽位的说明：实测当前百炼账号未开通 DeepSeek 托管（deepseek-* 模型 404），故注册表里 deepseek 槽位暂用 qwen-turbo + OpenAI 兼容协议演示"跨模型 + 跨协议"切换——协议差异演示价值不变；若账号开通 deepseek-v3，把注册表里的 model 改回即可，其余代码零改动（这正是注册表设计的意义）。

六、实测验证（5 项 self-test 全部通过）

Test 1 - role 校验：Message("robot", "hi") 构造时抛 ValueError——坏消息无法诞生
Test 2 - 上下文结构：as_dict() 输出原生格式，session_id 自动生成 uuid
Test 3 - 注册表拒绝：ModelAdapter("gpt-5") 抛 ValueError，提示已注册类型
Test 4 - qwen 真实调用：qwen-plus 原生协议回答注意力机制，返回值无 traceback 字段
Test 5 - 跨模型共享上下文：qwen-turbo（OpenAI 兼容协议）回复承接"多头注意力是注..."——第二问的'它'正确指代第一问的注意力机制

Test 5 的意义：上下文跨适配器共享

同一个 ConversationContext 先后喂给两个不同模型 + 不同协议的适配器：qwen-plus（dashscope 原生）回答第一问，qwen-turbo（OpenAI 兼容）回答第二问——第二问里的"它"被正确理解为第一问的"注意力机制"。这证明：上下文容器的数据契约足够通用，记忆在模型切换时无缝延续。char12-04 在服务端做过同样的验证（cache.json 落盘形态），本篇是它的内存形态、也是 char13 复合系统的地基。

九、动手练习

  1. 加一个新模型：在 MODEL_REGISTRY 注册 "turbo": {"model": "qwen-turbo", "protocol": "native"}，验证上层代码零改动即可切换——体会注册表的开闭原则。
  2. 上下文截断：给 ConversationContext 加 trim(max_messages) 方法，保留 system 消息 + 最近 N 条——为长对话控成本（对照 char08-05 的窗口裁剪）。
  3. 落盘恢复：把 as_dict() 输出写入 cache.json，重启后从文件恢复 ConversationContext（char12-04 模式的本篇落地方）。
  4. 令牌估算：加 estimate_tokens() 方法（按字符数 / 1.6 粗估），在 call 前打印本次上下文规模——建立成本意识。
  5. 协议对照实验：分别用 native 与 openai 协议问同一个问题，对比两种返回结构取内容的路径差异（resp.output.choices[0].message.content vs resp.choices[0].message.content）——这就是适配器替你抹平的细节。
