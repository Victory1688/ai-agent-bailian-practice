例13-2 用户意图识别与入口解析（char13-02）

第13章 项目案例：从零实现一个复合智能体系统 ｜ 改写基准：dashscope 原生协议 ｜ 状态：已实测验证（5 项 self-test 全部通过）

本篇是复合智能体系统的入口闸门：用户一句话进来，系统要先判断"用户想干什么"（查询 / 执行 / 对话 / 工具调用），抽取关键参数（城市、脚本名……），再交给下游调度。教材把这一步写成了一段 eval(LLM输出)——恰恰是整个项目里最危险的一行代码。本篇讲解围绕三个问题展开：为什么 eval 是安全洞、安全解析怎么做、意图识别的"兜底链"如何保证永不崩溃。

核心安全洞一句话：LLM 输出 = 不可信的外部输入。eval() 把字符串当代码执行，等于把系统控制权交给一个可能被提示注入操纵的远端模型。数据永远不能当代码执行——这是本篇改写的第一原则。

二、改写后总览：一条安全的意图识别流水线

用户请求 → INTENT_TEMPLATE（强化输出约束）
→ ModelInvoker（主模型 qwen-plus → 失败则备用 qwen-turbo）
→ extract_json（三步安全清洗，绝不执行）
→ validate_intent（白名单 + 类型校验，坏数据归"未知"）
→ IntentParser.parse（兜底链：主模型 → 备用模型 → 结构化"未知"）
→ 下游调度拿到的一定是 {"intent", "domain", "parameters"} 合法结构

改写保留教材的全部业务语义：意图四分类、parameters 键值抽取、主备双模型、失败归"未知"。变化全部集中在安全性（eval → json.loads）与健壮性（校验 + 日志 + self-test）上。

三、核心组件 1：extract_json —— 三步安全清洗

这是替代 eval 的关键函数。思路不是"想办法让 eval 跑通"，而是彻底换路线：把 JSON 从文本里"定位"出来，再用严格解析器读。

def extract_json(text: str):
    if not text:
        return None
    cleaned = text.strip()
    # 第一步：剥 ```json ... ``` 围栏（LLM 最常见的输出习惯）
    fence = re.search(r"```(?:json)?\s*(.*?)```", cleaned, re.S)
    if fence:
        cleaned = fence.group(1).strip()
    # 第二步：定位首个 { 并做括号配对（容忍 JSON 前后的说明文字）
    start = cleaned.find("{")
    if start == -1:
        return None
    depth = 0
    for i in range(start, len(cleaned)):
        if cleaned[i] == "{":
            depth += 1
        elif cleaned[i] == "}":
            depth -= 1
            if depth == 0:
                # 第三步：json.loads 严格解析——数据就是数据，永远不当代码执行
                try:
                    return json.loads(cleaned[start:i + 1])
                except json.JSONDecodeError:
                    return None
    return None
步骤处理对抗的真实场景
1 剥围栏正则提取 ```json ... ``` 内部内容模型无视指令，习惯性用 markdown 围栏包裹输出
2 括号配对从首个 { 起，按深度计数找到配对 }"好的，结果如下：{...} 请查收" 这类前后噪声
3 严格解析json.loads，失败返回 None单引号、True/None 等非 JSON 写法一律拒绝（这正是安全性的来源）
为什么第三步"严格"反而更安全：eval 宽松，所以 Python 代码能混进去执行；json.loads 严格，函数调用、__import__ 之类的字面量根本解析不合法，最多返回 None。宽松性就是攻击面。任何失败都返回 None，由上层走兜底——解析器本身永不抛异常穿透。

四、核心组件 2：validate_intent —— 坏数据止步于此

解析成功不等于数据合法。模型可能输出 {"intent": "查寻"}（错别字）、{"parameters": "上海"}（类型错）。校验函数做三件事：

def validate_intent(data) -> dict:
    if not isinstance(data, dict):
        return {"intent": "未知", "domain": "未知", "parameters": {}}
    raw_intent = str(data.get("intent", ""))
    # 白名单精确匹配 → 模糊包含归一化（容忍"天气查询"这类变体）→ 兜底"未知"
    intent = raw_intent if raw_intent in VALID_INTENTS else "未知"
    if intent == "未知":
        for it in VALID_INTENTS:
            if it != "未知" and it in raw_intent:
                intent = it
                break
    domain = data.get("domain")
    params = data.get("parameters")
    return {
        "intent": intent,
        "domain": domain if isinstance(domain, str) else "未知",
        "parameters": params if isinstance(params, dict) else {},
    }
  • 白名单精确匹配：intent 必须在 VALID_INTENTS = ("查询", "执行", "对话", "工具调用", "未知") 里；
  • 模糊包含归一化：模型输出"查询天气"这类变体时，包含"查询"即归一化，减少误杀；
  • 类型校验：domain 必须是字符串、parameters 必须是字典，否则给默认值——坏数据在入口就被拦下，不会传播到下游调度。
设计要点：校验失败的归宿是"未知"而不是抛异常。"未知"是教材原有的兜底语义，结构化之后下游可以程序化判断（重试 / 转人工 / 提示用户换说法），这正是"入口解析"作为闸门的意义。

五、核心组件 3：ModelInvoker + IntentParser —— 主备兜底链

ModelInvoker 是例 13-1 适配器模式的内联简化版（注册表 + native/openai 双协议），本篇给它增加了一层职责：调模型 → 安全解析 → schema 校验 三步串成一条结构化返回。

def run_intent_recognition(self, user_query: str) -> dict:
    try:
        # 用 replace 而非 format：模板内嵌 JSON 示例的花括号会被
        # format 误解析为占位符（KeyError: '"intent"'）——实测踩坑
        raw = self._invoke(INTENT_TEMPLATE.replace("{query}", user_query))
        data = extract_json(raw)
        if data is None:
            raise ValueError(f"模型输出不是合法 JSON: {raw[:80]}")
        return {"success": True, "data": validate_intent(data)}
    except Exception as e:
        logger.warning(f"[意图] {self.model_type} 解析失败: {e}")
        return {"success": False, "error": str(e)}

IntentParser 在其上组装兜底链：

主模型 qwen-plus（native 协议）→ 成功即返回
↓ 失败（网络 / 输出不合法）
备用模型（openai 兼容协议）→ 成功即返回
↓ 再失败
结构化"未知"：{"intent": "未知", "domain": "未知", "parameters": {}}
  • 永不抛异常：parse() 的返回值一定是合法结构，下游调度不需要防御性 try/except；
  • 失败原因全部落日志：哪个模型、什么原因失败，logging 可查（替代教材的 print）；
  • traceback 不外泄：错误信息止于日志，对调用方只暴露结构化结果。
实测踩坑：str.format 的花括号陷阱。改写时模板里内嵌了 JSON 示例 {"intent": ...}，若用 INTENT_TEMPLATE.format(query=...) 填充，format 会把 {"intent"} 当占位符解析，直接 KeyError: '"intent"'，主备模型全部失败。教材原版用的 str.replace("{query}", ...) 其实是对的——模板含花括号字面量时必须用 replace。此坑已写入代码注释。

六、实测验证（5 项 self-test 全部通过）

Test场景结果
1干净 JSON 直解{"intent": "查询", "domain": "天气", ...} 原样解析通过
2围栏 + 前后噪声清洗"好的，以下是识别结果：```json ...``` 请查收" → 正确提取 intent=执行
3恶意输出拒绝{'intent': '查询', 'cmd': __import__('os').system('echo hacked')} —— eval 会真的执行系统命令，extract_json 返回 None 拒绝；未闭合括号、空输出同样拒绝。安全洞已封
4真实 LLM 意图识别"请帮我查一下今天上海的天气" → {'intent': '查询', 'domain': '天气', 'parameters': {'location': '上海', 'date': '今天'}}，参数抽取正确
5教材 5 条批量识别"执行数据库清理脚本" → 执行/数据库运维；"陪我聊聊天" → 对话/闲聊，语义清晰样本精确命中；模糊样本（"生成短文"）只验白名单契约，合法
测试方法论：意图分类的断言策略。意图类别边界天然模糊——"生成一篇短文"判"执行"或"工具调用"都说得通。测试若对所有样本都断言具体值，就会把模型合理的分类差异当 bug。正确做法：语义边界清晰的样本（执行脚本、聊聊天）精确断言；模糊样本只验证契约（intent 必须落在白名单内）。Test 5 正是按此策略设计的。

九、动手练习与延伸阅读

练习 1：围栏变体清洗

LLM 有时输出 ``` {"intent": "查询"} ```（围栏语言标注缺失或前后有空格），有时 JSON 数组 [{...}, {...}]。修改 extract_json，让它也能处理"围栏内是 JSON 数组取首个对象"的情况，并为新行为补一条 self-test。

练习 2：意图扩展

给 VALID_INTENTS 增加"翻译"类别，同步扩充 INTENT_TEMPLATE 的枚举提示，然后测试"将这段文字翻译成英文：你好世界"能否稳定归到新类别——观察白名单扩列对模糊包含匹配的影响。

练习 3：复用 13-01 适配器

把本篇 ModelInvoker 删除，改为导入例 13-01 的 ModelAdapter + get_adapter，体会"接口层复用"后本篇代码量的缩减，以及两文件注册表统一管理的必要性。
