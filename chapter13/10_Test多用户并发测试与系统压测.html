一、教材原版问题诊断

教材原代码声称实现了「数十用户并发压测 + 平均响应/QPS/错误率指标」，逐行核查后发现八个问题（原代码已全部注释保留在 py 文件头部，编号对应）：

编号问题后果与辨析
①legacy 全线废弃 + 虚构类initialize_agent / AgentType.OPENAI_FUNCTIONS / Tool.from_function（13-08/13-09 同款）+ Qwen2Chat / DeepSeekChat 虚构类——import 即崩，从未跑通过。
②【最严重】共享实例并发agent = ConcurrentAgent(...) 在并发外创建一次，task_runner 闭包捕获同一个实例。改写后的 AgentCore 有 self.history 会话状态——多线程共享会导致串话（用户A的问题进了用户B的上下文，工具调用错配）。多用户语义下每个用户本就该有独立会话。
③字符串判错run 返回 "[ERROR] ..." 混流，统计靠 "[ERROR]" not in output 字符串包含——若模型回复恰好含 "[ERROR]" 字样会误判为失败；异常文案一变就失效。
④指标残缺教材声称输出「错误率指标」但只打印失败数没算百分比；压测只看平均值——LLM 响应是长尾分布，平均值会被掩盖，生产压测必须看 P95/P99。
⑤random.choice 无种子两次运行任务分配不同，结果不可复现——压测连基线都固定不下来，无法对比优化效果。
⑥输出顺序随机results[:5] 按 as_completed 完成顺序输出，每次运行不同，教材却展示为固定输出。
⑦20 并发必触发限流20 个线程同时打 LLM API，限流（429）几乎必然发生，教材无任何说明；traceback import 了从未使用。
⑧无 self-test + import 即执行run_demo() 写在模块顶层无入口保护。
本篇核心教学点——「有状态对象 + 多线程共享」：教材把一个带会话状态（history）的对象交给多个线程共用。 传统 Web 压测中「共享无状态 service」是安全的，但 Agent 实例自带会话状态—— 多用户并发压测的正确模型是「每请求独立实例」：既符合真实语义（每个用户独立会话），又天然规避串话。 判断依据不是「线程安全与否」的空谈，而是「对象内部有没有会被并发写的状态」。

三、核心组件详解（1）指标计算纯函数

3.1 _percentile：线性插值分位数

def _percentile(sorted_vals: list, p: float) -> float:
    """线性插值法，与 numpy.percentile 默认语义一致"""
    pos = p * (len(sorted_vals) - 1)
    lo, hi = math.floor(pos), math.ceil(pos)
    if lo == hi:
        return sorted_vals[lo]
    # 插值：pos 的小数部分决定两相邻元素的加权比例
    return sorted_vals[lo] + (sorted_vals[hi] - sorted_vals[lo]) * (pos - lo)

分位数实现选了线性插值法（numpy.percentile 默认语义）而非最近秩法：对 [1,2,3,4] 求 P50， 最近秩法得 3，插值法得 2.5——后者更平滑、更贴近主流工具的行为，压测报告可直接与观测平台对齐。 实测时先用最近秩法跑出一版，与手工计算的期望值对不上后换成插值法并修正断言——分位数算法没有「想当然」，必须对着定义验。

3.2 compute_metrics：九项指标一次算齐

def compute_metrics(results: list, total_time: float) -> dict:
    durations = sorted(r["duration"] for r in results)
    success_count = sum(1 for r in results if r["success"])
    failed_count = len(results) - success_count
    return {
        "total": len(results),
        "success_count": success_count,
        "failed_count": failed_count,
        "error_rate": failed_count / len(results),
        "avg_time": sum(durations) / len(durations),
        "p50_time": _percentile(durations, 0.50),
        "p95_time": _percentile(durations, 0.95),
        "max_time": durations[-1],
        "qps": len(results) / total_time,
    }
纯函数设计的价值：compute_metrics 不碰任何全局状态、不做 IO，输入输出确定—— 因此 Test 1 可以用 4 条 fake 数据手工算出每个指标的期望值做精确断言（错误率 25%、平均 2.5s、P50 2.5、P95 3.85、QPS 0.5）。 这是 13-09「指标可测」思想的延续：统计逻辑与执行逻辑分离，前者单测覆盖，后者真实链路覆盖。

四、核心组件详解（2）并发安全与串话检测

4.1 每请求独立会话（修复共享实例并发 bug）

def run_single_request(user_id: int, text: str) -> dict:
    agent = AgentCore()   # 每请求独立实例：history 不跨用户共享（修复串话）
    st = time.time()
    result = agent.run(text)
    duration = time.time() - st
    return {
        "user_id": user_id,
        "input": text,
        "success": bool(result.get("success")),      # 布尔，替代字符串匹配
        "reply": result.get("reply", result.get("error", ""))[:80],
        "duration": duration,
        "tool_hits": [s["tool"] for s in result.get("steps", [])],
    }

两个关键决策：

  1. 独立实例而非加锁：AgentCore 的 history 会被 run 写入。加锁可以做到线程安全，但会让并发压测退化成串行排队（测不出并发能力）；独立实例既符合「每个用户独立会话」的真实语义，又让请求真正并行——多用户压测的正确抽象就是多会话，不是多线程抢一个会话。dashscope SDK 本身线程安全，网络调用层可放心并发。
  2. success 是布尔不是字符串：直接消费 13-08 AgentCore.run 返回的结构化 {"success", "reply", "steps"}——彻底消除教材 "[ERROR]" in output 的误判可能。

4.2 _detect_cross_talk：串话检测（并发正确性的行为级验证）

def _detect_cross_talk(results: list) -> list:
    """规则：input 含天气词 → tool_hits 应含 get_temperature；
            input 含乘法词 → tool_hits 应含 multiply。"""
    suspects = []
    for r in results:
        if not r["success"]:
            continue
        weather_ask = any(k in r["input"] for k in ("天气", "温度", "气温"))
        math_ask = any(k in r["input"] for k in ("乘", "计算", "*"))
        if weather_ask and "get_temperature" not in r["tool_hits"]:
            suspects.append(r["user_id"])
        if math_ask and "multiply" not in r["tool_hits"]:
            suspects.append(r["user_id"])
    return suspects
串话检测的原理：如果多个线程共享了带 history 的实例，用户A的问题会混进用户B的上下文， 模型就会「答非所问」——最直接的行为信号就是工具调用错配（问天气的去调乘法、问乘法的去查天气）。 检测规则刻意与 13-09 的正确率指标区分：13-09 问「调对了吗」，本篇问「是不是在回答自己的问题」—— 后者是并发正确性指标，前者是能力指标。

五、核心组件详解（3）压测调度与报告

5.1 run_concurrent_test：可复现的并发调度

def run_concurrent_test(concurrent_users: int = DEMO_USERS,
                        seed: int = RANDOM_SEED) -> dict:
    random.seed(seed)    # 固定种子：每次运行任务分配完全一致
    tasks = ["请查询北京的天气", "广州今天什么天气", "请帮我计算 12 * 13",
             "算一下9乘以7是多少", "帮我查查上海的气温"]
    start_time = time.time()
    with ThreadPoolExecutor(max_workers=concurrent_users) as pool:
        futures = {pool.submit(run_single_request, i, random.choice(tasks)): i
                   for i in range(concurrent_users)}
        results = [f.result() for f in as_completed(futures)]
    total_time = time.time() - start_time
    results.sort(key=lambda r: r["user_id"])   # 按用户排序（完成顺序≠展示顺序）
    metrics = compute_metrics(results, total_time)
    suspects = _detect_cross_talk(results)
    return {"metrics": metrics, "results": results, "cross_talk_suspects": suspects}

对比教材的三个修正：seed 固定（任务分配可复现）、结果按 user_id 排序（修复输出顺序随机）、 返回结构化报告字典（替代 print 混流）。

5.2 LLM 压测与 Web 压测的本质差异

维度传统 Web 服务压测LLM Agent 服务压测（本篇）
并发成本并发 1 万也几乎零成本每个请求真实消耗 token费用线性增长——并发数要克制（本篇 self-test 用 3，demo 用 6）
限流自己服务的容量自己控API 平台侧限流（429）是硬约束，20 并发直接打必触发；13-08 的主备回退会被限流连带触发
响应时间量级毫秒级，QPS 上万秒级（实测单请求 1.6~2.0s），QPS 天然是个位数——QPS 对 LLM 服务是次要指标，P95 才是
分布形态近似正态长尾分布（偶发的慢请求拉高平均值）——只看平均值会严重误判，必须看 P95/P99
会话状态service 通常无状态，可共享Agent 实例带 history，每请求独立实例才符合多用户语义

实测数据解读：
  • QPS 1.57 的含义：3 用户 × 每请求约 1.9s 墙钟 → QPS≈1.57。LLM 服务的 QPS 天然是个位数， 压测重点应放在错误率与 P95 上——这正是改写补全这两个指标的原因；
  • P95 与平均值接近（1.89 vs 1.64）说明本轮无严重长尾；生产中若 P95 远超平均值，说明存在慢请求聚集（限流重试、网络抖动），平均值完全看不出来；
  • 串话检测 0 可疑从行为层面证明了「每请求独立实例」的并发模型正确——若沿用教材共享实例写法，history 交错会导致工具调用错配，此检测项会立刻报警。

动手练习（由浅入深）
