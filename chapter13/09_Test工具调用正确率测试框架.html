一、教材原版问题诊断

教材原代码声称实现了「Qwen + Deepseek + LangChain Tools + 三项指标（工具名准确率、参数提取成功率、返回一致性）」，但逐行核查后发现八个问题：

编号问题后果与辨析
①【最严重】测试逻辑本身是坏的if case["expected_tool"] in output——expected_tool 是内部工具名（weather_tool），output 是最终自然语言回复（"北京天气为晴，温度25°C"）。工具名永远不会出现在回复里，正确率永远 0%，即使模型正确调了工具也被判失败。这是「测试框架测不出被测对象」的经典反模式。
②三项指标一项都没实现教材评论里写了三个指标名字，但代码里只有一个文本匹配，参数提取和返回一致性根本没有独立计算。
③legacy 全线废弃initialize_agent / AgentType.OPENAI_FUNCTIONS / Tool.from_function（13-08 同款，import 即崩）。
④虚构类 Qwen2Chat / DeepSeekChat同前。
⑤Tool.from_function 双重包装同 13-03 / 13-08。
⑥「故意触发错误」用例语义错误第 6 条用例是「你知道北京和月球的温度吗」，教材说「故意触发错误」但测试逻辑本身已烂，这条用例的存在意义完全模糊。
⑦错误字符串混流run 返回 "[ERROR] ..." 与正常输出同通道。
⑧无 self-test零验证。
本篇核心教学点——测试逻辑反模式：测试框架用「内部状态的字符串匹配」来验证「外部行为」，这是反模式。 正确做法是把被测主体内部执行轨迹（steps）暴露出来，与预期契约做结构化比对。 这和 13-08 确立的「steps 可观测性」是直接衔接的——13-08 让 AgentCore.run 返回 steps，13-09 消费这个 steps 做测试。

二、改写后总览

改写思路：把 13-08 的 AgentCore 当作被测主体，用 importlib 动态加载它的 TOOLS_SPEC / MODEL_REGISTRY / AgentCore， 保证工具名和被测主体完全一致；测试框架包在外面，从 AgentCore.run 返回的 steps 里提取实际工具调用轨迹，与预期契约结构化比对。

整体执行流程

TEST_CASES（六项契约：tool + params + result_pattern）
  ──→ run_tool_test(model_name)
    ──→ 临时切 MODEL_REGISTRY 到被测模型 → 循环 TEST_CASES
        ──→ AgentCore.run(case["input"]) → 拿到 {"success", "reply", "steps"}
        ──→ 从 steps 提取实际轨迹（不再看 reply 文本！）
        ──→ 三项指标各自独立比对：
          · _check_tool_name（预期工具序列 vs 实际序列）
          · _check_params（必需参数存在且值匹配）
          · _check_result_pattern（工具返回匹配正则）
        ──→ 汇总 metrics 字典（tool_name_rate / param_rate / return_rate / overall）
run_multi_model_compare 对多个模型跑同一份测试集 → 对比不同模型的综合得分

文件结构（改写后）

部分职责
importlib 动态加载从 13-08 加载 AgentCore / TOOLS_SPEC / MODEL_REGISTRY——保证被测主体与测试框架使用完全相同的工具定义
TEST_CASES6 条测试用例，每条含三项契约（expected_tools / expected_params / expected_result_pat）
三项检查函数_extract_actual_tools / _check_tool_name / _check_params / _check_result_pattern——各自独立比对
run_tool_test执行全量测试集，返回结构化 metrics dict（含 details 列表）
run_multi_model_compare多模型对比入口
format_metrics把 metrics 格式化为可读报告（print 时调用）

三、核心组件详解（1）测试集与三项契约

3.1 动态加载被测主体

不用复制一份 AgentCore，而是用 importlib 从 13-08 动态加载——这样工具名（get_temperature / multiply）和 TOOLS_SPEC 格式与 13-08 完全一致，避免两处定义漂移：

_CHAR08_PATH = os.path.join(_CHAR13_DIR, "08_LangChain的通用Agent主控链条.py")
_spec = importlib.util.spec_from_file_location("char13_08", _CHAR08_PATH)
_mod08 = importlib.util.module_from_spec(_spec)
_spec.loader.exec_module(_mod08)
AgentCore = _mod08.AgentCore
MODEL_REGISTRY = _mod08.MODEL_REGISTRY
TOOLS_SPEC = _mod08.TOOLS_SPEC

3.2 TEST_CASES：三项契约结构化

教材原测试集只有 expected_tool 一个字段，改写后每条用例有三项契约（分别对应三个指标）：

字段含义用途示例
expected_tools预期模型会调用的工具名序列（可多个）tool_name_accuracy["get_temperature"] 或多工具 ["get_temperature", "get_temperature"]
expected_params预期工具调用的关键必需参数（None 跳过此指标）param_extraction_rate{"city": "北京"} 或 {"a": "7", "b": "8"}
expected_result_pat预期工具返回的正则模式（None 跳过）return_consistencyr"北京.*温度" 或 r"56\.?"
TEST_CASES = [
    {"id": "T01", "input": "请查询一下北京的天气",
     "expected_tools": ["get_temperature"],
     "expected_params": {"city": "北京"},
     "expected_result_pat": r"北京.*温度"},
    {"id": "T04", "input": "请帮我计算7乘以8",
     "expected_tools": ["multiply"],
     "expected_params": {"a": "7", "b": "8"},
     "expected_result_pat": r"56\.?"},
    # 多工具场景（原教材"故意触发错误"，语义纠正）
    {"id": "T06", "input": "你知道北京和月球的温度吗？",
     "expected_tools": ["get_temperature", "get_temperature"],  # 两次调用
     "expected_params": None,    # 多参数不硬编码
     "expected_result_pat": None},
]
T06 语义纠正（教材原"故意触发错误"）：教材原逻辑把月球场景单工具触发 ValueError 当作"故意错误"， 改写后纠正为多工具 + 错误回填场景：模型预期两次 get_temperature 调用（北京正常、月球触发 13-08 确立的 双层失败语义——工具错误回填给模型而非炸穿）。expected_params 和 expected_result_pat 设为 None（多参数不硬编码）， 工具名指标独立验证序列。

四、核心组件详解（2）三项指标实现

三项检查函数各自独立，互不影响——任何一项不通过都不阻断其他两项的验证。这是与教材「一匹配全通过」的关键差异。

4.1 _check_tool_name：工具名准确率

def _check_tool_name(expected: list, actual: list) -> bool:
    """预期工具序列 vs 实际序列"""
    if not expected and not actual:
        return True
    if expected and not actual:
        return False  # LLM 直答但预期要调工具 → 工具名失败
    return expected == actual

比对策略是序列精确匹配：expected 是 ["get_temperature"]，actual 也必须是 ["get_temperature"]。 空 actual 代表 LLM 直答没调工具（轻量模型 qwen-turbo 偶有此行为），如果 expected 非空则判为失败——因为模型跳过了工具能力。

4.2 _check_params：参数提取成功率

def _check_params(steps: list, expected_params: dict | None) -> bool:
    """必需参数是否存在且值匹配"""
    if expected_params is None:
        return True
    if not steps:
        return False  # LLM 直答没调工具 → 参数提取失败
    first_step = steps[0]
    actual_args = first_step["args"]
    for key, exp_val in expected_params.items():
        if key not in actual_args:
            return False
        if actual_args[key] != exp_val:
            return False
    return True

只检查必需参数（TEST_CASES 里声明的那些 key），不要求参数完全一致——这样即使模型多传了无关字段也不算失败。 空 steps 时直接返回 False（没调工具就谈不上参数提取）。

4.3 _check_result_pattern：返回一致性

def _check_result_pattern(steps: list, pattern: str | None) -> bool:
    """工具返回文本是否匹配预期正则"""
    if pattern is None:
        return True
    if not steps:
        return False
    for s in steps:
        if re.search(pattern, s["result"]):
            return True
    return False

用正则而非精确字符串匹配——因为工具返回可能有轻微变化（比如"北京当前温度为26°C"和"北京天气为晴，温度25°C"虽然业务不同但都含"北京"+"温度"）。 空 steps 时返回 False（没工具结果就谈不上返回一致性）。

空 steps 边界（实测坑）：qwen-turbo 比 qwen-plus 轻量，某些用例下直答不调工具——这是 LLM 的正常行为 （轻量模型可能认为"12 和 13 相乘"可以自己算）。三项检查函数都加了空 steps 处理： expected 非空但 steps 空 → False；expected 为 None（跳过）→ True。这比教材「硬编码所有用例都必调工具」更符合真实 LLM 行为。

五、核心组件详解（3）多模型对比

5.1 run_tool_test：单模型全量测试

def run_tool_test(model_name: str = "qwen-plus") -> dict:
    old_primary = MODEL_REGISTRY["primary"]["model"]
    MODEL_REGISTRY["primary"]["model"] = model_name
    try:
        agent = AgentCore()
        for case in TEST_CASES:
            result = agent.run(case["input"])
            steps = result.get("steps", [])
            actual_tools = _extract_actual_tools(steps)
            tool_ok = _check_tool_name(case["expected_tools"], actual_tools)
            param_ok = _check_params(steps, case["expected_params"])
            return_ok = _check_result_pattern(steps, case["expected_result_pat"])
            # ... 汇总 details
    finally:
        MODEL_REGISTRY["primary"]["model"] = old_primary

两个关键点：

  1. 临时切模型：把 MODEL_REGISTRY["primary"]["model"] 设成被测模型，finally 里无论成败都还原——避免污染全局状态；
  2. 每轮新建 AgentCore：每个 case 用新实例，避免前一个 case 的 history 干扰当前测试——这和 13-03 的「测试隔离」原则一致。

5.2 run_multi_model_compare：双模型并排对比

def run_multi_model_compare(models: list = None) -> list:
    if models is None:
        models = ["qwen-plus", "qwen-turbo"]
    return [run_tool_test(m) for m in models]

返回两个 metrics dict，key 完全一致——可以直接并排比较。实测 qwen-plus 综合得分 94.4%，qwen-turbo 61.1%—— 这正是教材想测但永远测不出来的效果（教材正确率永远 0%，无法区分模型差异）。

实测数据的教育意义：

  • 工具名准确率 83.3%（6 条里 1 条 FAIL）：T06 预期两次 get_temperature（北京 + 月球），实际只调了一次——LLM 对月球的"温度"自行拒绝，这属于"多工具覆盖不足"，不是工具调用能力本身的问题；
  • qwen-turbo 综合 61.1%：turbo 是轻量模型，在部分用例下选择直答而非调工具（T05 12×13、T06），拉低了三项指标——这正是不同模型在工具调用上的真实差异，教材永远测不出来；
  • 空 steps 是正常现象：轻量模型可能认为某些问题"自己能算"而跳过工具调用——测试框架应该容忍这种差异（指标如实反映），而不是硬编码"所有用例必调工具"。

八、与前后章节的衔接

关联篇章衔接点

13-03 工具调用链与异常回退execute_tool / _extract_tool_calls 同源；双层失败语义（工具错误回填而非炸穿）在 T06 月球场景被间接受益。
13-02 意图识别入口全章链路起点：意图识别 → 工具链 → 调度 → RAG → MCP → A2A → 主控 → 测试框架（本篇）。本篇的 metrics 是对前面所有篇章的"回头看"——不同模型在工具调用上的差异可以量化。
char12-06 模型限流回退主备回退思路：MODEL_REGISTRY 临时切槽位到被测模型——这篇的多模型对比就是回退思路的"正面应用"（不是失败时的主备，而是主动对比不同模型）。
测试方法论沉淀从 13-08 LLM 非确定性分路径验契约 → 13-09 空 steps 正常化（不调工具不是错，指标如实反映）→ 逐步形成了"对 LLM 的测试不应锁定路径、应聚焦契约"的方法论。
