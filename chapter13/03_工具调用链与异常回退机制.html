例13-3 工具调用链与异常回退机制（char13-03）

第13章 项目案例：从零实现一个复合智能体系统 ｜ 改写基准：dashscope 原生 function calling ｜ 状态：已实测验证（6 项 self-test 全部通过）

本篇给复合智能体装上手和脚：模型不再只会说话，而是能发起工具调用（查天气、算算式），系统替它执行工具、把结果喂回去，直到模型给出最终回答。同时建立回退机制。教材版有两条致命伤：工具内部又藏了一个 eval，以及把"工具查不到数据"当成"模型坏了"去触发回退——本篇的题眼就是把这两层失败拆开。

二、改写后总览：双层回退语义

改写最核心的设计决策是把"失败"分成两类，走不同的处理路径：

失败类型例子正确处理（本篇实现）
工具级失败
（业务数据问题）		未知城市查不到天气、表达式语法错误、工具名不存在返回结构化错误 {"success": false, "error": ...} 以 role=tool 回填给同一个模型——错误是数据，模型可见、可向用户改述，链路不中断、不回退
模型级失败
（系统故障）		网络超时、限流、模型名不存在（InvalidParameter）抛异常 → 上层捕获 → 主备回退 qwen-plus → qwen-turbo → 全败返回兜底文案
用户请求 → ToolAgentManager.run_with_tools
↓ 主模型 qwen-plus（dashscope 原生 function calling）
模型请求工具？ → execute_tool 执行 → 结果（或结构化错误）回填 → 再调模型（循环 ≤ 4 轮）
↓ 模型给出最终回答，返回
仅当模型级失败 → 备用模型 qwen-turbo 重跑同一条工具链 → 全败 → 兜底文案
为什么教材的回退是错的：教材里"未知城市"触发 DeepSeek 回退后，DeepSeek 调的还是同一个工具、查的还是同一个城市——结果注定还是失败。回退解决的是"谁来想"的问题（模型坏了换模型），解决不了"数据有没有"的问题。混淆两类失败，回退机制就退化成"把同一个错误再犯一遍"。

三、核心组件 1：safe_eval —— AST 白名单求值

工具内部的 eval 洞怎么封？不是给 eval 加过滤（黑名单永远漏），而是彻底换引擎：把表达式解析成 AST 树，只允许白名单内的节点参与计算。

_ALLOWED_BINOPS = {
    ast.Add: operator.add, ast.Sub: operator.sub,
    ast.Mult: operator.mul, ast.Div: operator.truediv,
    ast.Mod: operator.mod,
}
_ALLOWED_UNARYOPS = {ast.UAdd: operator.pos, ast.USub: operator.neg}

def _eval_node(node):
    if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
        return node.value
    if isinstance(node, ast.BinOp) and type(node.op) in _ALLOWED_BINOPS:
        return _ALLOWED_BINOPS[type(node.op)](_eval_node(node.left), _eval_node(node.right))
    if isinstance(node, ast.UnaryOp) and type(node.op) in _ALLOWED_UNARYOPS:
        return _ALLOWED_UNARYOPS[type(node.op)](_eval_node(node.operand))
    # 幂运算（ast.Pow）刻意不进白名单：9**9**9... 可在毫秒内打爆内存（DoS）
    raise ValueError(f"表达式包含不允许的语法：{type(node).__name__}")

def safe_eval(expr: str):
    tree = ast.parse(expr, mode="eval")
    return _eval_node(tree.body)

__import__('os').system('echo hacked')真的执行系统命令拒绝（Call 节点不在白名单）
(lambda: 1)()执行并返回 1拒绝

设计思想：白名单 > 黑名单。教材式修法是正则过滤 __import__ 等危险词——但编码变体、嵌套属性等绕法无穷无尽。AST 白名单反其道行之：默认一切拒绝，只放行明确列出的语法。功能上少一个幂运算符，换来的确定性是"这个引擎只能算数，干不了别的"。

四、核心组件 2：工具注册表 + execute_tool 统一入口

教材用 @tool 装饰器 + Tool.from_function（重复包装）。改写回归 function calling 的本质三件套：真实函数、JSON Schema 声明、统一执行入口。

def execute_tool(name: str, arguments: str) -> str:
    if name not in TOOL_FUNCS:                      # 白名单：不在表内一律拒绝
        return json.dumps({"success": False, "error": f"未知工具：{name}"}, ...)
    try:
        args = json.loads(arguments)                # 模型给的参数是 JSON 字符串
    except json.JSONDecodeError as e:
        return json.dumps({"success": False, "error": f"参数不是合法 JSON：{e}"}, ...)
    try:
        return TOOL_FUNCS[name](**args)
    except Exception as e:
        logger.warning(f"[工具] {name} 执行异常: {e}")
        return json.dumps({"success": False, "error": str(e)}, ...)
  • 永不抛出：任何失败都变成结构化 JSON 返回给模型——这是"工具错误是数据"原则的落地点；
  • 工具名白名单：模型幻觉出不存在的工具名时，返回"未知工具"错误而不是 KeyError 崩溃；
  • 错误带原因：执行异常进日志（logger.warning），对模型只暴露干净的错误信息。
工具函数内部的语义修正：教材 query_weather 对"未知城市" raise Exception；改写后返回 {"success": false, "error": "无法获取指定城市天气信息"}。查询没查到是正常的业务结果，模型拿到后可以回答用户"该城市暂无数据"——而不是让整条链路当成故障。

五、核心组件 3：ToolAgentManager —— 工具循环与主备回退

不用 LangChain 废弃的 initialize_agent，直接用 dashscope 原生 function calling 手写最小 Agent 循环（约 25 行）：

def _run_tool_loop(self, input_text: str, slot: str) -> str:
    messages = [{"role": "user", "content": input_text}]
    for _ in range(MAX_TOOL_ROUNDS):                # 轮数上限防无限循环
        resp = dashscope.Generation.call(
            model=MODEL_REGISTRY[slot]["model"],
            messages=messages, tools=TOOLS_SCHEMA,
            max_tokens=MAX_TOKENS, result_format="message")
        if resp.status_code != 200:
            raise RuntimeError(f"{resp.code} {resp.message}")   # 模型级失败 → 触发回退
        msg = resp.output.choices[0].message
        calls = _extract_tool_calls(msg)
        if not calls:                               # 模型不再要工具 → 最终回答
            content = getattr(msg, "content", None)
            return content if isinstance(content, str) else ""
        messages.append({"role": "assistant",
                         "content": getattr(msg, "content", "") or "",
                         "tool_calls": getattr(msg, "tool_calls", []) or []})
        for call in calls:
            result = execute_tool(call["name"], call["arguments"])
            messages.append({"role": "tool", "content": result})   # 结果回填
    raise RuntimeError(f"工具调用轮数超过上限 {MAX_TOOL_ROUNDS}")

上层 run_with_tools 只做一件事：遍历主备槽位，模型级异常时切下一个，全败返回教材同款兜底文案。每次尝试都记入 attempted_slots——这个记录让 self-test 能断言"回退真的发生了"。

实测踩坑：dashscope Message 的响应形态。首版代码按官方示例写 msg.tool_calls / call.function.name，实测暴露两个形态差异：模型未请求工具时，Message 对象上根本没有 tool_calls 属性（直接 AttributeError）；模型请求工具时，tool_calls 是元素为 dict 的列表而非 ToolCall 对象。因此抽出 _extract_tool_calls 统一兼容两种形态，assistant 消息也以原生 dict 回传（避免 SDK 对象二次序列化的不确定性）——这套兼容逻辑已写入代码注释，是"官方示例 ≠ 实际行为"的又一实证。
为何统一 dashscope 原生协议：例 13-1 已演示 native / openai 双协议适配，本篇主题是工具链与回退。而两种协议的 tool_calls 回填格式不同（openai 要求 tool_call_id），若再叠双协议会把代码撑爆且模糊焦点——故主备模型统一走原生协议，协议差异的复用职责交还 13-01 的 ModelAdapter（见第八节衔接）。

九、动手练习与延伸阅读

练习 1：给 safe_eval 加幂运算

把 ast.Pow 加入白名单，但增加防护：指数绝对值 ≤ 100 且底数绝对值 ≤ 1000 时才放行。思考为什么"直接放行 Pow"不行，而"有限制的放行"可以——体会白名单的粒度设计。

练习 2：并行工具调用

问模型"北京和上海的天气怎么样"，观察 qwen-plus 是否一次返回多个 tool_calls（列表长度 > 1）。当前的循环已按顺序逐个执行并回填——试着用 concurrent.futures 并行执行无依赖的工具调用（参考 char09 的线程池）。

练习 3：把工具搬上 MCP

参照 char12-07 的 McServer 实现，把 query_weather / calculate_expression 包装成 MCP 工具（JSON-RPC 2.0 tools/call），体会"进程内函数"与"标准化工具服务"的边界差异——以及为什么生产系统选后者。
