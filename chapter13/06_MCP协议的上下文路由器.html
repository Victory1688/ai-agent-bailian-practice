例13-6 MCP 协议的上下文路由器（char13-06）

第13章 项目案例：从零实现一个复合智能体系统 ｜ 改写基准：真实 MCP 规范（Anthropic 2024-11 发布，2025-06-18 修订）｜ 状态：已实测验证（5 项 self-test 全部通过）

复合智能体的多个子系统（知识问答 / 脚本执行 / 闲聊）需要一个路由器：识别用户意图，把请求分发给正确的子系统。教材版给消息加了个 call_type 字段就自称"MCP"——但真实 MCP（Model Context Protocol）是 Anthropic 发布、2025-06-18 修订的跨进程开放标准（JSON-RPC 2.0 信封 + initialize 生命周期 + tools/resources/prompts 原语）。本篇按真实规范重写：路由器成为 MCP 客户端，各子系统成为 MCP Server，意图路由建立在标准协议之上。

一、教材原版问题

编号问题后果
①"MCP"是借壳命名教材的 MCPMessage 只是普通消息 + call_type 字段，MCPContext 只是会话历史——与真实 MCP 毫无关系。学生带着"MCP 就是给消息加字段"的错误认知进入生产，是最危险的一类教学伤害
②虚构类 Qwen2Chat/DeepSeekChat + 过时 import同 13-01：import 即崩

④意图 → 模型 if/elif 硬编码路由映射写死在 route() 里（13-04 同款平行映射），新增意图要改代码

二、教材"MCP" vs 真实 MCP 规范（2025-06-18）

维度教材简化版真实 MCP 规范（本篇实现）
本质定位给消息对象加 call_type 字段客户端-服务端架构的跨进程开放协议

为什么必须较真：MCP 已是主流生态事实标准（Claude、OpenAI、各大 IDE 均已接入）。教材借壳的后果不是"代码跑不通"那么简单——学生以为见过 MCP 了，实际连 JSON-RPC 都没见过。本篇给的是可以对着官方文档读懂生产代码的最小实现。

三、改写后总览：协议化的路由链路

初始化：MCPRouter 对三个 server 逐一 initialize 握手（协商 protocolVersion=2025-06-18）
→ notifications/initialized 确认（通知无响应）

路由：用户消息 → MCPContext.get_last_intent（只认最后一条 user 消息）
↓ INTENT_ROUTES 路由表：意图 → (server, tool, 参数键)
↓ tools/call JSON-RPC 请求 → 目标 McServer.handle()
｜　├─ knowledge-server.ask_knowledge → qwen-plus 生成（qa）
｜　├─ ops-server.run_script → 模拟执行（tool）
｜　└─ chat-server.chitchat → qwen-turbo 闲聊（dialog）
↓ 返回结构化契约 {"success", "intent", "server", "response"}

教材的业务语义全部保留：三意图分类、关键词识别、不同意图走不同模型（qa→qwen-plus / dialog→qwen-turbo）、demo 场景原文。变化在于路由发生在标准协议之上，执行与路由彻底分离。

四、核心组件 1：McServer —— 真实 MCP 规范的最小服务端

class McServer:
    def handle(self, request: dict):
        method = request.get("method", "")
        req_id = request.get("id")
        if method.startswith("notifications/"):
            return None   # MCP 规范：通知不产生响应
        try:
            handler = {"initialize": self._initialize,
                       "tools/list": self._tools_list,
                       "tools/call": self._tools_call}.get(method)
            if handler is None:
                raise JsonRpcError(METHOD_NOT_FOUND, f"方法不存在：{method}")
            result = handler(request.get("params") or {})
            return {"jsonrpc": "2.0", "id": req_id, "result": result}
        except JsonRpcError as e:
            return {"jsonrpc": "2.0", "id": req_id,
                    "error": {"code": e.code, "message": e.message}}

    def _tools_call(self, params: dict) -> dict:
        name = params.get("name")
        if name not in self.tools:
            raise JsonRpcError(INVALID_PARAMS, f"工具 {name} 不在本 server 能力列表")
        for key in TOOL_SPECS[name]["inputSchema"].get("required", []):
            if key not in (params.get("arguments") or {}):
                raise JsonRpcError(INVALID_PARAMS, f"缺少必填参数：{key}")
        try:
            text = str(TOOL_SPECS[name]["execute"](**args))
            return {"content": [{"type": "text", "text": text}], "isError": False}
        except Exception as e:
            # 工具级错误按 MCP 规范用 isError 标记，不占用协议错误码
            return {"content": [{"type": "text", "text": f"工具执行失败：{e}"}],
                    "isError": True}
  • 单入口 handle()：请求 dict 进、响应 dict 出，所有方法走同一个门——这就是 JSON-RPC 2.0 的形态（生产中经 stdio/HTTP 传输，本篇进程内传递，传输层解耦：MCP 是协议不是传输方式）；
  • 两级错误语义：调用不存在的工具、缺参数 → 协议错误码 -32602；工具执行中业务失败（如脚本名为空、模型接口非 200）→ 正常响应 + isError: true。教材"一个 except 吞所有"的粗放错误处理被规范化；
  • initialize 校验：客户端带不兼容的 protocolVersion 来握手会被直接拒绝。

五、核心组件 2：MCPContext —— 意图劫持 bug 的修正

INTENT_KEYWORDS = {
    "qa": ("查询", "问答", "介绍"),
    "tool": ("执行", "运行"),
    "dialog": (),
}

def get_last_intent(self) -> str:
    for msg in reversed(self.history):
        if msg["role"] != "user":
            continue
        text = msg["content"]
        for intent, keywords in INTENT_KEYWORDS.items():
            if any(k in text for k in keywords):
                return intent
        return "dialog"      # 最后一条 user 不含已知关键词 → 闲聊
    return "dialog"
场景教材版（倒序扫全史）改写版（只认最后一条 user）
先说"查询GDP"，再说"执行统计脚本"tool（碰巧正确）tool
先说"执行备份脚本"，最后说"今天天气真不错啊"tool（旧意图劫持，错误路由）dialog（正确）

右列第二行就是 Test 3 实测的对照场景——教材版在"闲聊收尾"的常见对话形态下必然误路由。关键词表同时提为注册表常量（教材硬编码在方法体内），新增意图只改配置。

六、核心组件 3：MCPRouter —— MCP 客户端（路由与执行分离）

INTENT_ROUTES = {
    "qa":     ("knowledge-server", "ask_knowledge", "query"),
    "tool":   ("ops-server",       "run_script",    "script"),
    "dialog": ("chat-server",      "chitchat",      "message"),
}

def __init__(self):
    self.servers = build_servers()
    for name, server in self.servers.items():
        result = self._request(server, "initialize", {
            "protocolVersion": MCP_PROTOCOL_VERSION,
            "capabilities": {},
            "clientInfo": {"name": "context-router", "version": "1.0.0"}})
        self._notify(server, "notifications/initialized")

def route(self, context: MCPContext) -> dict:
    intent = context.get_last_intent()
    server_name, tool_name, arg_key = INTENT_ROUTES[intent]
    payload = context.get_last_user_message()      # 只转发当前问题，不重放全史
    result = self._request(self.servers[server_name], "tools/call",
                           {"name": tool_name, "arguments": {arg_key: payload}})
    text = result["content"][0]["text"]
    return {"success": not result.get("isError", False), "intent": intent,
            "server": server_name, "response": text}
  • 规范生命周期：构造时对每个 server 完成 initialize 握手（实测日志：三个 server 均协商到 2025-06-18）——先握手后调用是 MCP 的硬性要求，教材完全没有这个概念；
  • 只转发当前问题：get_last_user_message 替代教材的全史重放——路由器送出的是"这一件事"，而非混乱的历史拼接；
  • 结构化契约：返回 {"success", "intent", "server", "response"}，success 由 isError 翻转而来——错误不再混流；
  • 职责复位：路由器只做协议调用，问答/执行/闲聊由各自 server 的工具完成。
