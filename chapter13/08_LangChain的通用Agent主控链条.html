一、教材原版问题诊断

教材原代码声称实现了「Qwen3.0 + DeepSeek + 多工具 + 记忆链 + 异常回退」，但逐行核查后发现八个问题（原代码已全部注释保留在 py 文件头部，编号对应）：

编号问题后果与辨析
①标题写 Qwen3.0，代码却是 Qwen/Qwen1.5-7B-Chat标题与内容不符，教材叙述性错误（13-01 同款）。
②Qwen2Chat / DeepSeekChat 虚构类langchain_community.chat_models 里不存在这两个类，langchain.schema 也是过时 import——原代码 import 阶段就崩，从未真正跑通过。
③Tool.from_function 双重包装@tool 装饰器已经返回 StructuredTool 实例，再包一层 Tool.from_function(...) 是重复包装（13-03 同款教材通病），参数 schema 丢失。
④legacy 全线废弃initialize_agent / AgentType.OPENAI_FUNCTIONS / AgentExecutor / ConversationBufferMemory 均为 LangChain legacy API，1.x 已移除，官方推荐 LangGraph 或原生 function calling。
⑤【最严重】回退形同虚设initialize_agent(llm=self.model.qwen, ...) 把裸 qwen 实例交给 executor——AgentExecutor 内部调模型根本不经过 ModelWithFallback.invoke，注释自曝「切换在外部处理」但外部什么都没实现。回退代码写了等于没写；全败时还返回「系统暂时无法响应」字符串混流，调用方无法程序化区分成功与失败。
⑥「月球」用例异常炸穿工具 raise ValueError 且未配置 handle_tool_error → 异常炸穿 executor → 进 except 返回「调用失败，请稍后重试」。教材的预期输出实际跑不出来；正确做法是把工具错误作为数据回填给模型（13-03 已确立的双层语义）。
⑦traceback.format_exc() print 外泄完整堆栈直接打到用户界面，既泄露内部实现又不专业（13-01 同款）。
⑧无 self-test零验证，问题①到⑦全部无人发现。
本篇核心教学点——「假回退」：教材把回退写在一个类（ModelWithFallback）里，却把另一个裸实例（self.model.qwen）交给执行框架。 两段代码各写各的，回退逻辑与真正的模型调用路径完全脱节。这是工程上最常见的「自欺式防御」： 防御代码存在 ≠ 防御生效。判断标准只有一条——回退必须包在每一轮真实的模型调用外面。

二、改写后总览

改写思路：彻底摆脱 legacy LangChain，用 dashscope 原生 function calling 手写一个最小工具循环（13-03 已验证的模式）， 把「主控」三件套做实——回退内嵌调用层、工具错误回填、原生 messages 记忆。

整体执行流程

用户输入 ──→ 记忆注入（self.history + 本轮 user 消息）
  ──→ LLM 调用（_chat_with_fallback：primary → 失败则 backup，每轮循环都受保护）
  ──→ 分支判断：
    ├─ 无 tool_calls ──→ 终答：user 原话 + assistant 终答写入记忆，返回 {"success", "reply", "steps"}
    └─ 有 tool_calls ──→ assistant 消息原样回传 + 逐个执行工具（execute_tool 捕获一切异常）
          ──→ 工具结果以 role=tool 回填给同一模型 ──→ 回到 LLM 调用（最多 MAX_TOOL_ROUNDS=5 轮）
任何模型级故障兜底：全败 ──→ 返回 {"success": False, "error"}（结构化，不混流）

三、核心组件详解（1）工具层

3.1 TOOLS_SPEC：dashscope 原生 function calling 格式

这是本次改写实测中发现的最有价值的坑（详见第六节）。dashscope 原生 Generation API 的 tools 参数要求 外层 {"type": "function", "function": {...}} 包装，与 OpenAI 风格的裸 function 列表不同：

TOOLS_SPEC = [
    {"type": "function", "function": {
        "name": "get_temperature",
        # 描述刻意强化"必须调用"指引：避免模型对"月球天气"直接拒答不调工具
        "description": "查询指定城市的天气情况与当前温度。"
                       "涉及任何城市、地点的天气或温度问题时，必须调用本工具获取，"
                       "不要凭记忆回答；未收录的城市会由工具返回错误。",
        "parameters": {"type": "object",
                       "properties": {"city": {"type": "string", "description": "城市名称"}},
                       "required": ["city"]}}},
    {"type": "function", "function": {
        "name": "multiply",
        "description": "将两个数字相乘",
        "parameters": {"type": "object",
                       "properties": {"a": {"type": "string", "description": "数字a"},
                                      "b": {"type": "string", "description": "数字b"}},
                       "required": ["a", "b"]}}},
]
静默失败警告：实测传 OpenAI 风格的裸 function 列表（[{"name": ..., "parameters": ...}]，无外层包装） 时 dashscope 不报任何错误，但模型完全看不到工具定义，只能凭先验知识自造工具名（实测自造了不存在的 get_weather）。这与「LangGraph State 用裸 dict 导致字段静默裁剪」是同一家族的坑—— 接口不报错 + 行为诡异 = 优先怀疑数据格式不合协议。

3.2 工具实现与注册表

两个工具的教材业务逻辑原样保留，只修两处：裸 except 收敛为 except Exception（不再吞 KeyboardInterrupt）； 用 TOOL_IMPLS 字典注册表替代 Tool.from_function 双重包装：

def get_temperature(city: str) -> str:
    """根据城市名称获取当前温度（模拟）——教材原逻辑：月球抛错"""
    if city.lower() == "月球":
        raise ValueError("未找到对应城市")
    return f"{city}当前温度为26°C"

def multiply(a: str, b: str) -> str:
    """将两个数字相乘——教材原逻辑（裸 except 收敛为 except Exception）"""
    try:
        return str(float(a) * float(b))
    except Exception:
        return "输入格式不正确，请输入数字"

TOOL_IMPLS = {
    "get_temperature": get_temperature,
    "multiply": multiply,
}

def execute_tool(name: str, arguments: dict) -> str:
    """执行工具并结构化回填错误（13-03 确立：错误是数据，链路不断）"""
    if name not in TOOL_IMPLS:
        return f"工具执行失败：未知工具 {name}"
    try:
        return str(TOOL_IMPLS[name](**arguments))
    except Exception as e:
        return f"工具执行失败：{e}"
错误回填语义（双层失败模型，13-03 确立）：
  • 工具级失败（如月球未收录）：execute_tool 捕获后返回「工具执行失败：未找到对应城市」文本， 以 role=tool 消息回填给同一个模型——错误是数据，链路不断，模型收到后会自行生成致歉说明；
  • 模型级失败（网络/限流/坏模型名）：才触发主备回退（下一节的 _chat_with_fallback）。
两类失败走两条通道，互不误伤。

3.3 _extract_tool_calls：兼容两种实测形态

def _extract_tool_calls(message) -> list:
    """提取模型响应中的工具调用（13-03 实测兼容两种形态）"""
    calls = getattr(message, "tool_calls", None)
    if not calls:
        return []
    out = []
    for tc in calls:
        if isinstance(tc, dict):
            out.append(tc)
        else:
            out.append({"id": tc.id, "type": "function",
                        "function": {"name": tc.function.name,
                                     "arguments": tc.function.arguments}})
    return out

实测细节：模型未调工具时，返回的 message 对象没有 tool_calls 属性（用 getattr 兜住而非直接访问）； 调了工具时，元素可能是 dict 或对象两种形态——统一化成 [{"id", "type", "function": {"name", "arguments"}}]， 主循环无需再分支判断。

四、核心组件详解（2）主控与回退

4.1 模型注册表：主备槽位

MODEL_REGISTRY = {
    "primary": {"model": "qwen-plus"},
    "backup": {"model": "qwen-turbo"},
}

延续 13-04/13-05 的注册表模式。注：实测当前百炼账号未开通 DeepSeek 托管（deepseek-* 模型名返回 404）， 备用槽位用 qwen-turbo 演示回退语义。

4.2 _chat_with_fallback：回退内嵌在调用层（修复假回退）

def _chat_with_fallback(self, messages: list):
    """主备回退执行一轮 LLM 调用（回退在调用层真实生效）"""
    last_err = None
    for slot in ("primary", "backup"):
        self.attempted_slots.append(slot)          # 留痕：供 self-test 验证回退真实发生
        try:
            model = MODEL_REGISTRY[slot]["model"]
            logger.info(f"[模型] 使用 {slot}({model})")
            msg = self._invoke(model, messages)
            return msg.content, _extract_tool_calls(msg)
        except Exception as e:
            last_err = e
            logger.warning(f"[回退] {slot} 模型级失败: {e}")
    raise RuntimeError(f"所有模型均执行失败，最后错误：{last_err}") from last_err
对比教材假回退，关键差异有三：
  1. 位置对了：回退循环包在「每一轮真实的模型调用」外面——工具循环有几轮 LLM 调用，回退就保护几轮； 教材的回退写在与 executor 无关的另一个类里，executor 持有裸实例，永远走不到回退分支；
  2. 留痕了：attempted_slots 记录每次槽位尝试，self-test 可以断言「回退确实发生」而不是靠肉眼 print；
  3. 失败语义对了：全败抛 RuntimeError 并用 raise ... from last_err 保留异常链（13-04 确立）， 由 run 转成结构化的 {"success": False}——不再返回「系统暂时无法响应」错误字符串混流。

4.3 attempted_slots 的多轮语义（测试断言的坑）

工具循环中每一轮 LLM 调用都会独立走一遍主备流程。例如「查询北京温度」实际包含 2 轮 LLM 调用 （第 1 轮决定调工具、第 2 轮拿到工具结果生成终答），每轮各产生一条记录，所以一次 run 可能留下 ["primary", "primary"] 这样的序列。断言时不能只看首元素或长度——回退场景用「分对校验」： zip(slots[::2], slots[1::2]) 切成 (primary, backup) 对逐对验证（见第六节 Test 5）。

五、核心组件详解（3）run 主循环

def run(self, input_text: str) -> dict:
    """主控入口：记忆注入 → 工具循环（含错误回填）→ 终答写记忆"""
    steps: list = []
    self.attempted_slots = []
    try:
        # 多轮记忆注入（13-05 同款：历史 + 本轮 user 消息）
        messages = self.history + [{"role": "user", "content": input_text}]
        for round_no in range(1, MAX_TOOL_ROUNDS + 1):
            content, tool_calls = self._chat_with_fallback(messages)
            if not tool_calls:
                # 终答：本轮 user 与 assistant 终答写入记忆
                self.history.append({"role": "user", "content": input_text})
                self.history.append({"role": "assistant", "content": content})
                return {"success": True, "reply": content, "steps": steps}
            # 工具轮：assistant 消息（含 tool_calls）原样回传，再逐个回填结果
            messages.append({"role": "assistant", "content": content,
                             "tool_calls": tool_calls})
            for tc in tool_calls:
                name = tc["function"]["name"]
                try:
                    args = json.loads(tc["function"]["arguments"] or "{}")
                except json.JSONDecodeError:
                    args = {}
                result = execute_tool(name, args)
                steps.append({"round": round_no, "tool": name,
                              "args": args, "result": result[:120]})
                messages.append({"role": "tool", "tool_call_id": tc["id"],
                                 "content": result})
        return {"success": False, "steps": steps,
                "error": f"超过最大工具轮次（{MAX_TOOL_ROUNDS}）"}
    except Exception as e:
        return {"success": False, "steps": steps, "error": str(e)}

五个设计点

设计点说明
多轮记忆self.history 存「user 原话 + assistant 终答」两组消息，每轮 run 拼在 messages 前部注入——替代废弃的 ConversationBufferMemory（13-05 同款模式）。实测「再帮我乘一下12和13」的「再」字能正确接续上一轮的 7×8。
协议消息顺序function calling 的规范要求：assistant 消息（含 tool_calls）必须原样回传，随后逐个以 role=tool、tool_call_id 对应回填结果——顺序错了接口直接报错。
参数解析防御模型生成的 arguments 是 JSON 字符串，用 json.loads 解析并兜住 JSONDecodeError（空参给 {}），避免脏参数直接炸循环。
轮次上限MAX_TOOL_ROUNDS=5 防模型陷入「调工具 → 回填 → 再调工具」的无限循环（13-03 同款），超限返回结构化失败。
可观测性 steps每次工具调用记录 {round, tool, args, result截断120}——替代教材 verbose=True 的布尔开关：调用方拿到的是结构化轨迹数据，而不是一屏 print 日志。
关于「教材标题写 LangChain，改写后不用 LangChain」的说明：本例的教学意图是「主控链条」的机制—— 工具循环、回退、记忆、可观测性。教材用的 initialize_agent/AgentExecutor 在 LangChain 1.x 已全部移除， 官方推荐路线是 LangGraph 或原生 function calling。本改写选择 dashscope 原生 function calling 手写最小循环： 一是与全章「dashscope 统一」的硬约束一致，二是让新人能看清主控的每一步 mechanics（框架封装后恰恰看不见）。 记忆部分如需框架级方案，参考 char08-04 的 ConversationBufferWindowMemory（非 legacy 版本）。
